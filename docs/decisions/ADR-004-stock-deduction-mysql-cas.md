## 1. 背景

阶段 5 第一次给 `t_seat_inventory` 加上**写入路径**。要解决的问题一句话：

> **「判断有没有票」和「把票扣掉」必须是原子的。**

这两步一旦分开，并发下就会有两个请求同时读到"还剩 1 张"、同时认为自己可以买 —— **超卖**。
这不是一个新问题（`sql/03_rail_inventory.sql` 在阶段 2 就把这个陷阱写进了注释），
但阶段 5 是它第一次需要用**代码**回答，而不是用注释。

**约束条件**（来自项目边界，不是可以商量的）：

| 约束 | 来源 |
| --- | --- |
| 单机、单 MySQL 实例、无 Docker | 项目边界 |
| 阶段 5 不引入 Redis / MQ | [03-business-flow.md §一](../03-business-flow.md) 的范围表 |
| 必须能用**可复现的测试证明**不超卖，而不是靠论证 | 阶段 5 的完成判据 |

## 2. 备选方案

### 方案 ①：先 SELECT 判断，再 UPDATE

```java
// ❌ 经典错误，本项目明文禁止
int sold = mapper.selectSoldCount(trainId, date, seatType);
if (sold < total) {
    mapper.updateSoldCount(trainId, date, seatType, sold + 1);  // 用读到的值算新值
}
```

| 维度 | 评价 |
| --- | --- |
| 正确性 | 🔴 **会超卖**。两个事务都读到 `sold=19 < 20`，都执行 UPDATE，最后 `sold=20` 但**卖出了 2 张**（第二次的 `sold+1` 覆盖了第一次的写入 —— 丢失更新） |
| 性能 | 🟢 无锁竞争 |
| 结论 | ❌ **否决**。这是本项目要演示的第一个反面教材，不是候选 |

### 方案 ②：悲观锁（`SELECT ... FOR UPDATE` 后再改）

| 维度 | 评价 |
| --- | --- |
| 正确性 | 🟢 正确。行锁把临界区串行化 |
| 性能 | 🔴 持锁区间 = **整个业务逻辑的长度**（读价格 → 扣减 → 写订单 → 写明细 → 写流水）。热点车次的库存行成为全程串行的单点 |
| 复杂度 | 🟡 要自己保证**所有**访问该行的路径都加锁、加锁顺序一致，漏一处就破功 |
| 结论 | 🟡 **可用但放弃** —— 它与方案 ③ 的正确性来源**完全相同**（都是 InnoDB 行锁），但**多持了锁、少拿了清晰度**。见下方"决策"里的对比 |

### 方案 ③：条件 UPDATE（CAS）　✅ **最终选择**

```sql
UPDATE t_seat_inventory
   SET sold_count = sold_count + 1                    -- ① 自增由数据库算
 WHERE train_id = ? AND travel_date = ? AND seat_type = ?
   AND sold_count < total_count;                      -- ② 条件在 UPDATE 内部
```

| 维度 | 评价 |
| --- | --- |
| 正确性 | 🟢 正确，且**理由明确**：`UPDATE` 是当前读（locking read），InnoDB 读**最新已提交版本**并**重新求值 `WHERE`**。后到的事务在行锁上等待，前者提交后它重新判断 → 受影响 **0 行**，而不是覆盖 |
| 性能 | 🟢 持锁区间 = **一条语句**。业务逻辑（写订单等）虽然仍在同一事务内，但**条件判断与扣减的临界区只有这一条 SQL** |
| 复杂度 | 🟢 最低。不需要显式锁、不需要约定加锁顺序 |
| 可读性 | 🟢 **它的正确性写在 SQL 里，不是写在注释里** —— 读代码的人无法"忘掉"它 |
| 结论 | ✅ 采纳 |

### 方案 ④：Redis + Lua 原子扣减

| 维度 | 评价 |
| --- | --- |
| 正确性 | 🟢 正确（Lua 脚本在 Redis 里是单线程原子执行） |
| 性能 | 🟢 **显著更好** —— 内存操作，且把热路径从 MySQL 上摘掉 |
| 代价 | 🔴 引入**新的不一致来源**：Redis 和 MySQL 是两份数据，必须有预热、对账、回补。并且**判断与扣减虽然原子，但与落单不是** —— 扣了 Redis 却写库失败，需要补偿 |
| 结论 | ⏳ **不是阶段 5 的选项，是阶段 7 的目标**。见文末 |

### 方案 ⑤：分布式锁（Redisson / ZooKeeper）

| 维度 | 评价 |
| --- | --- |
| 正确性 | 🟢 正确 |
| 性能 | 🔴 **比方案 ② 更差** —— 每个请求多一次（或多次）网络往返，且锁的粒度通常比行锁大 |
| 结论 | ❌ **否决**。分布式锁解决的是"**没有单一权威数据源**"的问题。本项目在阶段 5 只有**一个** MySQL 实例，行锁就是这个问题的原生答案。**在没有分布式之前引入分布式解决方案，是为了用工具而用工具** |

## 3. 决策

**采用方案 ③：条件 UPDATE（CAS）。** 由五个具体判断共同构成，缺一个都不完整。

### 3.1 增量和条件都必须写在 SQL 里

```sql
SET sold_count = sold_count + 1     -- ✅ 数据库算
-- 而不是
SET sold_count = #{newValue}        -- ❌ Java 算完传进来 → 丢失更新 → 少卖
```

⚠️ **`#{newValue}` 那种写法看起来"也能跑通"，而且在低并发下真的不会出错** ——
这正是它危险的地方。它是方案 ① 的变体，超卖机制相同。

### 3.2 返回 `int`（受影响行数），不返回 `boolean`

0 / 1 / 抛异常是**三态**，压成 `boolean` 就只剩两态：

| 现实 | 返回 `int` | 返回 `boolean` |
| --- | --- | --- |
| 扣成功 | `1` | `true` |
| **售罄**（正常业务失败） | `0` | `false` —— **和"执行失败"分不开** |
| 系统异常（结果未知） | **抛异常** | 抛异常 |

`boolean` 恰好抹掉了 `sql/03_rail_inventory.sql:149` 那条规格
（"0 行 = **正常业务失败**，不是错误"）。**判据：三态必须能被调用方看见。**

### 3.3 读 price 在 UPDATE **之前**，但它不参与判断

执行顺序（`OrderService.createOrder`）：

```
① SELECT 库存行   → 取 price，并区分"未放票"（行不存在）与"售罄"（sold >= total）
② UPDATE 条件扣减 → 受影响行数说了算
```

**为什么 ① 在 ② 之前**（两个理由，都不是"习惯"）：

1. **没有 ① 就分不清"还没放票"和"已售罄"**。项目已把"还没放票 ≠ 已售罄"定为硬规则
   （[error-codes.md §三](../api/error-codes.md)）—— 前者是"过几天再来"，后者是"换车次"。
   反向顺序（先 UPDATE 再 SELECT）也能区分，但那次 SELECT 会落在**持锁区间内**，
   白白拉长热点行的 X 锁持有时间。
2. ① 是**快照读**（不加锁），所以它不会延长锁窗口。

⭐ **① 不会退化成方案 ① 那个错误写法。判据很明确：**

> **① 的结果从不作为扣减的充分条件。**
> 即使 ① 读到"有票"，仍然照常执行 ②，由 ② 的受影响行数说了算。

① 只做两件事：(a) 取 price，(b) 给"0 行"这个结果**分类**。

### 3.4 唯一索引是第一道防线，"判断"是第二道

`t_order_item` 上的 `uk_user_train_date_seat (user_id, train_id, travel_date, seat_type)`
是 **UNIQUE**，所以"同一用户同车同日同席别有两张票"在**物理上不可能**。

这带来一个必须写进文档的认知修正
（[05-seckill.md §六](../05-seckill.md) 的 ② 号校验）：

> 那条"重复购票"校验 SQL 永远返回 0 行，**不是因为业务代码写对了，
> 而是因为唯一索引让"超过 1 行"物理上不可能**。
> 它的真实作用是：**证明那个唯一索引真的建了。**

### 3.5 撞唯一索引后**只能 throw，不能 return**　🔴 本方案最危险的一条

重复下单时，写 `t_order_item` 会抛 `DuplicateKeyException`。如果这样写：

```java
try {
    orderItemMapper.insert(item);
} catch (DuplicateKeyException ex) {
    return orderResponse(409, "请勿重复购票");   // 🔴🔴 灾难
}
```

Spring 的事务拦截器看到方法**正常返回** → **COMMIT**。于是：

```
rail_inventory：扣减已提交     ← 少了一张票
rail_order    ：订单已回滚     ← 但没有订单
HTTP          ：返回 409「请勿重复购票」 ← 看起来完全正常
```

**不报错、不告警、日志干净，只有对账 SQL 能发现。** 这就是"少卖"。

> **判据（写进代码注释、写进校验 SQL、写进复盘）**：
> **`catch` 块里只能 `throw`，不能 `return`** —— 除非能保证走到这个 `catch` 时本次事务还没有写过任何东西。

### 3.6 捕 `DuplicateKeyException`，不捕父类

| 异常 | 该不该捕 | 理由 |
| --- | --- | --- |
| `DuplicateKeyException` | ✅ 捕 | 就是唯一索引撞车，正常业务失败 → 409 |
| `DataIntegrityViolationException`（父类） | ❌ **不能捕** | 它同时覆盖 `1364`（NOT NULL 违规）等 —— 那些是**代码 bug、必须 500**。捕了就变成"必现的编码错误被伪装成正常的业务拒绝" |
| `3819`（CHECK 违反） | — | **Spring 根本不翻译它**，所以不存在"顺手兜住 CHECK"这条退路。这个念头是错的 |

## 4. 跨库写的边界（本 ADR 的时效性条款）

方案 A 的下单事务要写**三个 schema**：

```
rail_train.t_train                    读（车次信息）
rail_inventory.t_seat_inventory       写（扣减）+ rail_inventory.t_stock_flow 写
rail_order.t_order / t_order_item     写
```

而数据源 URL 只指向 `rail_train`。**这样能成一个事务，是因为：**

> **InnoDB 的事务是服务器级的，不是库级的。**
> `rail_train` / `rail_inventory` / `rail_order` 是**同一个 MySQL 实例上的三个 schema**
> （MySQL 里 schema ≡ database）。一条连接上的 `START TRANSACTION`
> 同时覆盖它们 —— 所以这是**本地事务**，不是分布式事务。

实现手法：**全限定表名**（`@TableName("rail_inventory.t_seat_inventory")`）。

🔴 **这个结论的前提是一条部署事实："三个 schema 在同一个实例上"。**
它在阶段 5~7 成立，**阶段 8 拆服务后消失** ——
代码分住两个进程，才第一次变成真正的分布式事务问题。

⭐ **这就是为什么要写在这里，而不是只写在代码注释里**：
将来有人看到"下单事务跨了三个库"，很容易得出"这个项目用了分布式事务"
或者反过来的"跨库事务不可能，所以这段代码一定有问题"。
**两种结论都是错的。**

## 5. 为什么最终要换成 Redis　⏳ **未决，待阶段 6 数据**

⚠️ **本节故意不写结论。**

[ADR-003](ADR-003-service-granularity.md) 里对这条 ADR 立过一条约束：

> 库存扣减方案 —— **必须先压出 MySQL 方案的真实瓶颈数据**，否则就是背答案。

**这条约束我们只遵守了一半，而且是有意为之：**

| 部分 | 能否现在决定 | 为什么 |
| --- | --- | --- |
| 用条件 UPDATE（本 ADR §3） | ✅ **能** | 它是**正确性**决策。正确性的判据是"并发下不超卖"，不依赖性能数字 —— 五个备选方案的取舍都能靠推理说清，且 `OrderConcurrencyTest` 给出了可执行的证明路径 |
| 什么时候换成 Redis | ⛔ **不能** | 它是**性能**决策。判据是"MySQL 方案在多大并发下成为瓶颈"，**这个数字现在不存在** |

所以本 ADR 的标题特意限定为"（方案 A —— MySQL 条件 UPDATE）"。
**它兑现了 ADR-003 的承诺，但没有提前回答那个还不该被回答的问题。**

### 阶段 6 需要产出的、能回答这个问题的数据

| # | 要测出来的 | 为什么它决定"要不要换" |
| --- | --- | --- |
| 1 | 方案 A 的 QPS / P95 / P99（**在 mapper 日志关掉之后测**） | 这是基线。没有它，阶段 7 的"提升了多少"无从谈起 |
| 2 | 瓶颈**在哪**：是 HikariCP 连接池？是热点行的 X 锁串行？是磁盘 IO？ | 如果瓶颈是连接池，加 Redis **解决不了** —— 得先调池。**改错地方比不改更糟** |
| 3 | 热点行锁的等待时长（同一行的并发事务排队时间） | 这是 Redis 方案**直接针对**的那一项。它不显著，换 Redis 的收益就不显著 |
| 4 | 把并发度**逐步**加上去，曲线在哪个点拐弯 | 拐点位置决定"需不需要换"，而不是"多少 QPS 算慢" |

⚠️ **不预先承诺结论。** 可能的结局包括"在当前数据量与机器上测不出瓶颈" ——
如果真是这样，**如实写下来**，那是本机条件下最诚实的结论，
而不是编一个数字去论证一个已经选好的答案。

| # | 事项 | 何时处理 |
