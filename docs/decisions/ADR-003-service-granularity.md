# ADR-003：微服务拆分粒度

- **状态**：✅ 已接受（2026-09-15）
- **决策者**：开发者本人
- **相关文档**：[阶段 0 设计 §4](../architecture/phase0-design.md#四微服务拆分方案)

---

## 背景

项目需要体现 Spring Cloud 微服务能力（注册发现、网关、服务间调用、容错降级），但只有一名开发者、一台 Windows 办公机、且 Docker 不可用。

**核心矛盾**：拆得越细，微服务知识点覆盖越全、面试故事越完整；但每多一个服务，就多一个 JVM 进程、多一份配置、多一处故障点，且**分布式复杂度是超线性增长的**（N 个服务的潜在调用路径是 N² 量级）。

因此问题的实质不是"能拆几个"，而是：**"分界线应该画在哪里，才能让每一刀都切在真实接缝上？"**

---

## 备选方案

### 方案 A：单体（1 个进程）

| 维度 | 评价 |
| --- | --- |
| 并发正确性 | 🟢 **最好保证**——本地事务、单进程内锁，没有任何分布式问题 |
| 性能 | 🟡 够用。秒杀场景的瓶颈在 DB 和 Redis，不在"是否拆服务" |
| 微服务知识点 | 🔴 **零覆盖**。Nacos/Gateway/Feign/服务容错全部无从谈起 |
| 面试价值 | 🔴 低。无法回答"为什么用微服务" |
| 运维成本 | 🟢 最低（1 个进程） |

**结论**：这不是一个可选项，但**它是必经的阶段**——见下方"决策"中的演进路径。

### 方案 B：4 个服务（gateway / user / train / order，库存并入 train）

| 维度 | 评价 |
| --- | --- |
| 并发正确性 | 🟢 好——库存表归 train-service，扣减逻辑与余票查询在同一服务内 |
| 微服务知识点 | 🟢 覆盖全部核心组件 |
| 运维成本 | 🟡 4 服务 + 3 中间件 ≈ 7~8 个进程 |
| **短板** | 🟡 **"服务降级"的故事讲不完整**——余票查询可以降级、库存扣减绝对不能降级，但两者在同一个服务里，无法对它们施加不同的降级策略；"库存服务挂了会怎样"这个经典追问没有干净的答案 |

### 方案 C：5 个服务（额外拆出 `rail-inventory-service`）—— ✅ **最终选择**

| 维度 | 评价 |
| --- | --- |
| 并发正确性 | 🟢 好，但**引入了一个必须规避的陷阱**（见下方"硬性约束"） |
| 微服务知识点 | 🟢 覆盖全部，且**服务治理的故事更完整** |
| 运维成本 | 🔴 5 服务 + 3 中间件 ≈ 9~10 个进程 |
| 优势 | 库存有了**唯一权威点**；可以独立限流、独立扩展；**"降级策略分离"成为可能** |

### 方案 D：6+ 个服务（再把余票查询拆出去）

❌ **已否决**。理由见 [阶段 0 设计 §4.2 Q2](../architecture/phase0-design.md)：余票查询与库存扣减操作**同一份数据**，拆开后立即产生"读模型与写模型如何同步"的问题，有同步就有延迟，有延迟就会出现"显示有票但下单失败"——**这个不一致对用户是纯粹的困扰，换不来任何收益**。读压力用缓存和只读副本解决，更快更便宜。

---

## 决策

**采用方案 C：5 个服务。**

```
rail-gateway         :8080   统一入口、JWT 校验、限流
rail-user-service    :8081   注册、登录、用户查询
rail-train-service   :8082   车次、站点、经停站、票价
rail-inventory-service :8083 库存权威数据、预热、对账、回补落库、余票查询
rail-order-service   :8084   下单、秒杀、订单状态机、模拟支付
```

**演进路径**：阶段 3~7 先写**单体**（方案 A），阶段 8 一次性拆成方案 C。

> **为什么不一开始就多模块**：因为要**亲手体会拆分的痛**。不经历过单体，你无法回答"哪些依赖在拆分后变成了远程调用""跨服务事务到底麻烦在哪"。这个过程本身就是最好的面试素材。

### 选择方案 C 的核心理由

1. **库存有了唯一权威点**——超卖问题收敛到一个服务、一处代码、一个可审计的地方。
2. **降级策略可以分离**——这是方案 B 做不到的：
   - `rail-train-service`（查票）：压力大时**可以降级**，返回缓存余票 + 提示"可能有延迟"
   - `rail-inventory-service`（库存）：**绝对不能降级**，返回假的扣减成功等于超卖
   - **判断标准：假的响应会不会造成资损。** 不会 → 可以降级；会 → 绝不能降级。
     **如果两者在同一个服务里，这个判断就无法落地。**
3. **独立扩展成为可能**——库存服务的 QPS 特征与查票完全不同，独立后可以单独限流、单独扩容。

## 硬性约束（由本决策引入，必须遵守）

### ⛔ 秒杀热路径上，禁止 order-service 同步 Feign 调用 inventory-service

```
✅ 允许：order-service ──(Redis 客户端直连)──▶ Redis
❌ 禁止：order-service ──(OpenFeign 同步)──▶ inventory-service ──▶ Redis
```

**为什么禁止**：多一跳 HTTP RPC，就要付出**连接池占用、序列化、网络超时、线程阻塞**的全部代价。秒杀链路本来就只有"Redis 一次往返 + 一次消息投递"，加一跳 RPC 会让异步化省下来的时间**原样还回去**，让"拆 5 个服务"这个决定变成纯粹的负担。

**为什么这个错误特别容易犯**：因为它**看起来更符合微服务规范**——"所有数据访问都必须通过 owner 服务"。但规范的目的是降低耦合，不是为了制造一跳。

**Redis 是共享中间件，不是任何服务的私有数据。** order-service 直连它是正当的，与"数据所有权"不冲突——真正有 owner 的是 MySQL 的 `t_seat_inventory`，而它由 inventory-service 独占。

### 数据所有权表（一张表只能有一个 owner）

| schema | owner | 表 |
| --- | --- | --- |
| `rail_user` | user-service | `t_user` |
| `rail_train` | train-service | `t_train`、`t_station`、`t_train_station` |
| `rail_inventory` | inventory-service | `t_seat_inventory`、`t_stock_flow` |
| `rail_order` | order-service | `t_order`、`t_order_item`、`t_local_message` |

**禁止**：跨服务直连数据库、跨服务 JOIN、两个服务写同一张表。

---

## `rail-inventory-service` 到底干什么（必须能回答，否则它不该存在）

| 职责 | 说明 |
| --- | --- |
| `t_seat_inventory` 的唯一 owner | 数据边界清晰，库存改动只有一个入口 |
| **预热** | 把 MySQL 库存灌入 Redis；多实例需分布式锁（见设计文档 §6.4） |
| **对账** | 定时比对 Redis 与 MySQL，发现不一致告警 |
| **回补落库** | 阶段 9 消费 MQ 消息更新库存 |
| 余票查询 | 权威来源（带缓存） |

> ⚠️ **诚实标注**：如果一个服务说不清"它到底独占做了什么"，那它就不该被拆出来。
> **阶段 8 拆分时必须回头验证这五条是否站得住**；若站不住，应当合并回 train-service，并把这个决策的修正记录下来。

## 代价与已知缺陷

| # | 代价 | 具体表现 | 缓解措施 |
| --- | --- | --- | --- |
| **C1** | **运维成本真实且高** | 5 服务 + Nacos + MySQL + Redis + Sentinel ≈ **9~10 个常驻进程**（阶段 9 引入 MQ 后升到 11 个）。办公机上启动要排队，内存要精打细算 | 按需启动（开发某服务时只起它 + 依赖）；在 `scripts/` 下提供一键启停脚本 |
| **C2** | **跨库事务彻底不可能** | `t_seat_inventory` 与 `t_order` 分属不同 schema，"扣库存 + 写订单"在 DB 层面完全无法用本地事务保证 | 这正是分布式系统的现实。阶段 7 的方案 B 必须正面处理"Redis 扣成功但订单写失败"的窗口 |
| **C3** | **热路径有加 RPC 的诱惑** | 见上方"硬性约束" | 写进 ADR + Code Review 检查项 |
| **C4** | **故障点变多** | 9~10 个进程，任意一个挂了都有影响 | 阶段 8 必须逐个服务实测"挂掉之后会怎样"，形成故障矩阵 |
| **C5** | **调试链路变长** | 一个请求跨 3 个服务，出错要翻 3 份日志 | 全链路统一 `traceId`（网关生成，透传下游，写入所有日志）—— **这个必须在阶段 8 就做，不要等到出问题** |
| **C6** | **启动依赖顺序** | 服务启动时 Nacos 必须先就绪 | 启动脚本按序拉起；服务端配置重试 |

## 什么条件下这个决策会失效

| 触发条件 | 应当采取的行动 |
| --- | --- |
| 阶段 8 拆分时，发现 `rail-inventory-service` 的职责说不清 | **合并回 train-service**，修正本 ADR 为"4 个服务"，并记录原因 |
| 办公机资源实在撑不住 10 个进程 | 合并回 4 个服务；"降级策略分离"改用**同一服务内的不同线程池 / 不同限流规则**近似实现，并在文档中说明这是妥协 |
| 阶段 7 压测发现方案 B 的瓶颈根本不在 DB | 重新评估整个拆分方案的必要性——**先有数据，再谈架构** |
| 需要多机房部署 | 引入单元化，库存按车次分片，本 ADR 需整体重审 |

## 面试追问与应答要点

**Q1：为什么拆 5 个服务？**

> 分界线画在**"数据所有权不同"**和**"扩展需求不同"**的地方。
> 具体来说：`rail-inventory-service` 独立出来，是因为它可以和查票服务施加**完全相反的降级策略**——查票能降级（返回缓存 + 提示延迟），库存绝对不能降级（返回假成功等于超卖）。判断标准是"假的响应会不会造成资损"。
> 如果两者在同一个服务里，这个判断就无法落地。

**Q2：为什么不拆更多？**

> 再往下拆的诱惑是拆出"余票查询服务"，我不拆。
> 因为余票查询和库存扣减操作的是**同一份数据**，拆开后立刻产生"读模型与写模型如何同步"的问题。有同步就有延迟，有延迟就会出现"显示有票但下单失败"——**这个不一致对用户是纯粹的困扰，换不来任何收益**。读压力用缓存和只读副本解决，更快更便宜。

**Q3：拆这么多服务，运维不累吗？**

> 累，这是真实的代价，我不否认。9~10 个常驻进程在一台办公机上是要精打细算的。
> 我接受这个代价，是因为**这个项目的目标是理解而不是交付**——单人的运维负担换来了对服务边界、降级策略、分布式事务的完整实践。如果要上生产，我会重新评估，很可能合并回 4 个。

**Q4：库存既然在 Redis 里扣，为什么还要独立的库存服务？**

> 因为**"扣减动作"和"数据所有权"是两件事**。
> Redis 是共享中间件，order-service 直连它做原子扣减，这是热路径，加一跳 RPC 会把异步化的收益原样还回去。
> 但 **MySQL 的 `t_seat_inventory` 是权威数据**，必须只有一个 owner——它负责预热（把真实票额灌进 Redis）、对账（发现 Redis 和 DB 不一致）、回补落库。这些都不是热路径操作，放在独立服务里正合适。
> **面试官想听的其实是这个**：我没有为了形式上的"数据只由 owner 访问"，在秒杀链路上制造一跳 RPC。

**Q5：如果让你重做，你会拆几个？**

> 我会**先拆 4 个**，把 `rail-inventory-service` 留作观察。
> 因为"库存该不该独立"取决于两个可验证的事实：① 它是否真的成为独立的扩展瓶颈；② 降级策略分离是否真的必要。这两个问题**在没有压测数据前无法回答**，而我现在的选择是基于"面试故事更完整"这个非技术理由——**这一点我应该诚实承认**。
