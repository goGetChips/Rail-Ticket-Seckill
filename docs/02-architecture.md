# 系统架构与微服务拆分

**读者**：想知道"系统由哪些服务组成、为什么这么拆、请求怎么流动"的人。
**解决什么问题**：架构方案的选择过程、服务边界的判据、服务挂掉之后会发生什么。
**不包含**：业务流程（→ [03](03-business-flow.md)）、秒杀细节（→ [05](05-seckill.md)）、技术版本（→ [04](04-technology.md)）。

---

## 一、三套候选架构：先论证，再选

同一份业务有三种做法，它们都真实存在于生产系统中。

### 方案 A：请求直接操作 MySQL 库存

```
Client → Gateway → Order Service → MySQL(UPDATE ... WHERE sold_count < total_count)
```

靠条件 UPDATE 的 `affected rows = 0/1` 判断扣减是否成功。

| 维度 | 评价 |
| --- | --- |
| 性能 | 🔴 **最差**。热点行是同一行，所有并发都在抢同一把行锁，MySQL 串行化处理 |
| 一致性 | 🟢 **最好**。单条 SQL 原子，天然不超卖，不依赖任何外部组件 |
| 复杂度 | 🟢 **最低**。没有缓存、没有 MQ、没有对账 |
| 实现成本 | 🟢 半天 |
| 面试价值 | 🟡 中。它是**基准线**——没有它，你无法回答"加了 Redis 到底提升了多少" |

### 方案 B：Redis + MySQL（同步双写）

```
Client → Gateway → Order Service → Redis(Lua 预扣) → MySQL(同步写订单+扣库存) → 返回
```

| 维度 | 评价 |
| --- | --- |
| 性能 | 🟡 中。Redis 挡住了无效请求，但**成功的请求仍然同步打 DB**，DB 依然是瓶颈 |
| 一致性 | 🟡 中。Redis 扣成功但 MySQL 写失败 → 需要回补 Redis，回补本身可能失败 |
| 复杂度 | 🟡 中。开始出现"两个数据源如何一致"的问题 |
| 实测数据 | — 阶段 7 实测 |

### 方案 C：Redis + Lua 预扣 + MQ 异步落库

```
Client → Gateway → Order Service → Redis(Lua 预扣) → MQ → 立即返回「排队中」
                                                          ↓
                                             Consumer → 写订单 + 落库存账
```

| 维度 | 评价 |
| --- | --- |
| 性能 | 🟢 **最好**。响应时间与 DB 完全解耦 |
| 一致性 | 🔴 **最差（复杂度最高）**。要处理消息丢失、重复消费、消费失败、库存回补、对账 |
| 复杂度 | 🔴 **最高** |
| 实现成本 | 🔴 3~5 天（含补偿和对账） |
| 面试价值 | 🟢 **最高**。最终一致性、幂等、消息可靠性全在这里 |

### 六维对比总表

| 维度 | A 直连 MySQL | B Redis + MySQL | C Redis + MQ + MySQL |
| --- | --- | --- | --- |
| 性能 | ★☆☆☆☆ | ★★★☆☆ | ★★★★★ |
| 一致性（实现难度，越低越好） | ★★★★★ | ★★★☆☆ | ★☆☆☆☆ |
| 复杂度（越低越好） | ★★★★★ | ★★★☆☆ | ★☆☆☆☆ |
| 可靠性 | ★★★★★ | ★★★☆☆ | ★★★☆☆ |
| 实现成本（越低越好） | ★★★★★ | ★★★☆☆ | ★☆☆☆☆ |
| 面试价值 | ★★☆☆☆ | ★★★★☆ | ★★★★★ |

### 🔵 结论：最终架构选 C，但**分阶段走到 C**

**不一开始就写 C**，实施路径必须是：

```
阶段 5：写 A（单体 + MySQL 条件 UPDATE）→ 压测 → 亲眼看到瓶颈
   ↓
阶段 7：升级到 B（引入 Redis）          → 压测 → 对比提升
   ↓
阶段 9：升级到 C（引入 MQ）            → 压测 → 对比提升
```

**为什么必须这样**：如果直接写 C，你永远无法回答面试官那句最致命的话——**"如果不加 Redis，会怎么样？"** 你只能背"会很慢"，而说不出"我在 200 并发时看到 `Lock wait timeout` 占比多少、P99 从多少涨到多少"。**亲手测出来的数字，才是你的。** 这也是这个项目区别于"抄开源项目"的根本。

## 二、微服务拆分：5 个服务

> ✅ 已拍板（2026-09-15）。完整的备选对比与代价见 [ADR-003](decisions/ADR-003-service-granularity.md)。

### 2.1 服务清单

| 服务 | 端口 | 职责 | 数据库 | 拥有的表 | 被谁调用 |
| --- | --- | --- | --- | --- | --- |
| `rail-gateway` | 8080 | 统一入口、路由、JWT 校验、限流 | 无 | 无 | Client |
| `rail-user-service` | 8081 | 注册、登录、签发 JWT、用户查询 | `rail_user` | `t_user` | gateway |
| `rail-train-service` | 8082 | 车次、站点、经停站、票价 | `rail_train` | `t_train`、`t_station`、`t_train_station` | gateway |
| `rail-inventory-service` | 8083 | **库存权威数据**、预热、对账、回补落库、余票查询 | `rail_inventory` | `t_seat_inventory`、`t_stock_flow` | gateway、order-service（异步） |
| `rail-order-service` | 8084 | 下单、秒杀、订单状态机、模拟支付 | `rail_order` | `t_order`、`t_order_item`、`t_local_message` | gateway |

### 2.2 为什么拆这些服务

因为它们的**扩展需求不同**，这才是拆服务的正当理由：

| 服务 | 读写特征 | 扩展需求 |
| --- | --- | --- |
| user | 极低频写 | 几乎不需要扩展 |
| train | 读极多、写少（余票查询是最高频接口） | 需要独立扩读副本 |
| order | 秒杀瞬间写极高 | 需要独立削峰、独立扩容 |
| gateway | 无状态、纯转发 | 需要独立扩容 |

**如果合成一个单体**：秒杀时 order 的写流量会挤占 train 的读连接池，一次抢票把整个系统（包括查票）打挂。这才是拆分的真实理由——不是"看起来像微服务"。

### 2.3 为什么不拆更多

拆出 `rail-inventory-service` 之后**边界到此为止**。再往下拆的诱惑是拆出"余票查询服务"，**这个不拆**：

- **读写分离不等于服务拆分**。余票查询和库存扣减操作**同一份数据**，拆开后立刻产生"读模型与写模型如何同步"的问题——有同步就有延迟，有延迟就会出现"显示有票但下单失败"。**这个不一致对用户是纯粹的困扰，换不来任何收益。**
- 读压力用**缓存 + 只读副本**解决，更快、更便宜，不需要动服务边界。

### 2.4 `rail-inventory-service` 到底干什么

> ⚠️ **诚实标注**：如果一个服务说不清"它到底独占做了什么"，那它就不该被拆出来。

| 职责 | 说明 |
| --- | --- |
| `t_seat_inventory` 的唯一 owner | 数据边界清晰，库存改动只有一个入口 |
| **预热** | 把 MySQL 库存灌入 Redis；多实例需分布式锁 |
| **对账** | 定时比对 Redis 与 MySQL，发现不一致告警 |
| **回补落库** | 阶段 9 消费 MQ 消息更新库存 |
| 余票查询 | 权威来源（带缓存） |

**阶段 8 拆分时必须回头验证这五条是否站得住**；若站不住，应当合并回 train-service，并把修正记录下来。

## 三、服务之间怎么调用

**核心原则：热路径上不做同步的跨服务 HTTP 调用。**

| 调用 | 方式 | 为什么 |
| --- | --- | --- |
| gateway → 各服务 | HTTP 路由 | 网关的职责就是转发 |
| order → train（校验车次/票价） | **OpenFeign 同步** | 不在最热路径，结果可本地缓存；必须立即拿到结果 |
| order → Redis（原子扣减） | Redis 客户端**直连** | **这是热路径**，绝对不能包一层 HTTP |
| order → inventory / train（落库存账） | **MQ 异步** | 不在请求线程内，允许延迟 |

### ⛔ 由拆分决策引入的硬性约束

```
✅ 允许：order-service ──(Redis 客户端直连)──▶ Redis
❌ 禁止：order-service ──(OpenFeign 同步)──▶ inventory-service ──▶ Redis
```

**为什么这个错误特别容易犯**：因为它**看起来更符合微服务规范**——"所有数据访问都必须通过 owner 服务"。但规范的目的是降低耦合，不是为了制造一跳。

**Redis 是共享中间件，不是任何服务的私有数据。** order-service 直连它是正当的，与"数据所有权"不冲突——真正有 owner 的是 MySQL 的 `t_seat_inventory`，而它由 inventory-service 独占。

## 四、数据库边界：单实例 + 4 个 schema

**本机方案**：单个 MySQL 8 实例 + 4 个 schema。

| schema | owner 服务 | 表 |
| --- | --- | --- |
| `rail_user` | user-service | `t_user` |
| `rail_train` | train-service | `t_train`、`t_station`、`t_train_station` |
| `rail_inventory` | inventory-service | `t_seat_inventory`、`t_stock_flow` |
| `rail_order` | order-service | `t_order`、`t_order_item`、`t_local_message` |

**为什么不起 4 个 MySQL 实例**：一台办公机上跑 4 个实例，内存和启动时间都不可接受，而且**教学价值很低**——"跨库"和"跨实例"要写的代码几乎一样（都不能 JOIN、都不能本地事务），但运维成本差 4 倍。

**规则：一张表只能有一个 owner 服务，其他服务一律禁止直连该库。**

具体反例（面试可以直接讲）：

- ❌ `order-service` 直接 `JOIN rail_train.t_train` 拿车次信息 → 车次表加字段、改分片规则时，order 的代码会**静默出错**（不是编译报错，是运行时报错），而且 order 团队完全不知情
- ❌ `order-service` 直接 `UPDATE rail_inventory.t_seat_inventory` → **两个服务同时写一张表，库存对不上时无法定位是谁改的**
- ✅ 正确做法：需要车次信息就调 `rail-train-service` 的接口；需要改库存就发消息让 inventory-service 自己改

### ⚠️ 已知缺陷：单实例多 schema 挡不住跨库 JOIN

技术上 JOIN 是通的（跨实例就不通），所以必须靠**纪律和 Code Review** 保证不跨库查询，而不能靠物理隔离。**这一点面试时要主动讲。**

**生产怎么做**：每个 schema 独立实例/独立集群，用物理隔离强制边界。

### ⚠️ 代价：跨库事务彻底不可能

`t_seat_inventory` 与 `t_order` 分属不同 schema，"扣库存 + 写订单"在 DB 层面**完全无法用本地事务保证**。这本来就是分布式系统的现实，但拆库之后**你无法再用"反正还在一个库里"来回避它**。方案 B 必须正面处理"Redis 扣成功但订单写失败"这个窗口。

## 五、服务挂掉之后会怎样

这块是 Spring Cloud 学习的核心，也是面试高频。**每个服务的故障表现都必须能说清楚。**

| 挂掉的服务 | 现象 | 系统行为 | 是否有损 |
| --- | --- | --- | --- |
| `user-service` | 登录失败 | 新用户无法登录；**已登录用户凭 JWT 仍可下单**（网关只验签不查库） | 部分可用 |
| `train-service` | 查票失败 | 返回降级数据（缓存余票）或 503；**下单链路需判断**：若校验车次是强依赖则下单也不可用 | 降级可用 |
| `order-service` | 完全不可下单 | 最严重。秒杀入口不可用 | 不可用 |
| `redis` | **灾难** | 秒杀闸门失效，若不降级则所有请求打到 DB → DB 被打挂 → 全站雪崩 | **必须降级** |
| `mq` | 下单返回失败 | 请求线程发不出消息，无法承诺"排队中" | 不可用（但**不能假装成功**） |
| `mysql` | 订单查不到、库存落不了账 | Redis 仍在扣，产生"幽灵库存" | 需对账修复 |

**最值得讲的两条**：

1. **Redis 挂掉时必须"快速失败"而不是"降级到 DB"**——降级到 DB 等于把全部秒杀 QPS 直接灌给 MySQL，会把可恢复的故障变成不可恢复的雪崩。正确做法是直接返回"系统繁忙，请稍后重试"。
2. **MQ 发不出去时，绝不能返回"抢票成功"**。宁可让用户重试，也不能给出无法兑现的承诺。

### 降级判据（贯穿全项目）

> **能不能降级，取决于「假的响应会不会造成资损」。**
>
> 不会 → 可以降级（查票可以返回缓存余票 + 提示"可能有延迟"）；
> 会 → 绝不能降级（库存扣减返回假成功 = 超卖）。

这条判据是 `rail-inventory-service` 独立存在的核心理由。

## 六、演进路径与方式

### 6.1 项目演进方式：先单体，阶段 8 再拆

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 先单体单模块，阶段 8 再拆** ✅ | **亲身体会拆分的痛**（包结构重写、配置拆分、依赖梳理）；符合真实企业演进路径 | 拆分那一次改动量大（约 1~2 天） |
| B. 一开始就建多模块 Maven | 后期省事 | **你永远不知道"为什么要拆"**——因为没经历过不拆的痛 |

选 A 的理由：**这个项目的目标是理解，不是交付**。亲手把单体拆成微服务，对"服务边界怎么划""哪些依赖会变成远程调用""跨服务事务怎么办"的理解远比一开始就搭好骨架深刻，而且这个过程本身就是极好的面试素材。

### 6.2 规模扩大后如何继续拆

| 触发条件 | 拆分动作 |
| --- | --- |
| 库存成为独立扩展单元（多种库存类型、需要独立限流） | 从 train-service 拆出 `rail-inventory-service` ✅ **已提前决策** |
| 余票查询 QPS 远超下单 | train-service 拆读写，加只读副本 |
| 订单量增长导致单库压力大 | order 按 `user_id` 或时间分片 |
| 需要多机房 | 引入单元化，库存按车次分片 |

**关键：演进路径要提前设计，但不要提前实现。**

### 6.3 `rail-common` 的边界（阶段 8 建模块时遵守）

只放**无状态的、纯数据结构的**东西（DTO、统一响应体、错误码常量）。**绝不放** Service、配置类、数据库实体——那会让所有服务被迫耦合在一起，等于拆了个寂寞。**这是很多项目的真实错误，值得写进 ADR。**
