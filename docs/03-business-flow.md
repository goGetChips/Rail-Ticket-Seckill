# 核心业务流程

**读者**：想知道"用户能做什么、一次购票/秒杀在系统里怎么走完"的人。
**解决什么问题**：功能边界、状态流转、主链路时序、以及"跑到什么程度算这个阶段完成"。
**不包含**：为什么这么拆服务（→ [02](02-architecture.md)）、Redis/Lua 的实现细节（→ [05](05-seckill.md)）。

> ⚠️ **本文描述的是目标流程。** 当前仓库只实现了车站查询两个接口，其余流程均为**计划中**。各流程的实现状态见 [status/development-status.md](status/development-status.md)。

## 一、功能边界

### 1.1 范围内

**功能**

- 用户：注册、登录（JWT）、查询个人信息
- 车次：车次列表查询、经停站查询、按出发/到达站查询可售车次
- 余票：查询某车次某日某席别余票
- 购票：提交购票请求 → 异步生成订单 → 查询订单结果
- 秒杀：热门车次限时抢购（**核心场景**）
- 模拟支付：支付成功 / 超时未支付自动关单回补库存

**非功能**

- 不超卖（可证明）
- 同一用户同一车次不重复下单（可证明）
- MQ 重复消费不产生重复订单（可证明）
- 单机压测到 1000 并发可用，尽机器能力冲击 5000
- 全链路有日志、有关键指标可观测

### 1.2 范围外（且明确记录理由）

| 不做 | 理由 | 面试时怎么说 |
| --- | --- | --- |
| RocketMQ/Kafka 集群、主从 | 单机教学，集群运维与并发正确性无关 | "我保证了单节点下的正确性，集群下的主从切换一致性我没有验证过，不吹" |
| Seata / TCC 分布式事务 | 引入成本远大于收益，用"异步 + 对账"能达到同等效果 | "我先论证了为什么不用，而不是不会用" |
| 分库分表 | 单机数据量根本用不到 | "我知道什么时候该分，但这个项目的数据量不分" |
| 链路追踪（SkyWalking） | 阶段后期可选，非主线 | — |
| 前端页面 | 用 JMeter + curl 即可验证 | — |

### 1.3 与真实铁路系统的差异

| 真实系统 | 本项目 | 原因 |
| --- | --- | --- |
| 区间库存（A→B 与 B→C 共享座位） | **简化为整段库存** | 区间库存是铁路特有复杂度，与并发正确性无关，会淹没主线 |
| 真实支付、对接银行 | 模拟支付接口（直接改订单状态） | 同上 |
| 实名制、乘车人管理 | 只存 userId | 同上 |
| 座位排布、选座 | 只按席别扣总数 | 同上 |
| 候补、改签、退票 | 不做 | 同上 |

> **这个边界在面试里是加分项而非减分项**——主动说明"我砍掉了什么、为什么砍"，比假装做了全部更有说服力。

## 二、订单状态机

**当前 DDL 定义的取值**（`t_order.status TINYINT`）：

```
0 = 待支付 ──支付成功──▶ 1 = 已支付
     │
     └──超时未支付 / 主动取消──▶ 2 = 已取消   （触发库存回补）
```

> ⚠️ 设计文档的早期版本里还画过 `FAILED` 状态。**当前 DDL 中没有这个状态**——建表脚本才是权威，见 [06-database.md](06-database.md)。

**所有状态流转一律用条件 UPDATE 做 CAS**，不用分布式锁：

```sql
UPDATE t_order SET status = 1 WHERE order_no = ? AND status = 0;
-- 受影响 1 行 = 本次生效
-- 受影响 0 行 = 订单已被处理过（重复支付 / 已取消），直接返回成功
```

**为什么受影响 0 行时应该"返回成功"而不是报错**：支付回调重复到达是常态（网络重试）。此时用户的诉求是"我付过的钱算数"，而钱确实已经记上了。报错会让用户以为支付失败，可能重复付款。这叫**幂等**：同样的请求执行多次，结果和执行一次相同。

同类手法还有"支付与超时关单的竞态"——见 [05-seckill.md](05-seckill.md) 的异常路径 E6。

## 三、主链路：一次购票

```
1. 用户查余票
   Client → Gateway → train-service
   命中缓存直接返回；未命中查 MySQL t_seat_inventory

2. 用户提交购票请求
   Client → Gateway（校验 JWT、解析 userId、限流）→ order-service

3. order-service 执行 Redis Lua 原子扣减
   ├─ -1 库存不足   → 响应"已售完"（不落库、不发消息）
   ├─ -2 用户重复   → 响应"请勿重复提交"
   ├─ -3 未预热     → 响应 503 + 告警（**这是系统故障，不是售罄**）
   └─ >= 0          → 扣减成功，继续

4. 落单
   方案 B（阶段 7）：同步写 t_order + t_order_item，直接返回订单结果
   方案 C（阶段 9）：写本地消息表 PENDING → 发 MQ → 返回"排队中"

5. 支付
   POST 支付接口 → 条件 UPDATE 把订单从 0 改为 1
   受影响 0 行 → 已被处理过，直接返回成功

6. 超时未支付
   延时消息（或定时扫描）触发 → 条件 UPDATE 改为 2 → 发消息回补库存
```

## 四、秒杀主链路（方案 C 完整形态）

> 📌 **阶段 9 的形态。** 阶段 7 的方案 B 没有 MQ，第 4 步改为同步写库、直接返回订单结果。两者的差异本身就是很好的面试对比点（见下方）。

```
1. Client 提交抢票请求
2. Gateway  校验 JWT → 解析出 userId → 限流（令牌桶）

3. order-service:
   3.1 本地缓存校验车次有效性（命中则跳过 Feign）
   3.2 执行 Redis Lua 原子扣减（见上）
   3.3 生成 order_no，写本地消息表 PENDING
   3.4 发送 MQ 消息（ORDER_CREATE + ORDER_TIMEOUT 延时消息）
   3.5 立即返回"抢票排队中，请稍后查询结果"

4. order 消费者:
   4.1 幂等检查：order_no 是否已处理（本地消息表 / 唯一索引）
   4.2 写 t_order（status=0 待支付）+ t_order_item
   4.3 写秒杀结果到 Redis（供客户端轮询）
   4.4 ack

5. inventory 消费者:
   5.1 幂等检查
   5.2 UPDATE t_seat_inventory SET sold_count = sold_count + 1
   5.3 ack

6. 超时未支付 → ORDER_TIMEOUT 消息 → 关单 + 发 STOCK_RELEASE → 回补库存
```

**为什么返回"排队中"而不是"成功"**：请求线程没有写 DB，**它没有资格承诺订单已创建**。返回"排队中"是诚实的；返回"成功"而订单后来创建失败，是欺骗用户。**这不是技术细节，是正确性边界。**

### 方案 B 与方案 C 的差异（阶段 7 vs 阶段 9）

| 对比项 | 方案 B（无 MQ） | 方案 C（有 MQ） |
| --- | --- | --- |
| 秒杀响应 | 直接返回订单结果 | 返回"排队中"，客户端轮询 |
| 幂等压力 | **只需要处理"用户重复提交"** | 还要处理 MQ 重复投递、消费失败补偿 |
| 异常路径 | 只剩 E4（重复提交）/ E8（Redis 宕机）/ E9（预热丢失） | E1~E9 九条全都要做 |

**引入 MQ 换来了什么**：吞吐上限、响应时间与 DB 解耦。
**付出了什么**：必须自己做消费幂等、消息可靠性、补偿和对账。**这个交换本身就是面试的好素材。**

## 五、验收标准（可执行、可证伪）

阶段结束时必须能跑出这些结果，**跑不出来就是没完成**：

| 编号 | 验收项 | 验证方式 | 状态 |
| --- | --- | --- | --- |
| A1 | 1000 并发抢 100 张票，**恰好卖出 100 张** | 压测后 `SELECT COUNT(*) FROM t_order WHERE status != 2`，必须 `<= 100` | 计划中（阶段 7~10） |
| A2 | 库存**从未为负 / 从未超卖** | `SELECT * FROM t_seat_inventory WHERE sold_count > total_count` 必须返回 0 行；Redis 中 `GET` 库存必须 `>= 0` | 计划中 |
| A3 | 同一用户重复提交 100 次，**只产生 1 个订单** | 脚本循环提交 → `COUNT(*) FROM t_order_item WHERE user_id=? AND ...` 必须为 1 | 计划中 |
| A4 | 人为让 MQ 重复投递同一消息，**不产生重复订单** | 手动重发消息 → 订单数不变 | **⏸️ 阶段 9 才可验证**（MQ 已推迟） |
| A5 | Redis 与 MySQL 库存最终一致 | 对账 SQL 返回 0 行差异（允许短时间窗口不一致） | 计划中（阶段 9） |
| A6 | 有一份真实压测报告，含 QPS/P95/P99/错误率 | JMeter 报告 + 机器配置 + commit hash | 计划中（阶段 6/10） |

**A1、A2、A3、A5 是"能证明不超卖"的凭证**（A4 待阶段 9）——面试官问"你怎么证明不会超卖"时，答案是这套**可复现的验证**，而不是"我用了 Redis 所以不会超卖"。

具体的验证 SQL 见 [05-seckill.md](05-seckill.md) 第六节。
