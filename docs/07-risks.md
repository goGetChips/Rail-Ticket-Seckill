# 高并发风险清单与已知缺陷

**读者**：想知道"这套设计会在哪里出问题"的人。
**解决什么问题**：每条风险的**触发场景 → 后果 → 对策 → 在哪个阶段解决**，以及本设计**已知没解决**的地方。
**不包含**：风险的实现方案（→ [05](05-seckill.md)）、真实踩过的坑（→ [troubleshooting/](troubleshooting/README.md)）。

> ⚠️ **本文是"推演"，不是"实录"。** 表中所有风险**除已标注实测的以外，都尚未在本机发生过**。
> 真实发生过的故障记录在 [troubleshooting/README.md](troubleshooting/README.md)，那里面每一篇都有原始日志。
>
> 🟡 **阶段 5 的标注**：表中标了 **`阶段 5 已实现`** 的项，意思是**对策的代码已经写好**，
> 但**测试一次都没跑过**（MySQL 被 DLP 加密起不来）。
> 它们**仍然属于"推演"** —— 写上"已实现"只是说"不再是一张白纸"，
> **不等于"这条风险已经验证被挡住了"**。

## 一、正确性类（后果最严重，都是资损）

| # | 风险 | 触发场景 | 后果 | 对策 | 阶段 |
| --- | --- | --- | --- | --- | --- |
| R1 | **超卖** | 两请求同时读到库存=1 | 资损，**不可逆** | 🟡 **阶段 5 已实现**：条件 UPDATE（CAS）+ DB 唯一索引兜底 + CHECK 约束 + 对账 SQL。阶段 7 换成 Lua 原子扣减 | **5**/7 |
| R2 | **重复下单** | 用户狂点提交 / MQ 重复投递 | 用户被扣两次款 | 🟡 **阶段 5 已实现**（前两层）：`uk_user_train_date_seat` 唯一索引 + 409 业务拒绝。第三层（MQ 幂等）待阶段 9 | **5**/7/9 |
| R3 | **库存变负** | Lua 逻辑写错 / 未预热的 key 被当作 0 | 超卖 | 🟡 **阶段 5 的 MySQL 版已实现**：CHECK `ck_sold_non_negative` + 对账 SQL ⑤。Lua 那一半待阶段 7 | **5**/7 |
| R4 | **少卖（库存泄漏）** | 预扣成功但订单没写成功；或用户不付款且无人回滚 | **不超卖，但直接损失收入**；用户反复投诉"明明有票却买不到" | 🟡 **阶段 5 已实现检测**（注意：是**检测**，不是**杜绝**）：`t_stock_flow` 流水表 + 对账 SQL ④。阶段 5 的少卖来源是一个具体得多的坑 —— **`catch` 块里写 `return` 会让 Spring 提交事务**，扣减提交而订单回滚，接口仍返回 409。彻底杜绝要等阶段 7 的预扣 TTL + 超时状态机 | **5**/7/9 |
| R5 | **回滚误伤已支付订单** | 超时关单任务与支付回调同时到达，关单任务没重查状态就回滚库存 | **超卖 + 资金纠纷**，最严重的一类事故 | 🟡 **阶段 5 已实现一半**：支付侧的状态机 CAS 已写好，且**"受影响 0 行"会再读一次状态** —— 已支付→幂等 200、**已取消→409（不是 200）**。回补库存那一半待阶段 7 | **5**/9 |
| R6 | **幽灵库存** | Redis 扣成功，MQ 发送失败 | 票被扣了但卖不出去，库存凭空消失 | 本地消息表 + 补偿任务 + 对账 | 9 |
| R7 | **支付 vs 关单竞态** | 用户恰在超时瞬间支付 | 订单状态错乱 | 🟡 **阶段 5 的状态机部分已实现**（[05 §5 E6](05-seckill.md)）；阶段 5 还没有关单任务，所以这个竞态**今天无法真实发生** | **5**/9 |
| R8 | **支付回调重复 / 乱序 / 伪造** | 渠道重试回调；成功与失败通知乱序到达；攻击者伪造回调 | 重复处理 → 状态异常；**伪造 → 票被白拿（资金损失）** | 验签 + 回调原文落库 + 状态机拒绝非法迁移 + 幂等应答 | 9 |

> **R4 的补充**：回滚动作应由「**超时取消**」驱动，而不是由「用户点击取消」驱动。用户可能不点、可能点两次、可能在支付成功后才点——只有超时任务这一个**确定性触发点**，才能保证回滚一定发生。
>
> ⚠️ **阶段 5 让 R4 的"对策"这一栏必须被读得更仔细**：阶段 5 做到的只是**能发现少卖**，
> 不是**不会少卖**。判据是：`t_stock_flow` 里每一条订单都有对应的扣减流水
> （对账 SQL ④）。**"能发现"和"不发生"是两件事，不能混着说。**
>
> **R5 的一句话总结**：**永远不要"先回滚库存再看订单状态"。** 顺序反了就会把一张已经付款的票卖两次。
> 阶段 5 是它的镜像版本：**永远不要"看到 0 行就返回成功"** —— 必须再读一次状态，
> 因为"已经是我想要的状态"（已支付）和"永远不可能变成我想要的状态"（已取消）是**两个不同的 409/200 分支**。

## 三、流量与容量类

| # | 风险 | 触发场景 | 后果 | 对策 | 阶段 |
| --- | --- | --- | --- | --- | --- |
| R15 | **开售瞬间流量尖峰 + 预热未完成** | 预热任务没跑完就开售，扣减返回"未预热"→ 大量请求同时回源 | **开售第一秒系统就不可用**，而这正是最不能出错的时刻 | 预热提前量 + 预热完成校验（统计 key 数与预期比对，不一致则告警）+ 回源加锁限流 + 提前扩容 | 7/10 |
| R16 | **脚本刷票 / 限流绕过** | 黄牛用脚本在开售瞬间发起远超正常量的请求；限流只按 IP 做则换代理即可绕过 | 票被脚本抢走，真实用户流失；系统容量被无效流量消耗 | 网关按「用户 + 接口 + IP」三维限流；业务唯一约束；必要时加人机校验（**不能全量校验，会伤害正常用户**） | 8 |
| R17 | **热点行锁竞争 / DB 连接池耗尽** | 慢 SQL 导致连接释放不及时 | 全站不可用 | HikariCP 配超时 + 慢 SQL 监控 + 压测观察 | 6/10 |
| R18 | **Feign 超时级联** | 某下游变慢，调用方线程被占满 | 雪崩 | 连接/读超时 + 熔断降级 | 8 |
| R19 | **Nacos 感知延迟** | 实例刚下线，调用方还在往它发请求 | 少量请求失败 | 重试 + 熔断兜住窗口期 | 8 |
| R20 | **MQ 消息积压** | 消费者处理慢或挂掉 | 用户长时间"排队中" | 并行消费 + 积压告警 | 9 |

> **R15 的判据**：预热不是"跑过就行"，而是**跑完且校验通过**。校验不通过时应当**考虑推迟开售或降级提示**，而不是硬着头皮开。

## 六、本设计的已知缺陷（诚实清单）

> **主动列出缺陷，比被人问出来强。** 以下是当前**没有解决或解决不彻底**的地方。

| # | 缺陷 | 为什么没解决 | 什么时候必须解决 |
| --- | --- | --- | --- |
| D1 | Redis 主从切换会导致超卖 | 需要 Redlock 或 ZooKeeper 等重量级方案，教学项目单节点规避 | 生产环境 |
| D2 | 单 MySQL 实例多 schema **无法物理阻止跨库 JOIN** | 只能靠纪律和 Code Review | 生产环境拆独立实例 |
| D3 | "写 Redis + 写本地消息表"不是原子的，仍有极小窗口丢消息 | 彻底解决需要 Redis 作为唯一入口 + 反向回补，复杂度高 | 阶段 9 细化 |
| D4 | MQ 单节点，Broker 挂掉消息丢失 | 集群部署超出单人项目范围 | 生产环境 |
| D5 | 没有链路追踪，跨服务问题定位靠日志 grep | 引入 SkyWalking 需要额外资源 | 阶段 10 可选 |
| D6 | 座位号后置分配，高并发下分配逻辑未设计 | 与并发正确性主线无关 | 不在范围 |
| D7 | 没有车次日历表，无法表达"某天停运" | 见 [06 §3.2](06-database.md) | 不在范围 |
| D8 | 不做区间票，短途乘客占用全程运力 | 见 [06 §2 决策 1](06-database.md) | 不在范围 |
| D9 | 四个服务共用一个 `rail` 数据库账号 | 本地开发便利 | 生产环境每服务独立账号 |
| **D10** | **🔴 库存 / 订单的写入路径住在 `rail-train-service` 里** | 阶段 5 的下单事务要写 `rail_inventory`（扣减 + 流水）和 `rail_order`（订单 + 明细），但代码在 train-service 里 —— **这三张表的 owner 分别是 `rail-inventory-service` 和 `rail-order-service`**。现阶段合法（同一个 MySQL 实例，本地事务），但**代码归属是错的**：`rail` 账号对该库本来就有写权限，数据库层面从没拦过 | **阶段 8 拆分时必须消除**：扣减 + 流水迁 `rail-inventory-service`，订单 + 明细迁 `rail-order-service`。见 [status §六 技术债 #14/#16](status/development-status.md) |
| **D11** | **阶段 5 的测试数据靠手工清理** | 并发测试真的会往库里写订单 / 票 / 流水，而它们**不能靠事务回滚清理**（并发测试禁用 `@Transactional`）。目前靠 `@AfterEach` 显式 `DELETE` 兜着，JMeter 留下的数据只能照 [sql/12](../sql/12_verify_stage5_order.sql) 文末的注释手工删 | 阶段 6 CI 化时 |

> **D3 值得注意**：它意味着"消息不丢"在本项目里是**概率上极高、但不是数学上保证**。面试被追问到这一层时，正确回答是承认这个窗口并说出彻底的解法，而不是坚持"我的方案不会丢消息"。
>
> **D10 值得注意**：它是 **R22 的另一面**。R22 说"拆分后跨库事务不可能"，
> D10 说"现在这个跨库事务是能成的、但代码放错了地方"。
> **两条必须一起讲**，只讲其中一条都会让人得出错误结论
> （只讲 R22 → 以为阶段 5 的代码有 bug；只讲 D10 → 以为拆服务不用改事务边界）。
