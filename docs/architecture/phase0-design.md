## 一、需求分析

### 1.1 这个项目真正要解决的问题

不是"实现一个铁路售票系统"，而是：

> **在有限库存 + 瞬时高并发 + 分布式多服务的条件下，如何保证"不超卖、不丢单、不重复下单"，并且能说清楚每一处取舍的理由。**

功能是载体，并发正确性才是目标。这决定了设计优先级：

| 优先级 | 目标 | 说明 |
| --- | --- | --- |
| P0 | **正确性** | 不超卖、不重复下单。正确性不能被性能妥协。 |
| P1 | **可解释性** | 每一处设计都能回答"为什么"和"为什么不用 X"。 |
| P2 | **性能** | 快速响应、抗突发流量、降低 DB 压力。 |
| P3 | **功能完整度** | 够用即可，不做真实支付/实名/座位排布。 |

**为什么把正确性放在性能前面**：秒杀场景下超卖是资损，且**不可逆**（票已经卖给两个人了）；而性能不足只是体验问题，可以通过限流把超出的流量挡在门外。用限流把系统保护成"慢但对"，好过"快但错"。

### 1.2 核心并发矛盾

一句话概括：**"判断"与"扣减"必须是原子的。**

```
线程 A: 读库存 = 1 ──┐
线程 B: 读库存 = 1 ──┤  两个线程都认为"还有票"
线程 A: 扣减 → 0    ──┤
线程 B: 扣减 → -1   ──┘  超卖
```

这个问题在单机、单线程下不存在，在**任何**并发场景下都存在。它会在本项目的三个阶段以三种不同形态反复出现（MySQL 行锁 → Redis 原子性 → 分布式一致性），这正是这个项目的教学主线。

### 1.3 与真实铁路系统的差异（明确边界）

| 真实系统 | 本项目 | 原因 |
| --- | --- | --- |
| 区间库存（A→B 与 B→C 共享座位） | **简化为整段库存**（出发站-到达站 作为一个售卖单元） | 区间库存是铁路特有复杂度，与并发正确性无关，会淹没主线 |
| 真实支付、对接银行 | 模拟支付接口（直接改订单状态） | 同上 |
| 实名制、乘车人管理 | 只存 userId | 同上 |
| 座位排布、选座 | 只按席别扣总数 | 同上 |
| 候补、改签、退票 | 不做 | 同上 |

**这个边界在面试里是加分项而非减分项**——主动说明"我砍掉了什么、为什么砍"，比假装做了全部更有说服力。

## 二、MVP 边界

### 2.1 范围内（In Scope）

**功能**
- 用户：注册、登录（JWT）、查询个人信息
- 车次：车次列表查询、经停站查询、按出发/到达站查询可售车次
- 余票：查询某车次某日某席别余票
- 购票：提交购票请求 → 异步生成订单 → 查询订单结果
- 秒杀：热门车次限时抢购（核心场景）
- 模拟支付：支付成功 / 超时未支付自动关单回补库存

**非功能**
- 不超卖（可证明）
- 同一用户同一车次不重复下单（可证明）
- MQ 重复消费不产生重复订单（可证明）
- 单机压测到 1000 并发可用，尽机器能力冲击 5000
- 全链路有日志、有关键指标可观测

### 2.2 范围外（Out of Scope，且明确记录理由）

| 不做 | 理由 | 面试时怎么说 |
| --- | --- | --- |
| RocketMQ/Kafka 集群、主从 | 单机教学，集群运维与并发正确性无关 | "我保证了单节点下的正确性，集群下的主从切换一致性我没有验证过，不吹" |
| Seata / TCC 分布式事务 | 引入成本远大于收益，且本项目用"异步 + 对账"能达到同等效果 | "我先论证了为什么不用，而不是不会用" |
| 分库分表 | 单机数据量根本用不到 | "我知道什么时候该分，但这个项目的数据量不分" |
| 链路追踪（SkyWalking） | 阶段后期可选，非主线 | — |
| 前端页面 | 用 JMeter + curl 即可验证 | — |

### 2.3 验收标准（可执行、可证伪）

阶段结束时必须能跑出这些结果，**跑不出来就是没完成**：

| 编号 | 验收项 | 验证方式 |
| --- | --- | --- |
| A1 | 1000 并发抢 100 张票，**恰好卖出 100 张** | 压测后执行 `SELECT COUNT(*) FROM t_order WHERE status != 'CANCELLED'`，结果必须 `<= 100` |
| A2 | 库存**从未为负** | `SELECT * FROM t_seat_inventory WHERE sold_qty > total_qty` 必须返回 0 行；Redis 中 `GET` 库存必须 `>= 0` |
| A3 | 同一用户重复提交 100 次，**只产生 1 个订单** | 脚本循环提交 → `SELECT COUNT(*) FROM t_order WHERE user_id=? AND ...` 必须为 1 |
| A4 | 人为让 MQ 重复投递同一消息，**不产生重复订单** | 手动重发消息 → 订单数不变。**⏸️ 阶段 9 才可验证**（决策 2 推迟了 MQ） |
| A5 | Redis 与 MySQL 库存最终一致 | 对账 SQL 返回 0 行差异（允许短时间窗口不一致） |
| A6 | 有一份真实压测报告，含 QPS/P95/P99/错误率 | JMeter 报告 + 机器配置 + commit hash |

**A1、A2、A3、A5 是"能证明不超卖"的凭证**（A4 待阶段 9）——面试官问"你怎么证明不会超卖"时，答案是这套可复现的验证，而不是"我用了 Redis 所以不会超卖"。

> **注意 A4 的阶段变化**：因为 MQ 推迟到阶段 9，**阶段 7 的方案 B 不存在"消息重复消费"问题**——订单是同步写的。这意味着方案 B 的幂等压力比方案 C 小，只需要处理"用户重复提交"。**这个差异本身就是一个很好的面试对比点**：引入 MQ 换来了什么（吞吐、响应时间），又付出了什么（必须自己做消费幂等）。

## 三、系统架构候选方案

> 这是你明确要求的部分：**先论证，再选**。以下三种方案都真实存在，各有适用场景。

### 方案 A：请求直接操作 MySQL 库存

```
Client → Gateway → Order Service → MySQL(UPDATE ... WHERE stock > 0)
```

**做法**：用 `UPDATE t_seat_inventory SET sold_qty = sold_qty + 1 WHERE train_id=? AND travel_date=? AND seat_type=? AND sold_qty < total_qty`，靠 `affected rows = 0/1` 判断是否扣减成功。

| 维度 | 评价 |
| --- | --- |
| 性能 | 🔴 **最差**。热点行是同一行，所有并发都在抢同一把行锁，MySQL 串行化处理。压测会看到大量 `Lock wait timeout`。 |
| 一致性 | 🟢 **最好**。单条 SQL 原子，天然不超卖，不依赖任何外部组件。 |
| 复杂度 | 🟢 **最低**。没有缓存、没有 MQ、没有对账。 |
| 可靠性 | 🟢 高。少一个组件就少一处故障点。 |
| 实现成本 | 🟢 半天。 |
| 面试价值 | 🟡 中。它是**基准线**——没有它，你无法回答"加了 Redis 到底提升了多少"。 |

### 方案 B：Redis + MySQL（同步双写）

```
Client → Gateway → Order Service → Redis(Lua 预扣) → MySQL(同步写订单+扣库存) → 返回
```

**做法**：Redis 里用 Lua 原子预扣，扣成功后**同步**写 MySQL，两步都在请求线程内完成。

| 维度 | 评价 |
| --- | --- |
| 性能 | 🟡 中。Redis 挡住了无效请求，但**成功的请求仍然同步打 DB**，DB 依然是瓶颈（只是流量被过滤了一层）。 |
| 一致性 | 🟡 中。Redis 扣成功但 MySQL 写失败 → 需要回补 Redis，回补本身可能失败。 |
| 复杂度 | 🟡 中。开始出现"两个数据源如何一致"的问题。 |
| 可靠性 | 🟡 中。 |
| 实现成本 | 🟡 1~2 天。 |
| 面试价值 | 🟢 高。它是 Redis 与 DB 一致性问题的最佳教学样本。 |

### 方案 C：Redis + Lua 预扣 + MQ 异步落库

```
Client → Gateway → Order Service → Redis(Lua 预扣) → MQ → 立即返回"排队中"
                                                        ↓
                                          Consumer → 写订单 + 落库存账
```

| 维度 | 评价 |
| --- | --- |
| 性能 | 🟢 **最好**。请求线程只做「Redis 一次往返 + 一次消息投递」，响应时间与 DB 完全解耦。 |
| 一致性 | 🔴 **最差（复杂度最高）**。需要处理：消息丢失、重复消费、消费失败、库存回补、对账。 |
| 复杂度 | 🔴 **最高**。 |
| 可靠性 | 🟡 取决于补偿机制是否完整；做不好会出现"票扣了但订单没生成"的幽灵库存。 |
| 实现成本 | 🔴 3~5 天（含补偿和对账）。 |
| 面试价值 | 🟢 **最高**。最终一致性、幂等、消息可靠性全在这里。 |

### 六维对比总表

| 维度 | A 直连 MySQL | B Redis + MySQL | C Redis + MQ + MySQL |
| --- | --- | --- | --- |
| 性能 | ★☆☆☆☆ | ★★★☆☆ | ★★★★★ |
| 一致性（实现难度，越低越好） | ★★★★★ | ★★★☆☆ | ★☆☆☆☆ |
| 复杂度（越低越好） | ★★★★★ | ★★★☆☆ | ★☆☆☆☆ |
| 可靠性 | ★★★★★ | ★★★☆☆ | ★★★☆☆ |
| 实现成本（越低越好） | ★★★★★ | ★★★☆☆ | ★☆☆☆☆ |
| 面试价值 | ★★☆☆☆ | ★★★★☆ | ★★★★★ |

### 🔵 结论：选 C，但**分阶段走到 C**

**最终架构选方案 C**，理由：

1. 方案 C 是唯一能回答"高并发"这个命题的架构——A 和 B 的瓶颈都在 DB 同步写入上，而那正是秒杀场景的核心矛盾。
2. 面试追问的深度集中在 C 的难点上（最终一致性、幂等、对账），A/B 讲不出同等深度的故事。
3. 方案 C 的"复杂度高"是**特性不是缺陷**——复杂度正是要学的东西。

**但是——不要一开始就写 C。** 实施路径必须走：

```
阶段 5：写 A（单体 + MySQL 乐观锁）→ 压测 → 亲眼看到瓶颈
   ↓
阶段 7：升级到 B（引入 Redis）    → 压测 → 对比提升
   ↓
阶段 9：升级到 C（引入 MQ）      → 压测 → 对比提升
```

**为什么必须这样**：如果直接写 C，你永远无法回答面试官那句最致命的话——**"如果不加 Redis，会怎么样？"** 你只能背"会很慢"，而说不出"我在 200 并发时看到 `Lock wait timeout` 占比 37%，P99 从 80ms 涨到 4.2s"。**亲手测出来的数字，才是你的**。这也是这个项目区别于"抄开源项目"的根本。

## 四、微服务拆分方案

### 4.1 ✅ 决策：5 个可运行服务

> 本节已按 §15 决策 3 更新为 5 个服务。拆分理由与代价见 [ADR-003](./decisions/ADR-003-service-granularity.md)。

| 服务 | 端口 | 职责 | 数据库 | 拥有的表 | 被谁调用 |
| --- | --- | --- | --- | --- | --- |
| `rail-gateway` | 8080 | 统一入口、路由、JWT 校验、限流 | 无 | 无 | Client |
| `rail-user-service` | 8081 | 注册、登录、签发 JWT、用户查询 | `rail_user` | `t_user` | gateway |
| `rail-train-service` | 8082 | 车次、站点、经停站、票价 | `rail_train` | `t_train`、`t_station`、`t_train_station` | gateway |
| `rail-inventory-service` | 8083 | **库存权威数据**、预热、对账、回补落库、余票查询 | `rail_inventory` | `t_seat_inventory`、`t_stock_flow` | gateway、order-service（异步） |
| `rail-order-service` | 8084 | 下单、秒杀、订单状态机、模拟支付 | `rail_order` | `t_order`、`t_order_item`、`t_local_message` | gateway |

**端口分配说明**（已按 2026-09-15 实测校正）：

8080 留给 Gateway。**Nacos 3.x 把控制台拆成了独立进程、有自己独立的端口**——实测它默认占用了 8080，已改为 **8888**。

⚠️ **不要混淆 8848 和 8888**：`8848` 是 Nacos **服务端**端口（Spring 客户端注册发现走这里，gRPC 走 `9848/9849`）；控制台端口是另一个。我在阶段 0 的初稿里把两者搞混了，写成了"把控制台改到 8848"——**那是错的**，8848 上跑的是服务端本身。

#### 关键设计：Redis 库存是共享的预扣层，MySQL 才有 owner

这是拆出 inventory-service 后**必须讲清楚**的边界，也是最容易被面试官追问的点：

| 角色 | 由谁承担 | 为什么 |
| --- | --- | --- |
| **Redis 的写入者**（秒杀扣减） | `order-service` **直连 Redis** | 热路径，绝不能包一层 HTTP（见下） |
| **Redis 的预热者** | `inventory-service` | 它是 `t_seat_inventory` 的 owner，只有它知道真实票额 |
| **Redis 的对账者** | `inventory-service` | 定时比对 Redis 与 MySQL，发现不一致告警 |
| **权威数据（source of truth）** | MySQL 的 `t_seat_inventory` | Redis 只是**前置闸门 + 加速层**，可丢可重建 |

> **⛔ 由决策 3 引入的硬性约束**：秒杀热路径上，`order-service` **必须直连 Redis**，**禁止**通过 OpenFeign 同步调用 `rail-inventory-service` 来扣库存。
>
> **为什么**：多一跳 HTTP RPC，就要付出连接池占用、序列化、网络超时、线程阻塞的全部代价。这会把异步化省下来的时间原样还回去，让"5 个服务"这个决定变成纯粹的负担。
>
> **这是拆出独立库存服务后最容易犯的设计错误**——因为它看起来"更符合微服务规范"（所有数据访问都通过 owner 服务）。但规范的目的是降低耦合，不是为了制造一跳。
>
> **面试标准答法**："Redis 是共享中间件，order-service 直连它是正当的；inventory-service 管的是 MySQL 权威表，两者职责不重叠。我不会为了形式上的'数据只由 owner 访问'，在秒杀热路径上加一跳 RPC。"

> **为什么这样定**：如果让 order-service 也拥有库存表，就会出现两张表被两个服务写，一致性无从保证。让 Redis 成为"无主的共享预扣层"、MySQL 表有唯一 owner，责任链才是清晰的。面试被问"Redis 和 MySQL 谁是权威"时，这就是答案。

### 4.2 回答你提出的 7 个问题

**Q1：为什么拆这些服务？**

因为它们的**扩展需求不同**，这才是拆服务的正当理由（不是为了"看起来微服务"）：

| 服务 | 读写特征 | 扩展需求 |
| --- | --- | --- |
| user | 极低频写 | 几乎不需要扩展 |
| train | 读极多、写少（余票查询是最高频接口） | 需要独立扩读副本 |
| order | 秒杀瞬间写极高 | 需要独立削峰、独立扩容 |
| gateway | 无状态、纯转发 | 需要独立扩容 |

**如果合成一个单体**：秒杀时 order 的写流量会挤占 train 的读连接池，一次抢票把整个系统（包括查票）打挂。这才是拆分的真实理由。

**Q2：为什么不拆更多（比如把余票查询也拆出去）？**

拆出 `rail-inventory-service` 之后，**边界就到此为止**。再往下拆的诱惑是拆出"余票查询服务"，**这个不拆**，理由：

- **读写分离不等于服务拆分**。余票查询和库存扣减操作的是**同一份数据**，拆开后两者之间立刻产生"读模型与写模型如何同步"的问题——而同步就有延迟，有延迟就会出现"显示有票但下单失败"。**这个不一致对用户是纯粹的困扰，换不来任何收益。**
- 余票查询的压力可以用**缓存 + 只读副本**解决，这是更快、更便宜的手段，不需要动服务边界。

**为什么现在这个粒度是对的**：5 个服务的分界线，恰好画在**"数据所有权不同"**和**"扩展需求不同"**的地方——这才是拆服务的正当理由。每一刀都切在真实接缝上，而不是切在"看起来应该拆"的地方。

**运维成本必须如实记录**：5 个服务 + Nacos + MySQL + Redis + Sentinel Dashboard ≈ **9 个常驻进程**（阶段 9 引入 MQ 后升到 11 个）。在一台办公机上，这意味着**启动要排队、内存要精打细算**。这是选择 5 个服务必须支付的代价，见 [ADR-003](./decisions/ADR-003-service-granularity.md)。

**Q3：服务之间如何调用？**

两种方式，**按"是否在秒杀热路径上"划分**：

| 调用 | 方式 | 为什么 |
| --- | --- | --- |
| gateway → 各服务 | HTTP 路由 | 网关的职责就是转发 |
| order → train（校验车次/票价） | **OpenFeign 同步** | 不在最热路径，且结果可本地缓存；必须立即拿到结果 |
| order → Redis（原子扣减） | Redis 客户端直连 | **这是热路径**，绝对不能包一层 HTTP |
| order → train（落库存账） | **MQ 异步** | 不在请求线程内，允许延迟 |
| train → order（同理） | MQ 异步 | 同上 |

> **核心原则：热路径上不做同步的跨服务 HTTP 调用。** 每多一跳网络，就多一份超时风险和延迟。秒杀链路里唯一允许的同步远程调用是 Redis。

**Q4 / Q5：数据库如何划分？哪些服务拥有自己的库？**

**✅ 本机方案：单个 MySQL 8 实例 + 4 个 schema**（`rail_user`、`rail_train`、`rail_inventory`、`rail_order`）。

| schema | owner 服务 | 表 |
| --- | --- | --- |
| `rail_user` | user-service | `t_user` |
| `rail_train` | train-service | `t_train`、`t_station`、`t_train_station` |
| `rail_inventory` | inventory-service | `t_seat_inventory`、`t_stock_flow` |
| `rail_order` | order-service | `t_order`、`t_order_item`、`t_local_message` |

**为什么不真的起 4 个 MySQL 实例**：🔴 一台办公机上跑 4 个 MySQL 实例，内存和启动时间都不可接受，而且**它教学价值很低**——"跨库"和"跨实例"要写的代码几乎一样（都不能 JOIN、都不能本地事务），但运维成本差 4 倍。

**⚠️ 一个必须诚实说明的副作用**：拆出 `rail_inventory` 之后，`t_seat_inventory` 和 `t_order` 分属不同 schema，**"扣库存 + 写订单"在数据库层面完全无法用本地事务保证**。这本来就是分布式系统的现实，但现在你**无法再用"反正还在一个库里"来回避它**。阶段 7 的方案 B 必须正面处理"Redis 扣成功但订单写失败"这个窗口。

**但要诚实说明代价**：单实例多 schema **无法防住"跨 schema JOIN 的诱惑"**（技术上 JOIN 是通的，跨实例就不通）。所以必须靠**纪律和代码审查**来保证不跨库查询，而不能靠物理隔离。这一点面试时要主动讲——**这是本方案的已知缺陷**。

**生产怎么做**：每个 schema 独立实例/独立集群，物理隔离强制边界。

**Q6：哪些数据不能跨服务直接访问？**

**规则：一张表只能有一个 owner 服务，其他服务一律禁止直连该库。**

具体反例（面试可以直接讲）：

- ❌ `order-service` 直接 `JOIN rail_train.t_train` 拿车次信息 → 车次表加字段、改分片规则时，order 的代码会**静默出错**（不是编译报错，是运行时报错），而且 order 团队完全不知情。
- ❌ `order-service` 直接 `UPDATE rail_inventory.t_seat_inventory` → **两个服务同时写一张表，库存对不上时无法定位是谁改的**。
- ✅ 正确做法：需要车次信息就调 `train-service` 的接口；需要改库存就发消息让 `train-service` 自己改。

**Q7：规模扩大后如何继续拆？**

🔵 演进路径（写进 ADR-003，不现在做）：

| 触发条件 | 拆分动作 |
| --- | --- |
| 库存成为独立扩展单元（如出现多种库存类型、需要独立限流） | 从 train-service 拆出 `rail-inventory-service`，接管 `t_seat_inventory` 与 Redis 预热/对账 |
| 余票查询 QPS 远超下单 | train-service 拆读写，加只读副本 |
| 订单量增长导致单库压力大 | order 按 `user_id` 或时间分片 |
| 需要多机房 | 引入单元化，库存按车次分片 |

**关键：演进路径要提前设计，但不要提前实现。** 现在拆 5 个服务，是为了 3 年后可能发生的场景，付出的是今天 100% 的成本。

### 4.3 服务故障时会发生什么（服务容错视角）

这块是 Spring Cloud 学习的核心，也是面试高频。**每个服务的故障表现都必须能说清楚**：

| 挂掉的服务 | 现象 | 系统行为 | 是否有损 |
| --- | --- | --- | --- |
| `user-service` | 登录失败 | 新用户无法登录；**已登录用户凭 JWT 仍可下单**（因为网关只验签不查库） | 部分可用 |
| `train-service` | 查票失败 | 网关返回降级数据（缓存余票）或 503；**下单链路需判断**：若校验车次是强依赖则下单也不可用 | 降级可用 |
| `order-service` | 完全不可下单 | 最严重。秒杀入口不可用 | 不可用 |
| `redis` | **灾难** | 秒杀闸门失效，若不降级则所有请求打到 DB → DB 被打挂 → 全站雪崩 | **必须降级** |
| `mq` | 下单返回失败 | 请求线程发不出消息，无法承诺"排队中" | 不可用（但**不能假装成功**） |
| `mysql` | 订单查不到、库存落不了账 | Redis 仍在扣，产生"幽灵库存" | 需对账修复 |

> **最值得讲的两条**：
> 1. **Redis 挂掉时必须"快速失败"而不是"降级到 DB"**——降级到 DB 等于把 10000 QPS 直接灌给 MySQL，会把可恢复的故障变成不可恢复的雪崩。正确做法是直接返回"系统繁忙，请稍后重试"。
> 2. **MQ 发不出去时，绝不能返回"抢票成功"**。宁可让用户重试，也不能给出无法兑现的承诺。

## 五、数据库设计

### 5.1 设计原则

1. **每张表只属于一个服务**，禁止跨服务直连。
2. **主键用 `BIGINT` 自增**（不是 UUID）——原因见下。
3. **所有表都有 `create_time` / `update_time`**，用 `DATETIME(3)`（毫秒精度，秒杀场景需要）。
4. **状态字段用 `VARCHAR` 而非 `TINYINT`**——见下。
5. **唯一约束是幂等的最后一道防线**，不是可选项。

> **为什么主键用 `BIGINT` 自增而不是 UUID**：InnoDB 的聚簇索引按主键物理排序。UUID 无序 → 每次插入都可能触发页分裂和随机 IO；自增 ID 顺序插入，写入性能高一个数量级。UUID 的唯一优势是"分布式下不冲突"，但本项目的订单号由「时间戳 + 用户ID 分片 + 序列」生成，不需要用主键承担这个职责。
>
> **为什么状态字段用 `VARCHAR` 而不是 `TINYINT`**：这是**教学项目**，直接用 `SELECT * FROM t_order` 就能看懂状态，排查问题成本极低。生产环境会为了索引体积和比较性能用 `TINYINT`——**这个取舍要主动说明，不要假装不知道**。

> **代价要诚实说明**：这需要"写 Redis + 写本地消息表"两步，严格来说两者也不是原子的（Redis 写成功、DB 写失败仍会丢消息）。**彻底的解决办法是让 Redis 成为唯一入口并在失败时回补**——这个缺口在阶段 9 详细处理，见 [§7.4](#74-异常路径矩阵)。

### 5.3 索引失效与慢查询预防

| ❌ 会走全表扫描的写法 | ✅ 正确写法 | 原因 |
| --- | --- | --- |
| `WHERE DATE(create_time) = '2026-09-15'` | `WHERE create_time >= '2026-09-15' AND create_time < '2026-09-16'` | 对索引列做函数运算 → 索引失效 |
| `WHERE order_no LIKE '%123%'` | `WHERE order_no = '123'` 或 `LIKE '123%'` | 前导通配符无法用索引 |
| `WHERE user_id = 1 OR 1=1` | 参数化查询 | — |
| `WHERE status != 'CANCELLED'` | 业务上改为枚举正向值 | `!=` 通常无法有效用索引 |

**验证方式**：所有查询上线前用 `EXPLAIN` 检查 `type` 列，出现 `ALL` 就必须优化。**这是压测之外必做的功课**，也是面试可以讲的实操细节。

## 六、Redis 方案

### 6.1 Key 设计

| Key | 类型 | TTL | 用途 |
| --- | --- | --- | --- |
| `rail:stock:{trainId}:{date}:{seatType}` | String(int) | 到发车日 + 1 天 | **可售余票**（原子扣减对象） |
| `rail:stock:init:{trainId}:{date}` | String | 1 天 | 预热完成标记（防重复预热） |
| `rail:train:{trainId}` | Hash/JSON | 30 min ± 随机 | 车次详情缓存 |
| `rail:train:empty:{trainId}` | String("1") | 5 min | **空值缓存**（防穿透） |
| `rail:seckill:result:{userId}:{trainId}:{date}` | String | 1 天 | 秒杀结果（供客户端轮询，避免查 DB） |

**TTL 加随机值的理由（防雪崩）**：如果 100 个热点车次的缓存都在同一秒过期，那一瞬间所有请求都会穿透到 DB。给 TTL 加 ±10% 的随机抖动，让过期时间分散开。

### 6.2 Lua 脚本：原子扣减（核心）

```lua
-- KEYS[1] = 库存 key
-- KEYS[2] = 用户去重 key (Set)
-- ARGV[1] = userId
-- 返回: >=0 扣减后的余票; -1 库存不足; -2 用户重复
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then return -3 end          -- key 不存在，视为未预热/已售罄
if stock <= 0 then return -1 end            -- 库存不足
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2                               -- 该用户已抢过
end
redis.call('DECR', KEYS[1])                 -- 扣减
redis.call('SADD', KEYS[2], ARGV[1])        -- 记录用户
return stock - 1
```

> **为什么整个逻辑必须写在同一个 Lua 脚本里**：
> Redis 执行 Lua 脚本时是**单线程、不可中断**的。如果把这四步拆成四次客户端调用，"判断库存"和"扣减库存"之间就会被其他请求插入——这正是 [§1.2](#12-核心并发矛盾) 描述的超卖场景。**Lua 把"判断 + 扣减 + 去重"变成一个原子操作，这是不超卖的第一道、也是最关键的保证。**
>
> **为什么库存 key 不存在时返回 -3 而不是当作 0**：这两种情况的处理完全不同——`0` 是正常售罄（返回"已售完"），key 不存在是**系统故障**（未预热或 Redis 被清空），应该告警并拒绝服务。**如果把故障当成售罄，用户会以为票卖完了，而实际上是系统坏了——这是最危险的一类 bug。**
>
> **⚠️ 已知限制（必须诚实说明）**：这个脚本的正确性依赖"**单节点 Redis**"。如果配置了主从，主节点扣减成功后**在同步到从节点之前宕机**，从节点升主后库存会"回滚"到旧值 → **超卖**。Redis 官方文档明确承认异步复制有这个窗口。本项目用单节点规避，**但面试被问到"Redis 宕机怎么办"时必须主动讲这个限制**，而不是说"Redis 不会宕机"。

### 6.3 缓存穿透 / 击穿 / 雪崩

| 问题 | 场景 | 本项目做法 | 是否需要分布式锁 |
| --- | --- | --- | --- |
| **穿透** | 查询不存在的车次，请求全部打到 DB | 空值缓存（`rail:train:empty:*`，TTL 5min） | 不需要 |
| **击穿** | 某热点车次缓存刚好过期，瞬间大量请求重建 | **逻辑过期 + 异步重建**：缓存不设物理 TTL，value 里存逻辑过期时间，发现过期后由一个线程异步重建、其余请求返回旧值 | 不需要（用"只让一个线程重建"的标志位即可） |
| **雪崩** | 大量 key 同时过期 | TTL 加 ±10% 随机抖动 | 不需要 |

> **为什么本项目"不需要"布隆过滤器**：车次数据量小（几千条），空值缓存已经足够，布隆过滤器的引入成本（数据同步、误判处理）大于收益。**面试时要说清楚："我知道布隆过滤器，但这个项目的数据量和穿透特征用空值缓存性价比更高。"** 这比硬加一个用不上的组件更能体现判断力。

### 6.4 分布式锁：这里到底需不需要？

**这是你明确要求论证的问题，我的结论是：主链路不需要，只有两个地方需要。**

| 场景 | 需要锁吗 | 理由 |
| --- | --- | --- |
| 秒杀扣库存 | ❌ **不需要** | Lua 脚本本身原子，加锁是**画蛇添足**，还会引入锁超时、锁误删、看门狗续期等一堆新问题 |
| 用户去重 | ❌ **不需要** | 已在同一个 Lua 脚本内完成 |
| 订单创建 | ❌ 不需要 | DB 唯一索引即可 |
| **库存预热** | ✅ **需要** | 多实例同时启动时，必须保证只有一个实例把 MySQL 库存灌入 Redis，否则会**重复累加**导致超卖 |
| **对账/补偿任务** | ✅ **需要** | 定时任务在多实例下会重复执行 |

**预热用的锁**：
```
SET rail:lock:warmup:{trainId}:{date} <uuid> NX PX 30000
```
- `NX`：不存在才设置（互斥）
- `PX 30000`：30 秒自动过期，**防止持锁实例崩溃后死锁**
- `<uuid>`：**释放锁时必须校验是自己的**，否则可能删掉别人刚拿到的锁

> **为什么释放锁要用 Lua 校验 uuid**：`if GET(key) == uuid then DEL(key)`。如果直接 `DEL`，会出现这种情况：A 拿锁 → A 卡住 30 秒 → 锁自动过期 → B 拿到锁 → A 醒来执行 `DEL` → **删掉了 B 的锁**。这是分布式锁最经典的 bug，也是面试高频考点。

### 7.1 🔴 选型：RocketMQ（阶段 9 决策，附验证门槛）

> **这是全项目最需要谨慎的决定。** 调研结论**推翻了我的直觉**，过程如下。

**直觉认为**：Windows 上 RabbitMQ 是一等公民，Docker 又不可用，应该选 RabbitMQ。

**调研结论（🟡 待该机器实证）指向相反**：

| 维度 | RocketMQ 5.x | RabbitMQ 4.x |
| --- | --- | --- |
| 部署方式 | **纯 Java**，官方 zip 含 `.cmd` 脚本，解压 + 设 `JAVA_HOME`/`ROCKETMQ_HOME` 即可 | 需**先安装 Erlang/OTP**（官方包不捆绑），再装 RabbitMQ |
| **管理员权限** | **不需要** | Erlang 必须用管理员账号安装，全机只能存在一个版本，路径不能有空格/中文 |
| 延时消息（订单超时关单） | ✅ **原生支持**，毫秒级任意时刻 | ❌ 无原生支持，只能 TTL + 死信队列硬拼 |
| 事务消息（Redis 扣减成功但 MQ 发送失败） | ✅ **原生支持**（半消息 + 回查） | ❌ 无对应物，需手写本地消息表 |
| 已知坑 | 官方 `runserver.cmd` 在 JDK 17 下会注入已移除的 `-XX:+UseConcMarkSweepGC`，需手工改脚本 | 延时插件 `rabbitmq_delayed_message_exchange` 已停止维护，其依赖的 Mnesia 在新版本被移除 |

**🔵 我的结论：推荐 RocketMQ**，决定性因素是**「零安装、不需要管理员权限」**——在一台装了 Asiainfo Security 的公司办公机上，这个优势压倒其他一切。

**但推荐附带了硬性前置条件（这是关键，不要跳过）**：

> ⏱️ **时间盒验证**：在正式把 RocketMQ 写进架构之前，**必须先花最多 45 分钟做一次启动验证**：
> 1. 设好 `JAVA_HOME` 和 `ROCKETMQ_HOME`
> 2. 修补 `runserver.cmd`（JDK 17 GC 参数问题）
> 3. `set JAVA_OPT_EXT=-Xms512m -Xmx512m` 控制内存
> 4. 启动 NameServer + Broker，确认端口 9876 / 10911 监听成功
>
> **起不来就立刻切换 RabbitMQ**，不要在这上面耗超过 45 分钟。
>
> 🔴 **以上全部是调研代理给出的结论，我没有在你这台机器上验证过。** 在你亲自跑通之前，架构文档里 RocketMQ 后面永远跟着"待验证"三个字。

**反转条件（什么情况下改选 RabbitMQ）**：
- RocketMQ 45 分钟内起不来
- 或者你所在环境安装 Erlang 不需要管理员权限（那 RabbitMQ 的门槛就消失了）

**为什么不用 Kafka**：它的优势是分区并行和海量吞吐，本项目消息量小、不需要回溯重放，而它**没有原生延时消息**——"订单超时关单"要自研时间轮。它的长处我一个用不上，短处我一个躲不掉。**场景不匹配，不是它不好。**

### 7.2 消息设计

| 消息 | 生产者 | 消费者 | 幂等键 |
| --- | --- | --- | --- |
| `ORDER_CREATE` | order-service（秒杀请求线程） | order-service（消费者） | `order_no` |
| `STOCK_DEDUCT` | order-service | train-service | `order_no` |
| `ORDER_TIMEOUT`（延时消息） | order-service（下单时发，延时 30 min） | order-service | `order_no` |
| `STOCK_RELEASE` | order-service（关单时） | train-service | `order_no` + `RELEASE` |

### 7.3 秒杀完整链路（主流程）

```
1. Client 提交抢票请求
2. Gateway  校验 JWT → 解析出 userId → 限流（令牌桶）
3. order-service:
   3.1 本地缓存校验车次有效性（命中则跳过 Feign）
   3.2 执行 Redis Lua 原子扣减
        ├─ 返回 -1 库存不足 → 直接响应"已售完"（不落库、不发消息）
        ├─ 返回 -2 用户重复 → 响应"请勿重复提交"
        ├─ 返回 -3 未预热  → 响应 503 + 告警
        └─ 返回 >= 0 扣减成功 ↓
   3.3 生成 order_no，写本地消息表 PENDING
   3.4 发送 MQ 消息（ORDER_CREATE + ORDER_TIMEOUT 延时消息）
   3.5 立即返回"抢票排队中，请稍后查询结果"
4. 消费者（order-service）:
   4.1 幂等检查：order_no 是否已处理（本地消息表 / 唯一索引）
   4.2 写 t_order（status=CREATED）+ t_order_item
   4.3 写秒杀结果到 Redis（供客户端轮询）
   4.4 ack
5. 消费者（train-service）:
   5.1 幂等检查
   5.2 UPDATE t_seat_inventory SET sold_qty = sold_qty + 1
   5.3 ack
6. 30 分钟后未支付 → ORDER_TIMEOUT 消息 → 关单 + 发 STOCK_RELEASE → train-service 回补 MySQL 库存
```

**为什么返回"排队中"而不是"成功"**：请求线程没有写 DB，**它没有资格承诺订单已创建**。返回"排队中"是诚实的；返回"成功"而订单后来创建失败，是欺骗用户。这不是技术细节，是**正确性边界**。

### 7.4 异常路径矩阵

**这张表是本项目的核心资产。** 面试官问"XX 情况怎么办"，答案就在这里。

| # | 异常场景 | 处理方式 | 残留风险 |
| --- | --- | --- | --- |
| E1 | Redis 扣减成功，MQ 发送失败 | 本地消息表 `PENDING` + 补偿任务扫描重发 | 写 Redis 成功但写本地消息表也失败（极小概率）→ 靠对账发现 |
| E2 | MQ 发送成功，消费者宕机 | MQ 未收到 ack → 重投 → 消费端幂等（唯一索引） | 无（至少一次 + 幂等 = 效果等价于恰好一次） |
| E3 | 消费者成功，DB 写失败 | 不 ack，消息重投；重投后仍失败 → 进入死信队列 | 死信需人工/定时任务介入 |
| E4 | MQ 重复投递（同一消息投 3 次） | 唯一索引 `uk_user_train_date_seat` 拦截，捕获重复键异常后**当作成功直接 ack** | 无 |
| E5 | 用户超时未支付 | 延时消息触发关单 → 发 `STOCK_RELEASE` | 见 E6 |
| E6 | **支付与超时关单的竞态** | 关单前用 `UPDATE t_order SET status='CANCELLED' WHERE order_no=? AND status='CREATED'`。**支付同理**：`WHERE status='CREATED'`。**靠状态机 CAS 保证只有一个成功**，失败方回滚自己的操作 | 无（这是本项目竞态处理的核心手法） |
| E7 | 消息积压 | 增加消费者并行度；先定位是消费慢还是生产突增 | 积压期间用户看到"排队中"时间变长 |
| E8 | Redis 整体宕机 | **快速失败，不降级到 DB**（返回 503） | 秒杀完全不可用，但 DB 不会被打挂 |
| E9 | 服务重启后 Redis 库存丢失 | 启动时扫描未结束的车次重新预热；`rail:stock:init:*` 标记防重复 | 预热窗口内该车次不可抢 |

> **E6 值得单独强调**：这是"最后一张票被两个人抢到"的**支付版本**。用 `WHERE status='CREATED'` 做条件更新，利用**单条 SQL 的原子性**做状态机 CAS——**不需要分布式锁**。数据库的条件更新本身就是原子的，这是很多人忽略的简单答案。

### 7.5 幂等的三层设计（面试高频）

| 层级 | 手段 | 挡住什么 |
| --- | --- | --- |
| 第一层 | Redis Lua 内 `SISMEMBER` 去重 | 99% 的重复点击（性能层） |
| 第二层 | 消费端查本地消息表 `message_id` | MQ 重复投递 |
| 第三层 | DB 唯一索引 `uk_user_train_date_seat` | **所有漏网的重复（正确性底线）** |

> **核心认知：幂等是消费端的责任，不是 MQ 的责任。** RocketMQ 和 RabbitMQ 都只保证"至少一次"投递。指望 MQ 不重复投递，等于把正确性交给一个它从未承诺过的保证。

## 八、Spring Cloud 组件清单

> 每个组件必须能回答：**为什么需要它？没有它会发生什么？**

| 组件 | 为什么需要 | 没有它会发生什么 |
| --- | --- | --- |
| **Spring Cloud Gateway** | 统一入口、集中鉴权、集中限流、隐藏内部拓扑 | ① 每个服务都要写一遍 JWT 校验，某天密钥升级漏改一个服务 → **部分接口鉴权静默失效**（安全漏洞，没人会发现）② 没有统一限流入口，恶意流量直达业务服务 ③ 前端要知道所有服务的地址，服务扩容/改端口要改前端 |
| **Nacos 注册中心** | 服务实例动态上下线，调用方自动感知 | 硬编码 IP → 服务扩容要改配置重启；实例宕机后调用方仍往死实例发请求，**表现为大量超时** |
| **Nacos 配置中心** | 配置集中管理、动态刷新 | 5 份 `application.yml` 各存一份 Redis 地址，改配置时漏改一份 → **"随机出现的数据不一致"**，极难排查 |
| **OpenFeign** | 声明式 HTTP 调用，像调本地方法一样调远程 | 手写 `RestTemplate` + 拼 URL + 手动反序列化，代码量大且易错 |
| **Spring Cloud LoadBalancer** | 客户端负载均衡，把请求分散到多实例 | 要么只用单实例（无扩展性），要么自己实现轮询/随机策略 |
| **Sentinel**（限流熔断降级） | 保护系统不被突发流量打垮；下游故障时快速失败 | 下游变慢 → 调用方线程池被占满 → **级联雪崩**，一个服务的慢变成全站不可用 |

### 必须能回答的"五连问"（每个组件都要过一遍）

以 Gateway 为例，这是面试的标准问法：

1. **为什么需要它？** —— 见上表。
2. **没有它会发生什么？** —— 见上表（要用具体故障场景描述，不是"不方便"）。
3. **它怎么工作的？** —— Gateway 基于 Spring WebFlux + Netty，请求进来后经过一串 `GatewayFilter` 链（鉴权、限流、改写），再由路由断言匹配到目标服务，通过 `LoadBalancer` 找到实例转发。**它是非阻塞的**，所以少量线程就能扛住大量并发连接。
4. **一个服务挂掉之后会发生什么？** —— Nacos 有心跳机制，实例下线后调用方拉取到新列表（有**秒级延迟**，这个窗口内的请求会失败）。所以必须配**重试 + 熔断**兜住这个窗口。
5. **什么时候需要降级？** —— 查票可以降级（返回缓存余票 + 提示"可能有延迟"）；**库存扣减绝对不能降级**（返回假的扣减成功 = 超卖）。**能不能降级，取决于"假的响应会不会造成资损"。**

### ⭐ 这次验证解决了什么（阶段 0 最大的未知数）

**我最初的判断是错的。** 我在阶段 0 开始时担心"Spring Cloud Alibaba 不支持 Spring Boot 3.5"，并据此准备了两条退路（降级 Boot 或弃用 SCA 组件）。

**实测结论：SCA 2025.0.0.0 与 Boot 3.5.16 完全兼容，依赖解析零冲突。** 退路不需要了。

**兼容性是如何确定的**（这个推理链值得记住，面试也可能被问到）：

| BOM | 其 parent `spring-cloud-dependencies-parent` 版本 | 说明 |
| --- | --- | --- |
| Spring Cloud 2025.0.3 | **4.3.4** | 2025.0.x 线 |
| Spring Cloud Alibaba 2025.0.0.0 | **4.3.0** | **同在 4.3.x 线 → 与 Spring Cloud 2025.0.x 对齐** ✅ |
| Spring Cloud 2025.1.3 | 5.0.3 | 2025.1.x 线 |
| Spring Cloud Alibaba 2025.1.0.0 | 5.0.0 | 同在 5.0.x 线 → 与 Spring Cloud 2025.1.x 对齐 |

> **判断 SCA 与 Spring Cloud 是否兼容的方法**：**看它们的 `spring-cloud-dependencies-parent` 父版本是否在同一条 minor 线上**。
> 这是比"版本号看起来像不像"可靠得多的判据——因为 SCA 的版本号（`2025.0.0.0`）和 Spring Cloud 的版本号（`2025.0.3`）**命名规则不同，不能直接对比**。

## 十、项目目录结构与演进方式

### 10.1 🔴 演进方式：先单体，再拆分（需你确认）

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 先单体单模块，阶段 8 再拆** | 就用手上这个骨架写业务 | **亲身体会拆分的痛**（包结构重写、配置拆分、依赖梳理）；符合真实企业演进路径 | 拆分那一次改动量大；需要你愿意经历一次"重构震荡" |
| **B. 一开始就建多模块 Maven** | 第一天就搭好 4 个模块 | 后期省事 | **你永远不知道"为什么要拆"**——因为没经历过不拆的痛 |

> **🔵 我推荐 A**。理由是**这个项目的目标是理解，不是交付**。亲手把一个单体拆成微服务，你对"服务边界怎么划""哪些依赖会变成远程调用""跨服务事务怎么办"的理解，会远比一开始就搭好骨架深刻。而且这个过程本身就是**极好的面试素材**（"我第一版写成了单体，发现 X 问题，于是拆成微服务，拆的过程中遇到 Y"）。
>
> **代价要说清楚**：拆分那一步会有较大改动量（大约 1~2 天），且需要一个"拆分后行为不变"的回归验证方式。

### 如何证明"不会超卖"（三种手段，缺一不可）

**手段 1：并发单元测试**

```java
// 200 个线程同时抢 100 张票，断言恰好卖出 100 张
int threads = 200;
CountDownLatch start = new CountDownLatch(1);
CountDownLatch done = new CountDownLatch(threads);
// 每个线程 await(start) 后同时发起抢票
start.countDown();
done.await();
// 断言：
// ① 成功数 == 100
// ② SELECT COUNT(*) FROM t_order WHERE status != 'CANCELLED' == 100
// ③ SELECT * FROM t_seat_inventory WHERE sold_qty > total_qty → 0 行
```

**手段 2：压测后数据校验（SQL）**

```sql
-- ① 超卖检查：必须返回 0 行
SELECT * FROM rail_inventory.t_seat_inventory WHERE sold_qty > total_qty;

-- ② 超卖检查（含锁定库存）：必须返回 0 行
SELECT * FROM rail_inventory.t_seat_inventory WHERE sold_qty + lock_qty > total_qty;

-- ③ 重复订单检查：必须返回 0 行
SELECT user_id, train_id, travel_date, seat_type, COUNT(*) c
FROM rail_order.t_order
WHERE status != 'CANCELLED'
GROUP BY user_id, train_id, travel_date, seat_type
HAVING c > 1;

-- ④ 订单数与库存一致性：两列必须相等
SELECT
  (SELECT COUNT(*) FROM rail_order.t_order WHERE status != 'CANCELLED') AS order_cnt,
  (SELECT SUM(sold_qty) FROM rail_inventory.t_seat_inventory) AS sold_cnt;

-- ⑤ Redis 与 MySQL 对账：Redis 余票 + MySQL 已售 必须等于总票额
--    Redis: GET rail:stock:{trainId}:{date}:{seatType}
--    MySQL: SELECT total_qty - sold_qty FROM t_seat_inventory WHERE ...
```

**手段 3：对账定时任务**

每 5 分钟跑一次上述 SQL，发现不一致就告警并记录。**这也是 Redis 与 MySQL 最终一致性的兜底。**

| 4 | 项目演进方式 | **先单体，阶段 8 再拆** | 开发者 |
| 5 | 认证放哪层 | **网关统一 JWT 校验 + 透传 userId**（采用推荐值） | 默认采纳 |
| 6 | 限流熔断组件 | **Sentinel**（采用推荐值，若 SCA 版本验证失败则转 Resilience4j） | 默认采纳 |

### 决策 1：Redis 使用第三方移植版 —— 🟡 待验证，且带风险

**决定**：使用 `zkteco-home/redis-windows`。

> **⚠️ 必须执行的验证动作（未完成前此决策不生效）**：
> 1. **只从该项目的 GitHub Releases 页面下载**，禁止使用任何网盘、CSDN、博客附件转载的压缩包。
> 2. 下载后核对 release 页公布的哈希值（若有）与文件实际哈希。
> 3. 记录下载 URL、文件哈希、下载日期，写入 `docs/troubleshooting/` 备查。
>
> **这是在一台装有 Asiainfo Security 的公司电脑上运行第三方二进制文件，合规与供应链风险由使用者承担。** 记录哈希的意义在于：万一出现安全事件，你有溯源依据。

**已知代价（如实记录）**：
- 这是社区移植版，**不是 Redis 官方发布**。出现行为差异时无法向官方求助。
- 版本号（8.x）来自项目自述，**不代表与官方 Redis 8.x 完全等价**。本项目用到的 `GET/SET/DECR/SADD/SISMEMBER/EXPIRE` 和 Lua 脚本都是最基础的能力，出差异的概率低，但**不能假设完全一致**。

**如果出现问题的回退路径**：切换 Memurai Developer 或确认能否装 WSL2。

### 决策 2：MQ 推迟到阶段 9

**决定**：阶段 1~8 **完全不引入 MQ**。

**这是明智的**——因为 MQ 的选型（RocketMQ vs RabbitMQ）取决于"哪个能在你这台机器上跑起来"，而这个问题**在阶段 1 排查环境时才会有答案**。现在选，是凭调研猜。

**对设计的影响（重要）**：

| 影响项 | 原设计（有 MQ） | 现设计（阶段 1~8） |
| --- | --- | --- |
| 下单方式 | Redis 预扣 → MQ → 异步创建订单 | Redis 预扣 → **同步写订单**（方案 B） |
| 秒杀响应 | "排队中"，客户端轮询 | 直接返回订单结果 |
| 异常路径 | E1~E9 九条 | **只剩 E4（重复提交）、E8（Redis 宕机）、E9（预热丢失）** |
| §7 全部内容 | 阶段 9 实现 | **阶段 9 才生效** |

**关键认知**：阶段 7 的"方案 B"（Redis 预扣 + 同步写库）**本身就是可运行的完整方案**，不是半成品。它能不超卖、能限流、能扛住远超方案 A 的并发。MQ 带来的是"更快响应 + 更高吞吐上限"，**不是"能不能用"**。

> **这反而让教学路径更好**：你会在阶段 7 亲手测出方案 B 的瓶颈（DB 同步写入），然后**带着真实的瓶颈数据**去阶段 9 引入 MQ。这比一上来就上 MQ 深刻得多。

### 决策 3：拆 5 个服务

**决定**：`rail-gateway` / `rail-user-service` / `rail-train-service` / `rail-inventory-service` / `rail-order-service`。

**我保留过不同意见**（建议 4 个），理由是单人运维成本与"库存正确性不依赖独立部署"。**你的决定已生效，但代价必须记录在案**，见 [ADR-003](./decisions/ADR-003-service-granularity.md) 的"代价与已知缺陷"一节。

**这次决策引入的硬性约束**——秒杀热路径上：

```
✅ 允许：order-service ──(Redis 客户端直连)──▶ Redis
❌ 禁止：order-service ──(OpenFeign 同步)──▶ inventory-service ──▶ Redis
```

**为什么禁止**：如果扣减走 inventory-service 的 HTTP 接口，秒杀链路就多了一跳网络 RPC——你会为此付出连接池、超时、序列化、线程阻塞的全部代价，**把异步化省下来的时间原样还回去**。Redis 是共享中间件，order-service 直连它是正当的。

**那 inventory-service 存在的意义是什么**（这个问题面试官一定会问）：
1. `t_seat_inventory` 表的**唯一 owner**（数据边界清晰）
2. **预热**：把 MySQL 库存灌入 Redis（多实例需分布式锁，见 §6.4）
3. **对账**：定时比对 Redis 与 MySQL，发现不一致告警
4. **回补落库**：阶段 9 消费 MQ 消息更新库存
5. 余票查询的**权威来源**（带缓存）

> **如果不能清楚回答"这个服务到底干什么"，那它就真的不该拆。** 上面五条必须站得住，否则阶段 8 拆分时应当合并回去。

### 决策 4：先单体再拆

**决定**：阶段 3~7 使用现有单模块骨架开发，阶段 8 拆分为 5 个模块。

**阶段 8 的已知代价**：约 1~2 天重构量（包结构、配置拆分、依赖梳理），且需要一个"拆分后行为不变"的回归验证方式（复用阶段 6/7 的压测脚本对比结果即可）。

### 决策 5：认证放网关

**决定**：网关统一校验 JWT，解析出 `userId` 后通过请求头（如 `X-User-Id`）透传给下游服务。

**必须在阶段 8 一并处理的安全问题**：`X-User-Id` 是**可伪造的**——如果攻击者能直连 `rail-order-service:8084` 并自己塞一个 `X-User-Id`，鉴权就被绕过了。生产做法：① 服务不对外暴露端口，只允许网关访问（内网隔离）；② 网关在转发时**先剥离客户端传入的 `X-User-Id`**，再写入自己解析的值。

> **这个坑正好是"没有网关会发生什么"的反面案例**——网关解决了鉴权分散问题，但**引入了信任传递问题**。面试时能主动讲出后者，说明你真正理解了，而不是背了"网关能做鉴权"。

### 决策 6：使用 Sentinel（转换条件已失效）

**决定**：使用 **Sentinel 1.8.9**（由 SCA 2025.0.0.0 固定引入）。

**原本的转换条件已失效**：原计划是"若 SCA 与 Boot 3.5.x 不兼容则转 Resilience4j"。阶段 0 已用真实的 `mvn dependency:tree` 验证 SCA 2025.0.0.0 与 Boot 3.5.16 解析零冲突（见 §8），**因此无需转换**。

**已验证可用的 Sentinel 组件**（来自依赖树）：
- `sentinel-core`、`sentinel-annotation-aspectj`（`@SentinelResource` 注解支持）
- `sentinel-spring-webflux-adapter`（**Gateway 接入用**）
- `sentinel-spring-webmvc-v6x-adapter`（普通服务接入用）
- `spring-cloud-circuitbreaker-sentinel`（熔断降级）
- `sentinel-transport-simple-http`（与 Dashboard 通信）
