# 文档索引与写作约定

本目录存放 Rail-Ticket-Seckill 的全部文档。项目根说明见 [../README.md](../README.md)。

这份文件解决两个问题：**docs 下每个目录装什么**，以及**一条新内容到底该写进哪个目录**。

## 二、新内容该写进哪个目录

写作时按下面的顺序自问，第一个答「是」的就是归属目录：

| 你在写的内容 | 归属 | 理由 |
| --- | --- | --- |
| 我在几个方案里选了一个，想记录为什么 | `decisions/` | 这是决策，不是知识 |
| 怎么把项目在本地跑起来 / 装什么软件 | `environment-setup.md` | 新人第一步要看的东西 |
| 系统由哪些服务组成、请求怎么流动 | `architecture/` | 结构与流向 |
| 某张表有哪些字段、某个索引为什么建 | `database/` | 数据层细节 |
| 某个接口怎么调、返回什么、错误码是什么 | `api/` | 对外契约 |
| 昨天线上/本地出了一个故障，我查了半天 | `troubleshooting/` | 有真实日志的复盘 |
| 我压测了，QPS 是多少、瓶颈在哪 | `performance/` | 有真实数据的实测 |
| 面试官问「你这个项目难点是什么」，我该怎么答 | `interview/` | 对外表达 |
| 一段代码的注释 / 一个类的职责 | 不放 docs，写进代码 | 就近原则 |

**判断口诀**：

- 带「**决定**」的 → `decisions/`
- 带「**结构**」的 → `architecture/`
- 带「**字段/索引**」的 → `database/`
- 带「**调用方式**」的 → `api/`
- 带「**日志/时间点**」的 → `troubleshooting/`
- 带「**数字/压测环境**」的 → `performance/`
- 带「**怎么装**」的 → `environment-setup.md`

## 三、通用写作规则

这几条对所有目录都适用，写之前请先读一遍。

**1. 每个技术决策写清五件事**

不管写在哪个目录，只要内容涉及「选了某个方案」，就必须回答：

| 要素 | 说明 |
| --- | --- |
| 做了什么 | 一句话说清最终采用的方案 |
| 为什么这么做 | 结合本项目的具体场景，不是通用优点 |
| 不这么做会出什么问题 | 具体到「会超卖」「连接池会满」这种程度，不写「会有问题」 |
| 对比了哪些替代方案 | 用表格列，至少两个备选 |
| 为什么没选它们 | 说清淘汰理由，不能只写「性能差」 |

**2. 禁止编造数字**

任何性能数字、压测结果、版本号、API 细节，没实测过就写「**待压测**」或「**待验证**」，并写清验证方法。这条没有例外。

不能出现的写法：

- 「QPS 达到 10000+」——除非附了压测报告链接和压测环境说明
- 「响应时间 5ms」——除非是从真实日志里摘出来的
- 「Redis 7.2.4」——除非从部署脚本或 `redis-server -v` 输出里抄的
- 「据说这样可以提升 3 倍」——「据说」不是依据

**3. 用工程语言，不用营销词**

| 不写 | 改写成 |
| --- | --- |
| 高性能 | 具体的机制，例如「扣减在 Redis 单命令内完成，不产生数据库行锁竞争」 |
| 企业级 | 删掉，说明它到底解决了什么 |
| 完美解决 | 「在当前并发假设下解决了；假设不成立时的表现待压测」 |
| 业界领先 | 删掉 |
| 极大地提升了 | 换成实测数字，或写「待压测」 |

**4. 代码片段只在必要处出现**

只有「不贴代码就讲不清」的地方才贴，且要短（一般不超过 15 行）。允许的场景：Lua 脚本的核心逻辑、唯一索引 DDL、状态机流转定义、关键配置项。不允许的场景：完整类实现、大段 CRUD、为了显得专业而贴的代码。

**5. 文件末尾用相对路径链接相关文档**

例如在 `decisions/0001-xxx.md` 末尾：

```markdown
相关文档：
- [系统架构](../architecture/overview.md)
- [库存表设计](../database/tables.md)
```

**6. 文档要能独立读懂**

每篇文档开头写清楚：这篇解决什么问题、读者是谁、前提假设是什么。不要假设读者读过你的另一篇文档。

## 四、`decisions/` 的 ADR 格式

**所有决策类内容必须用 ADR（Architecture Decision Record）格式**，不接受自由发挥的散文。原因是 ADR 有固定结构，能逼着作者把「为什么不选另一个」写出来，而这恰恰是最容易被省略、也最有价值的部分。

### 4.1 文件命名

```
decisions/NNNN-短标题.md
```

- `NNNN` 为四位递增编号，从 `0001` 开始，**一经分配不再修改**
- 标题用简体中文短横线连接，例如 `0001-库存扣减使用-Redis-Lua.md`
- 决策被推翻时**不删除原文件**，而是新增一个 ADR 并在其中声明「取代 ADR-0001」，同时在旧文件顶部标注「已被 ADR-00XX 取代」

### 4.2 模板

```markdown
# ADR-0001：库存扣减放在 Redis 用 Lua 脚本完成

- 状态：已采纳 / 已废弃 / 被 ADR-00XX 取代 / 讨论中
- 日期：YYYY-MM-DD
- 决策者：（开发者本人）
- 相关文档：链接

## 背景

描述促使这个决策的场景。用本项目的事实，不用行业泛论。
例：下单峰值远高于日常；同一车次库存是热点行；Redis 已用于余票缓存。

## 决策

一句话说清最终采用什么。必要时附极短代码片段（如 Lua 核心几行）。

## 理由

为什么在当前场景下这个方案成立。要具体到机制层面。

## 不考虑它会怎样

如果不做这个决策，会出现什么具体后果。
例：GET + DECR 两条命令之间存在竞态，库存为 1 时两个请求都会通过判断，产生超卖。

## 备选方案对比

| 方案 | 原子性 | 性能 | 复杂度 | 结论 |
| --- | --- | --- | --- | --- |
| ... | ... | ... | ... | 选用 / 未选 |

## 未选方案的原因

逐个说明为什么淘汰，不能只写「性能差」。

## 后果与代价

采用这个方案后引入了什么新问题，如何应对。
例：Redis 与 MySQL 之间变成最终一致，需要幂等消费与对账兜底。

## 验证方式

怎么证明这个决策是对的？写清验证手段和判定标准。
未实测的部分明确标注「待压测」。
```

### 4.3 尚未定稿的决策怎么处理

如果某个决策还在讨论中，**照常建 ADR 文件**，状态写「讨论中」，在「备选方案对比」里把各方案写全，末尾列出「待确认的问题」。不要因为没定下来就不写——**讨论过程本身就是这个项目最有价值的部分**。

当前处于「讨论中 / 待定」的决策至少有：

| 待决策项 | 说明 |
| --- | --- |
| MQ 选型 | RocketMQ / RabbitMQ / Kafka 三选一，判断维度：是否用事务消息、延迟消息、本地启动成本 |
| ORM 选型 | 库存扣减需要写裸 SQL，这一点会影响选择 |
| Web 层选型 | Spring MVC 还是 WebFlux |
| 是否引入网关 | 以及网关与 Nginx 的职责如何划分 |
| 单模块还是多模块 | 以及拆分时机 |

## 五、`troubleshooting/` 的硬性要求

**这个目录下的每一篇文档，必须包含真实日志和真实数据。** 没有日志支撑的「故障复盘」不允许写进来，因为它会污染整个项目的可信度——面试时被追问「日志里具体报的什么错」而答不上来，比没有这篇文档更糟。

### 5.1 准入条件

写之前自查，以下每一项都必须为「是」：

- [ ] 这个故障**真实发生过**，不是我设想的
- [ ] 有**原始日志**（异常栈、中间件日志、慢查询日志），且已脱敏后贴入
- [ ] 有**可复现的步骤或触发条件**（并发数、数据量、配置）
- [ ] 有**定位过程**，包括走过的弯路和排除掉的错误假设
- [ ] 有**量化证据**（错误率、耗时、库存差额等），不是「感觉变慢了」
- [ ] 有**修复验证**，说明修复后的观测结果

任何一项为「否」，这篇内容要么不写，要么只能写进 `architecture/` 的「已知风险」小节（且明确标注「尚未发生，仅为推演」）。

### 5.2 模板

```markdown
# 故障：并发下单出现库存为负

- 发生时间：YYYY-MM-DD HH:MM
- 环境：本地 Docker / 测试环境 / 其他
- 影响范围：（具体到接口和数据）
- 严重程度： blocker / 严重 / 一般

## 现象

观察到的客观事实。只写看到的，不写猜测。
例：库存字段出现 -2；订单表比库存流水多 3 条记录。

## 原始日志

（贴脱敏后的真实日志，保留时间戳和线程名）

## 复现条件

- 数据准备：
- 并发工具与参数：
- 复现概率：

## 定位过程

按时间顺序写，包括试错。写出「我一开始以为是什么，后来发现不是」，
这部分比结论更有价值。

## 根因

最终确认的原因，要能解释全部现象。

## 修复

改了什么（附关键 diff 或配置项）。如果修复方案本身是一个决策，
另建 ADR 并在 decisions/ 中记录。

## 验证

修复后如何确认问题消失，附观测数据。

## 经验

下次如何更早发现。是否需要加监控 / 加测试用例。
```

### 5.3 命名

```
troubleshooting/YYYY-MM-DD-简短现象.md
```

例：`troubleshooting/2026-10-03-并发下单库存为负.md`

## 六、`performance/` 的硬性要求

压测报告必须写清**测试环境**，否则数字没有意义。每篇报告至少包含：

| 项目 | 说明 |
| --- | --- |
| 机器配置 | CPU 核数、内存、磁盘类型；本地还是容器 |
| 部署形态 | 单机 / 多实例；中间件是否同机部署 |
| 数据规模 | 车次数量、库存量、用户量 |
| 压测工具与版本 | JMeter / wrk / k6 及版本 |
| 压测参数 | 并发数、持续时间、请求分布（读写比例） |
| 观测指标 | QPS、P95/P99 延迟、错误率、CPU/内存、数据库连接数、队列堆积 |
| 瓶颈定位 | 结论基于哪个指标，不要凭感觉 |
| 结论与局限 | 这组数据能说明什么、不能说明什么 |

**未压测的部分就写「待压测」**，并在文档里列出待测清单。不允许把「理论上支持 XX 并发」写成结论。

命名建议：`performance/YYYY-MM-DD-场景-简述.md`。

`architecture/design-spec.json` 已创建，但**内容为 `null`**，属于占位文件。

在补全它之前，`architecture/` 目录下的架构描述以 markdown 文档为准。补全后的 `design-spec.json` 应描述：服务清单、每个服务的职责边界、对外接口概要、依赖的中间件、部署形态。它应当与 markdown 文档内容一致——**如果两者冲突，以 markdown 为准并修正 JSON**，因为 markdown 更适合解释取舍。

## 八、文档维护约定

1. **文档与代码同一次提交**。改了行为就改文档，不攒着「以后再补」。
2. **ADR 只增不改**。决策变了就写新 ADR 标废弃，保留历史，这样能看出思路的演进。
3. **定期清理「待编写」**。每完成一个开发阶段，回头把该阶段产生的文档补齐，而不是等到最后集中写。
4. **不确定就标「待验证」**，并写清验证方法。含糊的确定性表述是本项目最不能接受的东西。
