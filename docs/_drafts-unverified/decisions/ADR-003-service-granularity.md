# ADR-003：服务拆分粒度

- 状态：已接受（Accepted）
- 日期：2026-09-15
- 决策范围：业务服务如何划分、服务边界判据、数据所有权归属
- 相关文档：ADR-001（总体架构与技术选型）、ADR-002（数据一致性与并发控制）、[ADR-004（Spring Cloud 组件栈）](./ADR-004-spring-cloud-stack.md)
- 设计规格：[design-spec.json](../architecture/design-spec.json)

---

## 1. 背景

本项目是一个 12306 风格的抢票（秒杀）系统。核心链路固定为：

```
查票 → 提交订单 → 扣减库存 → 支付 → 出票
```

这条链路的技术难点集中在三点：

1. **瞬时脉冲流量**：开抢时刻的请求量在极短时间内远高于日常，且流量会随着"抢不到"而反复重试放大。
2. **库存不能超卖**：余票扣减必须是原子的、有单一权威裁决点的，一旦出现两个扣减入口，超卖几乎不可避免。
3. **订单不能重复**：同一个请求重试、用户连点、网络超时重发，都可能产生重复订单。

同步约束（这些约束直接决定了本 ADR 的答案）：

| 约束 | 具体内容 | 对拆分的影响 |
| --- | --- | --- |
| 团队规模 | 单人 / 小团队开发，无独立团队边界 | 拆分不能以"团队自治"为理由 |
| 部署环境 | 本地或单机容器，资源有限 | 服务数量越多，本地启动成本越高（内存占用待实测） |
| 教学目标 | 让开发者真正理解分布式拆分与 Spring Cloud 组件 | 必须保留足够的分布式复杂度，不能退化成纯单体练习 |
| 交付节奏 | 教学项目，允许分阶段实现 | 可以接受"先拆、后合并"的演进路径 |

**计数约定**：本 ADR 中"服务"指独立部署的 Spring Boot 进程，**网关计入服务数量**。这是为了消除"4 服务还是 5 服务"的口径歧义。

---

## 2. 问题

我们要回答三个问题：

1. 整个系统应该拆成几个部署单元？
2. 拆分的边界画在哪里，依据是什么？
3. **具体争议**：库存服务（stock-service）该不该从车次服务里独立出来？

---

## 3. 备选方案

### 方案 A：单体（模块化单体）

一个 Spring Boot 进程，内部用 Maven 模块 / 包结构划分界限：

```
rail-ticket-app
├── module-user
├── module-ticket
├── module-stock
└── module-order
```

模块之间通过接口调用（Spring Bean 注入），共用一个数据库连接池，事务是本地事务。

**优点**

- 本地开发成本最低：一个进程、一个 JVM、一次启动。
- 事务简单：扣库存 + 建订单在同一个本地事务里，天然强一致，不会超卖、不会出现"扣了库存但订单没落库"。
- 调试简单：一次调用就是一次方法调用，没有网络、没有序列化、没有超时。
- 前期开发速度最快。

**缺点（对本项目是致命的）**

- **扩容粒度是整体**。抢票时压力集中在库存扣减，但单体只能整体加机器——查票、用户、订单这些低负载模块被一起复制，资源利用率低。
- **故障不隔离**。查票模块的一条慢 SQL 会把整个 Tomcat 线程池占满，连带库存扣减一起不可用。也就是说"查票"这个非核心功能可以把"下单"这个核心功能拖死。
- **无法体现教学目标**。本项目要学的就是服务注册发现、配置中心、声明式调用、熔断限流。单体里这些组件没有存在意义，写了也是摆设。
- **数据库连接池是共享的**。查票的慢查询与库存扣减抢同一个连接池，高并发下库存扣减拿不到连接。

### 方案 B：4 服务

```
gateway → user-service
        → ticket-service   （车次基础数据 + 余票查询 + 库存扣减）
        → order-service    （订单状态机 + 支付流水）
```

即：取消独立的库存服务，库存扣减逻辑并入 ticket-service。

**优点**

- 少一个部署单元，本地启动压力小。
- 扣库存和改余票在同一个服务内，余票查询与扣减之间的数据一致性更容易保证（同一份 Redis / 同一个库）。
- 少一跳网络调用，下单链路少一个故障点。

**缺点**

- 查票（读密集、可缓存、响应体大）与扣库存（写密集、RT 极短、热点行）挤在同一个进程里，**线程池、连接池、JVM 堆被两类完全不同的负载争夺**。
- 库存无法独立扩容：抢票时想只给库存加机器做不到。
- 库存无法独立限流：对 ticket-service 限流会连查票一起限，而查票本来是可以靠缓存扛住的。
- 库存扣减的权威点与车次数据的权威点混在一起，后续若要接第三个写入口（例如后台补票、退票回补）容易绕过边界。

**变体 B'**：另一个可能的 4 服务画法是"把 user-service 并进 gateway，由网关做认证"。

这个变体被明确否决：网关是基础设施组件，跑在 WebFlux 上，无状态、不做业务、不连数据库。把用户、乘车人、登录态塞进网关会让它变成有状态的业务服务，并且**任何业务逻辑变更都需要重启全站唯一入口**——把最不该停的组件变成发布最频繁的组件。

### 方案 C：5 服务（采纳）

```
gateway
  ├── user-service    （用户、登录态、乘车人）
  ├── ticket-service  （车次、站点、经停、票价；余票只读查询）
  ├── stock-service   （库存权威：扣减、回补、库存流水）
  └── order-service   （订单状态机、支付流水、通知触发）
```

调用方向（单向、无环）：

```
gateway ──> ticket-service ──┐
        ──> user-service     │
        ──> order-service ───┼──> stock-service
                             │
        （同步调用）
order-service ──> MQ ──> stock-service（异步回补 / 对账）
```

**优点**

- 库存有了唯一权威点，超卖问题收敛到一个服务里解决。
- 三类负载特征分离，可以各自扩容、各自限流、各自降级（详见第 6 节）。
- 完整的服务注册、发现、配置、调用、熔断链路都有真实落点，教学目标达成。

**缺点（必须承认并处理）**

- 扣库存与建订单跨越进程边界，本地事务失效，必须引入最终一致性方案（见第 6.4 节），复杂度上升。
- 多一次网络跳转，下单链路的 P99 会受影响（具体增量待压测）。
- 本地要同时启动 5 个进程 + MySQL + Redis + Nacos + Sentinel Dashboard，内存占用明显上升（具体数值待实测）。

### 方案对比

| 维度 | A 单体 | B 4 服务 | C 5 服务（采纳） |
| --- | --- | --- | --- |
| 部署单元数 | 1 | 4 | 5 |
| 库存独立扩容 | 不支持 | 不支持 | 支持 |
| 故障隔离（查票拖死下单） | 会 | 会（同进程） | 不会 |
| 超卖风险 | 低（本地事务） | 中（边界模糊） | 低（单一权威 + 原子扣减） |
| 跨服务一致性成本 | 无 | 低 | 高（需最终一致方案） |
| 本地启动成本 | 低 | 中 | 高 |
| 分布式组件有真实落点 | 否 | 部分 | 是 |
| 是否符合教学目标 | 否 | 部分 | 是 |

## 4. 决策

**采纳方案 C：5 服务。**

拆分后的服务职责与数据所有权如下。**数据所有权原则：一张表只能属于一个服务，禁止跨服务直连数据库，禁止跨服务 JOIN。**

| 服务 | 职责 | 拥有的表 | 依赖 |
| --- | --- | --- | --- |
| gateway | 路由、鉴权前置、限流、开抢时间闸门、链路 ID 注入 | 无（无状态） | 所有业务服务的路由目标 |
| user-service | 注册登录、令牌签发与校验、乘车人管理 | `t_user`、`t_passenger`、`t_token_blacklist` | 无 |
| ticket-service | 车次、站点、经停、席别票价；**余票只读查询**（读 stock-service 的数据或缓存） | `t_train`、`t_station`、`t_train_stop`、`t_seat_price` | stock-service（只读余票） |
| stock-service | **库存权威**：扣减、回补、库存流水、对账 | `t_stock`、`t_stock_log` | 无（不反向依赖订单） |
| order-service | 订单状态机、支付流水、超时取消、通知触发 | `t_order`、`t_payment` | user-service、ticket-service、stock-service |

注意依赖方向的一个关键设计：**stock-service 不依赖 order-service**。库存服务只认"扣减请求 + 请求号"，不关心订单长什么样。这样库存的可用性不被订单服务的发布、故障、慢查询影响；反过来订单服务挂掉也不会阻塞库存扣减。

### 各服务的负载特征与扩容手段

（以下为设计预期，具体数值待压测）

| 服务 | 读写特征 | 峰值特征 | 扩容手段 | 降级优先级 |
| --- | --- | --- | --- | --- |
| ticket-service | 读多写少 | 查询集中在开抢前 | 多实例 + Redis 缓存 | 可降级为缓存结果 |
| stock-service | 写密集、RT 极短 | 开抢瞬间的尖峰 | 多实例 + Redis 原子扣减 | 不可降级，只能限流排队 |
| order-service | 写为主 | 中等 QPS，可削峰 | 多实例 + MQ 异步落库 | 不可降级为"假成功" |
| user-service | 读多写少 | 低频，登录时才访问 | 2 实例足够 | 可短时降级（令牌本地校验） |

## 5. 为什么不拆更多：拆分边界的四条判据

每拆一个服务，都要付出确定的成本：

- 一个额外的部署单元与配置项
- 一次网络调用（新增超时、重试、序列化、错误处理）
- 一个额外的故障点
- 一条跨服务的数据一致性链路
- 一套额外的日志/监控/链路追踪接入

因此，**只有满足以下四条判据中的至少两条，才允许拆分**：

| 判据 | 说明 |
| --- | --- |
| J1 数据所有权清晰 | 该模块有自己独占的写表，不与其它服务共享写入口 |
| J2 扩容曲线独立 | 该模块的负载曲线与其它模块明显不同，需要单独扩缩容 |
| J3 故障域独立 | 该模块故障时必须不拖垮其它模块，或被拖垮的代价不可接受 |
| J4 团队/发布节奏独立 | 有独立团队，或需要独立发布节奏 |

按这四条判据逐一看候选拆分点：

| 候选 | J1 | J2 | J3 | J4 | 结论 | 理由 |
| --- | --- | --- | --- | --- | --- | --- |
| 认证中心（独立 SSO） | 否 | 否 | 否 | 否 | 不拆 | 认证是横切关注点。拆成独立认证中心只有在"多系统统一登录"场景才有收益。本项目只有一个前端，网关做令牌校验 + user-service 做令牌签发即可 |
| 支付服务 | 是 | 否 | 部分 | 否 | 暂不拆，标注为重新评审点 | 当前是模拟支付，支付是订单状态机的一个状态迁移，没有独立的对账/渠道路由/安全等级要求。**如果接入真实支付渠道，这条必须重新评审**：真实支付的合规、对账、渠道切换都要求独立部署 |
| 通知服务（短信/邮件） | 否 | 否 | 是 | 否 | 不拆 | 通知是异步 MQ 消费，量小且天然可失败重试，独立部署收益低于成本 |
| 车次基础数据服务 | 是 | 否 | 否 | 否 | 不拆 | 车次、站点、经停是同一份数据的三种读法，拆开只会导致重复缓存与缓存不一致 |
| 搜索服务（ES） | 是 | 否 | 部分 | 否 | 不拆 | 查询条件简单（出发站 + 到达站 + 日期），MySQL 联合索引 + Redis 缓存即可覆盖。引入 ES 只增加一个需要运维的存储组件（是否真的够用待压测验证查询耗时） |
| 管理后台服务 | 是 | 否 | 是 | 否 | 不拆 | 后台流量极低。用网关按 Path 区分路由、后台接口单独限流即可，不值得独立进程 |
| 对账服务 | 是 | 否 | 部分 | 否 | 不拆 | 对账以定时任务形式放在 order-service 内，读 stock-service 的流水做比对；量级小，独立部署无收益 |

**"不拆"不等于"不隔离"**。上面这些模块在自己的服务里仍然是独立包、独立接口，未来任何一条判据从"否"变成"是"（比如接入真实支付、查询量涨到 MySQL 扛不住），都可以按当时的判据重新评审。

## 6. 专项裁决：库存服务该不该独立？

这是本 ADR 里争议最大的一个问题，单独裁决。

### 6.1 正方（独立）的理由

1. **库存必须有唯一权威点**。只要存在两个扣减入口（比如 ticket-service 一个、order-service 一个），两个入口各自读-判断-写，就一定存在竞态窗口，超卖只是概率问题。
2. **负载特征与查票完全相反**。余票查询是"读多、可缓存、响应体大、可以容忍秒级延迟"；库存扣减是"写密集、必须极短 RT、不可缓存、对延迟极敏感"。放在同一个进程里，两者共享 Tomcat 线程池、数据库连接池、Redis 连接池。**查票的一条慢查询会让库存扣减拿不到连接**——这不是理论风险，是共享资源池的必然结果。
3. **降级策略冲突**。查票可以在系统压力大时降级为"返回缓存余票 + 提示可能有延迟"；库存扣减绝对不能降级（不能返回假的扣减成功）。如果两者在同一个服务里，无法只降级查票而不影响扣减；独立后可以对 ticket-service 限流降级、对 stock-service 保容量。

### 6.2 反方（不独立）的理由

1. 扣库存与建订单强耦合，拆开后本地事务失效，必须引入跨服务一致性方案（TCC / 事务消息 / 对账），复杂度显著上升。
2. 多一跳网络调用，下单链路变长，失败面变大。
3. 教学项目数据量小，本地单机跑，独立扩容的收益看不到。

### 6.3 裁决

**采纳独立方案。** 决定性理由是第 6.1 节的第 1 条和第 3 条：**唯一权威点**是正确性问题（超卖），**降级策略冲突**是可用性问题（不能只降级一部分）。这两条不随项目规模变化而变化，不是"量小就可以不算"的问题。

对反方第 1 条（一致性成本）的回应是：**不引入分布式事务**。

本项目对"扣库存 + 建订单"的一致性方案是：

```
1. stock-service 用 Redis + Lua 做原子预扣（权威、瞬时、不可超卖）
2. stock-service 返回扣减结果（成功 / 库存不足）
3. 扣减成功 → order-service 落订单（待支付）
4. 扣减成功但订单落库失败 → 由 stock-service 的库存流水 + 定时对账补偿回补
5. 扣减记录与订单通过 request_no 关联，可双向追溯
```

即：**接受短暂不一致，用对账兜底**，而不是用 XA / Seata AT 追求强一致。理由：

| 方案 | 一致性 | 对 Redis 扣减是否适用 | 运维成本 | 选择 |
| --- | --- | --- | --- | --- |
| 本地事务（不拆库存） | 强 | 适用 | 低 | 否（放弃了正确性之外的收益） |
| XA / 2PC | 强 | 不适用（Redis 不参与 XA） | 高 | 否 |
| Seata AT | 强（有全局锁） | 不适用（AT 只覆盖支持回滚的数据库） | 高 | 否 |
| TCC | 强（业务侵入大） | 适用 | 中高 | 否（每个参与方都要写 Try/Confirm/Cancel 三套逻辑） |
| **最终一致 + 对账** | 最终一致 | 适用 | 低 | **是** |

关键点：**库存的权威值是 Redis 里的原子计数，不是数据库行**。数据库里的库存是"账"，Redis 里的库存是"实"——两者最终一致，靠定时对账发现并修正偏差。这也解释了为什么 XA/Seata 在这里没有意义：它们保护不到真正的裁决点。

### 6.4 原子扣减：为什么必须靠代码才能讲清

朴素实现有一个典型的 TOCTOU（检查后使用）竞态：

```
读库存 → 判断是否充足 → 扣减        // 两步之间，另一个请求可能已经扣走了
```

即使把这三步写成数据库的 `UPDATE t_stock SET left = left - 1 WHERE left >= 1`，也只在单库单表下成立；一旦引入缓存层，判断逻辑回到应用侧，竞态重新出现。

所以扣减逻辑下沉到 Redis Lua 脚本执行。Redis 执行 Lua 脚本期间不会插入其它命令，**读-判断-写三步天然成为一个原子操作**：

```lua
-- KEYS[1] = 库存 key，例如 stock:{trainNo}:{travelDate}:{seatType}
-- ARGV[1] = 本次扣减数量
local left = tonumber(redis.call('GET', KEYS[1]) or '-1')
if left < tonumber(ARGV[1]) then
  return -1                       -- 库存不足
end
return redis.call('DECRBY', KEYS[1], ARGV[1])   -- 返回扣减后的余量
```

（这是逻辑示意，生产脚本还要处理 key 不存在、预热、回补等分支，最终脚本以 stock-service 代码为准。）

### 6.5 幂等与限购：数据库层的兜底

Redis 是权威裁决点，但"重试/连点产生的重复扣减"要靠请求号幂等来挡。数据库唯一索引是最后一道防线：

```sql
-- 幂等：同一个请求号只允许落一条订单，重复提交直接触发唯一键冲突
ALTER TABLE t_order ADD UNIQUE KEY uk_request_no (request_no);

-- 限购：同一用户同一车次同一席别限购 1 张
-- 注意：这条是业务规则，需要业务方确认（是否允许一个账号给同行人购票）
ALTER TABLE t_order
  ADD UNIQUE KEY uk_user_train_seat (user_id, train_no, travel_date, seat_type);
```

两条索引的分工：`uk_request_no` 挡"同一次请求被重试多次"，`uk_user_train_seat` 挡"用户绕过前端反复提交"。前者是幂等，后者是限购——**幂等是技术正确性，限购是业务规则，不要混为一谈**。

### 6.6 订单状态机（跨服务一致性的落点）

订单状态流转是"库存回补"的唯一触发依据，因此必须显式定义：

```
待支付(PENDING) ──支付成功──> 已支付(PAID) ──出票──> 已出票(ISSUED)
      │                                    
      └──超时未支付 / 用户取消──> 已取消(CANCELLED)  ──> 触发库存回补
已支付 ──退款──> 已退款(REFUNDED) ──> 触发库存回补
```

回补是**幂等**的：以 `order_no` 为幂等键，重复回补不重复加库存。状态机流转与回补动作在同一处代码实现，避免"改了状态忘了回补"。

### 6.7 独立后的代价与对应措施

| 代价 | 措施 |
| --- | --- |
| 跨进程，本地事务失效 | 最终一致 + 库存流水 + 定时对账（6.3） |
| 多一跳网络调用 | 短超时 + 熔断 + 有限重试（见 ADR-004） |
| 库存扣减成功后订单落库失败 | 库存流水表记录每次扣减，对账任务比对"已扣减无订单"的记录并回补 |
| 排查链路变长 | 全链路 traceId，网关注入，Feign 透传 |

## 7. 后果

### 正面

- 超卖问题被收敛到 stock-service 一个服务、一个 Lua 脚本、一处代码可审计。
- 库存可以独立扩容与限流，抢票时只为库存加机器。
- 查票（可降级）与扣减（不可降级）的降级策略可以分开配置。
- 服务注册发现、配置中心、声明式调用、熔断限流在本项目里都有真实落点，不是摆设。

### 负面（明确接受）

- 下单链路从"一次本地方法调用"变成"至少两次跨进程调用"，链路更长，P99 受影响（增量待压测）。
- 必须实现并维护对账任务，否则最终一致会退化成"永远不一致"。
- 本地开发要同时启动 5 个 Spring Boot 进程 + MySQL + Redis + Nacos + Sentinel Dashboard，内存与启动时间成本明显上升（具体数值待实测）。
- 调试从"看堆栈"变成"看链路追踪"，前期需要投入接入链路追踪的成本。

### 需要长期遵守的约束

- 新表必须先确定归属服务，不允许两个服务同时写一张表。
- 跨服务只允许通过 API 或 MQ 交互，禁止直连对方数据库。
- 任何新增拆分点必须逐条对照第 5 节的四条判据，并在 ADR 中记录。

| 待验证项 | 验证方式 | 影响 |
| --- | --- | --- |
