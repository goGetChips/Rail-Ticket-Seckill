# ADR-004：Spring Cloud 组件栈

- 状态：已接受（Accepted）
- 日期：2026-09-15
- 决策范围：网关、注册中心、配置中心、服务调用、负载均衡、熔断限流的选型与配置原则
- 相关文档：ADR-001（总体架构与技术选型）、ADR-002（数据一致性与并发控制）、[ADR-003（服务拆分粒度）](./ADR-003-service-granularity.md)
- 设计规格：[design-spec.json](../architecture/design-spec.json)

---

## 1. 本文档怎么读

本文档按"先决条件 → 逐个组件 → 全局串联"的顺序组织。第 2 节是**先决条件**，因为版本组合选错的话，后面所有组件都跑不起来，很多"组件用不了"的问题实际是版本问题。

每个组件统一回答五个问题（下称"五连问"）：

1. **为什么需要它？**
2. **没有它会发生什么？**（用具体故障场景描述，不写抽象好处）
3. **它到底怎么工作的？**（原理层面，不抄源码）
4. **一个服务挂掉之后具体会发生什么？**
5. **什么时候需要降级？降级后用户体验是什么？**

第 7 节把六个组件串起来，做一次完整的故障时间线演练，这一节是本文档的收口。

阅读建议：面试中真正拉开差距的不是"这个组件是干什么的"，而是第 4 问和第 5 问——**故障时会发生什么、多久恢复、用户看到什么**。这两问才是工程经验。

## 2. 先决条件：版本组合与兼容性地雷

### 2.1 问题

Spring Cloud 的组件栈由三个版本维度共同决定，而不是一个：

| 维度 | 说明 |
| --- | --- |
| Spring Boot 版本 | 由 `spring-boot-starter-parent` 决定，本项目根 pom 当前为 `3.5.9`，`java.version=17` |
| Spring Cloud Release Train 版本 | 决定 Spring Cloud 官方组件（Gateway、OpenFeign、LoadBalancer）的版本 |
| Spring Cloud Alibaba（SCA）版本 | 决定 Nacos 注册/配置、Sentinel 等阿里系组件的版本 |

三者的兼容关系是**串联**的，不是并联的：

```
Spring Boot 版本  ←必须匹配→  Spring Cloud Release Train  ←必须匹配→  Spring Cloud Alibaba
```

SCA 的版本号形如 `20XX.0.Y.Z`，其中前四位（`20XX.0`）对应它所适配的 Spring Cloud Release Train。而每个 Release Train 官方只支持特定范围的 Spring Boot 版本（以 Spring 官方的 compatibility matrix 为准）。

**由此得出的核心风险**：Spring Boot 的主线迭代节奏快，而 Spring Cloud 与 SCA 的发布节奏滞后于 Boot。当根 pom 使用了较新的 Boot 版本（本项目当前是 3.5.x 线）时，很可能出现"**最新版 SCA 尚未适配该 Boot 版本**"的情况。这就是本项目最大的版本地雷。

> 具体哪个 SCA 版本适配哪个 Boot 版本，**本文档不写死**——版本关系变动频繁，写死的表格很快就会过期并且会误导人。动手前必须打开三份官方文档交叉核对（见 2.4）。
> 待验证：SCA 当前是否有适配 Boot 3.5.x 的正式发布版本。

### 2.2 版本错配的具体症状（现象 → 原因 → 处理）

| # | 症状 | 根本原因 | 处理 |
| --- | --- | --- | --- |
| 1 | 启动时 `NoSuchMethodError` / `NoClassDefFoundError`，类名指向 `org.springframework.cloud.client.*` 或 `com.alibaba.cloud.*` | Boot / Spring Cloud / SCA 三者中至少两个版本错配，导致同一接口在不同 jar 里签名不同 | 三者统一到官方矩阵中同一行 |
| 2 | 启动报 `Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway` | 网关模块同时引入了 `spring-boot-starter-web`（Servlet 栈）与 `spring-cloud-starter-gateway`（WebFlux 栈） | 网关模块显式排除 web starter，禁止引入任何基于 MVC 的库 |
| 3 | `bootstrap.yml` 完全没生效，Nacos 配置读不到 | Spring Cloud 2020 之后默认不再启用 bootstrap 上下文 | 二选一：引入 `spring-cloud-starter-bootstrap`，或改用 `spring.config.import` 方式声明配置源（推荐后者，具体语法随版本变化，待验证） |
| 4 | 服务注册不上 / 配置拉取 404 | Nacos **客户端**版本与 Nacos **服务端**版本不匹配（这是第四个版本维度，容易被漏掉） | 客户端与服务端同版本线，或按官方兼容表选择 |
| 5 | 编译期或启动期 `javax.*` 找不到 | Boot 3.x 已全面迁移到 `jakarta.*`，某个依赖仍停留在 Boot 2.x 时代的 Servlet API | 排查依赖树，剔除携带旧 Servlet API 的传递依赖 |

症状 1 和 2 是实际排查中最高频的两类。症状 2 有一个简单的预防手段：**网关模块的 pom 里不出现 `spring-boot-starter-web`**，把它作为一条 code review 检查项。

### 2.3 降级方案：如果 SCA 与 Boot 3.5 不兼容怎么办

四个可选方案：

| 方案 | 做法 | 优点 | 代价 | 何时选 |
| --- | --- | --- | --- | --- |
| **1. 降 Boot 版本**（首选） | 把根 pom 的 `spring-boot-starter-parent` 降到 SCA 官方支持的版本 | 改动最小（一行）；整个 SCA 栈（Nacos + Sentinel + 网关适配）都能用；与国内面试常见技术栈一致 | 失去较新 Boot 版本的部分特性（3.5 相对被降到的版本差哪些特性，待核对）；`java.version` 可能需要一并调整（Boot 3.x 全线要求 Java 17+，若降到 Boot 2.x 则 Java 也要降，这一步代价较大） | 默认选择 |
| **2. 换掉 SCA 组件** | 注册中心换 Eureka/Consul，配置中心换 Spring Cloud Config/Consul KV，熔断限流换 Resilience4j，网关仍用 Spring Cloud Gateway | 全套 Spring 官方组件，兼容性由 Spring 官方保证，不需要赌 SCA 的发布节奏 | **偏离学习目标**：Nacos 与 Sentinel 在国内面试中出现频率高，换掉会削弱这个项目最想学的东西；Sentinel 的流控模型（Warm Up、匀速排队、关联/链路模式）在 Resilience4j 里没有直接对应物，要重新学一套概念 | 方案 1 的降级幅度过大时（例如需要退回 Boot 3.0 一线），或明确以"Spring 官方栈"为学习目标 |
| **3. 用 SCA 快照/预发布版** | 引入 SCA 的 snapshot 仓库 | 能拿到最新适配 | 不稳定，构建不可复现，教学项目引入随机故障源，排查成本会转移到"到底是我写错了还是快照有 bug" | 不推荐 |
| **4. 混合：只用 Nacos 官方 SDK** | 不走 SCA starter，直接用 `nacos-client` 写适配层；熔断用 Resilience4j | 绕开 SCA 的版本约束 | 自己维护自动装配、服务发现集成、配置刷新，代码量不小；失去 `@RefreshScope` 这类开箱能力 | 不推荐，除非方案 1、2 都不可行 |

**决策：优先方案 1（降 Boot 版本）。** 判断依据是：本项目的首要目标是学会 Spring Cloud Alibaba 这套国内主流栈，栈的完整性比 Boot 的小版本号重要；Boot 版本差异对本项目用到的特性（Web、数据访问、异步）影响有限。若评估后发现方案 1 需要把 Boot 降回 3.0 一线（降幅过大、会牵连其它依赖），则切换到方案 2，并在切换时显式记录这个取舍。

### 2.4 强制动作（不遵守就会踩坑）

1. **动手前先核对三份官方文档**：SCA 的版本说明、Spring Cloud 的版本兼容矩阵、Spring Boot 的版本说明。三者的交集才是可用组合。
2. **版本只在根 pom 的 `<properties>` 里声明一次**，子模块一律不写版本号。使用 `dependencyManagement` 统一收敛。
3. **加 `maven-enforcer-plugin`**，启用 `dependencyConvergence`（依赖收敛）或 `requireUpperBoundDeps` 规则，把版本冲突在**构建期**暴露出来，而不是等启动时报 `NoSuchMethodError`。
4. **先做最小验证工程**：只引 gateway + nacos-discovery + nacos-config + openfeign + sentinel，跑通"注册 → 发现 → 读配置 → 调用 → 限流"五件事，确认版本组合可用之后，再开始写业务代码。
   这一步能省掉后面几天的排查时间——因为业务代码写完之后再遇到版本问题，你无法区分"是版本问题还是我代码写错了"。

## 3. 组件总览

| 组件 | 角色 | 部署形态 | 本项目是否单点 |
| --- | --- | --- | --- |
| Spring Cloud Gateway | 流量入口 | 独立进程（WebFlux） | 本地单实例，是已知单点 |
| Nacos（注册中心） | 服务地址簿 | 独立进程/集群 | 本地单实例，客户端有本地缓存兜底 |
| Nacos（配置中心） | 配置下发 | 与上同一进程 | 同上 |
| OpenFeign | 声明式调用 | 进程内库 | 不适用（库不会挂） |
| Spring Cloud LoadBalancer | 选实例 | 进程内库 | 不适用 |
| Sentinel | 限流熔断 | 进程内库 + Dashboard | 规则持久化到 Nacos；Dashboard 挂了不影响已生效规则 |

一个必须先建立的心智模型：

> **库（library）和进程（process）的故障行为完全不同。**
> OpenFeign、LoadBalancer、Sentinel 客户端都是库，它们"挂"的唯一方式是**所在业务进程挂**。它们的危险不在于自己挂，而在于**默认配置会让你在依赖故障时把自己拖死**。
> Gateway、Nacos 是进程，它们有真正的单点问题，但也因此有集群和本地缓存的兜底手段。

## 4. 组件逐个拆解（五连问）

### 4.1 Spring Cloud Gateway

#### 4.1.1 为什么需要它

- **单一入口**：客户端（网页、App）只认一个域名。后端服务增减、改名、换端口、换 IP，对客户端完全不可见。
- **横切关注点收口**：令牌校验、CORS、请求日志与 traceId 注入、请求体大小限制、超时、灰度路由、协议转换，全部集中在一处实现，而不是在 4 个业务服务里各写一遍。
- **抢票场景特有：开抢时间闸门**。在网关层校验"当前时间是否已到开抢时间"，未到直接拒绝。这一层挡掉的是**完全无效的流量**——如果不在网关挡，这些请求会一路穿透到 stock-service 才被拒，白白消耗掉最宝贵的库存服务容量。

#### 4.1.2 没有它会发生什么（故障场景）

假设没有网关，前端直连 4 个业务服务：

1. **鉴权逻辑重复且会漂移**。4 个服务各自实现令牌校验。某天令牌签名算法升级，user-service 改了，order-service 忘了改——结果是部分接口鉴权失效。这是安全漏洞，而且不会有人主动发现。
2. **CORS 配 4 遍**。漏配一个，前端就报跨域错误，而错误信息指向的是浏览器而不是后端，排查方向容易跑偏。
3. **恶意流量直击核心**。脚本绕过前端，直接对 stock-service 的扣减接口发压。没有统一入口就没有统一限流，库存服务被打爆，正常用户全部下单失败。
4. **服务地址变更需要前端发版**。本地开发端口随机、容器重调度换 IP，客户端硬编码的地址全部失效。

#### 4.1.3 它到底怎么工作的

网关建立在 Spring WebFlux + Reactor Netty 之上，是**非阻塞事件循环模型**，与 Spring MVC 的"一请求一线程"模型根本不同。这一点决定了两件事：网关能用少量线程扛住大量并发连接；以及网关模块不能引入 MVC 依赖。

一次请求的流水线：

```
请求到达
  → RoutePredicateHandlerMapping：用断言（Predicate）匹配路由，确定走哪条 Route
  → 组装过滤器链：GlobalFilter（全局）+ 该 Route 的 GatewayFilter（路由级），按 order 排序
  → pre 阶段：过滤器按顺序执行（改写请求头、加 traceId、校验令牌、限流……）
  → NettyRoutingFilter：转发到目标 URI
       若 URI 写成 lb://stock-service，则交给 LoadBalancer 解析成真实 ip:port
  → post 阶段：过滤器逆序执行（改写响应码、响应体、记录耗时）
  → 响应返回客户端
```

断言（Predicate）的常见类型：`Path`、`Method`、`Header`、`Query`、`Cookie`、`RemoteAddr`，以及**时间类断言 `After` / `Before` / `Between`**——开抢闸门直接用它就能实现，不需要写代码。

过滤器的能力边界：可以改请求头、改路径、改响应状态码、改响应体、短路请求（直接返回不转发）。**短路能力是降级的基础**——降级本质上就是"匹配到某个条件时，不转发，直接返回预设响应"。

#### 4.1.4 一个服务挂掉之后会发生什么

分两种情况，结论完全不同：

**情况一：下游业务服务挂掉。**
网关本身不受影响，它只是收到连接失败或读超时，返回 502/504 给客户端。

但这里有一个致命细节：**如果网关到下游没有配置超时，网关自己会被拖死**。下游不响应时，网关的 Netty 连接会一直挂着等待，连接池被慢请求占满，新的请求排不上队——于是网关从"转发者"变成"受害者"，整个站点（包括那些本来健康的服务）全部不可用。
所以必须给网关配置连接超时与响应超时（具体属性名随版本变化，待验证）。

**情况二：网关自身挂掉。**
全站不可用，因为它是唯一入口。缓解手段：网关是无状态的，起多实例，前面挂一层 Nginx/SLB 做健康检查与摘除。单实例挂掉时，上游 LB 摘除它，影响是"在途请求失败 + 短暂抖动"，不是持续故障。
**本地教学环境只有单实例，这是一个已知的、被接受的单点**——真实生产环境不应如此。

#### 4.1.5 什么时候降级、降级后用户体验

| 触发条件 | 降级动作 | 用户体验 |
| --- | --- | --- |
| 网关限流触发 | 直接返回 429 + 统一 JSON 体（如 `{"code":"RATE_LIMITED","msg":"当前访问人数过多，请稍后重试"}`），不转发 | 明确被拒，1 秒内知道结果。比"转圈 30 秒后失败"好得多 |
| 未到开抢时间 | 短路返回"距离开始还有 N 秒" | 这是业务规则，不是故障降级，但对用户体验是正向的 |
| 查票路由下游不可用 | 路由改写到一个只读兜底端点，返回缓存余票 | 能看票，但会看到"余票信息可能有延迟"的标注 |
| 下单路由下游不可用 | **不降级**，直接快速失败 | "当前排队人数过多"——宁可明确失败，也绝不能让用户以为下单成功了 |
| 非核心路由（历史订单、推荐） | 直接返回静态占位或 503 | 功能缺失但主链路可用 |

### 4.2 Nacos（注册中心）

#### 4.2.1 为什么需要它

服务实例的地址是**动态的**：扩容、缩容、重启、容器重新调度，IP 和端口都在变。调用方不可能硬编码一份地址列表。注册中心解决的是"调用方如何知道现在有哪些可用实例"这个问题。

#### 4.2.2 没有它会发生什么（故障场景）

不用注册中心，常见替代是"配置文件里写死一份 IP 列表"：

1. **扩容要改配置并重启所有调用方**。想把 order-service 从 2 个实例扩到 4 个，得改 order-service 的调用方（gateway、ticket-service）的配置文件，然后重启它们。抢票高峰期做这件事等于自伤。
2. **故障实例无法自动摘除**。某个实例进程假死（还在监听端口但不响应），调用方从配置里读到的列表仍然包含它，会持续把请求打到它上面。**从"实例挂掉"到"有人发现并手动改配置重启"，恢复时间以分钟到小时计**。在这段时间里，用户持续看到随机失败（轮询到坏实例就失败）。
3. **无法做灰度**。新版本实例没法只让一部分流量进来。

#### 4.2.3 它到底怎么工作的

**注册**：服务提供者启动时，把自己的 `serviceName + ip + port + 元数据` 注册到 Nacos。默认注册为**临时实例（ephemeral）**。

**健康检查**：两类实例的机制完全不同，这是理解 Nacos 故障行为的关键。

| 实例类型 | 健康检查方式 | 一致性模型 | 不健康时的行为 |
| --- | --- | --- | --- |
| 临时实例（默认） | 客户端主动上报心跳；服务端超过阈值未收到心跳则标记不健康，再超时则**直接剔除** | Distro 协议（AP，各节点负责一部分实例并异步复制） | 标记不健康 → 剔除 |
| 非临时实例（持久实例） | 服务端主动探测（TCP/HTTP） | Raft/JRaft（CP） | 只标记不健康，**不剔除** |

心跳的默认阈值量级是：数秒上报一次，十几秒未收到标记不健康，几十秒未收到剔除（**具体默认值以所用版本文档为准，待验证**）。

**这里有一个必须理解的取舍**：临时实例走 AP 模型，意味着**不同 Nacos 节点上的实例列表在某一瞬间可能不一致**。这是刻意的选择——换来的是 Nacos 节点挂掉后新的服务仍能注册（可用性优先）。如果选 CP（比如用 Zookeeper），一旦发生分区，整个注册中心不可写，新服务注册不上，对抢票场景是更严重的问题。

**发现**：消费者启动时拉取全量实例列表并**缓存到本地内存**，之后订阅变更。变更推送走 UDP（不可靠），因此客户端还有定时轮询作为兜底——所以"推送丢了"不会导致永久不一致，只会延迟。

#### 4.2.4 一个服务挂掉之后会发生什么

这里要分清楚"谁挂了"：

**业务实例挂了（未优雅下线，比如进程崩溃）：**

```
t=0      实例崩溃，进程消失
t=0~15s  注册中心仍认为它健康（心跳还没超时）
         消费者仍在往它发请求 → 连接被拒 / 超时 → 用户看到失败
t≈15s    Nacos 判定不健康，可能先标记再剔除
t≈15s+   变更推送给消费者
```

**关键推理**：从"实例实际挂掉"到"调用方不再选它"之间存在一个**时间窗口**，这个窗口由"心跳超时阈值"决定。在这个窗口内发生的请求必然失败。这不是 bug，是心跳式健康检查的固有延迟。

**Nacos 注册中心自身挂了：**

- **已启动的消费者基本不受影响**：Nacos 客户端在本地缓存了实例列表（还有磁盘上的 failover 快照文件），会继续用缓存列表调用。也就是说 **Nacos 挂了不等于全站立刻挂**。
- 受影响的是：新启动的服务注册不上；实例列表发生变化（扩容、某实例下线）时消费者感知不到；新启动的消费者拿不到实例列表。
- 所以影响是"系统冻结在当前状态，不能变更"，而不是"立刻不可用"。这个区别在面试里答出来会很加分。

**优雅下线（进程收到 SIGTERM，主动注销）：**
感知窗口接近 0。所以生产上必须配优雅停机——它让"故障窗口"从十几秒降到接近零，是性价比最高的一项配置。

#### 4.2.5 什么时候降级、降级后用户体验

| 场景 | 降级手段 | 用户体验 |
| --- | --- | --- |
| 单个 Nacos 节点挂 | 客户端自动切换其它节点（集群至少 3 节点） | 无感知 |
| Nacos 集群整体不可用 | 客户端本地缓存 + failover 快照文件继续提供实例列表 | 基本无感知；代价是系统"冻结"，实例变更不生效 |
| 实例心跳超时窗口内的失败请求 | 不是注册中心的降级，而是调用方的兜底：短超时 + 有限重试 + 熔断 | 失败的请求数被压到窗口内的一小部分 |

**结论**：注册中心的降级主要靠"客户端缓存 + 集群部署"，用户通常不可感知。真正影响用户体验的不是 Nacos 挂，而是**心跳窗口 + 列表缓存的叠加延迟**（详见 4.5）。

### 4.3 Nacos（配置中心）

#### 4.3.1 为什么需要它

- 配置变更不需要重新构建、重新部署。
- 多环境（开发/测试/生产）隔离，避免本地误连生产库。
- 敏感配置（数据库密码）与代码分离。
- 限流阈值、超时时间这类**运行期需要调整的参数**必须能动态生效。

#### 4.3.2 没有它会发生什么（故障场景）

配置写在各个服务的 `application.yml` 里：

1. **改一个限流阈值要重启所有服务**。抢票过程中发现某个阈值设得太严，需要调整——重启 5 个服务意味着一段时间的不可用，而且是在高峰期。**结果是没人敢改**，只能等下次发布窗口，故障持续。
2. **配置漂移**。5 个服务各自维护 `application.yml`，Redis 地址、数据库连接参数重复 5 份。某次只改了 4 份，剩下的那个连了旧库——症状是"随机出现的数据不一致"，排查难度极高。
3. **环境不一致**。本地配置和线上配置有差异（本地连了测试库），"本地能跑，线上挂"。

#### 4.3.3 它到底怎么工作的

**配置的层级隔离**：

```
namespace（环境：dev / test / prod）
  └── group（项目或业务分组）
        └── dataId（通常是 服务名.yml）
```

**客户端启动时**：拉取全量配置到内存，同时在本地磁盘写一份快照（failover 文件，位于用户目录下的 `nacos/config/` 目录）。

**配置变更如何感知——长轮询（Long Polling）**：

```
客户端：发起一个带当前配置 md5 的请求，服务端不立即答复，而是 hold 住这个连接（最长约 30 秒）
服务端：这期间如果配置变了 → 立即返回，告诉客户端"变了，来拉新的"
        如果 30 秒内没变 → 返回空，客户端立刻再发起一次长轮询
```

**为什么不用服务端主动推？** 因为客户端通常在公司防火墙/NAT 之后，服务端无法主动对客户端建立连接。长轮询用"客户端主动发起但服务端延迟应答"的方式，模拟出了推的效果，同时穿透了防火墙。这是一个非常经典的设计取舍，值得记住。

**配置变更后 Bean 怎么更新**：靠 `@RefreshScope`。被它标注的 Bean 在配置变更后会被销毁并重新创建。
**注意陷阱**：不是所有 Bean 都能安全刷新。连接池类 Bean（DataSource、Redis 连接池）重建时会先销毁旧连接池——在高并发下重建瞬间可能大量请求失败。**连接池相关的配置变更，应当走发布流程，而不是运行期热更新。**

#### 4.3.4 一个服务挂掉之后会发生什么

**Nacos 挂了：**

- **运行中的服务不受影响**：配置已经在 JVM 内存里，业务照常跑。用户完全无感。
- 改配置改不动了（长轮询一直超时）。
- 新启动的实例连不上 Nacos 时，会尝试用本地快照启动（**具体行为以版本为准，待验证**）。风险在于：如果本地快照很旧，新实例会用一份过期的配置启动，可能出现"新扩容的实例连的是旧数据库"这类问题。

**业务服务挂了**：与配置中心无关。但要注意一个反向影响：如果配置中心不可用导致某个服务启动失败（拿不到必要配置且没有本地默认值），会造成**"Nacos 挂了之后，服务一旦重启就再也起不来"**的连锁反应。防范手段见 4.3.5。

#### 4.3.5 什么时候降级、降级后用户体验

| 场景 | 降级手段 | 用户体验 |
| --- | --- | --- |
| Nacos 不可用，服务运行中 | 无需降级，内存配置继续生效 | 无感 |
| Nacos 不可用，服务需启动 | 本地快照文件 + `application.yml` 中的安全默认值 | 无感（但可能用到旧配置） |
| 配置项缺失 | 代码中的默认值必须存在且保守（超时默认非 0、限流阈值默认偏严、开关默认关闭） | 无感 |

**硬性要求**：**任何一条从配置中心读取的关键参数，代码里都必须有一个保守的默认值。** 这条规则的作用是切断"配置中心挂了 → 服务起不来 → 全站雪崩"这条链路。配置文件里的 `@Value("${xxx:默认值}")` 里那个默认值不是摆设。

### 4.4 OpenFeign（声明式服务调用）

#### 4.4.1 为什么需要它

- **接口即契约**：用一个 Java 接口描述远程调用，调用方像调本地方法一样调用远程服务，不需要手写 URL 拼接和序列化。
- **横切逻辑收口**：超时、重试、日志、请求头透传（traceId、用户身份）通过统一的拦截器实现，不需要在每个调用点重复。
- **与注册中心/负载均衡天然集成**：写服务名而不是 IP，地址解析交给框架。

#### 4.4.2 没有它会发生什么（故障场景）

用 `RestTemplate` 手写调用：

1. **URL 字符串满天飞**。`"http://" + host + ":" + port + "/stock/deduct?trainNo=" + trainNo`——服务改名或路径调整时，只能靠全局搜索替换，漏掉一处就是运行时 404。
2. **超时配置各写各的**。A 调用点配了 3 秒，B 调用点忘了配。忘配的那个就是雪崩的起点（见 4.4.4）。
3. **请求头透传断链**。traceId 没透传，跨服务排查时链路断在服务边界上，只能靠时间戳猜。
4. **错误处理重复**。每个调用点各写一遍 try-catch、超时判断、降级分支。

#### 4.4.3 它到底怎么工作的

```
@EnableFeignClients 扫描 @FeignClient 接口
  → 为每个接口生成 JDK 动态代理对象（业务代码注入的其实是这个代理）

调用时代理内部依次做：
  1. Contract 解析：把方法上的注解（@GetMapping 等）解析成 RequestTemplate
  2. RequestInterceptor 链：依次改写请求（注入 traceId、令牌、统一 header）
  3. 服务名解析：把 http://stock-service 中的服务名，交给 LoadBalancer 解析成 ip:port
  4. Client 发送：默认实现基于 HttpURLConnection，可替换为 OkHttp / Apache HttpClient 以获得连接池
  5. Decoder 解码：把响应体反序列化成方法返回类型
```

**两个容易被忽略的点**：

- 第 3 步的"服务名解析"就是 4.5 节的 LoadBalancer，两者是同一件事——Feign 负责"怎么发"，LoadBalancer 负责"发给谁"。
- 第 4 步的默认 Client 实现**没有连接池**。高并发下连接复用率低，会明显影响吞吐。生产上通常换成带连接池的实现（具体选型待评估）。

#### 4.4.4 一个服务挂掉之后会发生什么

**Feign 是进程内库，它自己不会挂。挂的是它调用的下游。** 真正的危险来自默认配置。

危险链条如下：

```
stock-service 响应时间从 20ms 恶化到 30s（比如 GC 停顿、慢查询、连接池耗尽）
  → order-service 中每一个调用库存的线程都被占住 30s（如果读超时没配或配得过长）
  → order-service 的请求处理线程池在几十秒内被耗尽
  → order-service 对所有请求都无响应——包括那些与库存完全无关的接口
  → 上游网关到 order-service 的连接开始堆积，网关资源也被占住
  → 整个站点不可用
```

这就是**级联雪崩**：一个非核心依赖（甚至只是一次慢查询）拖垮全站。注意它的关键特征——**系统不是"拒绝服务"，而是"全部变慢"**。变慢比拒绝更糟，因为：
- 用户的请求占着连接不放，还会手动重试，流量反而放大
- 没有明确的失败信号，无法触发自动恢复
- 需要人工介入才能恢复

**防住这条链路的三个动作，缺一不可**：

1. **显式配置连接超时和读超时**。默认读超时可能长达数十秒量级（**具体默认值以版本为准，待验证**），对抢票场景完全不可接受。超时必须按接口的重要性分档：核心接口（库存扣减）用短超时（快速失败），非核心接口可以稍长。
2. **配熔断**。连续失败或慢调用比例超阈值后直接快速失败，不再消耗线程和连接（见 4.6）。
3. **按依赖分级**。核心依赖与非核心依赖使用不同的线程池/信号量隔离，避免互相影响。

#### 4.4.5 什么时候降级、降级后用户体验

降级通过 `@FeignClient(fallbackFactory = ...)` 或 Sentinel 的 `blockHandler` 实现。**降级逻辑必须区分接口类型**：

| 被调接口 | 降级动作 | 用户体验 | 允许吗 |
| --- | --- | --- | --- |
| 余票查询 | 返回最近一次缓存快照，并标注"余票信息可能有延迟" | 能看票，数据可能不是最新的 | 允许 |
| 车次/经停详情 | 返回缓存数据，或返回"该功能暂不可用" | 功能缺失 | 允许 |
| 库存扣减 | **不允许返回假的成功**。转 MQ 排队并返回排队号，或返回"当前排队人数过多" | 从"等 30 秒后失败"变成"1 秒内得到明确答复" | 不允许伪造成功 |
| 创建订单 | 同上 | 同上 | 不允许伪造成功 |

**降级设计的第一原则：降级可以降功能，不能降正确性。** 返回一个假的下单成功，比返回一个明确的失败严重得多——它会让用户以为抢到票了，而实际没有。

### 4.5 Spring Cloud LoadBalancer（负载均衡）

#### 4.5.1 为什么需要它

一个服务有多个实例，调用方需要决定**这一次请求发给谁**。同时它还承担着"配合注册中心把流量从故障实例上挪开"的职责。

#### 4.5.2 没有它会发生什么（故障场景）

- 客户端硬编码单个实例地址：无法水平扩容，那台机器就是吞吐上限。
- 实例挂了，调用方全部失败，没有分摊也没有故障转移。
- 无法做灰度（新版本实例无法只接一部分流量）。
- 无法做权重路由（大机器多接一点流量）。

#### 4.5.3 它到底怎么工作的

- Spring Cloud LoadBalancer 是 Ribbon 的替代品（Ribbon 已进入维护状态，新项目不应再使用）。
- 数据来源：`ServiceInstanceListSupplier` 从 `DiscoveryClient`（本项目即 Nacos）获取实例列表。**这个列表是带缓存的**（默认缓存时长在几十秒量级，**具体值待验证**）。
- 默认策略：`RoundRobinLoadBalancer`（轮询）。可替换为随机，或自定义权重策略。
- 接口是响应式的（返回 `Mono`/`Flux`），以便与 WebFlux 和 Feign 的异步链路集成。
- **职责边界**：LoadBalancer 只负责"选实例"，**不负责重试**。重试是 Feign/Retryer 的职责。这个边界很容易搞混。

#### 4.5.4 一个服务挂掉之后会发生什么

这是**整个 ADR 中最值得记住的一段推理**。

LoadBalancer 是库，不会挂。真正的问题是：**一个实例挂掉之后，调用方要多久才能停止给它发流量？**

答案由两段延迟叠加而成：

| 阶段 | 延迟来源 | 量级 |
| --- | --- | --- |
| 第一段 | 注册中心的心跳超时窗口：实例挂了但 Nacos 还不知道 | 十几秒到几十秒（默认阈值，待验证） |
| 第二段 | 消费者的 LB 实例列表缓存：Nacos 已剔除，但调用方本地列表还没刷新 | 几十秒（默认缓存时长，待验证） |
| （优化项） | 若配置了优雅停机，第一段可压缩到接近零 | 接近零 |

**结论**：在最坏情况下，从"实例挂掉"到"调用方不再选它"之间，可能存在一个**数十秒量级的窗口**，这个窗口内的请求会随机失败。这就是用户可感知的失败窗口，也是面试里问"服务挂掉后多久恢复"的标准答案的来源。

**这个窗口无法靠注册中心本身消除**（除非用 CP 模型，但那样代价更大），只能靠**调用侧的兜底**把它压到用户可接受的程度：

1. **短超时**：让失败快速暴露，而不是让线程挂着等。
2. **有限重试**：重试到另一个健康实例。**但下单/扣减接口不能无脑重试**——必须保证幂等（请求号 + 唯一索引，见 ADR-003 第 6.5 节），否则重试会变成重复下单。
3. **熔断**：连续失败后直接快速失败，不再尝试，避免把时间浪费在必然失败的请求上。

#### 4.5.5 什么时候降级、降级后用户体验

| 场景 | 降级手段 | 用户体验 |
| --- | --- | --- |
| 个别实例不稳定（偶发失败） | 权重降级（把该实例权重调低）或临时下线 | 无感 |
| 整个服务不可用 | 熔断打开，配合业务降级（缓存结果 / 快速失败） | 看到明确的降级提示 |
| 跨机房调用变慢 | 同机房优先策略 | 无感（延迟下降） |

**注意**：负载均衡层的重试必须是幂等的。这一点在抢票系统里尤其重要——重试造成的重复下单，比一次失败严重得多。

### 4.6 Sentinel（熔断限流）

#### 4.6.1 为什么需要它

两点，缺一不可：

- **抢票是脉冲流量**：开抢瞬间的请求量远超系统容量，必须限流，否则数据库先被打穿。
- **下游故障时要快速失败**：让请求快速失败，比让它长时间等待更有价值——快速失败释放线程，等待会耗尽线程。

#### 4.6.2 没有它会发生什么（故障场景）

这是本文档里最需要讲清楚的一段，因为它直接回答"限流到底有什么用"。

**没有限流时，开抢瞬间发生的事：**

```
1. 真实用户 + 脚本的请求同时到达，总量远超系统容量
2. 所有请求都进入 stock-service（因为没有入口限流）
3. Redis 连接池先被占满 → 后续请求开始排队
4. 数据库连接池被占满 → 排队加剧
5. 平均响应时间从 20ms 恶化到 20s
6. 用户看到页面转圈，不知道成没成功 → 手动重试、疯狂刷新
7. 流量再放大数倍
8. 系统彻底不可用，而且【流量不会自己退】，必须人工介入才能恢复
```

**注意第 3、4 步的关键特征：请求不是被拒绝，而是被挂起。** 这是最坏的失败模式。

**有限流时，同样场景：**

```
1. 容量内的请求正常进入，快速返回结果
2. 容量外的请求在入口处被拒绝，立即收到明确响应
3. 系统始终运行在容量范围内，不会进入排队恶化的正反馈
```

**核心价值**：限流**不增加系统吞吐量**，它改变的是失败的分布——把"所有人一起慢慢失败"变成"一部分人正常成功、一部分人快速明确失败"。这句话是限流存在的全部理由，面试里答出这句基本就够了。

#### 4.6.3 它到底怎么工作的

**架构**：Sentinel 是**客户端库**，统计和决策都在业务进程内完成，不依赖中心节点。Dashboard 只负责展示监控和下发规则。

**责任链（Slot Chain）**：每个受保护的资源被访问时，依次经过一串 Slot：

| Slot | 职责 |
| --- | --- |
| `NodeSelectorSlot` | 构建资源之间的调用树 |
| `ClusterBuilderSlot` | 建立统计维度（来源、入口等） |
| `StatisticSlot` | **滑动窗口统计**，记录 QPS、RT、异常数 |
| `FlowSlot` | 校验限流规则，决定是否放行 |
| `DegradeSlot` | 校验熔断规则，决定是否短路 |

**滑动窗口的实现**：用 `LeapArray`（时间轮式的滑动窗口，秒级分桶）。这决定了 Sentinel 限制的是"每秒的通过量"。理解这一点，才能理解为什么限流阈值要按 QPS 而不是按并发数来思考。

**限流的两个维度**：

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| 流控模式 | 直接 / 关联 / 链路 | 关联模式适合"两个资源争抢同一份资源"的场景（如读操作会挤占写操作时，限制读来保写） |
| 流控效果 | 快速失败 / Warm Up / 匀速排队 | Warm Up 用于冷启动预热（系统刚启动时缓存是空的，直接放全量流量会打穿）；匀速排队等价于漏桶，把尖峰削平，用户等待但最终成功 |

**熔断机制**：Sentinel 使用三种熔断策略（较新版本已用它们替代了旧的"平均 RT"策略）：

- 慢调用比例
- 异常比例
- 异常数

**断路器状态机**：

```
CLOSED（正常放行，持续统计）
   │ 统计指标超过阈值
   ▼
OPEN（熔断时长内，所有请求直接拒绝，不发起真实调用）
   │ 熔断时长到期
   ▼
HALF_OPEN（放少量探测请求通过）
   │ 探测成功 → 回到 CLOSED
   │ 探测失败 → 回到 OPEN
```

**规则持久化**：默认规则存在内存里，**重启即丢失**。生产上必须持久化到 Nacos 或本地文件。教学项目里如果只配 Dashboard 推送而不持久化，重启一次规则就没了，会出现"限流昨天还好用今天怎么没生效"的困惑。

#### 4.6.4 一个服务挂掉之后会发生什么

**Sentinel 客户端库在业务进程内，不存在"Sentinel 挂掉"这回事。**

真正需要关心的是 Dashboard 和规则源：

| 谁挂了 | 影响 |
| --- | --- |
| Sentinel Dashboard | 已下发的规则在客户端内存中继续生效，限流熔断照常工作。只是看不到实时监控、改不了规则 |
| Nacos（规则持久化源） | 客户端有本地缓存，规则继续生效（**具体缓存行为待验证**）。改不了规则 |
| 业务进程本身 | 这个进程的限流统计和规则一起消失；其它实例不受影响 |

**所以 Sentinel 的可用性风险很低**，它的价值在于"配置一次，长期有效"。这也意味着：**规则设计错误不会被自动纠正**，一条写错的规则可能长期存在并持续误伤流量。

#### 4.6.5 什么时候降级、降级后用户体验

**限流降级**：

- 快速失败：返回统一的限流响应，前端展示"当前抢票人数过多，请稍后再试"。
- **前端必须配合**：被限流后按钮禁用 3~5 秒。否则用户会连续点击，把限流拒绝的流量又放大一遍——限流反而成了流量放大器。
- 匀速排队：用户看到"排队中"，等待后成功。体验是"慢但成功"，适合库存扣减这类不能失败的场景。

**熔断降级**：

| 被熔断的下游 | 降级动作 | 用户体验 |
| --- | --- | --- |
| stock-service（查余票） | 返回缓存余票 + "余票信息可能有延迟" | 能看票，数据可能旧 |
| stock-service（扣减） | 快速失败 + 引导排队 | "当前排队人数过多" |
| ticket-service | 返回缓存车次列表 | 车次信息可能不全 |
| user-service | 令牌本地校验（不调远程） | 基本无感 |

**降级优先级必须提前定好，不能临时决定**。故障发生时没有人有时间开会讨论先关哪个功能：

| 优先级 | 功能 | 降级手段 |
| --- | --- | --- |
| 1（最高，保） | 库存扣减 / 下单 | 限流 + 匀速排队；**不降级为假成功** |
| 2（保） | 支付回调 | 不可降级（涉及资金） |
| 3 | 余票查询 | 缓存余票 + 延迟提示 |
| 4 | 车次详情 / 经停 | 缓存或返回"暂不可用" |
| 5（先关） | 历史订单、推荐、营销活动 | 直接关闭入口 |

**这张表的价值在于**：它把"降级"从一次临场决策变成一次事前设计。抢票系统在开抢那一刻是没有人能做决策的——所有决策必须在事前做完。

## 5. 网关限流 vs 服务限流：两道防线，不要只做一道

| | 网关限流 | 服务限流（Sentinel 客户端） |
| --- | --- | --- |
| 限流维度 | 按路由、按来源 IP、按请求头（用户标识） | 按资源（方法/接口）、按调用来源、按调用链路 |
| 优点 | 请求还没进内网就被挡掉，最省资源；能按 IP/用户维度限 | 能感知业务语义（如"扣减库存"这个资源）；能保护具体方法 |
| 缺点 | 感知不到业务语义，粒度粗 | 请求已经消耗了网关和网络资源才被拒 |
| 本项目用途 | 挡住未到时间的请求、挡住恶意 IP、按用户限流（防止单用户刷） | 保护库存扣减、保护慢查询接口、熔断下游 |

**两道都要做**，因为它们回答的是不同的问题：网关回答"这个请求配不配进来"，服务回答"这个资源还能不能承受"。

抢票场景的具体配置思路（**具体阈值待压测确定，不要拍脑袋填数字**）：

- 网关：按"用户标识 + 路由"限流，防止单个账号高频刷；按路由限流，限制总入口流量。
- 服务：库存扣减按 QPS 限流（保护 Redis/DB）；余票查询用匀速排队（可接受排队）；对下游 Feign 调用配熔断。

---

## 6. 熔断与限流的区别（高频面试点，必须分清）

| | 限流 | 熔断 |
| --- | --- | --- |
| 触发原因 | 进来的流量超过我设定的容量 | 我调用的下游出问题了 |
| 保护对象 | **保护自己**（不被过量请求打垮） | **保护自己不被下游拖垮**（快速失败，不占用资源等待） |
| 判断依据 | 当前 QPS / 并发数 | 下游的错误率、慢调用比例、异常数 |
| 恢复方式 | 流量降下来自动恢复 | 需要经过 HALF_OPEN 探测确认下游恢复 |
| 典型误用 | 阈值设得过高（等于没限）或过低（正常用户也被拒） | 熔断时长过短（下游还没恢复就又被打一次）或过长（下游恢复了流量还没回来） |

一句话区分：**限流是"我这边人太多了"，熔断是"下游那边坏了"。** 一个防内，一个防外。

## 7. 全局串联：stock-service 全部实例挂掉后的完整时间线

把前面六个组件串起来，看一次真实故障的完整演化。这是本文档最重要的一节。

**前提**：注册中心心跳窗口按"十几到几十秒"、LB 列表缓存按"几十秒"量级估算（**具体默认值待验证**）；已配置 Feign 超时与 Sentinel 熔断。

| 时刻 | 发生什么 | 涉及组件 | 用户看到什么 |
| --- | --- | --- | --- |
| t=0 | stock-service 所有实例进程崩溃 | — | 无异常 |
| t=0 ~ 数十秒 | 注册中心仍认为实例健康（心跳未超时），消费者继续选到已死实例 | Nacos 注册中心 | 部分请求失败（随机，轮询到坏实例时） |
| t=0 起 | 每次选到坏实例 → 连接被拒或等待连接超时（取决于超时配置） | Feign 超时配置 | 失败的请求在超时后返回错误 |
| t≈数十秒 | Nacos 判定不健康并剔除 → 推送变更 | Nacos 注册中心 | 失败率上升（因为实例列表在快速收缩） |
| t≈数十秒 ~ 更久 | 消费者本地 LB 缓存过期后刷新，列表中不再有 stock-service | LoadBalancer | 请求不再打向坏实例，但**全部失败**（没有可用实例） |
| t=熔断窗口内（如错误率超阈值） | Sentinel 熔断打开，调用**立即失败**，不再占用线程和连接 | Sentinel | 失败变成"瞬间返回"，不再是长时间等待 |
| 熔断打开后 | order-service 线程池恢复，非库存相关接口恢复正常 | Sentinel + Feign | 下单失败的响应变快；其它功能可用 |
| 熔断打开后 | 查票走缓存余票降级；下单走快速失败或排队降级 | 降级逻辑 | "余票信息可能有延迟" / "当前排队人数过多" |
| 恢复时刻 | stock-service 重启 → 注册到 Nacos → 消费者列表刷新 → HALF_OPEN 探测成功 → 熔断关闭 | 全部 | 服务恢复，流量回归 |

**从这条时间线里能提炼出的三条结论**：

1. **用户可感知的故障时长 = 注册中心感知延迟 + LB 缓存延迟 + 熔断开启时间**。三者叠加。想缩短，只有三条路：缩短超时、提前开启熔断、优雅停机。
2. **熔断的作用不是"避免失败"，而是"把慢失败变成快失败"**。故障期间失败是必然的，熔断改变的是失败的形式和代价。
3. **降级逻辑必须在故障发生前写好并测试过**。故障期间没有时间写降级代码；没测试过的降级代码在故障时大概率也是坏的（比如返回了假的成功）。

## 8. 替代方案总对比

| 关注点 | 本项目选择 | 替代方案 | 为什么不选 |
| --- | --- | --- | --- |
| 网关 | Spring Cloud Gateway | Zuul 1 | 基于 Servlet 的阻塞模型，一请求一线程，网关作为全站入口不适合这种模型；且已不是主流选择 |
| | | Nginx + Lua | 能力足够且更贴近生产（真实生产常在网关前再加一层 Nginx），但需要额外学习 Lua 与 OpenResty 体系；本项目要学的是 Java 侧的网关能力（断言、过滤器、与注册中心集成），用 Nginx 会绕开这些 |
| | | 不用网关 | 见 4.1.2 的四个故障场景 |
| 注册中心 | Nacos | Eureka | 已进入维护状态，社区活跃度低；且只有注册能力，没有配置中心 |
| | | Consul | 功能完整（注册 + KV + 健康检查），但在国内的使用与资料密度低于 Nacos，与学习目标（国内主流栈）不符 |
| | | Zookeeper | CP 模型，分区时不可写，新服务注册不上；对抢票这种"可用性优先"的场景不合适；且需要额外运维 ZK 集群 |
| 配置中心 | Nacos Config | Spring Cloud Config | 需要搭配 Git 仓库，配置变更的实时性依赖额外机制（Bus + MQ），链路更长 |
| | | Apollo | 功能强（权限、审计、灰度），但需要独立部署一整套服务，对教学项目偏重 |
| | | Consul KV | 可用，但不如 Nacos 的 namespace/group/dataId 分层贴合 Spring 的使用习惯 |
| 服务调用 | OpenFeign | RestTemplate 手写 | 见 4.4.2 |
| | | Dubbo | RPC 性能与生态都好，但需要引入另一套注册/协议体系；且本项目大量使用 HTTP 语义（幂等、状态码、Header 透传），HTTP 更自然 |
| | | gRPC | 需要 proto 编译流程，前后端联调与调试成本上升；教学项目收益不明显 |
| 负载均衡 | Spring Cloud LoadBalancer | Ribbon | 已进入维护状态，新项目不应使用 |
| | | Nginx 层负载 | 是服务端负载均衡，解决不了"客户端从注册中心感知实例变化"的问题，两者不是替代关系而是互补关系 |
| 熔断限流 | Sentinel | Hystrix | 已停止维护；且基于线程池隔离，模型比 Sentinel 的信号量/滑动窗口重 |
| | | Resilience4j | 是 Spring Cloud 官方推荐方向，与 Boot 版本兼容性更好；但缺少 Sentinel 的 Dashboard、Warm Up、匀速排队、关联/链路流控模式。**这是方案 2 降级路径的备选，若 SCA 版本不兼容则启用** |
| | | 自己写限流 | 滑动窗口、预热、熔断状态机的边界条件很多，自己写的版本在故障时通常不可靠 |

## 9. 后果

### 正面

- 六个组件各自解决一个明确问题，职责不重叠：网关管入口、注册中心管地址、配置中心管参数、Feign 管调用、LoadBalancer 管选实例、Sentinel 管保护。
- 每个组件都有明确的降级策略，且降级优先级被提前确定。
- 故障行为可推理：能回答"谁挂了、挂多久、用户看到什么"这三个问题。

### 负面（明确接受）

- 组件多，本地环境需要额外起 Nacos 与 Sentinel Dashboard，启动成本上升（具体内存占用待实测）。
- 版本组合存在不确定性（2.1 节），可能需要先做一次版本验证工作，甚至降级 Boot 版本。
- 组件本身的配置项很多，默认值大多不适合抢票场景（尤其是超时），需要逐项审查。**默认配置是危险的**——这是本节最需要记住的一句话。

### 需要长期遵守的约束

- 所有跨服务调用的超时必须显式配置，禁止依赖默认值。
- 所有降级逻辑必须有测试覆盖，不允许存在"未验证的降级代码"。
- 下单/扣减相关的重试必须幂等。
- 从配置中心读取的关键参数必须在代码中有保守默认值。
- 流控阈值必须来自压测，不允许凭感觉填写。
