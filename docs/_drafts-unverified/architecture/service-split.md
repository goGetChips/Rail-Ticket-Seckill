### 0.3 业务前提（本文所有推导的起点）

抢票系统与普通电商的区别，决定了拆分方式：

1. **有确定的开售时刻**。流量不是平缓的，是在开售那一秒从接近 0 跳到峰值。峰值持续短（秒级到分钟级），但绝对值高。这个形状意味着：系统的瓶颈是**写路径上的单点资源竞争**，不是功能复杂度。
2. **库存是强约束且不可为负**。票卖超了不能"事后补偿"，用户已经付款、已经上车。所以库存这条链路上不允许任何"先放行后校验"的降级。
3. **读多写少，且读可以容忍短暂陈旧**。车次、时刻、经停站属于低频变更数据，可以缓存；余票数字允许秒级陈旧（用户看到"有票"但下单失败是可接受的，反过来"显示无票但实际有票"也不影响正确性）。
4. **钱走第三方**。支付动作发生在外部渠道，回调是异步、可能重复、可能乱序的。

### 0.4 术语约定

| 术语 | 含义 |
|---|---|
| 库存 | 某车次 + 某乘车日期 + 某席别的可售数量 |
| 预扣 | 在 Redis 中先把数量减掉，DB 稍后异步落账 |
| 落账 | 把 Redis 的扣减结果写回数据库并留下流水 |
| 强依赖 | 被调方不可用时，调用方必须失败（不可降级放行） |
| 弱依赖 | 被调方不可用时，调用方可以继续（降级或延后） |
| 读模型 | 为查询专门准备的数据结构（缓存、ES 索引、宽表） |

## 1. 为什么需要拆：先定位瓶颈，再谈拆分

拆分不是目的。**先问"单体扛不住的地方具体在哪一行代码上"，再去决定边界落在哪里**。如果按"业务名词"拆（用户、车次、订单、支付），拆出来的往往是一堆共享同一个数据库的伪微服务。

本项目对单体形态做逐步推演，瓶颈按出现顺序排列：

| 顺序 | 单体下的具体问题 | 现象 | 指向的拆分动作 |
|---|---|---|---|
| 1 | 开售瞬间所有请求打同一个 JVM，Tomcat 线程池被打满 | 全站接口一起变慢，包括"查车次"这种跟抢票无关的接口 | 把查询流量和写入流量分开伸缩 |
| 2 | 库存扣减和订单创建在同一事务里，长事务持有行锁 | 数据库连接池被占满，慢 SQL 堆积，随后整个应用雪崩 | 把库存扣减独立出来，让它可以用非关系型手段承载 |
| 3 | 查询车次时 JOIN 库存表，抢票的写锁阻塞了查询 | 用户"刷新一下有没有票"把写路径拖慢 | 读写分离 + 读模型独立 |
| 4 | 发短信的代码在下单方法里同步调用 | 短信通道抖动几分钟，期间全站下不了单 | 非核心动作异步化，物理隔离 |
| 5 | 支付回调处理和订单超时取消写同一张订单表 | 状态互相覆盖，出现"已支付订单被取消" | 订单状态收敛到一个服务，状态迁移原子化 |
| 6 | 想给库存单独扩容，只能整个应用一起复制 | 扩容成本高，且扩容的是无用的查询代码 | 按服务独立伸缩 |

**关键判断**：单体真正的问题不是"代码乱"，而是**不同性质的负载被绑在同一个进程和同一个数据库连接池里，互相争抢，且无法独立伸缩**。所以拆分的主线是"按资源竞争特征和伸缩需求切"，而不是"按业务名词切"。

### 1.1 决策卡：为什么最终选择"中等粒度拆分"

**做了什么**：拆成 7 个服务（1 个网关 + 6 个业务服务），而不是保持单体，也不是拆成十几个。

**为什么这么做**：这个项目里只有一条链路真正需要独立伸缩（库存扣减），一条链路真正需要物理隔离（通知），一条链路真正需要状态收敛（订单）。其余部分（用户、车次）是低频变更的支撑数据，独立部署的价值低于它带来的运维和分布式事务成本。

**不这么做会出什么问题**：保持单体，则库存扣减的热点行锁会连带拖慢查询，且每次扩容都要复制全部代码；拆得过细，则一条下单链路要跨 5 个服务做分布式事务，正确性风险远大于性能收益 —— 在抢票场景下，**正确性风险是不可接受的**。

**对比的替代方案**：

| 方案 | 优点 | 缺点 | 是否选择 |
|---|---|---|---|
| 纯单体 + 加机器 | 无分布式事务，开发最快 | 热点行锁与查询互相拖累；无法独立伸缩；故障一起挂 | 否（作为 P0 阶段的过渡形态保留） |
| 粗拆 3 个服务（网关/交易/支撑） | 分布式事务少，边界简单 | 库存热点仍在交易服务内，与订单共享数据库，伸缩不彻底 | 否（但接近本项目的最小可用形态） |
| 本项目：7 服务中等粒度 | 热点链路可独立伸缩；故障可隔离；事务边界仍可控 | 需要处理跨服务最终一致性 | **是** |
| 细拆 12+ 服务（含独立秒杀、搜索、出票、风控） | 理论伸缩性最好 | 一条链路跨 5+ 服务，一致性成本高；教学项目里大部分服务没有独立伸缩的必要 | 否（作为十倍规模的演进目标，见第 7 章） |

## 2. 服务清单

端口是**本项目约定**（不是行业标准），统一使用 80xx 段，网关占 8080。

| 服务名 | 端口 | 职责 | 数据库 | 拥有的表 | 被谁调用 |
|---|---|---|---|---|---|
| `gateway` | 8080 | 统一入口：路由、登录态校验、限流、请求日志、灰度 | 无独立业务库（限流计数在 Redis） | — | 客户端；调用除 notify 外的全部下游 |
| `user-service` | 8081 | 注册登录、令牌签发校验、乘车人管理、实名信息 | `db_user` | `t_user`、`t_passenger`、`t_user_role` | gateway（校验令牌）、order-service（取乘车人快照） |
| `train-service` | 8082 | 车次、经停站、时刻、席别票价；余票**查询读模型**的构建者 | `db_train` | `t_train`、`t_train_station`、`t_seat_price`、`t_train_calendar` | gateway、order-service（校验车次与票价）、inventory-service（取席别定义） |
| `inventory-service` | 8083 | 库存预热、原子预扣、回滚、余额查询、库存流水 | `db_inventory` | `t_ticket_stock`、`t_stock_flow` | order-service（Feign 同步扣减/回滚）、MQ 消费者（异步落账） |
| `order-service` | 8084 | 下单编排、订单状态机、超时取消、出行凭证 | `db_order` | `t_order`、`t_order_item`、`t_order_status_log`、`t_local_message` | gateway、payment-service（回调经 MQ）、inventory 的回滚结果 |
| `payment-service` | 8085 | 支付单、渠道下单、回调验签、退款 | `db_payment` | `t_payment`、`t_payment_callback_log`、`t_refund` | gateway、order-service（发起支付/查支付结果） |
| `notify-service` | 8086 | 短信、推送、站内信；模板与发送记录 | `db_notify` | `t_notify_task`、`t_notify_template` | 只被 MQ 调用，没有任何服务同步调用它 |

配套的中间件（不属于服务，但决定了上面的调用方式）：

| 组件 | 用途 | 谁在用 |
|---|---|---|
| Redis | 库存预扣、余票缓存、限流计数、分布式锁 | gateway、train、inventory、order |
| 消息队列 | 异步解耦（本项目选型见 4.5） | order、payment、inventory、notify |
| 定时任务调度 | 库存预热、订单超时取消、对账 | inventory、order |
| 注册中心与配置中心 | 服务发现、动态配置 | 全部服务 |

### 2.1 调用关系图（文字版）

```
客户端
  │  HTTP
  ▼
gateway ──同步──▶ user-service       (令牌校验/乘车人)
  │    ──同步──▶ train-service      (车次与票价查询)
  ▼
order-service ──同步──▶ train-service     (下单前校验车次存在、票价一致)
  │           ──同步──▶ inventory-service (原子预扣，强依赖，失败即下单失败)
  │           ──同步──▶ payment-service   (创建支付单，返回收银台参数)
  │           ──异步──▶ MQ: order.created / order.cancelled / order.paid
  ▼
MQ ──▶ inventory-service (落账、超时回滚)
   ──▶ notify-service    (短信/推送)
   ──▶ 其他消费者        (统计、风控留痕)
payment-service ──异步──▶ MQ: payment.succeeded / payment.failed
```

**这张图里只有 5 条同步调用边**（gateway→user、gateway→train、order→train、order→inventory、order→payment）。其余全部异步。这个比例不是巧合，是第 4 章的判定标准推出来的结果。

## 3. 拆分的依据与逐服务论证

### 3.1 拆分依据（四个判据）

对每个候选服务问四个问题，只要有**一个**是"是"，且合并成本可控，就值得独立：

| 判据 | 含义 | 对应本项目 |
|---|---|---|
| 伸缩特征是否不同 | 需要的实例数、CPU/IO 比例是否和别的模块差很多 | inventory（写密集、热点）与 train（读密集、可缓存）差异极大 |
| 故障影响面是否应被限制 | 它挂了是否应该拖垮主链路 | notify 挂了绝不该影响下单 |
| 数据所有权是否清晰 | 数据是否有唯一写入方 | 库存只有 inventory 能写，其他人只能读 |
| 变更频率是否不同 | 发版节奏是否互相牵制 | train 的数据模型受业务规则影响，变更频繁；user 很稳定 |

### 3.2 逐服务论证（决策卡格式）

#### 决策卡 A：`inventory-service` 独立

- **做了什么**：把"库存"从订单里彻底剥离，成为唯一能修改库存的服务，且库存的扣减动作主要发生在 Redis 而不是数据库。
- **为什么这么做**：库存是全局唯一的热点资源。独立后它可以：单独扩容实例；单独使用 Redis 这种非关系型手段承载原子扣减；单独做预热和限流，不影响查询链路。
- **不这么做会出什么问题**：库存扣减与订单写在同一个库，扣减的行锁会与订单的插入争抢同一个连接池与同一个 buffer pool，查询余票的请求也会被写锁挡住。开售瞬间表现为"整个服务一起慢"，而且加机器无效（热点在单行）。
- **替代方案与取舍**：

| 方案 | 说明 | 为什么不选 |
|---|---|---|
| 库存留在 order-service 内 | 少一个服务，无跨服务调用 | 热点写与订单状态写共享资源，无法独立伸缩 |
| 库存放数据库 + 悲观锁 `SELECT ... FOR UPDATE` | 一致性最直观 | 热点行上锁排队，连接被长时间占用，**待压测**确认具体拐点，但方向上是本项目要避免的 |
| 库存放数据库 + 乐观锁版本号 | 无长事务 | 热点行冲突率极高时重试风暴，重试本身又放大流量 |
| 库存放 Redis + Lua 原子扣减（本项目） | 脚本在 Redis 中单线程执行，"读—判断—减"天然串行化；单次扣减的网络往返通常远小于一次数据库写事务（具体差距**待压测**） | 需要处理"缓存与数据库最终一致"与"预扣后未落单"的补偿，见风险 R1/R2/R3 |

#### 决策卡 B：`order-service` 独立且独占状态机

- **做了什么**：订单的**所有**状态迁移（创建、支付成功、取消、退款）都只能通过 order-service 的接口完成，其他服务不允许写订单表。
- **为什么这么做**：订单状态是"钱"的账本。支付回调（外部触发，可能乱序重复）与超时取消（内部定时触发）天然并发，必须由一个服务用条件更新统一裁决，否则必然出现"已支付订单被取消"。
- **不这么做会出什么问题**：如果 payment-service 收到回调后直接更新订单表的状态字段，那么它与超时取消任务之间存在竞态：两者都读到 `CREATED`，一个改成 `PAID`，一个改成 `CANCELLED`，后写覆盖先写，用户付了钱订单没了。
- **替代方案与取舍**：

| 方案 | 为什么不选 |
|---|---|
| 支付回调直接更新订单表 | 两个写入方并发覆盖，无法用条件更新保证正确性 |
| 用分布式事务协调状态变更 | 跨服务 2PC 在抢票场景下协调器本身成为瓶颈与单点 |
| 状态迁移收敛在 order-service，用 `WHERE status = 期望前态` 的条件更新（本项目） | 单条 SQL 的原子性即可裁决并发，谁先成功谁生效，另一方影响行数为 0 后走补偿分支 |

#### 决策卡 C：`payment-service` 独立

- **做了什么**：支付单、渠道交互、回调验签、退款独立成服务。
- **为什么这么做**：它是唯一与外部系统打交道的服务，外部系统的超时、抖动、签名规则变更都只应影响它自己。
- **不这么做会出什么问题**：渠道回调慢会把 order-service 的工作线程占住，连带影响下单。且渠道的签名密钥会扩散到多个服务，安全面变大。
- **替代方案与取舍**：把支付放进 order-service（省一次 RPC，但外部依赖与内部逻辑耦合，扩容时被迫一起扩容）；引入独立"支付网关/渠道路由层"（本项目只有单一渠道，属于过度设计，十倍规模时再考虑，见 7.2）。

#### 决策卡 D：`train-service` 独立

- **做了什么**：车次基础数据与查询读模型独立，对外提供"查车次、查经停、查票价"。
- **为什么这么做**：读多写少，可以长时间缓存；写路径（调图、票价调整）与交易路径完全无关，发版互不影响。
- **不这么做会出什么问题**：车次数据变更（例如加开临客）要发布订单服务，风险不对等 —— 改一个静态数据的发布导致交易服务重启。
- **替代方案与取舍**：把车次作为 order 的一部分（会导致订单服务持有大量低频读数据，缓存与伸缩策略被污染）；单独再做 `search-service` 用搜索引擎（本项目数据量下不必要，十倍规模时拆，见 7.2）。

#### 决策卡 E：`user-service` 独立，且**不**再拆出 `auth-service`

- **做了什么**：注册登录与用户资料、乘车人放在一起。
- **为什么这么做**：认证和用户资料共享同一份数据（用户凭证、状态、角色），且令牌校验是**每个请求都要做**的高频只读操作，它需要的是"快"，不需要"独立伸缩"。
- **不这么做会出什么问题**：拆出 auth 后，gateway 校验令牌要调 auth，取乘车人要调 user，两个服务都要访问用户表 —— **一张表两个写入方**，这是微服务里最典型的错误边界。
- **替代方案与取舍**：独立认证中心（在有多端、多租户、SSO 需求时才值得，本项目没有）；无状态 JWT 完全不查库（本项目选用，见 4.6，代价是吊销需要额外机制）。

#### 决策卡 F：`notify-service` 独立，且**只**被 MQ 调用

- **做了什么**：通知服务没有任何同步调用入口，全部消费 MQ 消息。
- **为什么这么做**：这是纯粹的弱依赖。它在物理上就无法阻塞主链路 —— 因为调用它的路径根本不存在。
- **不这么做会出什么问题**：短信通道的超时（外部不可控）会直接变成下单接口的 P99 抖动。哪怕加了熔断，也只是"少挂一点"，不如从调用关系上消除这个可能性。
- **替代方案与取舍**：在本服务内用线程池异步发短信（进程内异步，实例重启会丢消息，且与业务争抢线程资源）；用 `@Async` + 内存队列（同上，无持久化）。

#### 决策卡 G：`gateway` 独立

- **做了什么**：所有客户端流量先经过网关，在网关完成路由、令牌校验、全局限流、请求日志。
- **为什么这么做**：限流应该在**流量进入系统之前**生效。如果限流逻辑散落在各服务里，那么被限流的请求已经消耗了网关、负载均衡、连接建立的资源。
- **不这么做会出什么问题**：每个服务各自实现限流，规则不一致、无法做全局限额，且每个服务都要重复实现鉴权。
- **替代方案与取舍**：在 Nginx/负载均衡层做（适合粗粒度 IP 限流，做不了基于用户维度的业务限流）；不做网关直连服务（客户端需要感知所有服务地址，服务拆分对客户端不再透明）。

### 3.3 为什么不拆更多：合并决策

面试里"为什么不拆更多"比"为什么拆"更能体现判断力。以下每一个"不拆"都有明确理由。

| 候选服务 | 是否拆 | 理由 |
|---|---|---|
| `seckill-service`（抢票单独成服务） | **不拆**，抢票编排放在 order-service | "抢票"本质是"扣库存 + 建订单"的编排，它不拥有任何数据。拆出去以后，一次抢票要跨 order、seckill、inventory 三个服务做一致性，而其中两个服务都只是"转发"。**没有数据所有权的服务不值得存在**。 |
| `auth-service` | **不拆**，与 user-service 合并 | 见决策卡 E。拆分会造成用户表两个写入方。 |
| `search-service`（ES 车次搜索） | **暂不拆** | 当前查询用关系库 + 缓存即可覆盖。ES 的价值在复杂检索（多条件、模糊、排序组合），抢票场景的查询条件高度确定（出发地、目的地、日期）。十倍规模时再拆，见 7.2。 |
| `ticket-service`（出票/凭证） | **不拆**，并入 order-service | 出行凭证与订单是同一份数据的不同视图，1:1 关系，无独立伸缩需求。 |
| `refund-service`（退款） | **不拆**，并入 payment-service | 退款是支付单的逆向操作，共享渠道适配与对账逻辑。 |
| `stock-query-service`（余票查询） | **不拆**，查询归 train-service，扣减归 inventory-service | 这是本设计里唯一容易搞混的边界：**读余票走 train-service 的读模型，扣减走 inventory-service**。理由见下。 |
| `admin-service` / `audit-service` / `log-service` | **不拆** | 后台管理是低频功能，独立部署收益低；审计与日志先落库表，需要时再接采集组件。 |
| `risk-service`（风控） | **不拆**，先以拦截规则内嵌在 gateway | 风控需要数据积累才有价值，早期拆分只会得到一个"什么都拦不住"的空服务。 |

#### 关于"余票查询"与"库存扣减"分属两个服务的补充说明

这是本设计中唯一需要额外解释的边界：

- 用户看到的"余票 X 张"是**读模型**，可以被缓存、可以有秒级陈旧、可以在 Redis 或本地缓存里，它服务于"展示"。
- 扣减用的库存是**权威数据**，只有 inventory-service 能改，它服务于"正确性"。
- 两者的关系是：读模型由 inventory-service 的扣减结果**异步投影**而来（通过 MQ 或定时同步），**读模型永远不参与扣减决策**。

**不这样分的后果**：如果让 train-service 用自己缓存的余票数去做"看起来还有票就放行"，那缓存陈旧就会直接变成超卖。**读模型只能用来展示，不能用来裁决**。

#### 反模式说明：为什么不"一表一服务"

初学者常见的拆法是把每个实体拆成一个服务（用户服务、乘车人服务、席别服务、站点服务）。这会得到十几个"纳米服务"，每个都只有 CRUD，最终：

- 一次"查询某车次的经停站与票价"要跨 3 个服务，网络开销远大于查询本身；
- 每个服务都要自己实现鉴权、限流、日志，重复代码膨胀；
- 事务边界被打碎，任何一次组合写入都变成分布式事务。

**判据**：服务边界应该对齐"事务边界 + 数据所有权 + 伸缩特征"，而不是对齐"数据库表的数量"。

## 4. 服务间调用方式：同步（OpenFeign）还是异步（MQ）

### 4.1 判定标准（决策清单）

对每一条调用边，按顺序问下面 5 个问题，**第一个回答"是"的选项即为结论**：

| 顺序 | 问题 | 选它则用 |
|---|---|---|
| 1 | 调用方是否必须在本响应内拿到结果才能继续（用户要立刻知道成败）？ | **同步** |
| 2 | 被调方不可用时，调用方是否必须失败（不能降级放行）？ | **同步** |
| 3 | 这次调用是否会修改调用方之外的数据，且允许延迟生效？ | **异步** |
| 4 | 被调方是否是弱依赖（挂了不影响主流程正确性）？ | **异步** |
| 5 | 这次调用的结果是否会被多个下游消费（一对多）？ | **异步** |

**核心原则**：**同步调用传递"必要性"，异步消息传递"事实"。** 需要对方现在就回答的用同步；只是通知对方"这件事已经发生了"的用异步。

### 4.2 逐条调用边

| 调用方 → 被调方 | 方式 | 同步/异步 | 为什么 | 不可用时怎么办 |
|---|---|---|---|---|
| gateway → user-service | OpenFeign | 同步 | 必须立刻判断令牌有效性，否则无法决定是否放行 | 拒绝请求（401/503），不能放行未鉴权流量 |
| gateway → train-service | OpenFeign | 同步 | 查询结果要立刻返回给用户 | 走网关本地缓存兜底，仍失败则返回"查询繁忙" |
| order → train-service | OpenFeign | 同步 | 下单前必须确认车次存在、席别有效、**票价与用户看到的一致**（防篡改） | 拒绝下单。**不能用缓存放行** —— 票价是钱的依据 |
| order → inventory-service | OpenFeign | 同步 | 强依赖：必须立刻知道"扣到了没有"，否则无法给用户确定结果，也无法决定是否继续 | 拒绝下单（快速失败）。**绝不允许降级为"先记单、后扣减"**，那等于放弃防超卖 |
| order → payment-service | OpenFeign | 同步 | 需要拿到渠道收银台参数（支付单号、跳转信息）才能返回给用户 | 拒绝创建支付单，订单停留在"待支付"，用户可稍后重试 |
| payment → MQ: `payment.succeeded` | MQ | 异步 | 渠道回调的时间点不可控；且"支付成功"要同时驱动订单状态推进、通知、统计，是一对多 | 消息堆积，恢复后重放；订单保持待支付，**不能由渠道重试来驱动业务** |
| order → MQ: `order.created` | MQ | 异步 | 通知、统计、埋点都不需要在响应内完成 | 堆积，主链路无感 |
| order → MQ: `order.cancelled`（驱动库存回滚） | MQ | 异步 | 回滚可以延迟生效，但它**必须最终发生**，所以要有重试与对账兜底 | 堆积；库存被多占，属于"少卖"，由对账任务发现，见 R2 |
| inventory → MQ: `stock.deducted`（落账/投影读模型） | MQ | 异步 | 扣减已经在 Redis 完成，DB 落账是"记账"，可以延迟 | 堆积；Redis 是权威，DB 落后；由对账任务校验 |
| 任意 → inventory（读余票） | OpenFeign | 同步 | 展示需要立刻返回 | 返回缓存的余票数字，可标注"仅供参考" |

### 4.3 为什么主链路（下单）坚持同步

- **做了什么**：`order → inventory` 的预扣用 OpenFeign 同步调用，超时即失败，不做"稍后重试扣减"。
- **为什么这么做**：抢票场景下用户必须立刻知道结果。更重要的是，**库存是这个系统里唯一不能事后补救的资源** —— 如果先返回"抢到了"再异步扣减，扣减失败时只能反过来取消订单，用户体验与系统复杂度都更差。
- **不这么做会出什么问题**：异步扣减 + 立即返回成功 = 系统会在库存耗尽时仍然给出大量"抢到了"，随后批量取消。这在抢票场景里是重大事故（用户可能已经安排行程）。
- **替代方案与取舍**：

| 方案 | 优点 | 缺点 | 是否选择 |
|---|---|---|---|
| 全异步下单（收到请求即返回"排队中"，结果靠轮询/推送） | 接入层不需要在峰值内完成扣减，削峰效果最好 | 需要排队与结果查询机制，用户认知成本高；且**排队本身仍需要一个串行化的扣减点**，并没有消除热点，只是把它挪到了队列消费者 | 否（本项目不引入排队层；这是更大流量的路线，见 7.2） |
| 同步扣减 + 快速失败（本项目） | 语义清晰，用户立刻得到确定结果 | 库存服务成为下单链路的强依赖，必须重点保障 | **是** |
| 同步扣减 + 失败重试 | 减少因瞬时抖动导致的失败 | 重试会放大热点流量，且重试期间的"待定"状态需要额外状态机 | 否（只允许对**幂等**的扣减在同一请求内做有限次重试，参数待压测） |

### 4.4 为什么这些动作必须异步

| 动作 | 如果同步做会怎样 |
|---|---|
| 发短信 / 推送 | 外部通道抖动直接变成下单接口抖动；通道限流时还会反向压垮线程池 |
| 写统计/埋点 | 与交易争抢数据库；统计表写入量大，容易引发锁等待 |
| 余票读模型投影 | 每次扣减都同步刷新所有缓存与索引，扣减耗时被放大数倍 |
| 超时未支付回滚 | 本身就是定时触发的延迟动作，没有同步的调用方 |
| 支付结果驱动的后续动作 | 渠道回调的线程不应承载业务逻辑，回调只做"验签 + 发消息 + 立刻应答"，否则渠道会因超时而重试，产生重复回调 |

**异步的代价必须写清楚**（否则就是只讲好处）：引入 MQ 后你会得到三个新问题 —— 消息可能重复（要做消费幂等，见 R8）、消息可能丢失（要做本地消息表与重试，见 R9）、消息可能乱序（要用状态机兜住，见 R12）。**异步不是免费的，它把"分布式一致性问题"从调用时推迟到了消费时**。

### 4.5 MQ 选型对比

本项目选型时对比过三种主流消息中间件：

| 维度 | 本项目关注点 | Kafka | RabbitMQ | RocketMQ |
|---|---|---|---|---|
| 顺序消息 | 同一订单的状态变更需要局部有序 | 分区内有序，需自建分区键约定 | 队列内有序，需单消费者 | 支持消息组顺序，语义直接 |
| 事务/半消息 | 本地消息表的替代表达方式 | 支持事务消息但语义偏流处理 | 需靠 publisher confirm + 手工补偿 | 提供事务消息语义，贴合"本地事务 + 发消息"这一模式 |
| 延迟消息 | 订单超时取消需要延迟触发 | 需自建时间轮或外部调度 | 需插件支持 | 原生支持延迟级别 |
| 消息重试与死信 | 回滚类消息必须能重试到成功 | 需自行实现 | 支持 | 支持，且重试队列语义清晰 |
| 运维复杂度 | 教学项目要能本地跑起来 | 依赖较重 | 轻 | 中等 |

**结论**：本项目按"顺序 + 延迟 + 重试"三项需求选择 RocketMQ 这一路线。**待验证**：具体版本的延迟级别粒度是否满足订单超时精度要求；若不满足，改为"延迟消息只做粗粒度唤醒 + 数据库扫描精确到期"，即延迟消息仅作为触发器，真正的到期判断以订单表的超时时间为准（这个兜底设计无论如何都要有，见 R2）。

### 4.6 Feign 调用的工程约束

同步调用必须显式设置四件事，否则默认配置会在故障时放大问题：

| 约束 | 做法 | 不做的后果 |
|---|---|---|
| 超时 | 连接超时与读超时都要设置，且读超时要小于上游（gateway）的超时 | 默认超时可能极长，线程被挂住的请求堆积，最终线程池耗尽 |
| 重试 | **只对幂等的 GET 类调用开启重试**；扣减类 POST 默认不重试，或由业务层用幂等键重试 | 超时后自动重试会在"实际已成功但响应丢失"时造成重复扣减 |
| 熔断/隔离 | 对 inventory、train 分别配置熔断与线程池隔离，避免一个下游拖垮所有下游 | 一个慢下游占满共享线程池，导致其他正常下游也调不通 |
| 降级 | 明确每个调用的降级行为（拒绝 / 走缓存 / 排队），且**降级行为必须写进代码而不是文档** | 故障时靠人临时决策，容易做出"放行"这种错误降级 |

**特别强调**：`order → inventory` 这条边的降级行为是"拒绝下单"，任何把它改成"放行"的改动都是超卖事故的根因。这条约束在 [高并发风险清单](./high-concurrency-risks.md) 的 R1 里会从数据层面再兜一次底。

## 5. 数据库划分

### 5.1 划分原则

1. **一个服务一个库（schema）**，服务只连自己的库。
2. **一个数据只有一个写入方**。其他服务想要数据，要么调接口，要么订阅消息，要么在本地冗余一份快照。
3. **禁止跨库 JOIN，禁止跨库事务**。跨库 JOIN 在物理上不可行（不同实例/不同连接），跨库事务在抢票场景下不可接受（协调器成本与单点）。
4. **冗余是有意的，但只冗余"不会变"或"变了也不影响正确性"的字段**。

### 5.2 表归属

| 库 | 表 | 写入方 | 说明 |
|---|---|---|---|
| `db_user` | `t_user` | user-service | 账号、凭证、状态 |
| `db_user` | `t_passenger` | user-service | 乘车人，下单时被 order 读取并**快照** |
| `db_train` | `t_train` / `t_train_station` / `t_seat_price` | train-service | 车次、经停、票价定义 |
| `db_train` | `t_train_calendar` | train-service | 开行日历（哪些日期开行） |
| `db_inventory` | `t_ticket_stock` | inventory-service | 权威库存：总量与已售量 |
| `db_inventory` | `t_stock_flow` | inventory-service | 每一次扣减/回滚的流水，用于对账 |
| `db_order` | `t_order` / `t_order_item` | order-service | 订单主表与明细 |
| `db_order` | `t_order_status_log` | order-service | 状态迁移日志，排查"订单为什么变成这样" |
| `db_order` | `t_local_message` | order-service | 本地消息表，保证"改状态"和"发消息"原子 |
| `db_payment` | `t_payment` | payment-service | 支付单 |
| `db_payment` | `t_payment_callback_log` | payment-service | 渠道回调原文留痕，用于对账与纠纷 |
| `db_payment` | `t_refund` | payment-service | 退款单 |
| `db_notify` | `t_notify_task` / `t_notify_template` | notify-service | 通知任务与模板 |

### 5.3 哪些数据不能跨服务直接访问（含具体反例）

**规则**：任何服务都不得读取或写入非自己库中的表。特别地，**交易链路中的三个库（order、inventory、payment）之间完全隔离**。

#### 反例推演：如果 `order-service` 直接 JOIN 了 `train` 的表，会发生什么

假设 order-service 为了"少一次 RPC"，在自己的 Mapper 里写了这样的 SQL：

```sql
-- 反面示例，禁止这样写
SELECT o.*, t.train_no, t.depart_time, s.price
  FROM t_order o
  JOIN db_train.t_train t ON t.id = o.train_id
  JOIN db_train.t_seat_price s ON s.train_id = t.id AND s.seat_type = o.seat_type
 WHERE o.user_id = ?
```

按严重程度从高到低，会依次发生：

1. **数据库账号与网络权限被迫打通**。order-service 需要 train 库的读权限，两个库的连接信息进入同一个配置文件。此后"删库/改库"的爆炸半径不再可控 —— 一次误操作影响两个服务的所有数据。
2. **train 的表结构变更会直接打挂订单查询**。train-service 把票价字段改名或拆表，order-service 的 SQL 在编译期不会报错（跨库 SQL 没有编译校验），只会在**线上运行时**抛异常。发布顺序被强行绑定：必须同时发版，微服务的独立发布能力当场失效。
3. **失去独立扩容能力**。订单纯查询的压力会打到 train 库上。抢票时订单量最大，train 库（本可以只服务查询、甚至只读副本）被拖慢，**查询车次也一起变慢** —— 这正是第 1 章里"查询被写入拖累"的问题，绕了一圈又回来了。
4. **无法做数据迁移与分片**。order 想按 `user_id` 分片，train 想按 `train_id` 分片，跨库 JOIN 让两者不可能各自独立分片。
5. **读到了不该读的状态**。订单要展示"下单时的票价"，JOIN 拿到的是**当前**票价。票价调整后，历史订单显示的价格会跟着变 —— 用户看到的金额和支付金额不一致，直接产生纠纷。**正确的做法是下单时把票价、车次号、出发到达时间快照进 `t_order_item`**。
6. **缓存与限流策略相互污染**。JOIN 的结果集无法被 order 单独缓存（它混合了两个服务的生命周期），也无法只给 train 侧加限流。

**结论**：跨库 JOIN 省下的是一次网络往返，付出的是**部署独立性、故障隔离、可迁移性、数据正确性**四项成本。这在本项目里是明确不划算的。

#### 其他禁止事项

| 禁止 | 反例 | 正确做法 |
|---|---|---|
| 直接读别人的表 | payment-service 直接查 `db_order.t_order` 判断订单金额 | 由 order-service 通过接口/消息传递订单金额，或冗余快照 |
| 直接写别人的表 | payment-service 回调里直接 `UPDATE db_order.t_order SET status='PAID'` | payment 发消息，order 自己用状态机更新（决策卡 B） |
| 跨库事务 | 用 XA/2PC 同时提交订单与库存 | 本地消息表 + 最终一致 + 对账兜底（见 5.5） |
| 共享一个库的不同表 | 所有服务连一个库，只分表前缀 | 一服务一库，物理隔离连接与权限 |

### 5.4 允许的冗余：快照 vs 引用

冗余不可避免（订单必须记住下单时看到的信息），但要对冗余分类处理：

| 冗余类型 | 例子 | 一致性要求 | 保证方式 |
|---|---|---|---|
| **快照**（写时固化，此后永不更新） | `t_order_item` 里的车次号、出发到达时刻、**下单时票价**、乘车人姓名与证件号 | 不需要与源数据一致，它就是历史事实 | 下单时从 train/user 取回后一次性写入 |
| **展示用副本**（可陈旧） | 订单列表里显示的车次当前状态（如"晚点"） | 允许秒级陈旧 | 查询时实时调用 train-service，或由消息更新副本 |
| **计数/聚合**（可重建） | 某车次已售数量 | 允许最终一致 | 由 `t_stock_flow` 流水重算，对账任务校验 |
| **权威数据**（不可冗余） | 库存余额、订单状态、支付单状态 | 强一致，唯一写入方 | **不允许冗余到别的服务作为决策依据** |

**关键判据**：冗余字段如果被用来**做决策**（例如拿冗余的余票数字判断能不能下单），它就不再是副本而是权威数据 —— 这就是超卖的入口。冗余只能用于**展示**。

### 5.5 分布式一致性策略：不用 2PC，用本地消息表 + 对账

**做了什么**：跨服务的数据一致性采用"本地事务 + 本地消息表 + 异步投递 + 消费幂等 + 定时对账"。

**为什么这么做**：抢票链路对可用性的要求高于强一致。用 2PC/XA 会让协调者成为单点与瓶颈（协调期间资源被锁定，热点行锁被拉长到跨服务），而且多数消息中间件与 NoSQL（Redis）根本不参与 XA。

**不这么做会出什么问题**：要么放弃一致性（出现"扣了库存没有订单"却无人发现），要么用 2PC 让系统在开售峰值下更容易整体不可用。

**替代方案与取舍**：

| 方案 | 为什么不选 |
|---|---|
| XA / 2PC | 协调器单点、锁持有时间长、Redis 不参与、性能与可用性代价过高 |
| TCC（Try-Confirm-Cancel） | 需要为每个参与者写三套接口与幂等逻辑，本项目参与方少且补偿逻辑简单，成本收益不匹配 |
| Saga（长事务编排） | 适合流程长、步骤多的场景；本项目下单链路只有 2 个写操作，杀鸡用牛刀 |
| 本地消息表 + 最终一致 + 对账（本项目） | 实现简单、无协调者、失败可重试、差异可被发现（对账是最后一道防线） |

**本地消息表的工作方式**（说明为什么它能解决"状态改了但消息没发出去"）：

```
BEGIN;
  UPDATE t_order SET status='CANCELLED' WHERE order_no=? AND status='CREATED';
  INSERT INTO t_local_message(msg_id, topic, payload, status) VALUES (...,'PENDING');
COMMIT;                                   -- 两者同库同事务，要么都成，要么都不成
-- 独立线程扫描 t_local_message 中 PENDING 的记录并投递到 MQ，
-- 投递成功置 SENT；投递失败保留 PENDING 下轮重试（消息带 msg_id 供消费端幂等）
```

这条链路保证的是**至少一次投递**，所以消费端必须幂等（见 [高并发风险清单](./high-concurrency-risks.md) R8）。它**不能**保证不重复，也不保证实时 —— 这正是需要"对账任务"的原因：**任何最终一致方案都必须配一个能发现差异的机制，否则差异会永远存在且无人知晓**。

## 6. 服务容错：各服务挂掉之后会怎样

### 6.1 依赖强弱分级

设计容错的第一步是把依赖分成两类，并且**写死在代码里**：

| 分级 | 定义 | 本项目中的依赖 | 默认行为 |
|---|---|---|---|
| 强依赖 | 不可用则业务必须失败 | order→inventory（扣减）、gateway→user（鉴权）、order→train（票价校验） | 快速失败，明确报错 |
| 弱依赖 | 不可用则降级或延后 | gateway→train（查询）、order→payment（创建支付单）、所有 MQ 通知类 | 走缓存/延后/静默丢弃 |

### 6.2 逐服务故障表现

| 挂掉的服务 | 用户可见表现 | 主链路是否中断 | 降级/恢复动作 | 数据是否会不一致 |
|---|---|---|---|---|
| `gateway` | 全站不可访问 | **是（全站）** | 多实例 + 负载均衡；客户端重试；静态降级页 | 否 |
| `user-service` | 无法登录/注册；令牌校验失败 | 已登录用户若用无状态令牌可继续查询，下单涉及乘车人时失败 | 令牌本地校验不查库（见下）；乘车人信息在下单时通过快照传入，避免运行时强依赖 | 否 |
| `train-service` | 车次查询报错或返回陈旧数据 | 查询降级可用；**下单必须失败**（票价校验不可跳过） | 网关/order 侧本地缓存兜底展示；开售前的车次与库存已预热，可短时撑住 | 否（拒绝下单不会有脏数据） |
| `inventory-service` | 所有下单失败，报"系统繁忙" | **是（交易中断）** | **不做业务降级**，只做快速失败与告警；已预扣但未落账的库存靠 Redis 中的预扣记录与超时回滚兜住 | 可能出现"少卖"，由对账发现（R2） |
| `order-service` | 无法下单、无法查看订单 | **是** | 支付回调消息在 MQ 堆积，恢复后重放；定时取消任务恢复后补跑 | 否（消息可重放，状态机幂等） |
| `payment-service` | 无法发起支付；已支付用户的订单状态不推进 | 下单可成功，支付环节中断 | 渠道回调消息堆积；**必须按渠道对账文件补单** —— 渠道不会因为你挂了就重发 | 可能出现"用户已付钱但订单仍是待支付"，由渠道对账修复（R14） |
| `notify-service` | 收不到短信/推送 | **否** | 消息堆积，恢复后消费；对已过期的通知（如"开售提醒"）直接丢弃 | 否 |
| MQ 集群 | 所有异步链路中断；同步下单仍可完成 | 部分（同步链路可用） | 本地消息表持续累积 PENDING，恢复后补投；**注意**：若 MQ 长时间不可用，本地消息表会膨胀，需要监控与告警 | 短期内会积累大量待补偿动作，恢复后需观察对账结果 |
| Redis | 库存预扣不可用 → 下单全失败 | **是（交易中断）** | 不退化为"直接查库扣减"作为默认行为（会把数据库打死），只允许人工开关切换；见下 | 否，但可用性受损 |
| 数据库（某服务自己的） | 该服务全部接口失败 | 该服务对应能力中断 | 只读能力可走从库；写能力不可用 | 否 |

### 6.3 三个必须写清楚的容错判断

#### 判断一：`inventory-service` 挂掉时，**绝不降级放行**

| 方案 | 结果 | 选择 |
|---|---|---|
| 拒绝所有下单，返回"系统繁忙" | 用户没抢到，但系统数据正确 | **是** |
| 降级为"先记录下单意向，库存恢复后扣减" | 库存恢复后大量扣减失败，用户从"抢到了"变"没抢到"，且此期间的订单数可能远超库存 | 否 |
| 降级为"直接查数据库扣减" | 热点行锁 + 连接池被打满，把数据库拖垮，**故障范围从库存服务扩大到整个数据库** | 否（只保留人工开关，且要限流） |

**记忆点**：**库存服务是"宁可不可用，不可不正确"的服务。**

#### 判断二：`gateway` 的令牌校验不能每次都同步查 user-service

如果每个请求都同步调 user-service 校验令牌，那么：

- user-service 成为全站单点，它一挂全站不可用；
- 每个请求多一次 RPC，网关吞吐被这个调用限制。

做法：使用**无状态令牌**（在网关本地用密钥验签并解析出用户与角色），只有"需要用户详细资料"的接口才同步调 user-service。代价是令牌吊销不能立刻生效 —— 需要在 Redis 里维护一个吊销名单（按令牌 ID），网关验签后查一次 Redis（本地缓存 + 短 TTL）。**这是一个有意的取舍：用"吊销延迟"换"全站可用性"，延迟窗口的具体取值待压测后按业务容忍度确定。**

#### 判断三：熔断与隔离的粒度

| 方案 | 说明 | 取舍 |
|---|---|---|
| 每个下游一个独立线程池（线程池隔离） | 一个下游变慢只占满自己的池 | 线程资源开销大，适合慢且不可控的下游（payment 调渠道） |
| 信号量隔离 | 只限制并发数，无线程切换开销 | 适合快且可控的下游（Redis 相关） |
| 不隔离 | 实现最简单 | 一个慢下游占满共享池，**其他正常下游一起不可用**，本项目明确不采用 |

**待压测**：各下游的超时时间、熔断阈值、隔离方式的并发上限，都需要在压测中按"故障注入"的方式确定，本文不给出具体数值。

### 6.4 容错总结表

| 服务 | 强/弱依赖 | 挂掉时主链路 | 是否允许业务降级 |
|---|---|---|---|
| gateway | 强 | 全站中断 | 否 |
| user | 强（鉴权）/ 弱（资料） | 部分 | 令牌本地校验 |
| train | 弱（查询）/ 强（下单校验） | 查询可用，下单失败 | 查询可降级，校验不可 |
| inventory | 强 | 交易中断 | **绝不降级** |
| order | 强 | 交易中断 | 否 |
| payment | 强（发起支付）/ 弱（回调推进） | 支付中断 | 回调靠渠道对账补 |
| notify | 弱 | 不中断 | 可丢弃过期消息 |

## 7. 规模扩大十倍后的演进路径

### 7.1 演进原则

1. **只有出现可观测的瓶颈才演进**，不预先做分片。每一阶段都写清楚触发条件，触发条件靠压测与监控数据判定，**本文不给数值，因为没实测过**。
2. **每次演进都要保留回滚路径**。
3. **正确性机制（对账、幂等、状态机）先于性能机制（分片、缓存）**。先把对账做出来，再去优化性能 —— 否则出了问题无法发现。

### 7.2 分阶段演进

| 阶段 | 触发条件（待压测后量化） | 动作 | 影响的服务 | 验证方式 |
|---|---|---|---|---|
| S1 读扩展 | 查询接口的 P99 随并发线性上升，数据库 CPU 先于应用 CPU 饱和 | train 库加只读副本，查询走从库；余票读模型进 Redis；网关加本地缓存 | train、gateway | 从库延迟监控；缓存命中率；对照压测 |
| S2 热点写下沉 | 扣减接口的耗时随并发上升且数据库出现行锁等待 | 库存预扣完全走 Redis Lua，DB 仅异步落账（本项目 P2 阶段已做） | inventory | 并发测试 + 对账（见风险文档第 19 章） |
| S3 拆分抢票编排 | 下单链路的实例数与库存实例数的最优值差异显著，或订单表写入成为瓶颈 | 拆出 `seckill-service`：只做"限流 + 校验 + 调用扣减 + 落预订单"；order-service 退化为订单生命周期管理 | order、inventory、新增 seckill | 对照压测；对账无差异 |
| S4 引入排队削峰 | 接入层在开售瞬间仍然过载，且上游限流会误伤正常用户 | 引入排队层：请求先入队，返回排队号，结果通过轮询/推送返回；队列消费者按系统容量定速消费 | gateway、新增 queue/push | 排队时长分布；丢弃率；端到端成功率 |
| S5 数据分片 | 单表单库的容量或写入吞吐成为瓶颈（监控到具体指标后再定） | order 按 `user_id` 分片（查询维度是"我的订单"）；inventory 按 `train_id` + 日期分片（访问维度是"某车次某天"）；用分片中间件统一路由 | order、inventory | 分片后对账结果一致；跨片查询清单化 |
| S6 搜索独立 | 查询条件变复杂（多段行程、中转、模糊站点），关系库无法覆盖 | 拆出 `search-service`，用搜索引擎承载查询，数据由 train-service 通过消息投影 | 新增 search、train | 索引与源数据对账 |
| S7 单元化/多机房 | 单机房容量触顶，或需要机房级容灾 | 按用户维度做单元化：同一用户的订单、库存、支付落在同一单元，减少跨单元调用 | 全部 | 机房级故障演练 |

### 7.3 分片方案对比（S5 的备选）

| 方案 | 优点 | 缺点 | 是否选择 |
|---|---|---|---|
| 不做分片，只升级硬件 | 改动为零 | 有物理上限，且成本非线性上升 | 作为 S5 之前的过渡 |
| 数据库原生分区（按日期） | 改动小，对应用透明 | 只在单实例内分区，无法解决单实例写入瓶颈；跨分区查询仍需扫描 | 否（可用于冷热数据分离这一子目标） |
| 应用层双写/分片路由（自研） | 完全可控 | 分片规则、路由、聚合查询、扩容迁移全部要自己实现，出错概率高 | 否 |
| 分片中间件（如 ShardingSphere 这类路线） | 对应用近乎透明，支持分片路由与读写分离 | 引入中间件复杂度；跨片 JOIN 与分布式事务仍需避免 | **是** |
| 换用分布式数据库 | 无分片感知 | 迁移成本与运维能力要求高，教学项目不适用 | 否 |

**分片键选择的理由**（这是分片里最重要的决策）：

| 表 | 分片键 | 为什么 | 不这样选的后果 |
|---|---|---|---|
| `t_order` | `user_id` | 最高频查询是"我的订单列表"，`user_id` 分片可让查询命中单片 | 用 `order_no` 分片则"我的订单"要扫全部分片 |
| `t_ticket_stock` | `train_id` + 出行日期 | 访问模式是"某车次某天某席别"，天然聚簇；且能把热点车次打散到不同分片 | 用自增 ID 分片则热点车次仍集中在一个分片上，分片等于没分 |
| `t_payment` | `order_no`（或 user_id，两者择一后保持一致） | 支付查询一般由订单号驱动 | 与订单分片键不一致会导致对账要跨片关联 |

**注意一个矛盾**：`t_order` 按 `user_id` 分片，而按车次维度统计销量需要跨全部分片。解决办法是**把统计类需求交给离线数仓（通过 binlog/消息同步到分析库）**，不要在交易库上做跨片聚合。这也是第 8 章对账 SQL 写在"离线宽表"上的原因。

### 7.4 明确不做什么（避免过度设计）

| 不做 | 理由 |
|---|---|
| 不上来就分库分表 | 分片会永久提高所有查询与运维的复杂度，必须在真的需要时才做 |
| 不引入服务网格 | 当前服务数量下，SDK 形态的治理组件足够；网格带来额外的运维与排查成本 |
| 不自建注册中心/配置中心 | 属于基础设施，不是本项目的教学重点 |
| 不做多机房双活 | 数据同步与冲突解决的成本远超当前收益（S7 才考虑） |
| 不为"可能的未来需求"预留接口 | 预留的抽象通常与真实需求不符，反而增加理解成本 |

## 8. 面试速查：这套拆分的高频追问

| 追问 | 一句话回答 |
|---|---|
| 为什么库存要单独一个服务？ | 它是全局唯一热点且唯一不可事后补救的资源，需要独立伸缩与独立的存储形态（Redis 原子扣减），并且必须做到"宁可不可用，不可不正确"。 |
| 为什么抢票不单独拆一个服务？ | 因为它没有数据所有权，拆出去只增加一条分布式事务链路，不带来伸缩收益（S3 阶段流量真的到了才拆）。 |
| 下单为什么用同步，不用 MQ 削峰？ | 用户必须立刻知道成败，且异步扣减失败只能反向取消订单，用户体验与一致性都更差。真实削峰应该发生在更上游（排队层，S4）。 |
| 余票查询和库存扣减为什么是两个服务？ | 前者是读模型（可陈旧、只用于展示），后者是权威数据（不可陈旧、用于裁决）。**读模型不能参与扣减决策。** |
| 为什么不用 2PC？ | 协调者单点、锁持有时间跨服务、Redis 不参与；改用本地消息表 + 消费幂等 + 对账，把一致性成本从"运行时锁"换成"离线发现差异"。 |
| 某个服务挂了怎么办？ | 先看是强依赖还是弱依赖：强依赖快速失败（拒绝服务），弱依赖降级或延后。库存挂了一定拒绝下单，通知挂了主链路无感。 |
| 十倍流量怎么扩？ | 先读扩展（从库+缓存），再热点写下沉（Redis Lua），再拆抢票编排，再排队削峰，最后才分片；每一步都由压测数据触发，并保留回滚路径。 |
