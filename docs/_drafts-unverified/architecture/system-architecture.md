# 系统架构总览

> 面向读者：想真正搞懂秒杀原理、并准备拿这个项目去面试的 Java 开发者。
> 本文只讲设计，不讲实现细节代码。凡是没有实测过的地方，一律写"待压测验证"或"待验证"，不写数字。
> 本文的直接上游文档是本目录下的 `design-spec.json`（当前内容为 `null`，即规格尚未落库；本文中被标注为"设计预期"的内容，落地时以补全后的规格为准）。

---

## 0. 先给结论

- 采用 **方案C：Redis + MQ + MySQL**。
- MySQL 是**最终权威（source of truth）**；Redis 是库存的**准入副本 + 裁决闸门**。
- Redis 负责"谁有资格买"，MySQL 负责"谁真的买到了"，两者靠 **MQ 异步 + 幂等 + 对账** 收敛。
- 系统的核心矛盾不是"快"，而是 **在超高并发下不超卖、不少卖、且不把数据库打死**。

## 1. 业务场景

### 1.1 一句话场景

一列热门车次（例如某条热门线路的某个席别），**可售库存 100 张**。开售瞬间，有 **1000 / 5000 / 10000** 个并发请求同时涌向抢票接口，每个请求都想要 1 张票。

最终结果只有两种：**100 个请求成功拿到购买资格，其余全部失败**。系统的任务是：这个结果必须准确、可解释、可复现，而且数据库不能倒。

### 1.2 名词约定

| 名词 | 含义 |
| --- | --- |
| 车次库存（ticket） | 某个车次 + 某个席别 + 某个乘车日期的可售余票，本文档中"库存"默认指这一行的 `stock` 字段 |
| 秒杀请求 | 用户点击"立即抢票"后发出的下单请求 |
| 扣减 | 把库存减 1 的动作 |
| 资格 | 在 Redis 中扣减成功的请求所获得的、可以进入落库流程的权利 |
| 落库 | 在 MySQL 中写入订单并把库存真正扣掉 |
| 超卖 | 卖出的票数 > 库存数 |
| 少卖 | 卖出的票数 < 库存数（有人拿了资格但最终没成交，且库存没有回补） |

### 1.3 三个并发量级下，天真的写法（方案A 的写法）会发生什么

假设：不做任何前置拦截，`秒杀接口` 直接开事务、`SELECT ... FOR UPDATE` 锁库存行、`stock = stock - 1`、写订单、提交。

**1000 并发**

- 同一行库存记录上，请求排队等待行锁，事务串行执行。
- 请求线程全部阻塞在数据库上。连接池被瞬间占满，池上限是一个固定值（具体默认值以所选连接池的文档为准，本文不写死）。
- 结果：请求响应时间被拉长到秒级甚至更长，部分请求拿不到连接直接抛异常。前端表现为"转圈然后报错"。
- 更糟的是：用户不知道自己是"没抢到"还是"系统挂了"，于是**重试**。重试把 1000 并发放大成 2000、3000 并发。

**5000 并发**

- 上面每一步都在恶化。数据库的连接数、活跃会话数、锁等待队列同时上涨。
- 数据库 CPU 花在事务调度和锁管理上，而不是花在真正的读写上。
- 大量事务最终以**锁等待超时**告终；业务侧如果没做兜底，就会出现"扣了库存但订单没写成功"或"订单写了但库存没扣"这类脏数据。
- 此时系统进入**雪崩前的正向反馈环**：越慢 → 重试越多 → 越慢。

**10000 并发**

- 数据库基本相当于被 DDoS。即使没崩，吞吐也已经和"业务成功率"无关了——成功的请求数是靠数据库硬扛出来的，而不是靠架构设计出来的。
- 更本质的问题：**10000 个请求抢 100 张票，9900 个请求从一开始就注定失败，但它们全都跑到数据库里去走了一遍完整事务。**
- 这 99% 的无效工作量，是后面所有架构设计要干掉的东西。

### 1.4 从这个场景提炼出的四个硬需求

| 编号 | 需求 | 不满足会怎样 |
| --- | --- | --- |
| R1 | **不超卖**：任何情况下卖出的票 ≤ 100 | 资损、用户投诉，事务型系统最不可接受的错误 |
| R2 | **快速失败**：注定失败的请求要在极早的阶段被拒绝，且拒绝要便宜 | 数据库被无效流量打死 |
| R3 | **不把存储层打穿**：到达 MySQL 的写请求量必须被压到和库存同量级（≈100 量级，而非 10000 量级） | 数据库连接池/锁队列成为瓶颈，整体不可用 |
| R4 | **结果可解释、可对账**：Redis 与 MySQL 最终必须一致，不一致要能发现并修复 | 出现"显示抢到了但没订单"或"有订单但库存没减"的幽灵数据 |

## 2. 候选方案六维对比

三个方案是**递进关系**，不是并列关系。面试时正确的讲法是："我先看最简单的，发现它撑不住，于是加一层；加了一层后发现还缺一块，于是再加一层。"

### 2.1 方案A：请求直接操作 MySQL 库存

**做了什么**

- 接口内开启数据库事务。
- `SELECT ... FOR UPDATE` 锁住对应车次的库存行。
- 判断 `stock > 0`，是则 `UPDATE t_ticket SET stock = stock - 1 WHERE id = ?`，同时 `INSERT INTO t_order ...`。
- 提交事务，返回结果。

**为什么这么做（它的合理性）**

- 这是最符合直觉的写法：库存就在数据库里，那就用数据库的事务和行锁来保证不超卖。
- 在**低并发**下它是完全正确的，而且是最简单、最容易推理的。单机、几十并发的内部系统，这么写没有任何问题。
- 它提供了**强一致性**：事务提交的那一刻，库存和订单就是一致的，不存在中间态。

**不这么做会出什么问题（如果我们停在方案A）**

- 就是第 1.3 节描述的整个过程：连接池耗尽、行锁排队、请求堆积、重试放大、数据库成为唯一瓶颈。
- 关键判断：**数据库的行锁是"串行化"手段，而秒杀需要的是"过滤"手段。** 用串行化去处理 10000 个请求，等于让 10000 个人排一队过一个门。正确做法是在门前先劝退 9900 个人。

**对比过的替代方案与不选的原因**

- 替代：把隔离级别调到 `READ COMMITTED` 减少间隙锁 → 有帮助，但解决的是锁粒度问题，不是"请求量本身"的问题，量级上仍然不成立，所以不作为独立方案，只作为数据库侧的调优项保留。
- 替代：用乐观锁（版本号 / `UPDATE ... WHERE stock >= 1`）替代 `FOR UPDATE` → 确实能减少锁持有时间、避免悲观锁排队，**但** 它把压力从"锁等待"转移成了"大量失败的 UPDATE 语句仍然要到达数据库"。10000 条 UPDATE 里有 9900 条影响行数为 0，数据库仍然要解析、执行、回滚它们。所以乐观锁是必要的兜底（见第 5 节唯一索引与条件更新），但不是主力方案。

### 2.2 方案B：Redis + MySQL

**做了什么**

- 库存预热：开售前把 `t_ticket.stock` 同步到 Redis 的一个计数器 key 上。
- 秒杀请求进来后，**先在 Redis 里扣减**，用 Lua 脚本保证"判断 + 扣减"是一个原子操作。
- Redis 扣减成功的请求，才去走 MySQL 落库（写订单 + 扣库存）。
- Redis 扣减失败（库存不足）的请求，直接返回"已售罄"，不碰数据库。

**为什么这么做**

- 把 R2（快速失败）和 R3（保护存储层）一次性解决了：**Redis 是单线程执行 Lua 的，天然串行化，不需要锁，且内存操作极快。**
- 到达 MySQL 的请求量从"并发量"变成了"库存量"。10000 并发进来，只有 100 个请求会走到数据库。
- 这正好对应 R3 的需求：让存储层承受的写入量和它的业务容量匹配，而不是和流量匹配。

**不这么做会出什么问题（如果我们停在方案B）**

- **Redis 扣减成功 ≠ MySQL 落库成功。** 两者之间是一个跨系统的写操作，没有事务能覆盖它。
- 如果同步落库（在请求线程里直接写 MySQL），那么：Redis 扣减成功后的 100 个请求会同时压向数据库，形成一次**小规模但真实的写风暴**；更严重的是，如果响应超时、应用崩溃、网络抖动，就会出现"Redis 已经扣了，但 MySQL 没写"的**少卖**，或者重试导致"MySQL 写了两次"的**超卖**。
- 也就是说：方案B 解决了"量"的问题，但把"分布式一致性"的问题引进来了，而且是在请求的同步链路上，用户要等它。

**对比过的替代方案与不选的原因**

- 替代：Redis 扣减成功后，同步写 MySQL，用本地事务 + 失败补偿。→ 用户请求的 RT 里包含了数据库的写时间，且失败补偿逻辑散落在业务代码里，面试时很难讲清楚边界。不选。
- 替代：不用 Lua，用 `DECR` + 判断返回值。→ `DECR` 本身是原子的，但"判断库存是否 < 0 然后回滚"是两步，中间有窗口，且库存为负时要 `INCR` 回来，这段逻辑在应用侧重试时会出错。用 Lua 把两步合成一步，是一个更干净的不变量。不选非 Lua 写法。

### 2.3 方案C：Redis + MQ + MySQL（最终方案）

**做了什么**

- 在方案B 的基础上，把"Redis 扣减成功 → MySQL 落库"这一段**从同步改成异步**：
  - Redis 扣减成功的请求，向 MQ 投递一条"下单消息"，然后**立即向用户返回"排队中/抢购中"**，让前端轮询结果。
  - 消费者从 MQ 拉取消息，执行 MySQL 落库（写订单 + 扣库存），落库结果写回一个可查询的结果（Redis 结果 key 或订单表）。
- 引入**幂等**：消息里带业务唯一键（如 `userId + ticketId` 或预生成的请求号）， MySQL 侧用唯一索引兜底，消费重复消息不会产生第二张订单。
- 引入**对账**：定时任务比对 Redis 库存与 MySQL 库存、比对 MQ 消息与订单，发现不一致就修复并告警。

**为什么这么做**

- **削峰**：MQ 把"瞬时 100 个并发写"变成"消费者按自己节奏消费的 100 条消息"。数据库的写入速率从此由消费者控制，而不是由流量控制。
- **解耦**：秒杀接口的 RT 不再包含数据库写入时间，用户感知的是"提交成功，等待结果"，而不是"卡了 3 秒然后失败"。
- **可重试**：落库失败时，消息可以重投，这是 MQ 天然提供的能力，不需要业务自己写补偿循环。
- **可观测**：MQ 的堆积量本身就是一个非常好的监控指标（堆积上涨 = 消费者跟不上）。

**不这么做会出什么问题（如果我们停在方案B）**

- 落库阶段的任何抖动都会直接变成用户请求的失败，而用户会重试，重试又回到 Redis 的扣减逻辑，可能把已经扣掉的库存重复占用（详见第 6 节幂等设计）。
- 没有缓冲，就没有"重试"的余地。而秒杀链路里最需要的能力就是：**能安全地重试。**

**对比过的替代方案与不选的原因**

- 替代：用线程池 + 内存队列（`BlockingQueue`）代替 MQ。→ 单机内存队列在应用重启时丢消息，且没有多实例之间的分发能力，属于"看起来像削峰，实际上是丢数据"。**不选**（但可以在教学里作为"错误示范"实现一版，用来对比）。
- 替代：用数据库表当队列（`SELECT ... FOR UPDATE SKIP LOCKED` 轮询）。→ 又把压力拉回了数据库，和 R3 直接冲突。**不选**。
- MQ 选型（RocketMQ / RabbitMQ / Kafka）：秒杀场景需要的是"能重试、能延迟（超时未支付关单）、最好有事务消息"的队列。RocketMQ 的事务消息与延迟消息是它在这个场景下最常被提到的理由；RabbitMQ 需要用 TTL + 死信队列自己拼延迟；Kafka 的强项是吞吐与分区顺序，不是这种低频精确投递。**最终选型在环境搭建阶段确定，本文不预设具体中间件与版本，落地时以所选中间件的官方文档为准（待验证）。**

### 2.4 六维对比表

| 维度 | 方案A：直接操作 MySQL | 方案B：Redis + MySQL | 方案C：Redis + MQ + MySQL |
| --- | --- | --- | --- |
| **性能**（吞吐/延迟） | 最差。全部请求压在数据库行锁上，吞吐由单行锁的串行能力决定。注：本文不给出具体 QPS 数字，待压测验证 | 好。Redis 承担过滤，到达数据库的写请求 ≈ 库存量。瓶颈从数据库转移到 Redis 单 key 热点 | 最好。在前者基础上把数据库写入从请求链路里摘出去，用户侧 RT 不再包含落库耗时，数据库写入速率可被消费者限速 |
| **一致性** | 最强。单库本地事务，提交即一致 | 中。Redis 与 MySQL 是两次独立写，存在中间态；需要幂等与补偿，否则会少卖/重复下单 | 中（但可控）。最终一致性：接受短暂不一致，用幂等 + 重试 + 对账收敛。可证明"最终不超卖、不少卖" |
| **复杂度** | 最低。一个事务搞定，代码量最小 | 中。多引入 Redis、Lua 脚本、库存预热、缓存与数据库的一致性处理 | 最高。额外引入 MQ、幂等表、结果查询/轮询、对账任务、消费失败处理 |
| **可靠性**（故障时的行为） | 数据库是单点。数据库一慢，整条链路全挂，且没有缓冲 | Redis 挂 → 秒杀不可用（但可降级为"售罄"或"稍后再试"）；数据库挂 → 已扣减的资格丢失 | 最好。MQ 提供缓冲与重投；消费者挂了消息还在；Redis 挂了同样不可用，但已投递的消息不会丢 |
| **实现成本** | 最低。无需额外中间件 | 中。需要额外部署 Redis，需要写 Lua、预热脚本 | 高。需要额外部署 MQ，需要写生产者、消费者、幂等、对账、结果查询接口 |
| **面试价值** | 低。面试官会认为"没做过并发场景" | 中高。能讲清楚 Lua 原子性、库存预热、缓存与数据库一致性 | 最高。能把"限流—缓存—异步—幂等—对账"整条链路讲完整，且每一层都有明确的存在理由和被否决的替代方案 |

### 2.5 结论与理由

**结论：采用方案C（Redis + MQ + MySQL）。**

理由按优先级排列：

1. **只有方案C 同时满足 R1~R4。** 方案A 违反 R2、R3；方案B 违反 R4（缺少可靠的收敛机制）；方案C 四项都满足——不超卖由 Lua + 唯一索引双重保证，快速失败由 Redis 承担，存储层保护由 Redis + MQ 共同承担，可对账由幂等键 + 对账任务承担。
2. **方案C 的复杂度是"有回报的复杂度"。** 多出来的 MQ、幂等、对账三块，每一块都对应一个明确的故障场景（落库失败、消息重复、Redis 与 MySQL 漂移），不是为架构而架构。
3. **它是一条可以被追问到底的链路。** 面试时回到"为什么这里要加这一层"，每一层都有"不加会怎样"的具体答案，这正是一个教学项目应该提供的价值。
4. **它是可降级的。** 如果 MQ 挂了，可以临时降级为方案B（同步落库）扛一小段时间；如果 Redis 挂了，可以降级为"全部返回系统繁忙"。方案C 不是把鸡蛋放在一个篮子里，而是把鸡蛋放在多个可以互相兜底的篮子里。

```text
                                       v
+=======================================================================+
| 存储层 (Storage)                                                       |
|                                                                       |
|   MySQL (最终权威):                                                    |
|     t_ticket   库存行 (stock)                                          |
|     t_order    订单 (唯一索引 uk_user_ticket 兜底防重)                  |
|                                                                       |
|   职责: 持久化、事务、最终一致性基准。所有对账以本层为准                 |
+=======================================================================+
```

### 3.2 每一层的职责与边界

| 层 | 职责 | 不该做的事 | 为什么这样切 |
| --- | --- | --- | --- |
| 接入层 | 终止连接、限流、挡掉明显非法/重复请求 | 不写业务逻辑，不感知库存 | 逻辑放在离数据库越近的地方越贵；能在外层解决的，不要留给内层 |
| 服务层 | 业务规则、状态机、幂等、降级；无状态 | 不持有跨请求的内存状态（否则无法水平扩容） | 无状态才能靠加实例扛量；有状态（如本地队列）会在重启时丢数据 |
| 中间件层 | 承接瞬时流量、把并发整形为恒定消费速率 | 不作为权威数据源（Redis 的数据是可以从 MySQL 重建的） | Redis 快但可能丢（取决于持久化配置）；MQ 只做传输不做存储的最终形态 |
| 存储层 | 持久化与最终一致性基准 | 不承担过滤职责 | 数据库的价值在于"准"，不在于"快"；把过滤职责交给它是用错工具 |

### 3.3 流量过滤比例（设计预期，待压测验证）

下表是**设计预期**，不是实测结果。所有比例都必须在压测后回填，未回填前一律视为未知。

| 过滤点 | 过滤手段 | 设计预期（待压测验证） |
| --- | --- | --- |
| 端上 | 点击后按钮置灰、同一用户同一车次只提交一次 | 规则性过滤：同一用户的重复提交压到 1 次（这是规则，不是测出来的数字） |
| Nginx | 按 IP/用户的请求速率限制、连接数上限 | 设计预期拦住脚本刷单与超量重试，具体比例 待压测验证 |
| 服务层-参数校验 | 车次不存在、不在售卖时间、参数非法 | 与流量无关，取决于请求合法性，待压测验证 |
| 服务层-用户去重 | 同一用户重复请求直接返回上一次的结果 | 设计预期把"同一用户重试"的重复流量全部吃掉，具体比例 待压测验证 |
| 服务层-售罄标记 | 库存卖空后置"已售罄"，后续请求不查 Redis 直接失败 | 设计预期在卖空后立刻把后续流量全部挡在 Redis 之前，具体比例 待压测验证 |
| Redis Lua | 库存不足直接返回失败 | 结构性结果：**通过量 ≤ 库存数（100）**，这是算法保证的，不是压测出来的 |
| MQ | 只有拿到资格的请求才投递消息 | 结构性结果：**入队消息数 ≤ 库存数（100）** |
| MySQL | 只承接消费者的落库写入 | 结构性结果：**写事务数 ≤ 库存数（100）** |

规律：越靠后的过滤点，其通过量越是被**算法**而不是被**性能**决定的。这正是架构设计的目标——把"性能问题"转化为"规则问题"。

## 4. 秒杀主链路时序

下面从用户点击开始，逐步走完整条链路。每一步都列出**正常分支**和**失败分支**。

### 步骤 0：库存预热（开售前，运营/定时任务触发）

- 做什么：把 `t_ticket` 中该车次的 `stock` 写入 Redis 的库存 key；同时清除上一次的售罄标记和结果缓存。
- 为什么：Redis 里必须有库存，秒杀请求才有得扣。预热必须在开售**之前**完成。
- 失败分支：
  - 预热失败（Redis 不可用）→ **不允许开售**。宁可延迟开售，也不能在库存没进 Redis 的情况下放流量，否则所有请求都会走到"库存未初始化"分支。
  - 预热值与数据库不一致 → 由对账任务发现（见步骤 9）。
- 代码示意（Lua 里如何处理"库存 key 不存在"）：

```lua
-- KEYS[1] = 库存 key, ARGV[1] = 本次扣减数量(通常为 1)
local stock = redis.call('GET', KEYS[1])
if stock == false then return -2 end                       -- 未预热
if tonumber(stock) < tonumber(ARGV[1]) then return -1 end  -- 库存不足
redis.call('DECRBY', KEYS[1], ARGV[1])
return tonumber(stock) - tonumber(ARGV[1])                 -- 剩余库存
```

  这段脚本必须整体交给 Redis 执行：`GET` 与 `DECRBY` 之间的原子性由 Redis 的单线程执行模型保证，不需要额外加锁。返回值 `-2 / -1 / >=0` 就是三种分支的判据。

### 步骤 1：用户点击"立即抢票"

- 正常分支：端上按钮置灰，发起一次下单请求。
- 失败分支：
  - 用户连点 → 端上置灰挡住大部分；仍到达服务端的重复请求由步骤 3 的去重挡住。
  - 端上时间与服务器时间不一致导致"未到开售时间"→ 以服务端时间为准（服务端时间校验，见步骤 2）。

### 步骤 2：接入层（Nginx）

- 正常分支：连接建立，通过限流规则，转发到服务层某一实例。
- 失败分支：
  - 触发 IP/用户级限流 → 返回限流响应。**注意**：此时还没有产生任何业务副作用，用户重试是安全的。
  - 超过连接数上限 → 连接被拒绝。这是保护服务层的手段，代价是部分合法用户被误伤，需要把阈值调到合理区间（待压测确定）。

### 步骤 3：服务层-参数与前置校验

- 正常分支：车次存在、在售卖时间窗口内、用户已登录且具备购票资格，进入下一步。
- 失败分支：
  - 参数非法/车次不存在 → 返回明确错误，不产生副作用。
  - 不在售卖时间 → 返回"未开售/已结束"。
  - 用户未登录 → 返回未认证。

### 步骤 4：服务层-用户级去重

- 做什么：以 `userId + ticketId`（或请求号）为 key，用 `SETNX` 之类的原子操作在 Redis 中占位。
- 为什么：用户重试是秒杀场景里**最主要的流量放大器**。这一步把"同一用户重复请求"从 N 次压到 1 次。**它同时也是幂等的第一道防线。**
- 失败分支：
  - 已存在（重复提交）→ 直接返回上一次的处理结果（"排队中"或最终结果），不再走后续流程。
  - 占位成功但后续流程全失败 → 需要释放占位或让占位带 TTL 自然过期，否则用户会被永久挡住（"重试也没用"）。**这是必须处理的边界。**
- 对比：不用 Redis 去重，改用数据库唯一索引去重 → 唯一索引必须保留（作为最后一道防线），但如果只靠它，重复请求仍然会到达数据库，违反 R3。所以两者都要有，Redis 在前、唯一索引在后。

### 步骤 5：服务层-售罄快速失败

- 做什么：检查该车次的"售罄标记"。若已售罄，直接返回失败。
- 为什么：卖空之后，剩下的请求占绝大多数。让它们连 Redis 的 Lua 都不用执行，是最便宜的拒绝方式。
- 失败分支：标记误置（例如库存回补后忘记清除标记）→ 会导致"少卖"。所以**任何回补库存的操作都必须同时清除售罄标记**，这一点必须在代码评审清单里。
- 注意：售罄标记是**优化项，不是正确性依赖**。就算标记出错，Lua 脚本依然会正确地拒绝超量请求。这是刻意设计的冗余。

### 步骤 6：Redis Lua 原子扣减（核心裁决点）

- 正常分支：返回值 ≥ 0，说明扣减成功，拿到购买资格，进入步骤 7。
- 失败分支：
  - 返回 `-1`（库存不足）→ 返回"已售罄"，同时**可以**置售罄标记。不产生任何数据库副作用。
  - 返回 `-2`（未预热）→ 返回"系统繁忙，请稍后重试"。这属于**运维事故**，应触发告警，而不是当作正常业务失败。
  - Redis 连接超时/不可用 → 返回"系统繁忙"。此时**不能降级为直接查数据库**，否则流量会瞬间打穿 MySQL（这正是方案A 的处境）。
- 关键不变量：**Redis 中扣减成功的次数 ≤ 库存数**。这个不变量由 Lua 脚本的原子性保证，不依赖任何应用层的锁或重试逻辑。

### 步骤 7：投递 MQ

- 正常分支：把"下单消息"（包含 userId、ticketId、请求号、时间戳）投递到 MQ，然后**立即返回"排队中"**给用户。
- 失败分支：
  - 投递失败（MQ 不可用/超时）→ 必须**回滚 Redis 的扣减**（`INCR` 回去）或者进入本地补偿记录等待重投。
    - 选择回滚：实现简单，但回滚本身也可能失败，所以回滚失败必须落一条补偿记录。
    - 选择不回滚、只记录：库存会"少卖"，需要靠对账修复。
    - 本项目的选择：**先回滚 + 记录补偿日志，由定时任务兜底重投或回滚**（两种策略都要有，因为任何单一策略都会在极端情况下失效）。
  - 消息投递成功但用户没收到响应（网络问题）→ 用户重试，被步骤 4 的幂等挡住，返回"排队中"。**这就是幂等存在的意义。**
- 面试要点：这里是整条链路里**唯一一处需要"跨系统补偿"**的地方。Redis 扣减和 MQ 投递无法组成一个事务，所以必须显式设计补偿路径。

### 步骤 8：消费者落库

- 正常分支：消费消息 → 幂等检查 → 开启本地事务 → `INSERT INTO t_order` → `UPDATE t_ticket SET stock = stock - 1 WHERE id = ? AND stock >= 1` → 提交 → 回写结果到 Redis（供步骤 10 查询）。
- 失败分支：

| 失败情况 | 现象 | 处理 |
| --- | --- | --- |
| 消息重复投递 | 会尝试插入第二张订单 | 由唯一索引 `uk_user_ticket` 拒绝，捕获重复键异常后视为"已处理成功"，直接 ACK |
| 库存行已被扣光 | `UPDATE ... AND stock >= 1` 影响行数为 0 | 说明 Redis 与 MySQL 漂移（理论上不应该发生），回滚事务、记录异常、触发告警与对账 |
| 数据库暂时不可用 | 事务抛异常 | **不 ACK**，让消息重投；重投仍失败则进入死信队列，由人工/定时任务处理 |
| 消费者进程崩溃 | 消息未 ACK | MQ 在可见性超时后重新投递，幂等保证不会重复下单 |
| 落库成功但结果回写 Redis 失败 | 用户轮询不到结果 | 结果查询接口要有"回源到数据库"的兜底路径 |

- 唯一索引 DDL 示意（幂等的最后一道防线）：

```sql
-- 同一用户对同一车次只能有一张有效订单
-- 注意：如果业务允许"一个用户买多张"，这个唯一键要改成 (user_id, ticket_id, seq)
UNIQUE KEY `uk_user_ticket` (`user_id`, `ticket_id`)
```

  为什么必须有它：Redis 的幂等 key 可能因为过期、被误删、主从切换而失效；MQ 可能重复投递；消费者可能重平衡后重复消费。**应用层的幂等会失效，数据库的唯一约束不会。** 这是"纵深防御"的最后一层。

### 步骤 9：定时任务（超时关单 + 对账）

- 超时关单：订单在 N 分钟内未支付 → 关闭订单、回补库存（Redis 与 MySQL 都要加回去）、清除售罄标记。
- 对账：比对 Redis 库存与 MySQL 库存，比对 MQ 消息与订单表，发现差异则记录并修复。
- 失败分支：
  - 回补时重复回补 → 导致超卖。回补必须幂等（同样依赖订单状态机，见第 5 节）。
  - 对账任务本身挂掉 → 需要有对账任务的心跳监控（"对账没跑"比"对账发现不一致"更危险）。

### 步骤 10：用户查询结果

- 正常分支：轮询结果接口 → 读到"下单成功"或"已售罄"。
- 失败分支：
  - 一直读到"排队中"（消费者积压）→ 需要有**轮询次数上限**，超时后返回"结果确认中，请稍后在订单列表查看"，避免用户无限轮询打爆查询接口。
  - Redis 结果 key 已过期 → 回源到订单表查询。
- 设计要点：**查询接口必须是廉价的**，因为它会被高频轮询。它不应该触发任何写操作。

## 5. 数据流转与权威源

### 5.1 数据在哪一层被修改

| 数据项 | 存放位置 | 被谁修改 | 修改时机 |
| --- | --- | --- | --- |
| 库存计数（准入用） | Redis `stock:{ticketId}` | 秒杀接口的 Lua 脚本 / 定时任务的回补 | 抢购时扣减；超时关单时回补 |
| 用户去重标记 | Redis `order:dedup:{userId}:{ticketId}` | 秒杀接口 | 请求进入时 `SETNX`，带 TTL |
| 售罄标记 | Redis `soldout:{ticketId}` | 秒杀接口 / 定时任务的回补 | 库存扣到 0 时置位；回补时清除 |
| 下单结果（供轮询） | Redis `result:{requestId}` | MQ 消费者 | 落库完成后写入，带 TTL |
| 下单消息 | MQ Topic/Queue | 秒杀接口（生产）、消费者（消费） | 扣减成功后投递；消费成功后 ACK |
| 订单记录 | MySQL `t_order` | MQ 消费者 | 落库事务中 `INSERT` |
| 库存记录 | MySQL `t_ticket.stock` | MQ 消费者 / 定时任务 | 落库事务中 `UPDATE`；超时关单时回补 |
| 订单状态 | MySQL `t_order.status` | 支付回调（本项目为模拟）/ 定时任务 | 状态机流转 |

### 5.2 谁是权威（source of truth）

**MySQL 是最终权威。Redis 是 MySQL 库存的一份"准入副本 + 裁决闸门"。**

理由分三层：

1. **持久性**：Redis 的持久化（RDB/AOF）在极端故障下仍可能丢最后一段写入，而订单和库存是**不能丢**的数据。所以权威必须在 MySQL。
2. **可重建性**：Redis 里的所有数据都能从 MySQL 推导出来——库存来自 `t_ticket.stock`，去重标记来自 `t_order` 的存在性，结果来自订单状态。**能重建的数据不该是权威。**
3. **可审计**：出了纠纷要以订单表为准。对账的方向永远是"用 MySQL 修正 Redis"，而不是反过来。

### 5.3 那为什么"扣减资格"由 Redis 裁决？

这是个容易被追问的点，需要说清楚：

- 权威 ≠ 裁决点。**权威回答"最终是什么"，裁决点回答"此刻谁可以通过"。**
- 为什么不让 MySQL 裁决：第 1.3 节已经说明，让数据库裁决意味着 10000 个请求都要到数据库去排队，成本不可接受。
- Redis 裁决的代价：Redis 可能误判（例如它以为还有库存但 MySQL 已经没有了，或者反过来）。所以设计了**双重保险**：
  - MySQL 侧 `UPDATE ... WHERE stock >= 1` 保证即使 Redis 误判也**不会把库存写成负数**（不超卖）。
  - 对账任务保证 Redis 的误判会被发现并修正（不少卖）。
- 换句话说：**Redis 的裁决权是"被授权"的，MySQL 随时可以否决它。** 这是一个单向的授权关系，不是双主。

### 5.4 一致性模型总结

| 环节 | 一致性模型 | 说明 |
| --- | --- | --- |
| Redis 扣减 | 强一致（单 key，单线程执行 Lua） | 同一 key 上的所有扣减严格串行 |
| Redis → MQ | 最终一致（需补偿） | 投递失败要回滚或补偿，见步骤 7 |
| MQ → MySQL | 最终一致（幂等 + 重试） | 消息可重投，唯一索引保证不重复 |
| Redis ↔ MySQL | 最终一致（对账修复） | 以 MySQL 为准，周期性收敛 |
| 用户看到的结果 | 最终一致（"排队中" → 最终结果） | 用户接受短暂的不确定，换取系统的可用性 |

`t_order.status` 状态机（本项目只保留必要的状态）：

```text
  (下单消息消费成功, 占座)
        |
        v
     [0 待支付] --支付成功--> [1 已支付]   (终态)
        |  \
        |   \--用户取消--> [2 已取消]      (终态, 需回补库存)
        |
        \----超时未支付--> [3 已超时关闭]   (终态, 需回补库存)
```

状态机的意义：**回补库存这个动作必须由"从哪个状态转到哪个状态"来决定**，而不是由定时任务"扫到没支付的订单就加库存"来决定。否则超时任务和取消请求同时到达时，库存会被加两次（超卖）。正确做法是：`UPDATE t_order SET status = 3 WHERE id = ? AND status = 0`，影响行数为 1 的那个执行者才拥有回补权。

## 6. 系统边界

### 6.1 本项目明确不做的事

| 不做的部分 | 为什么不做 | 架构上留的口子 |
| --- | --- | --- |
| **真实支付** | 接入真实支付渠道涉及资质、回调验签、对账文件，与秒杀的核心矛盾（高并发下的库存裁决）无关，会淹没教学重点 | 订单状态机里保留 `待支付 → 已支付` 这条边；支付回调做成一个**独立的、幂等的** HTTP 接口（本项目由模拟接口触发）。只要回调具备"按订单号幂等 + 状态机校验"两个特征，将来换成真实支付渠道时，改动只在这一层 |
| **实名制/乘车人信息** | 涉及敏感个人信息存储与合规，且不改变并发模型 | 订单表预留乘车人信息的关联位置（或独立的 `t_passenger` 表），秒杀主链路只处理 `userId + ticketId`，不感知乘车人。将来加实名校验时，作为步骤 3 的前置校验插入即可，不影响后续任何一层 |
| **座位排布/选座** | 选座会把"库存扣减"从"一个计数器"变成"一批具体资源的选择"，是完全不同的问题（需要座位图、锁座、释放），复杂度与本项目的核心目标不匹配 | 库存模型停留在"席别级别的计数器"。将来要做选座，是在扣减成功后**追加一步"分配具体座位"**，这一步同样可以做成"分配失败则回滚资格"的独立环节，不影响秒杀主链路 |
| **退款** | 涉及资金流与逆向库存回补，属于交易系统的完整性问题 | 状态机里从 `已支付` 没有出边，这是一个**有意的封闭**。将来加退款，是新增一个 `已退款` 终态 + 一条回补路径；回补库存的实现（幂等、状态机守卫）在本项目里已经存在，可以直接复用 |
| **改签** | 涉及"扣新票 + 退旧票"的跨车次原子操作，边界复杂度高 | 与退款同理：改签 = 一次新的抢购 + 一次退款回补。本项目的幂等与回补机制是它的地基 |
| **分布式事务（2PC/Seata）** | 秒杀链路的一致性可以用"幂等 + 重试 + 对账"解决，引入分布式事务框架会把可用性和性能都拖下来，且面试时容易讲成背概念 | 本文档第 5.4 节明确写出了一致性模型。如果将来某个环节确实需要强一致，替换点被清晰地隔离在"消费者落库"这一个事务里 |

### 6.2 一个必须写清楚的设计取向

**本项目选择"最终一致 + 对账"，而不是"强一致"。**

- 理由：强一致（分布式事务）要求参与方在事务期间保持可用并持有锁，这在秒杀的高并发场景下是把可用性抵押出去换一致性，方向反了。
- 代价：用户会看到"排队中"这样的中间状态，系统需要一个对账任务来兜底。
- 什么情况下应该反过来选：如果业务是"扣款"而不是"占座"，或者规模小到不需要削峰，那么方案A 的强一致反而是更好的选择。**架构没有绝对的对错，只有和场景的匹配度。**

## 7. 环境搭建方案

本项目在本机（Windows 10）上需要运行：MySQL、Redis、MQ、以及 Spring Boot 应用。有两种落地路线。

> 说明：本项目的应用侧技术栈来自仓库现状——`pom.xml` 中声明了 Spring Boot 3.5.9 与 Java 17。Redis / MySQL / MQ 的具体版本本文不预设，搭建时以实际安装记录为准（待验证）。

### 7.1 路线 A：Docker Desktop + WSL2（推荐）

**思路**：所有中间件跑在容器里，本机只装 Docker Desktop。用一份 compose 文件描述整个环境。

**步骤**

1. 确认 Windows 版本支持 WSL2，并开启 CPU 虚拟化（BIOS/UEFI）。
2. 启用 WSL2：在管理员 PowerShell 中执行 `wsl --install`（或分别启用"适用于 Linux 的 Windows 子系统"与"虚拟机平台"两个 Windows 功能），按提示重启。
3. 安装一个 Linux 发行版（`wsl --install -d <发行版名>`），首次启动设置用户名密码。
4. 可选但推荐：在用户目录下创建 `.wslconfig`，限制 WSL2 可用的内存与 CPU，避免它默认占用过多宿主资源。
5. 安装 Docker Desktop，在设置中确认使用 **WSL2 backend**（而非 Hyper-V backend）。
6. 在 Docker Desktop 设置中确认容器与宿主机的端口映射方式，记录本机将使用的端口（MySQL / Redis / MQ）。
7. 编写 `docker-compose.yml`，声明 MySQL、Redis、MQ 三个服务，包含：镜像、端口映射、数据卷、环境变量（初始库名、用户、密码）、健康检查。
8. `docker compose up -d` 启动，用 `docker compose ps` 确认健康状态。
9. 用客户端（MySQL 命令行/图形客户端、`redis-cli`、MQ 控制台）分别连一次，确认能从 **Windows 宿主** 访问容器端口。
10. 应用侧通过 `application.properties` / `application-*.properties` 配置连接信息，**不把密码写进代码库**（用本地 profile 或环境变量）。

**代价**

- 首次拉取镜像的下载时间与磁盘占用（具体大小取决于所选镜像，待验证）。
- WSL2 的内存占用需要手动限制，否则会明显影响宿主机的开发体验。
- 需要理解"容器内的 localhost"和"宿主机的 localhost"不是一回事：应用如果也跑在容器里，连接地址要用 compose 的服务名；应用跑在宿主机（IDE 里直接运行）时，连接地址用 `localhost` + 映射端口。**这是新手最常踩的坑。**

**风险**

- 虚拟化未开启或与已有的虚拟机软件（Hyper-V / VMware / VirtualBox）冲突 → 表现为 Docker Desktop 起不来。
- 公司网络/代理导致镜像拉取失败 → 需要配置镜像加速或代理（具体配置方式随版本变化，以官方文档为准）。
- 端口冲突：本机已装过 MySQL/Redis 时会占用默认端口，需要在 compose 里改宿主映射端口。
- WSL2 与宿主机之间的时钟漂移，会影响依赖时间的逻辑（如"是否在售卖时间窗口内"）→ 开发期需要注意。
- 数据卷放在 WSL2 的文件系统里，直接在 Windows 侧编辑/备份不方便。

**收益**

- 一条命令得到一套**可重建、版本可控**的环境；换电脑时把 compose 文件带过去即可。
- 容器里跑的是 Linux 版本，和未来部署形态一致，避免了"本机跑得好、服务器上不一样"的问题。
- 面试时能讲清楚"我的环境是怎么编排的"，这是加分项。

### 7.2 路线 B：Windows 原生安装

**思路**：不用容器，直接把 MySQL、Redis、MQ 装成 Windows 服务。

**步骤**

1. MySQL：下载官方 Windows 安装包（MSI 或 ZIP），安装/解压，初始化数据目录，设置 root 密码，注册为 Windows 服务，配置 `my.ini`（字符集、端口、数据目录）。
2. Redis：**注意 Redis 官方并不提供 Windows 原生版本。** 常见做法有三种：
   - 使用社区维护的 Windows 移植版；
   - 使用商业兼容产品（如 Memurai）；
   - 只把 Redis 放在 WSL2 里单独跑（等于局部使用路线 A）。
   三种做法都需要注意：与官方 Linux 版本可能存在命令或行为差异（尤其是 Lua 脚本、持久化、模块相关的部分），**具体差异待验证**。
3. MQ：下载对应中间件的 Windows 版本（部分 MQ 的 Windows 支持不佳或根本没有官方 Windows 发行版，这本身就是该路线的一个风险点），配置数据目录、端口、启动脚本。
4. 逐个启动服务，用客户端连接验证。
5. 配置开机自启（Windows 服务方式），或每次手工启动。

**代价**

- 每一步都要手工配置：数据目录、字符集、端口、服务注册、防火墙放行。
- 卸载不干净会残留服务与数据目录，后续排查困难。
- 需要自己维护"环境说明文档"，否则换机器时无法复现。

**风险**

- **最大风险是与生产环境的行为差异**：尤其是 Redis 的 Windows 移植版，可能与官方版本在 Lua 脚本执行、内存淘汰、持久化行为上不一致，导致本地通过、线上失败。
- Windows 路径分隔符、文件权限、大小写敏感性与 Linux 不同，配置文件里的路径容易出错。
- 部分中间件在 Windows 上的官方支持有限，遇到问题时可参考的社区资料更少。
- 需要管理员权限才能注册服务、改防火墙。

**收益**

- 不需要虚拟化，适合公司电脑禁用虚拟化、或无管理员权限的场景。
- 启动一个中间件就是启动一个服务，心智负担低（对不熟悉容器的人）。
- 没有 WSL2 的内存开销。

### 7.3 两条路线的对比与推荐

| 维度 | 路线 A：Docker + WSL2 | 路线 B：Windows 原生 |
| --- | --- | --- |
| 环境可重建性 | 高（compose 文件即环境定义） | 低（靠文档和手工步骤） |
| 与生产环境一致性 | 高（Linux 容器） | 低（Redis/MQ 尤其明显） |
| 首次搭建时间 | 较长（下载镜像、配置 WSL2） | 因中间件而异，通常更繁琐 |
| 磁盘/内存占用 | 较高，可配置 | 较低 |
| 对管理员权限的依赖 | 需要（安装 WSL2 与 Docker） | 需要（注册服务、改防火墙） |
| 主要风险 | 虚拟化冲突、镜像拉取失败 | 版本行为差异、部分中间件无官方 Windows 版 |
| 面试可讲的内容 | 容器编排、环境即代码 | 手工排障经验 |

**推荐：优先路线 A。**

理由：

1. 本项目的核心是**高并发与分布式协作**，Redis 的 Lua 原子性、MQ 的投递语义是重点。这些行为在 Linux 版本上才有官方保证，用移植版验证会引入不必要的变量。
2. 环境可重建意味着**实验可以反复做**——压测要反复跑，环境随时能重置到干净状态，这是教学项目最需要的属性。
3. 本机是 Windows 10 Pro 19045，具备 WSL2 的软件条件（是否已开启虚拟化需要实际确认，待验证）。

**什么时候走路线 B**：本机无法开启虚拟化（BIOS 受限、公司策略）、没有管理员权限、或 WSL2 与已有虚拟机软件冲突且无法解决。走路线 B 时，建议**至少把 Redis 放到 WSL2 里**（如果 WSL2 本身可用），以避开 Windows 移植版的兼容性风险。
