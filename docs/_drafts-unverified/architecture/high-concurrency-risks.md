# 抢票系统高并发风险清单

> 本文把抢票场景下会真实发生的并发问题逐条展开：**触发时序 → 后果 → 解决方案（本项目 / 生产两栏）→ 在哪个阶段解决**。
> 最后一章专门回答"**如何证明不会超卖**"，给出可执行的验证手段与校验 SQL。
> 涉及的服务边界、数据库划分、调用方式，见 [微服务拆分设计](./service-split.md)。

## 0. 阅读方式与阶段定义

### 0.1 本文的口径

- 文中一切数量级（并发数、库存数、线程数）都是**参数**，不是实测结论。凡未实测处标注 **待压测 / 待验证**。
- 所有性能相关结论都以"方向"表述（"更慢"、"会排队"），不给具体数字。
- 编号 R1…R18 全局唯一，其他文档引用这些编号即指本节内容。

### 0.2 阶段定义（与拆分文档一致）

| 阶段 | 名称 | 这一阶段的目标 | 主要解决的风险 |
|---|---|---|---|
| P0 | 单体验证期 | 单体 + 数据库同步扣减 + 唯一约束兜底，**先把正确性跑通** | R1（部分）、R7、R12 |
| P1 | 读扩展与缓存期 | 余票读模型、缓存预热、读路径与写路径分离 | R3、R4、R5、R6、R15 |
| P2 | 抢票主链路期 | Redis Lua 原子预扣 + 异步落账 + 超时回滚 | R1、R2、R10 |
| P3 | 异步化与拆分期 | MQ 落地、服务拆分、支付与通知异步化 | R8、R9、R14、R17 |
| P4 | 一致性与验证期 | 对账任务、并发测试、压测、故障演练 | 全部（验证）、R13、R18 |
| P5 | 容量期 | 限流精细化、分片、排队削峰、多机房 | R11、R16 |

**为什么要分阶段**：一次性引入 Redis + MQ + 分片会让"出问题时不知道是哪一层的问题"。P0 先用数据库把语义跑对（哪怕性能差），后面每一层都是替换实现而**不改变语义**，这样正确性始终有一个已知正确的参照物。

### 0.3 风险总览

| 编号 | 风险 | 严重度 | 解决阶段 |
|---|---|---|---|
| R1 | 超卖：库存被扣成负数 | 致命 | P0 / P2 |
| R2 | 少卖：预扣后未支付且未回滚 | 高 | P2 / P3 |

| R8 | 消息重复消费 | 高 | P3 |
| R9 | 消息丢失：扣了库存没订单 / 付了钱没推进 | 致命 | P3 |

## 1. R1 超卖：库存被扣成负数

**严重度：致命。** 这是本系统唯一"不可事后补救"的错误 —— 票已经卖给了两个人，其中一人上车时会被拒。

### 触发场景（时序）

数据库方案下的典型时序（这是最经典的并发缺陷，必须能背出来）：

```
库存 stock = 1
T1: 线程 A 执行 SELECT stock FROM t_ticket_stock WHERE id=1        -- 读到 1
T2: 线程 B 执行 SELECT stock FROM t_ticket_stock WHERE id=1        -- 也读到 1
T3: 线程 A 判断 1 >= 1，执行 UPDATE ... SET stock = 1 - 1 = 0       -- 成功
T4: 线程 B 判断 1 >= 1，执行 UPDATE ... SET stock = 1 - 1 = 0       -- 也"成功"
结果：卖出 2 张，库存 0。超卖 1 张，且数据库里看不出任何异常。
```

Redis 方案下的错误时序（把"先查后减"从数据库搬到 Redis，问题原样保留）：

```
T1: 线程 A GET stock -> 1
T2: 线程 B GET stock -> 1
T3: 线程 A DECRBY stock 1 -> 0
T4: 线程 B DECRBY stock 1 -> -1        -- 扣成负数
```

**共同根因**：**"读取—判断—写入"三步不是原子的**。任何把它拆成两步以上操作的实现，在并发下都可能超卖。

### 后果

- 同一座位卖给多人，属于业务事故，需要人工赔付与改签；
- 已支付订单无法交付，触发批量退款与投诉；
- 更隐蔽的是：数据库里库存为 0、订单数为 N+1，**只有对账才能发现**（所以第 19 章的对账不是可选项）。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 核心手段 | Redis + Lua 脚本，把"读 + 判断 + 减"放进一次脚本执行。Lua 脚本在 Redis 中**原子执行**，脚本执行期间不会被其他命令插入 | 同左；超大规模时进一步把扣减分桶（把一份库存拆成多个子库存，各自在独立 key 上扣减，降低单 key 竞争） |
| 兜底约束 | 数据库层加**带条件的原子更新**，用 `total - sold >= 1` 作为 WHERE 条件，让数据库自己保证不会减成负数 | 同左；再加 CHECK 约束或触发器做最后一道防线（不同数据库支持情况不同，**待验证**本项目所用数据库的约束能力） |
| 读模型的定位 | 余票展示走缓存，**缓存值绝不参与扣减决策** | 同左 |
| 幂等 | 每次扣减必须带业务幂等键（见 R7），重复请求不重复扣减 | 同左，并把幂等键写进扣减流水，可追溯 |

**本项目选用的 Lua 脚本**（只有这段逻辑必须靠代码才能讲清，因为"是否原子"取决于它）：

```lua
-- KEYS[1] = 库存 key，例如 stock:{trainId}:{travelDate}:{seatType}
-- ARGV[1] = 本次扣减数量
-- 返回：>=0 表示扣减后的剩余量；-1 表示 key 不存在（未预热，需回源）；-2 表示售罄
local left = tonumber(redis.call('GET', KEYS[1]))
if left == nil then return -1 end
if left < tonumber(ARGV[1]) then return -2 end
return redis.call('DECRBY', KEYS[1], ARGV[1])
```

调用方按返回值分支：`>=0` 扣减成功；`-2` 售罄，直接返回"没票了"；`-1` 说明未预热，**回源查库后重新预热再扣，不能跳过预热直接扣**（否则会出现"Redis 里没这个 key"被当成"无限库存"）。

**数据库兜底的条件更新**（短，但它是防超卖的最后一道防线）：

```sql
UPDATE t_ticket_stock
   SET sold_qty = sold_qty + 1, version = version + 1
 WHERE train_id = ? AND travel_date = ? AND seat_type = ?
   AND total_qty - sold_qty >= 1;   -- 关键：把"判断"交给数据库
-- 判影响行数：0 表示扣减失败（售罄或并发冲突），绝不能当成功
```

注意这条 SQL 与"先 SELECT 再 UPDATE"的本质区别：**判断条件在 UPDATE 语句内部**，由数据库在行锁保护下求值，因此天然原子。这也是为什么 P0 阶段用数据库也能不超卖 —— 慢，但对。

### 替代方案对比

| 方案 | 是否防超卖 | 缺点 | 取舍 |
|---|---|---|---|
| 先查后改（应用层判断） | **否** | 并发下必超卖 | 禁用 |
| `SELECT ... FOR UPDATE` 悲观锁 | 是 | 热点行排队，事务持有行锁，连接池被占满（见 R10） | P0 可用，P2 被 Redis 方案替换 |
| 乐观锁（version 重试） | 是 | 热点冲突率高时重试风暴，重试流量放大 | 否 |
| 数据库条件更新（`WHERE total - sold >= 1`） | 是 | 热点行写竞争仍在 | **保留为兜底** |
| Redis + Lua 原子扣减 | 是 | 需要处理 Redis 与 DB 的最终一致（R3）、预扣未落单（R2） | **是（P2 主方案）** |
| 分布式锁包住整个扣减 | 是 | 锁的粒度大、持锁时间长；锁服务本身成为瓶颈与单点 | 否（除非扣减逻辑本身无法原子化） |

### 在哪个阶段解决

- **P0**：数据库条件更新 + 唯一约束，保证单体阶段就不超卖（此时性能不是目标）。
- **P2**：切换到 Redis Lua 原子预扣，数据库条件更新退化为落账时的兜底校验。
- **P4**：用第 19 章的三种手段证明不超卖（这一步不能省：**"我用了 Lua"不是证据，"我验证过"才是**）。

## 2. R2 少卖：预扣成功但订单未创建 / 未支付且未回滚

**严重度：高。** 不影响正确性（不会多卖），但**直接损失收入**，且用户会反复投诉"明明有票却买不到"。

### 触发场景（时序）

```
T1: order-service 调用 inventory 预扣成功（Redis 库存 -1）
T2: 写订单表时数据库连接超时 / 应用实例被重启 / 抛出未捕获异常
T3: 用户侧看到"下单失败，请重试"，库存少了一张，但没有对应订单
T4: 用户重试，又扣一张……（如果没有任何补偿，库存会被"吃掉"）
```

另一个常见分支：

```
T1: 订单创建成功，状态 = 待支付，库存已预扣
T2: 用户不付款、关掉页面、或者支付渠道跳转失败
T3: 没有任何人把这张票放回去 —— 直到有定时任务发现它
```

### 后果

- 库存"泄漏"：账面售罄，实际有大量票无人购买；
- 用户看到"有票但下单失败"（实际是被别人未支付的订单占着）；
- 泄漏量随并发升高而放大，**且没有对账就无人知道**。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 预扣的时效性 | 预扣时同时写一个**带 TTL 的占位记录**（例如 `order:lock:{orderNo}` 与库存 key 关联），TTL 到期即视为放弃 | 同左；TTL 按支付渠道的超时时间与业务容忍度设定 |
| 状态机兜底 | 订单状态机里"待支付"有明确的超时时间，超时任务用条件更新迁移到"已取消"并**发消息触发库存回滚** | 同左，且超时取消做成幂等操作（重复取消不影响库存） |
| 回滚的可靠性 | 回滚走 MQ，消费端幂等；回滚失败进重试队列，最终由对账任务发现并人工/自动修正 | 同左，并监控"待回滚"积压量 |
| 进程崩溃导致的缺口 | 库存流水表 `t_stock_flow` 记录每一次扣减；对账任务比对"流水 - 有效订单" | 同左；更严格的做法是两阶段（先写"预扣记录"再扣减），使缺口本身可查询 |
| 监控 | **待压测**后确定"预扣未落单数量"的告警阈值 | 常规监控项：待支付订单数、回滚积压量、库存流水与订单差异数 |

**关键设计选择**：回滚动作由"超时取消"驱动，而不是由"用户点击取消"驱动。用户可能不点、可能点了两次、可能在支付成功后才点 —— 只有超时任务这一个**确定性触发点**，才能保证回滚一定发生。

### 替代方案对比

| 方案 | 为什么不选 |
|---|---|
| 不做超时回滚，靠用户主动取消 | 用户不会主动取消，库存必然泄漏 |
| 预扣时不设 TTL，只靠订单超时 | 进程崩溃后订单都没写成功，超时任务无处触发 → 必须给预扣本身设 TTL |
| 定时全量扫描库存与订单核对并自动修正 | 修正逻辑危险（可能误回滚已支付订单，见 R17）；扫描成本高。正确做法是**扫描只产出差异报告，修正走幂等的回滚接口** |

### 在哪个阶段解决

P2（预扣 + TTL）与 P3（超时取消经 MQ 驱动回滚），P4 用对账验证。

## 3. R3 缓存与数据库余票不一致

**严重度：高。** 但它和 R1 有本质区别：**不一致本身不致命，致命的是拿不一致的数据做决策**。

### 触发场景（时序）

```
T1: 用户 A 下单成功，Redis 库存 100 -> 99，DB 落账消息还在 MQ 里排队
T2: 用户 B 查询余票，读到缓存 99 或数据库 100（取决于读哪边）
T3: 用户 B 看到"有票"并下单，实际扣减在 Redis 上，结果以 Redis 为准 —— 正确
T4: 但如果某个环节改成"用数据库的余票判断能不能放行"，T3 这一步就会超卖
```

真正危险的时序是"缓存更新与数据库更新顺序错乱"：

```
T1: 线程 A 更新数据库 sold_qty = 1
T2: 线程 B 更新数据库 sold_qty = 2
T3: 线程 B 先写缓存 stock = 98
T4: 线程 A 后写缓存 stock = 99        -- 缓存里是旧值，且它会长期存在
结果：数据库 98，缓存 99，缓存"看起来"多了一张票，且不会自愈。
```

### 后果

- 用户看到有票但下单失败（体验问题，可接受）；
- 用户看到无票但实际有票（收入损失，且用户不会重试）；
- 若缓存被用作决策依据 → **直接导致超卖**。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 权威定义 | **明确写死：扣减的权威是 Redis，账目的权威是数据库。** 两者职责不重叠 | 同左，并把这条规则写进代码注释与接口文档 |
| 更新顺序 | 采用"**先写数据库（或先发落账消息），再删缓存**"，而不是"更新缓存" —— 删除比更新安全，因为删除后的回源是幂等的 | 同左；缓存删除失败进重试队列（删除失败的消息也要重试） |
| 并发写覆盖 | 用"删除缓存"避免 T4 那种乱序写入（两个线程都只发删除指令，谁先谁后都不会留下错误值） | 同左；延迟双删作为兜底（**延迟时长待压测**，太短无效，太长影响体验） |
| 自愈 | 缓存 key 设置 TTL，即使某次更新失败，也会在 TTL 后回源修正 | 同左；对账任务定期抽样比对缓存与数据库 |
| 读路径 | 查询走缓存，**缓存未命中时查库并回填**；绝不因为"缓存有值"就跳过校验 | 同左 |
| 决策路径 | 下单时**不查缓存余票**，直接调 inventory 的扣减接口，由扣减结果决定成败 | 同左 |

**一句话记忆**：**缓存可以撒谎，扣减不会。** 展示用缓存，裁决用扣减。

### 替代方案对比

| 方案 | 为什么不选 |
|---|---|
| 强一致（所有读都查数据库） | 读流量全部打到数据库，失去缓存的意义 |
| 用分布式锁保证缓存与库的更新原子 | 锁粒度太大、开销高，且跨 Redis 与数据库无法真正原子 |
| 只信任缓存（数据库只做异步落账） | 数据库失去账本作用，一旦 Redis 丢失数据（重启、误删）将无法恢复，也无法对账 |
| 本项目：Redis 权威扣减 + 数据库异步记账 + 删除式缓存更新 + 对账 | 接受短暂不一致，换取性能与可恢复性 |

### 在哪个阶段解决

P1（读模型与更新策略）、P2（明确权威归属），P4（对账验证）。

## 4. R4 缓存穿透：查询不存在的车次 / 日期

**严重度：中。** 单独看不致命，但**被脚本利用时会变成打垮数据库的手段**。

### 触发场景（时序）

```
T1: 攻击者或异常客户端用不存在的 trainId / 日期疯狂请求查询接口
T2: 缓存永远不命中（因为该数据不存在，永远不会被缓存）
T3: 每个请求都穿透到数据库
T4: 数据库被大量"注定查不到"的查询打满
```

### 后果

数据库 CPU 被无效查询占满，正常查询与扣减一起变慢；属于"成本极低的攻击"。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 空值缓存 | 查询不存在的数据时，缓存一个**短 TTL 的空标记**，避免同一无效请求反复穿透 | 同左；空值 TTL 要比正常数据短得多，防止数据新增后长时间不可见 |
| 参数校验 | 在 gateway 与 train-service 入口校验参数格式（日期范围、ID 范围、席别枚举），非法直接拒绝，不进缓存也不查库 | 同左；把高频非法参数加入黑名单 |
| 布隆过滤器 | 本项目数据量小，**不引入**；用空值缓存 + 参数校验已足够 | 车次/日期组合量级大时，用布隆过滤器前置拦截（注意其"假阳性"特性与重建成本，**待验证**具体实现路线） |
| 限流 | 与 R11 共用网关限流规则，按用户与 IP 双维度 | 同左，且对"查询失败率高"的调用方做单独限流 |

### 在哪个阶段解决

P1。

## 5. R5 缓存击穿：热点车次缓存过期的瞬间

**严重度：高。** 与穿透的区别：穿透是"查不存在的数据"，击穿是"查一个非常热门的 key，而它刚好过期了"。

### 触发场景（时序）

```
T1: 热门车次的余票 key 到期（TTL 到点），key 被删除
T2: 开售瞬间，成千上万个请求同时到达
T3: 全部未命中缓存，全部回源查数据库
T4: 数据库瞬时被打满，可能连带拖垮同库的其他查询
T5: 回源结果还要写回缓存，写回动作本身又是一波压力
```

### 后果

开售瞬间数据库被单个热 key 的回源流量打满；表现为"只有热门车次查询变慢，其他车次正常"，排查时容易被误判。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 逻辑过期 | 缓存值里带一个"逻辑过期时间"，**物理上不设 TTL 或设很长**。读到逻辑过期时，返回旧值的同时**只有一个线程去异步重建** | 同左，通常配合独立的重建线程池 |
| 互斥重建 | 用分布式锁（`SETNX` 带 TTL）保证同一 key 只有一个线程回源，其余线程短暂等待或直接返回旧值 | 同左；锁的等待时间要短，避免请求堆积 |
| 热点预热 | 开售前主动把热门车次的库存与车次信息刷进缓存（见 R16），并**在开售期间不依赖 TTL** | 同左，且热身任务按车次热度分级 |
| 热点探测 | 本项目先用"人工指定热门车次"的方式（教学项目可控） | 用访问频次统计自动识别热 key（见 R15） |

**关键取舍**：击穿场景下"返回一个可能略旧的余票数"是可接受的（余票允许秒级陈旧），"让数据库被打满"是不可接受的。所以**优先返回旧值，而不是优先保证新鲜度**。但要注意：这个陈旧只影响展示，扣减仍然走 Lua 原子操作，不受影响。

### 在哪个阶段解决

P1。

## 6. R6 缓存雪崩：大量 key 同时失效 / Redis 本身不可用

**严重度：高。**

### 触发场景（时序）

```
场景 A（同时过期）：
T1: 预热任务在开售前统一给所有车次的余票设置了相同的 TTL
T2: 开售后经过一个 TTL 周期，所有 key 在同一秒集体失效
T3: 全部请求回源，数据库瞬时压力等于"没有缓存"

场景 B（Redis 故障）：
T1: Redis 主节点故障 / 网络分区
T2: 所有缓存读写失败
T3: 如果代码里有"缓存不可用则查库"的兜底逻辑，全部流量瞬间压到数据库
T4: 数据库被打垮 —— 故障从缓存层扩散到数据层
```

### 后果

缓存层故障演变成全站故障。**场景 B 是最危险的：一个"看起来很贴心"的兜底逻辑，会把局部故障放大成全局故障。**

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| TTL 打散 | 给 TTL 加**随机抖动**（在基准值上叠加随机量），避免同时失效 | 同左；按 key 类型分组设置不同基准 TTL |
| 多级缓存 | gateway/应用本地缓存（短 TTL）+ Redis 两级；本地缓存能挡住 Redis 抖动期的部分流量 | 同左；本地缓存失效后用"旧值 + 异步刷新"策略 |
| Redis 故障时的行为 | **明确决策：缓存不可用时，查询接口降级返回"稍后重试"，扣减接口快速失败。绝不自动降级为"直接查库"** —— 因为那会把数据库打死 | 同左；若必须支持"缓存挂了还能用"，则必须配合**数据库侧的强限流**，把放行流量限制在数据库能承受的范围内（阈值待压测） |
| 高可用 | 使用 Redis 的主从/哨兵或集群形态（具体形态待验证部署条件） | 同左，并做故障演练 |
| 预热 | 见 R16 | 同左 |

**必须记住的取舍**：**"降级到数据库"不是兜底，是把故障扩散到最后一层。** 正确的兜底是"限流 + 快速失败 + 保住数据库"，因为数据库保住了，恢复就是瞬间的；数据库挂了，恢复要以小时计。

### 在哪个阶段解决

P1。

## 7. R7 重复下单：用户重复提交与网络重试

**严重度：高。** 这会消耗真实库存，且用户会认为"系统乱扣我钱"。

### 触发场景（时序）

```
T1: 用户点击"抢票"，请求发出
T2: 网络慢，用户没看到响应，又点了一次（或前端按钮未置灰）
T3: 两个请求几乎同时到达 order-service，各自生成不同订单号
T4: 两次调用 inventory 扣减，两次都成功（因为扣的是两张票）
结果：同一用户同一车次产生两张订单，占用两份库存。
```

另一个变体：Feign 调用超时后自动重试。响应丢失但**服务端实际已成功**，重试会造成第二次扣减。

### 后果

用户重复占座、重复支付；库存被无效占用；客服需要处理取消与退款。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 接口幂等键 | 客户端生成幂等键（requestId），服务端以它建立唯一约束。同一幂等键的重复请求返回**第一次的结果**，不重复执行业务 | 同左；幂等键有明确的有效期与清理策略 |
| 数据库唯一约束 | 订单表加唯一索引：同一用户 + 同一车次 + 同一日期 + 同一席别只允许一张**有效**订单 | 同左 |
| 重复购票业务规则 | 通过 `active_flag` 字段配合唯一索引实现"取消后可再买" | 同左 |
| 前端 | 提交后按钮置灰 + 请求去重（同一动作在飞行中不重复发） | 同左，但**前端防护不能作为服务端防线**，服务端必须独立可防 |
| 服务间重试 | 扣减接口**默认不自动重试**；确需重试时由业务层用幂等键重试 | 同左 |

**唯一索引的实现要点**（必须靠 DDL 才能讲清楚"取消后还能再买"）：

```sql
-- 有效订单 active_flag = 1；取消/退票后置为 NULL
-- MySQL 的唯一索引允许多个 NULL，因此同一用户可以有任意多张已取消订单，
-- 但最多只能有一张有效订单。
ALTER TABLE t_order
  ADD UNIQUE KEY uk_user_active (user_id, train_id, travel_date, seat_type, active_flag);
```

取消订单的语句必须同步把 `active_flag` 置空：

```sql
UPDATE t_order SET status='CANCELLED', active_flag=NULL
 WHERE order_no=? AND status='CREATED';
```

**注意**：这里把"状态迁移"和"释放唯一约束"放在同一条 UPDATE 里，保证两者原子（见 R12）。

### 替代方案对比

| 方案 | 为什么不选 |
|---|---|
| 只靠前端置灰 | 前端可被绕过，接口直接被调用时无防护 |
| 只靠分布式锁（按 userId 加锁） | 锁只能防瞬时并发，防不住"用户 1 分钟后又点一次"；且锁失效时有风险 |
| 只靠数据库唯一索引 | 能防住，但重复请求会在业务逻辑执行到写库时才失败，**库存可能已经被扣了** —— 所以必须"入口幂等 + 数据库唯一约束"两层 |
| 本项目：入口幂等键 + 唯一索引 + 状态迁移原子化 | 两层防护，任一层失效另一层仍有效 |

### 在哪个阶段解决

P0（唯一索引 + 条件更新），P2 补充入口幂等键。

## 8. R8 消息重复消费

**严重度：高。** 消息中间件普遍提供"至少一次"投递语义，**重复是常态，不是异常**。

### 触发场景（时序）

```
T1: 消费者处理完消息，业务已提交，但还没来得及提交消费位点（或应答丢失）
T2: 消息中间件认为消费失败，重新投递同一条消息
T3: 消费者再次执行"库存回滚"，库存被减了两次（或加了两次）
```

### 后果

库存被多回滚（少卖）或多扣减（超卖）；通知短信重复发送；统计数字翻倍。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 幂等键 | 每条消息带全局唯一的 `msg_id`；消费端用 `msg_id` 建立唯一约束或去重表 | 同左；去重表按时间分区并定期清理 |
| 状态机幂等 | 消费逻辑不写"把状态改成 X"，而写"**如果当前是 A 则改成 B**"（条件更新）。重复消费时条件不成立，自然无副作用 | 同左；这是最可靠的幂等方式，因为它不依赖额外的去重表 |
| 流水表 | `t_stock_flow` 用"业务单号 + 操作类型"做唯一约束，重复插入直接失败 | 同左 |
| 顺序 | 局部有序（同一订单的消息按分区键路由）可以减小乱序概率，但**不能替代幂等** | 同左 |

**核心原则**：**幂等应该做在业务语义里，而不是靠"消息只会来一次"的假设。** 条件更新式的状态迁移天然幂等，是首选实现。

### 在哪个阶段解决

P3。

## 9. R9 消息丢失：扣了库存但订单没落 / 付了钱但订单没推进

**严重度：致命。** 前者的表现是"少卖"，后者的表现是"用户付了钱但订单还是待支付"。后者会直接引发投诉与资金纠纷。

### 触发场景（时序）

```
路径一（下单侧）：
T1: order-service 完成库存预扣
T2: 准备写订单 + 发"订单已创建"消息
T3: 实例在写库成功后、发消息前崩溃 → 消息永远发不出去
结果：库存被扣，但下游（通知、统计、读模型投影）都不知道有这笔订单。

路径二（支付侧）：
T1: 支付渠道回调 payment-service，支付成功
T2: payment-service 更新支付单成功，发消息给 order-service 时崩溃
T3: 渠道不会因为你崩溃就重发（它认为已经通知成功，或它的重试窗口已过）
结果：用户已付钱，订单仍是待支付，最终可能被超时取消 —— 钱票两空。
```

### 后果

- 路径一：库存泄漏（少卖），对账才能发现；
- 路径二：**最严重**，用户资金已支付但订单被取消，属于需要人工介入的事故。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 本地事务与消息的原子性 | 用**本地消息表**：状态变更与消息记录在同一个数据库事务中提交，再由独立线程投递。**投递失败的消息留在表里重试**，不会丢 | 同左；也可用消息中间件事务消息语义（见拆分文档 4.5 的选型） |
| 支付侧兜底 | **不能只依赖回调**。必须有两条独立路径：① 回调实时处理；② 主动查询渠道支付结果（定时补偿，查"待支付但已超时"的订单） | 同左；第三条路径是**渠道对账文件**（日终批量核对），这是唯一能发现"双方记录不一致"的手段 |
| 回调的落库 | 回调先**原文落库**（`t_payment_callback_log`）再处理，即使处理失败也能重放 | 同左；回调日志保留时间要覆盖对账周期 |
| 消费端确认 | 业务处理成功才确认消息；处理失败进入重试队列（非无限重试，超过次数进死信并告警） | 同左 |
| 差异发现 | 对账任务（见第 19 章）定时比对：库存流水 vs 有效订单、支付单 vs 订单状态 | 同左 |

**关键结论**：**支付相关的链路必须有"回调 + 主动查询 + 对账文件"三层保障**。只做回调的系统，一定会在某个时刻出现"用户付了钱但订单没变"的情况。

### 在哪个阶段解决

P3（本地消息表 + 主动查询），P4（对账）。

## 10. R10 热点行锁竞争与连接池耗尽

**严重度：高。** 它不是正确性问题，但会让**整个服务不可用**，影响面远超单个车次。

### 触发场景（时序）

```
T1: 开售瞬间，某热门车次的扣减请求全部命中数据库的同一行
T2: 第一个事务拿到行锁，其余事务进入锁等待
T3: 等待的事务一直占用数据库连接（连接被"锁等待"而不是"计算"占着）
T4: 连接池被占满，后续请求连连接都拿不到
T5: 与该库无关的接口（查询订单、查车次）也一起超时 —— 因为它们共用同一个连接池
```

**关键点在第 5 步**：热点行的锁等待会通过**连接池**这个共享资源，把故障扩散到完全无关的业务上。这正是拆分文档第 1 章里"加机器无效"的原因 —— 热点在单行，加应用实例只会增加等待锁的连接数。

### 后果

服务整体不可用；增加实例反而可能加剧锁竞争（更多连接抢同一行锁）。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 扣减下沉 | 扣减走 Redis Lua，**不碰数据库行锁**（P2）；数据库只做异步落账 | 同左 |
| 落账的写入方式 | 落账操作按库存维度做**批量/合并提交**（把短时间内同一 key 的多次扣减合并成一次累加），减少数据库写次数 | 同左；合并的窗口大小待压测 |
| 连接池隔离 | 不同用途使用不同的连接池/数据源：交易写、查询读、定时任务各自独立，避免互相占满 | 同左；按服务实例角色（写实例/读实例）拆分连接池大小 |
| 超时 | 所有数据库操作设置**语句超时**，避免慢语句长期占用连接 | 同左 |
| 拆分 | 库存独立成服务（见拆分文档决策卡 A），使热点只影响库存服务，不影响查询 | 同左 |
| 进一步 | 库存分桶：一个车次的库存拆成 N 个子 key 分别扣减，把单点竞争变成 N 点竞争 | 同左（S3/S5 阶段）；代价是"某桶卖完但整体还有票"需要处理（可从其他桶借票，逻辑复杂度上升，本项目暂不做） |

### 替代方案对比

| 方案 | 为什么不选 |
|---|---|
| 加应用实例 | 热点在数据库单行，加实例不解决锁竞争 |
| 加大连接池 | 只是让更多连接进入锁等待，可能让数据库负载更高 |
| 提高事务隔离级别解决 | 隔离级别不解决热点竞争的排队本质，反而可能加重锁范围 |
| 扣减移出数据库（本项目） | 是唯一真正解决热点的方式；代价是引入最终一致性（R3）与补偿（R2） |

### 在哪个阶段解决

P2（扣减下沉）、P4（连接池隔离与超时参数调优，**待压测**）。

## 11. R11 脚本刷票与限流绕过

**严重度：中（业务风险高，技术风险可控）。**

### 触发场景（时序）

```
T1: 黄牛用脚本在开售瞬间发起远超正常用户量的请求
T2: 正常用户点击时排在这些请求后面，抢不到票
T3: 若限流只按 IP 做，脚本切换代理 IP 即可绕过
T4: 这些请求还会消耗系统容量，降低真实用户的成功率
```

### 后果

票被脚本抢走，真实用户流失；系统容量被无效流量消耗。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 网关限流 | 按"用户 + 接口 + IP"三个维度限流；未登录请求按 IP 限流，已登录按用户限流 | 同左；多级限流（接入层 / 网关 / 服务层），并做全局限额（总放行量） |
| 业务规则 | 同一乘车人 + 同一车次 + 同一日期只允许一张有效订单（R7 的唯一索引） | 同左；再加"同一证件号全平台购票数上限"等规则 |
| 人机校验 | 在下单前引入验证码（本项目在 P5 才做，早期流量可控） | 同左；高风险行为触发二次校验，而不是全量校验（全量会伤害正常用户） |
| 风控 | 本项目先内置简单规则（短时间下单次数、失败率、设备指纹），**不单独拆风控服务**（见拆分文档 3.3） | 独立风控服务，基于行为序列做模型判断 |
| 排队 | 见拆分文档 S4；排队本身也是一种公平性手段 | 同左（抽签式排队比先到先得更能对抗脚本） |
| 限流的位置 | **必须在网关做**，让被限流的请求在进入业务前就被拒绝，不消耗下游资源 | 同左，并且在负载均衡层做一层粗粒度防护 |

### 在哪个阶段解决

P5（核心），P0 先有业务唯一约束。

## 12. R12 订单状态机并发更新冲突

**严重度：致命。** 典型的"两个写入方覆盖同一行"问题，会产生用户无法接受的错误状态。

### 触发场景（时序）

```
T1: 支付回调到达，payment 通知 order：支付成功
T2: 与此同时，超时取消任务扫描到这张订单（它刚刚超过支付时限）
T3: 两个处理流程都读到订单当前状态 = CREATED
T4: 支付流程写 status = PAID
T5: 取消流程写 status = CANCELLED        -- 覆盖了 PAID
结果：用户已付款，订单却被取消；库存被回滚（可能卖给了别人）。
```

**根本问题**：状态迁移不是原子的"读—判断—写"，且两个触发源（外部回调、内部定时）天然并发。

### 后果

钱票两空、超卖（库存被错误回滚后又卖给别人）、用户投诉、需要人工对账修复。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 原子迁移 | **所有状态变更都用条件更新**，把"前态"写进 WHERE 条件，由数据库裁决谁先成功 | 同左 |
| 影响行数=0 的处理 | 明确每种迁移失败后走什么分支（例如"取消失败说明已支付 → 不取消、不回滚、记日志"） | 同左；失败分支必须有日志与告警，便于事后追溯 |
| 状态机定义 | 状态与允许的迁移显式枚举，**非法迁移直接拒绝**（而不是"想改就改"） | 同左 |
| 迁移日志 | 每次状态变更写 `t_order_status_log`（含前态、后态、触发源、时间） | 同左；这是排查"订单为什么变成这样"的唯一依据 |
| 触发源收敛 | 支付回调与超时取消都**只是"事件"**，真正的状态变更只发生在一个服务里（order-service） | 同左 |

**状态机定义**（必须靠它才能说清"哪些迁移非法"）：

```
CREATED   --支付成功-->  PAID
CREATED   --超时未支付 / 用户取消-->  CANCELLED
PAID      --出票流程成功-->  TICKETED
PAID      --申请退款-->  REFUNDING  --渠道退款成功-->  REFUNDED

非法迁移（必须被拒绝）：
CANCELLED --> PAID        （已取消的订单不可能收到有效支付）
CANCELLED --> TICKETED
REFUNDED  --> 任何状态
TICKETED  --> CANCELLED   （已出票不能直接取消，只能走退款）
```

**原子迁移语句**（短，但它就是整个防线的全部）：

```sql
-- 只有当前仍是 CREATED 才允许取消；影响行数为 0 表示订单已被支付，取消必须放弃
UPDATE t_order
   SET status = 'CANCELLED', active_flag = NULL, cancel_time = NOW()
 WHERE order_no = ? AND status = 'CREATED';

-- 只有当前仍是 CREATED 才允许置为已支付
UPDATE t_order
   SET status = 'PAID', pay_time = NOW()
 WHERE order_no = ? AND status = 'CREATED';
```

两条 SQL 天然互斥：**谁先执行成功，另一个必然影响 0 行**。这比加分布式锁更可靠，因为它不依赖锁服务的可用性。

### 替代方案对比

| 方案 | 为什么不选 |
|---|---|
| 用分布式锁串行化同一订单的处理 | 可行但更重；锁服务不可用时业务不可用。条件更新不依赖外部组件，是更底层的保障 |
| 乐观锁 version 字段 | 同样可行，但需要额外读取 version 再比较；条件更新把前态直接写进 WHERE，更简洁且不需要额外字段 |
| 单线程队列串行处理所有订单事件 | 吞吐受限；且顺序消息本身也需要幂等与状态机兜底（R8） |
| 本项目：状态机 + 条件更新 | 无外部依赖，并发安全，失败分支明确 |

### 在哪个阶段解决

P0（状态机 + 条件更新），P3（引入支付回调触发源后重点验证）。

## 13. R13 分布式锁失效

**严重度：高。** 锁被误用比不用锁更危险，因为它会带来"以为安全"的错觉。

### 触发场景（时序）

**场景 A：锁超时释放，业务还没做完**

```
T1: 线程 A 获取锁，锁 TTL = 10 秒
T2: 业务因 GC / 慢 SQL / 网络抖动执行了 15 秒（TTL 到期，锁自动释放）
T3: 线程 B 获取到锁，开始执行同一段业务
T4: 线程 A 和 B 同时处于临界区 → 互斥失效
```

**场景 B：误删别人的锁**

```
T1: 线程 A 的锁到期自动释放，线程 B 获取了同名锁
T2: 线程 A 执行完毕，执行 DEL key 释放锁
T3: 删掉的是线程 B 的锁 → 线程 C 又能获取锁
T4: 临界区里同时有 B 和 C
```

**场景 C：锁与事务不同步**

```
T1: 在事务方法内加锁，业务执行完毕，锁释放
T2: 事务此时还没提交（锁在事务提交前就释放了）
T3: 其他线程拿到锁，读到的仍是旧数据 → 脏读式并发
```

### 后果

互斥失效 → 重复扣减 / 超卖；排查极其困难，因为现象偶发且依赖时序。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 锁的必要性审查 | **先问"没有锁能不能做对"**。本项目的核心扣减靠 Lua 原子脚本、状态迁移靠条件更新，**都不需要分布式锁**；锁只用于"缓存重建"这类场景 | 同左；把锁的使用范围限制到最小 |
| 加锁与释放的正确姿势 | 用成熟客户端（如 Redisson 这类路线），它负责"锁续期（看门狗）"与"释放时校验持有者"，避免场景 A、B | 同左；并监控锁等待时间与续期失败 |
| 事务边界 | 加锁范围必须**包含事务提交**，绝不能"锁在事务内、释放早于提交" | 同左；代码评审重点检查项 |
| 业务兜底 | 即使锁失效，正确性仍由数据库唯一约束与条件更新保证 —— **锁只是性能优化，不是正确性防线** | 同左 |

**这是一条重要的设计原则**：**正确性永远不能只依赖分布式锁。** 锁的失效是概率事件，而数据错误是确定事件。凡是"只有锁能保证正确"的设计，都要补一层数据库约束。

### 在哪个阶段解决

P2（缓存重建用锁）、P4（故障演练验证锁失效时的行为）。

## 14. R14 支付回调重复、乱序、伪造

**严重度：高。**

### 触发场景（时序）

```
重复：
T1: 渠道回调 payment-service，处理成功，应答超时
T2: 渠道认为失败，按自己的重试策略重复回调（可能多次）
T3: 若不幂等，支付单被重复处理，可能触发重复的后续动作

乱序：
T1: "支付成功"与"支付失败/关闭"两条通知几乎同时到达
T2: 处理顺序不确定
T3: 若不做状态校验，最终状态取决于谁最后写

伪造：
T1: 攻击者直接向回调地址 POST 伪造的"支付成功"
T2: 若不验签，订单被标记为已支付，票被白拿
```

### 后果

重复处理导致订单状态异常；伪造回调导致**资金损失**（票被白拿）。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 验签 | 回调必须验签（用渠道密钥校验签名），并且校验**金额与订单号与本地支付单一致** | 同左；密钥管理走配置中心/KMS，不硬编码 |
| 原文留痕 | 所有回调原文写入 `t_payment_callback_log`（含接收时间、来源、处理结果），先落库再处理 | 同左；保留周期覆盖对账周期 |
| 幂等 | 支付单状态用条件更新迁移（仅当处于"待支付"时才允许变成"成功"），重复回调影响行数为 0，直接返回成功应答 | 同左 |
| 乱序 | 状态机拒绝非法迁移（如从"已成功"到"失败"）；对"失败通知晚于成功通知"的情况，以**已成功的状态为准**并记录日志 | 同左 |
| 应答 | 处理逻辑只做"验签 + 落库 + 发消息"，立刻应答渠道，避免渠道因超时而重试 | 同左 |
| 兜底 | 主动查询 + 渠道对账文件（见 R9） | 同左 |

### 在哪个阶段解决

P3。

## 15. R15 Redis 热 key 与大 key

**严重度：中。**

### 触发场景（时序）

```
热 key：
T1: 某条明星车次，几乎所有请求都访问同一个库存 key
T2: 这个 key 落在集群的某一个节点上
T3: 该节点 CPU 打满，其他节点空闲 —— 集群的横向扩展能力在这个 key 上失效

大 key：
T1: 把"某车次所有日期的余票"塞进一个 Hash 或一个 List
T2: 每次读写都要序列化/传输整个结构
T3: 单次操作耗时长，阻塞 Redis 单线程，影响该实例上的所有其他命令
```

### 后果

Redis 单节点成为瓶颈或出现长耗时命令，表现为"Redis 整体变慢"，实际只与少数 key 有关。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| key 设计 | 库存 key 按"车次 + 日期 + 席别"拆分，**天然分散**，不做大聚合结构 | 同左；key 的设计规范写进开发约定 |
| 本地缓存 | 对极热 key 在应用侧加本地缓存，把 Redis 访问量降一个数量级 | 同左，配合热点探测自动识别 |
| 热点探测 | 本项目**待验证**：先用人工指定 + 监控慢查询的方式发现 | 用访问频次统计（如客户端埋点/代理层统计）自动识别热 key |
| 分桶 | 库存分桶（见 R10）同时也是热 key 的解法 | 同左 |
| 大 key 治理 | 禁止在 Redis 存集合型的业务数据；只存标量值（库存数字、状态标记） | 同左；定期扫描大 key 并治理 |

### 在哪个阶段解决

P1（key 设计规范）、P4（监控与治理）。

## 16. R16 开售瞬间流量尖峰与预热未完成

**严重度：高。**

### 触发场景（时序）

```
T1: 系统在开售前 1 分钟才开始预热缓存，预热任务执行了 90 秒（数据量大或慢查询）
T2: 开售时刻到达，部分车次的库存 key 还没写进 Redis
T3: 扣减请求返回 -1（key 不存在），触发"回源查库 + 重新预热"
T4: 大量请求同时回源，数据库被预热流量打满
T5: 同时，用户查询缓存也大量未命中 → 双重压力
```

### 后果

开售第一秒系统就不可用，而这正是流量最高、最不能出错的时刻。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 预热提前量 | 预热必须在开售前**足够早**完成，并留出校验时间（具体提前量待压测确定） | 同左；预热分批次、限速进行，避免预热本身打满数据库 |
| 预热完成校验 | 预热后有一个**校验步骤**：统计 key 数量与预期是否一致，不一致则告警并重试 | 同左；校验不通过时**考虑推迟开售或降级提示**，而不是硬着头皮开 |
| 回源保护 | 扣减返回 -1 时，回源必须**加锁 + 限流**（同一 key 只允许一个线程回源），其余快速失败 | 同左；回源流量单独限流 |
| 开售前的容量准备 | 提前扩容（扩容需要时间，必须在开售前完成，不能等流量来了再扩） | 同左；结合容量规划做定时扩容 |
| 削峰 | 见拆分文档 S4 排队层 | 同左 |
| 预热失败的可观测性 | 预热任务必须输出"预期 key 数 / 实际写入数 / 失败列表"，并接入告警 | 同左 |

### 在哪个阶段解决

P1（预热机制）、P5（容量与削峰）。

## 17. R17 库存回滚误伤已支付订单

**严重度：致命。** 这是 R12 的下游表现，单独列出是因为**它的后果是超卖**。

### 触发场景（时序）

```
T1: 订单超时取消任务扫描到订单 X（状态 CREATED），准备取消并回滚库存
T2: 与此同时，支付回调到达，订单 X 被置为 PAID
T3: 取消任务没有重新检查状态，直接执行库存回滚 → 库存 +1
T4: 刚放出的这张票被另一个用户买走（第二张订单）
结果：一张票卖了两次；第一个用户已付款却被取消。
```

### 后果

**超卖 + 用户资金纠纷**，是最严重的一类事故。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 回滚的前提 | **回滚必须以"状态迁移成功"为前提**：先执行条件更新（`WHERE status='CREATED'`），只有在影响行数为 1 时才发回滚消息 | 同左 |
| 回滚的幂等 | 回滚消息带唯一业务键，消费端用流水表唯一约束保证同一订单只回滚一次 | 同左 |
| 回滚的校验 | 回滚前再次确认订单未支付（读一次订单状态作为二次校验，条件更新作为最终裁决） | 同左；两道检查的成本极低，收益极高 |
| 对账 | 对账任务校验"库存 + 有效订单 = 总量"，任何偏差告警 | 同左 |

**一句话**：**永远不要"先回滚库存再看订单状态"**，必须先原子地确认订单确实被取消了，再回滚。顺序反了就会超卖。

### 在哪个阶段解决

P3（与 R12 同一批处理）。

## 18. R18 慢 SQL / 连接池 / GC 拖垮整个服务

**严重度：高。** 这是"间接风险"：本身不是并发缺陷，但会在高并发下被放大成整体不可用。

### 触发场景（时序）

```
T1: 某个查询缺少合适索引（例如"按用户查订单"没走索引）
T2: 单次查询耗时上升，占用连接时间变长
T3: 并发上来后，连接池被慢查询占满
T4: 其他所有接口拿不到连接，全部超时
T5: 上游（gateway）的重试进一步放大流量，形成正反馈 → 雪崩
```

### 后果

与 R10 类似：故障通过共享资源（连接池、线程池）扩散，影响面远超慢查询本身。

### 解决方案

| 维度 | 本项目怎么做 | 生产怎么做 |
|---|---|---|
| 索引 | 交易相关查询必须有覆盖索引；上线前用执行计划检查，禁止全表扫描出现在交易链路上 | 同左；慢查询日志 + 定期 Review |
| 语句超时 | 所有数据库访问设置语句超时，杜绝无限等待 | 同左 |
| 连接池隔离 | 交易写、查询读、定时任务使用独立连接池（见 R10） | 同左 |
| 线程池隔离 | 不同下游调用使用独立线程池/信号量（见拆分文档 6.3） | 同左 |
| 重试放大 | 上游重试必须带**退避**与**次数上限**，且只对幂等操作重试 | 同左；引入熔断，在下游持续失败时直接快速失败 |
| 压测 | 每个阶段结束后做压测，观察 P99 而不只是平均值；用故障注入验证降级行为 | 同左；常态化压测与容量评估 |
| 参数 | 连接池大小、线程数、超时的具体取值：**待压测** | 同左 |

### 在哪个阶段解决

P4。

## 19. 如何证明不会超卖

这一章是本文最重要的部分。**"我用了 Redis + Lua"不是证据，"我验证过"才是。**

下面给出三种互相独立、互相补位的验证手段。它们分别覆盖不同的失败模式，**三种都要做**：

| 手段 | 覆盖的失败模式 | 能发现的问题 | 不能发现的问题 |
|---|---|---|---|
| 并发单元测试 | 单实例内的并发竞争 | 代码里的"先查后改"、锁失效、非原子操作 | 多实例部署下的问题、消息重复、MQ 丢失 |
| JMeter 压测 + 数据校验 SQL | 真实请求链路下的竞争 | 端到端链路、缓存与数据库的不一致、连接池问题 | 低频的时序竞态（除非跑足够多轮） |
| 定时对账任务 | 长期运行中的累积差异 | 消息丢失、回滚遗漏、程序 bug 造成的库存泄漏 | 实时问题（对账是滞后的） |

### 19.1 手段一：并发单元测试（CountDownLatch）

**原理**：`CountDownLatch` 让 N 个线程在同一个时刻被放行，制造真实的并发竞争。如果代码里存在"先查后改"，这个测试几乎必然失败；反之，它能稳定通过（不是概率性的侥幸）。

```java
@Test
void 并发扣减不应超卖() throws Exception {
    int threads = 200;      // 并发线程数：参数，待压测后调整
    int stock   = 100;      // 初始库存：参数
    Long trainId = 1L; String date = "2026-10-01"; int seatType = 1;

    CountDownLatch ready = new CountDownLatch(threads);  // 所有线程就绪的信号
    CountDownLatch start = new CountDownLatch(1);         // 发令枪
    AtomicInteger success = new AtomicInteger();
    ExecutorService pool = Executors.newFixedThreadPool(threads);

    for (int i = 0; i < threads; i++) {
        pool.submit(() -> {
            ready.countDown();
            try {
                start.await();                 // 全部线程阻塞在这里，直到发令
                if (seckillService.tryDeduct(trainId, date, seatType) > 0) {
                    success.incrementAndGet();
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }
    ready.await();          // 等所有线程都起来了再发令，否则先跑的线程"偷跑"，压力不足
    start.countDown();      // 同一瞬间放行
    pool.shutdown();
    pool.awaitTermination(1, TimeUnit.MINUTES);

    assertEquals(stock, success.get(), "成功扣减数必须恰好等于库存");
    assertEquals(0, stockRepository.leftQty(trainId, date, seatType), "剩余库存必须恰好为 0");
    assertTrue(orderRepository.countActive(trainId, date, seatType) <= stock, "有效订单数不得超过库存");
    assertFalse(stockRepository.hasNegativeStock(), "不允许出现负库存");
}
```

**这个测试的边界（必须说清楚，否则会给人虚假的信心）**：

- 它验证的是**单实例**内的并发正确性。多实例部署时 Redis 是共享的，Lua 的原子性依然成立，但缓存重建、锁、回滚等环节可能需要独立的集成测试。
- 断言里最重要的是 **`成功数恰好等于库存`** 与 **`不允许负库存`** 这两条。只断言"没有负库存"是不够的 —— 那可能是大量请求失败导致的。
- 还应该补一个**反向测试**：`threads < stock` 时，成功数应等于 `threads`（证明不是所有请求都失败）。否则一个"永远返回失败"的实现也能通过上面的测试。

### 19.2 手段二：JMeter 压测 + 数据校验 SQL

**压测设计要点**：

1. 用固定库存的车次做压测对象（例如库存设为参数 S），并发用户数、循环次数都要**大于 S**，确保库存会被打满；
2. 记录压测的**成功订单数**、**失败响应数**；
3. 压测结束后**不要只看看报表**，必须跑下面的校验 SQL。

**注意跨库问题**：拆分成微服务后 `t_order`（order 库）与 `t_ticket_stock`（inventory 库）不在同一个数据库，**校验 SQL 不能在交易库上直接 JOIN**（这也正是拆分文档 5.3 说的跨库 JOIN 禁令）。正确做法是把两侧数据同步到**离线分析库**（通过 binlog 或消息同步），在分析库的宽表上执行校验。下面 SQL 中的 `ods_order` / `ods_stock` 就是这种同步后的表。

**校验 SQL 1：不允许出现负库存（最直接的断言）**

```sql
SELECT train_id, travel_date, seat_type, total_qty, sold_qty
  FROM ods_stock
 WHERE sold_qty > total_qty OR sold_qty < 0;
-- 期望：0 行。有任何一行都是超卖，必须立即定位。
```

**校验 SQL 2：成功订单数必须等于实际售出量**

```sql
SELECT s.train_id, s.travel_date, s.seat_type,
       s.sold_qty                          AS 库存表记录的售出量,
       COUNT(o.id)                         AS 实际有效订单数,
       s.sold_qty - COUNT(o.id)            AS 差异
  FROM ods_stock s
  LEFT JOIN ods_order o
         ON o.train_id    = s.train_id
        AND o.travel_date = s.travel_date
        AND o.seat_type   = s.seat_type
        AND o.status IN ('CREATED','PAID','TICKETED')   -- 有效订单：已取消的不算
 GROUP BY s.train_id, s.travel_date, s.seat_type
HAVING 差异 <> 0;
-- 期望：0 行。
-- 差异 > 0：多卖了（超卖，最严重）
-- 差异 < 0：少卖（有库存泄漏或被误回滚，对应 R2 / R17）
```

**校验 SQL 3：库存流水之和必须与售出量吻合**

```sql
-- t_stock_flow 记录每一次扣减（负数）与回滚（正数）
SELECT f.train_id, f.travel_date, f.seat_type,
       SUM(f.change_qty)                                   AS 流水净变化,
       s.total_qty - s.sold_qty                            AS 账面剩余,
       s.total_qty - SUM(f.change_qty)                     AS 流水推算剩余
  FROM ods_stock_flow f
  JOIN ods_stock s
    ON s.train_id = f.train_id AND s.travel_date = f.travel_date AND s.seat_type = f.seat_type
 GROUP BY f.train_id, f.travel_date, f.seat_type, s.total_qty, s.sold_qty
HAVING 账面剩余 <> 流水推算剩余;
-- 期望：0 行。这条 SQL 能发现"库存被改了但没有流水"的情况，
-- 例如程序 bug 直接改了 sold_qty，或某个回滚动作没有记录流水。
```

**校验 SQL 4：同一乘客同一车次不允许有重复有效订单**

```sql
SELECT passenger_id, train_id, travel_date, seat_type, COUNT(*) AS 订单数
  FROM ods_order
 WHERE status IN ('CREATED','PAID','TICKETED')
 GROUP BY passenger_id, train_id, travel_date, seat_type
HAVING COUNT(*) > 1;
-- 期望：0 行。对应 R7 的唯一索引是否真正生效。
```

**校验 SQL 5：Redis 与数据库的差异（需要把 Redis 快照落到分析库）**

```sql
-- redis_left：压测结束后立即抓取的 Redis 库存快照
-- 期望：Redis 剩余 + 有效订单数 = 总量
SELECT r.train_id, r.travel_date, r.seat_type, r.redis_left,
       s.total_qty, s.sold_qty, COUNT(o.id) AS 有效订单数,
       r.redis_left + COUNT(o.id) - s.total_qty AS 偏差
  FROM ods_redis_stock_snapshot r
  JOIN ods_stock s ON s.train_id = r.train_id AND s.travel_date = r.travel_date AND s.seat_type = r.seat_type
  LEFT JOIN ods_order o
         ON o.train_id = r.train_id AND o.travel_date = r.travel_date
        AND o.seat_type = r.seat_type AND o.status IN ('CREATED','PAID','TICKETED')
 GROUP BY r.train_id, r.travel_date, r.seat_type, r.redis_left, s.total_qty, s.sold_qty
HAVING 偏差 <> 0;
-- 期望：0 行。
-- 注意：压测刚结束时 Redis 与数据库之间**允许**存在短暂差异（落账是异步的），
-- 所以这条 SQL 必须在"异步落账完成之后"执行，或改为对比"Redis 剩余 + 有效订单数"这一恒等式。
```

**压测结论的表述规范**（教学项目里很容易写成营销话术，这里给出正确写法）：

| 不要写 | 应该写 |
|---|---|
| "系统支持 X 万 QPS" | "在并发 N、库存 S 的条件下，成功订单数 = S，5 条校验 SQL 均为 0 行差异；并发继续升高后的拐点待压测" |
| "性能很好" | "P99 延迟为 X ms（在 N 并发下测得，机器配置为 …），瓶颈出现在 …" |
| "不会超卖" | "在上述测试条件下未观察到超卖；测试覆盖单实例并发与端到端链路，多机房场景未覆盖" |

### 19.3 手段三：定时对账任务

**为什么必须有对账**：前两种手段都是"一次性验证"，只能证明验证期间没问题。系统长期运行时，消息丢失、进程崩溃、回滚遗漏都会产生偏差，**没有对账就没有人知道**。对账是最终一致系统的最后一道防线。

**对账任务的设计**：

```
1. 触发：定时执行（频率按业务容忍度定，越频繁越早发现，但成本越高 —— 待压测后确定）
2. 数据源：离线分析库（各服务的库通过 binlog/消息同步过来），不在交易库上做跨库查询
3. 比对项（每一项独立产出差异记录）：
   a. 库存恒等式：Redis 剩余 + 有效订单数 = 总量            → 违反则为超卖/少卖
   b. 库存流水：SUM(change_qty) = total_qty - sold_qty      → 违反则为漏记流水
   c. 订单即可支付：支付单"成功"但订单仍是"待支付"且已超时   → 违反则为消息丢失（R9）
   d. 终态订单：已取消订单是否都产生了回滚流水              → 违反则为回滚遗漏（R2/R17）
   e. 重复订单：同一乘客同一车次多张有效订单                → 违反则为幂等失效（R7）
4. 输出：差异写入 t_reconcile_diff（差异表），字段包含：类型、业务键、两侧的值、发现时间、状态
5. 告警：差异数 > 0 立即告警；差异表要有"未处理差异"的看板
6. 修正：修正动作只能调用**幂等的业务接口**（例如幂等的回滚接口），
   不允许在对账任务里直接 UPDATE 业务表 —— 否则对账任务本身会成为新的错误来源
```

**对账任务的核心 SQL**（与 19.2 的校验 SQL 同源，但加上"差异落表"与"未处理差异查询"）：

```sql
-- 差异落表（以库存恒等式为例）
INSERT INTO t_reconcile_diff(diff_type, biz_key, left_value, right_value, found_time, status)
SELECT 'STOCK_MISMATCH',
       CONCAT(r.train_id, ':', r.travel_date, ':', r.seat_type),
       r.redis_left + COUNT(o.id),
       s.total_qty,
       NOW(),
       'OPEN'
  FROM ods_redis_stock_snapshot r
  JOIN ods_stock s
    ON s.train_id = r.train_id AND s.travel_date = r.travel_date AND s.seat_type = r.seat_type
  LEFT JOIN ods_order o
         ON o.train_id = r.train_id AND o.travel_date = r.travel_date
        AND o.seat_type = r.seat_type AND o.status IN ('CREATED','PAID','TICKETED')
 GROUP BY r.train_id, r.travel_date, r.seat_type, r.redis_left, s.total_qty
HAVING r.redis_left + COUNT(o.id) <> s.total_qty;

-- 未处理差异（告警与看板的数据源）
SELECT diff_type, COUNT(*) AS 差异数, MIN(found_time) AS 最早发现时间
  FROM t_reconcile_diff
 WHERE status = 'OPEN'
 GROUP BY diff_type;
```

**对账的局限（必须承认）**：

- 它是**滞后**的：差异被发现时，可能已经持续了一段时间；
- 它依赖数据同步的**完整性**：如果 binlog 同步本身丢了数据，对账结果不可信；
- 它能**发现问题**，但不能自动修复所有问题（资金类差异必须人工介入）。

**因此三种手段的关系是**：单元测试防住"代码级并发缺陷"；压测防住"链路级问题"；对账兜住"运行期的累积偏差"。**三者都不是可选项。**
