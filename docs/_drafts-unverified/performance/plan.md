# 压测计划（Load Test Plan）

> 项目：Rail-Ticket-Seckill（火车票秒杀）
> 技术栈基线：Spring Boot 3.5.9 / Java 17（见仓库 `pom.xml`）
> 被测接口定义见 [`../api/api-spec.md`](../api/api-spec.md)

## 0. 本文档的定位与一条硬规则

**当前状态：项目中没有任何实测数据。** 被测服务尚未实现（`src/main/java` 下只有一个空的启动类），压测环境尚未搭建，JMeter 脚本尚未编写。

因此本文档**只回答"怎么测"**：测什么目标、在什么环境下测、脚本怎么设计、指标怎么采、数据怎么记。本文档**不含任何性能数字**，包括但不限于 QPS、响应时间、错误率、容量结论。

### 0.1 结果记录规则（本文档最重要的一条）

**任何一次压测的结果，如果在记录时没有同时留下机器配置、压测时间、Git commit、中间件版本这四项元数据，该结果一律视为无效，不得写入任何文档、不得用于前后对比、不得对外引用。**

理由：压测数据的可比性完全依赖环境一致性。同一份代码在 8 核和 4 核上、在机械盘和 NVMe 上、在 MySQL 默认配置和调优后配置上，结果可能相差数倍。缺少元数据的"QPS 是 3000"这句话，没有任何信息量，甚至会误导优化方向——你无法判断某个变化是代码改动带来的，还是因为那次压测恰好在机器空闲时跑的。

这条规则不是形式主义，它是压测这件事能否产出有效结论的前提。执行模板见第 7 节。

### 0.2 面向读者

需要亲手跑这套压测、并要用结果去支撑技术决策（或面试讲述）的 Java 开发者。每一步都写清"为什么这么设计"，因为**压测最容易出的错不是工具用错，而是测出来的东西根本不是你想测的**。

## 1. 压测目标

### 1.1 目标并发档位

| 档位 | 并发用户数 | 目的 | 关注点 |
| --- | --- | --- | --- |
| L1 | 100 | 基准线。确认链路通、基线指标可复现 | 功能正确性、指标稳定性（连续跑多次波动应很小） |
| L2 | 500 | 观察线性区。确认系统是否仍能按预期扩展 | 资源利用率（CPU / DB 连接）是否成比例增长 |
| L3 | 1000 | 寻找拐点。定位指标开始明显劣化的位置 | 响应时间的 P95/P99 是否开始非线性抬升 |
| L4 | 5000 | 极限与失效模式。看系统怎么坏 | 是优雅拒绝（快速失败 + 429/业务码）还是雪崩（线程池打满、连接池耗尽、超时级联） |

**为什么用这四个档位而不是均匀取点？** 压测的目的不是"测出最大 QPS 是多少"，而是**找到系统的行为拐点，并确认拐点之后的失效模式是否可控**。L1 验证方法本身正确，L2/L3 定位拐点，L4 验证保护机制是否生效。这是一条"基准 → 拐点 → 失效"的路径，比均匀取点更有信息量。

**待压测 / 待验证：** 每一档的实际表现、拐点出现在哪个并发区间、L4 是否触发熔断或限流——全部待实测回填。

### 1.2 分阶段目标

| 阶段 | 前置条件 | 目标 |
| --- | --- | --- |
| 阶段一：单机基准 | 环境搭好、脚本跑通 | 拿到 L1–L4 的原始指标，确认无数据正确性问题 |
| 阶段二：定位瓶颈 | 阶段一完成 | 定位第一瓶颈（CPU / DB / Redis / 锁 / 线程池 / 连接池），**一次只改一个变量** |
| 阶段三：优化后复测 | 优化项落地 | 用第 6 节的对比模板量化优化效果，确认无回退 |
| 阶段四：正确性压测 | 任意阶段 | 超卖校验（第 5.4 节），验证并发下的数据一致性 |

### 1.3 明确的非目标

- **不追求"最大 QPS 数字"。** 单机 Windows 环境下测出的绝对数字没有对外意义（见第 2 节）。
- **不做分布式压测。** 单机 JMeter 在某个并发档位会成为瓶颈，此时应记录"JMeter 自身已成瓶颈"，而不是继续加压制造无意义的数字。
- **不做长时间稳定性测试（TODO：可作为后续补充）。** soak test（如数小时）能暴露内存泄漏与连接泄漏，但单机环境跑长测会被压测机自身的资源波动干扰，优先级低于拐点定位。

## 2. 压测环境

### 2.1 环境描述

**当前计划的部署形态：单机部署。**

| 角色 | 部署位置 | 说明 |
| --- | --- | --- |
| 被测应用（Spring Boot） | 本机 | 与其余角色同机 |
| MySQL | 本机 | 与其余角色同机 |
| Redis | 本机 | 与其余角色同机 |
| RabbitMQ | 本机 | 与其余角色同机 |
| 压测工具（JMeter） | 本机 | 与其余角色同机 |
| 操作系统 | Windows 10 Pro 19045 | 见 `mvnw.cmd` / `.mvn/wrapper` |
| CPU / 内存 / 磁盘 | **待填**，压测前必须记录（见 7.1） | 型号、核数、主频、内存容量、磁盘类型（HDD/SATA SSD/NVMe） |

### 2.2 结论必须打折：同机部署的资源争抢

**这是本计划中最重要的一条约束：压测机、被测应用、以及全部中间件跑在同一台机器上，它们会互相抢资源。**

具体抢什么：

| 争抢的资源 | 谁和谁抢 | 影响 | 方向 |
| --- | --- | --- | --- |
| CPU | JMeter 线程（大量）、应用线程池、MySQL 后台线程、Redis 单线程、RabbitMQ Erlang 调度 | JMeter 在高并发时自身 CPU 占用很高，与应用直接竞争 | **低估**应用真实容量 |
| 内存 | JMeter 堆、应用堆、MySQL buffer pool、Redis 数据集、RabbitMQ 队列 | 总内存固定，某方压力大就挤压其他方（触发 swap 时全盘皆输） | **低估**，且可能因 swap 严重失真 |
| 磁盘 IO | MySQL redo/undo/binlog/数据文件、RabbitMQ 持久化消息、日志文件、JMeter 结果写入 | 秒杀场景是写密集（订单落库），磁盘是常见瓶颈 | **低估** |
| 网络 | 全部走本机回环（loopback） | loopback 不经过物理网卡，**没有真实网络延迟**；但同时所有进程共享同一网络栈 | 双向：RT 可能**偏乐观**（无网络延迟），吞吐可能**偏悲观**（网络栈软中断与应用抢 CPU） |
| 端口 / 文件句柄 | JMeter 的高并发连接与瞬时端口 | Windows 动态端口范围有限，高并发下可能 `TIME_WAIT` 堆积导致连接失败 | **污染错误率**：把环境限制误判为应用错误 |

**因此，本环境下所有结论的适用范围必须被限定为：**

> 本次压测测的是"**在单机 Windows 环境下、应用与全部中间件与压测工具同机部署时，这套系统表现出的行为与瓶颈位置**"。
> 它**不是**应用在生产部署形态下的容量数字，**不能**用来回答"这套系统能扛多少并发"。
> 它可以用来回答的是：① 优化前后**相对**变化（同一环境下对比，变量控制得当则有效）；② 瓶颈**位置**（瓶颈在哪里，比瓶颈有多大更重要）；③ 功能与数据正确性（超卖校验不受环境影响）。

**优化前后对比也受此影响。** 因为两次压测在同一环境、同一时段、同样的干扰条件下进行，相对变化（"提升了 X%"）比绝对值可信得多。但即便如此，仍必须满足第 7 节的元数据记录要求，否则连相对变化都不可信。

### 2.3 如果要拿到更可信的结论（可选方案对比）

| 方案 | 隔离程度 | 成本 | 结论 |
| --- | --- | --- | --- |
| 全部同机（当前方案） | 无隔离，互相争抢 | 最低，无需额外机器 | ✅ 本项目当前采用，结论按 2.2 打折 |
| 压测机独立（两台机器：一台 JMeter，一台应用+中间件） | 压测工具不再与应用抢 CPU | 需第二台机器 | ⚠️ **优先推荐的下一步**。这是投入产出比最高的一次环境改进——它直接消除最大的一项干扰 |
| 应用与中间件分离（三台及以上） | 可分别定位应用瓶颈与中间件瓶颈 | 需多台机器或容器 | ⚠️ 进一步改进，用于细分瓶颈归属 |
| 容器化 + 资源限额（Docker `--cpus` / `--memory`） | 可给每个角色设定 CPU/内存上限，隔离度接近独立机器 | 需要 Docker 与更长的环境搭建时间；Windows 上 Docker 走 WSL2，本身有额外开销 | 未采用，可作为后续方案 |
| 云上按量付费的多机环境 | 隔离最好，可横向扩展 | 有费用 | 未采用 |

**为什么不选容器化？** 在 Windows 上 Docker Desktop 依赖 WSL2 虚拟机，网络与文件 IO 相比原生进程多一层转发，会给压测结果引入**新的、难以量化的**干扰。在一个"结论已经要打折"的环境里再叠加一层不可控变量，不如先接受同机部署、把结论限定清楚。

### 2.4 Windows 环境下的已知限制

这些都需要在压测前处理或在结论中说明，否则会污染数据：

| 限制 | 现象 | 处理 |
| --- | --- | --- |
| 动态端口耗尽 | 高并发短连接下大量 `TIME_WAIT`，连接失败 | JMeter 开启 keep-alive 复用连接；必要时调整动态端口范围（`netsh int ipv4 set dynamicport tcp`）；端口状态用 `netstat` 统计 |
| `TIME_WAIT` 回收慢 | 同样导致连接失败，且被误计为应用错误 | **JMeter 侧断言要把"连接被拒绝/超时"与"应用返回错误码"区分统计**，否则错误率指标失真 |
| 文件句柄与线程数上限 | 高并发下应用无法创建线程 / 打开文件 | 确认 JVM 线程栈大小（`-Xss`）与系统限制；监控应用线程数 |
| 文件系统性能差异大 | NTFS 与 Linux ext4 在高并发小文件写入上表现不同（日志、MySQL 数据文件） | 压测前关闭或降低不必要的日志级别（应用日志、MySQL 慢日志在采集时要权衡） |
| 时间精度 | `System.currentTimeMillis()` 在旧版 Windows 上精度约 15.6ms | 统计 RT 分布时注意，Java 17 在 Windows 上已改善，但**待验证** |

## 3. JMeter 脚本设计

### 3.1 测试计划结构

```
Test Plan: Rail-Ticket-Seckill
├── User Defined Variables           # 变量：host、port、协议、路径、并发数（便于一处改全局）
├── HTTP Request Defaults            # 默认服务器/IP/端口/编码 UTF-8
├── HTTP Header Manager              # 全局头：Content-Type、Accept
├── HTTP Cookie Manager              # 保留（当前设计用 JWT，但登录流程可能用到）
├── setUp Thread Group               # 预热：登录/拿 token（若走接口生成）
├── Thread Group: 秒杀下单主场景
│   ├── CSV Data Set Config          # 1000 个已登录用户 token
│   ├── User Parameters / 变量随机化  # 随机 activityId、seatType、requestId
│   ├── HTTP Sampler: POST /api/v1/seckill/orders
│   │   ├── JSON Extractor           # 提取 traceId / retryAfterMillis
│   │   ├── Response Assertion       # HTTP 状态码断言
│   │   └── JSON Assertion           # $.code 断言
│   ├── Timer: Constant Throughput Timer / Precise Throughput Timer
│   └── （可选）HTTP Sampler: 轮询 /api/v1/seckill/result
├── Thread Group: 查询场景（车次/座位）
├── （可选）Backend Listener         # 实时指标上报
└── tearDown Thread Group            # 清理与数据校验触发
```

**为什么用 `User Defined Variables` 而不是把值散落在 Sampler 里？** 压测需要反复调整并发数与目标地址，值散落会导致每次改都要在多个 Sampler 里翻找，极易漏改导致某次压测的数据实际来自不同配置——而这正是"结果不可比"的常见来源。

**为什么断言要分两层（HTTP 状态码 + `$.code`）？** 见 [`../api/api-spec.md`](../api/api-spec.md) 第 3 节：本设计里业务失败返回 HTTP 200 + 非 0 业务码。如果只断言 HTTP 状态码，**"库存不足"会被统计为成功**，压测结果会显示"成功率 100%"而实际上几乎没人抢到票。这是本项目压测中最容易犯的错误。

### 3.2 线程组配置

| 档位 | 线程数（用户） | Ramp-up（秒） | 循环次数 | 说明 |
| --- | --- | --- | --- | --- |
| L1 | 100 | 待定（建议先按"缓慢加压"设置，确认无异常后再收紧） | 待定 | 先慢后快，确保是系统能力而非瞬间冲击 |
| L2 | 500 | 同上 | 待定 | — |
| L3 | 1000 | 同上 | 待定 | — |
| L4 | 5000 | 同上 | 待定 | 需先确认 JMeter 自身能否支撑该线程数（见 3.8） |

**关于 Ramp-up 的具体取值：** 本计划不预设数值，因为它取决于压测目的。有两种截然不同的用法，**必须在每次压测记录中写明用的是哪种**：

| 用法 | Ramp-up | 测的是什么 | 适用档位 |
| --- | --- | --- | --- |
| 缓慢加压 | 较大（与目标并发成比例） | 系统的**稳态处理能力**（容量） | L1–L3 |
| 瞬时冲击 | 极短（如 1 秒内起全部线程） | 系统的**抗尖峰能力**（秒杀真实场景） | L4 与第 5.3 节的尖峰场景 |

同一份线程组配置，Ramp-up 不同会得出完全不同的结论。**不写明 Ramp-up 的压测结果没有意义。**

**线程组的其他设置：**

| 设置项 | 取值 | 理由 |
| --- | --- | --- |
| "Same user on each iteration" | 保持默认（否） | 尽量模拟不同用户；但本项目 token 来自 CSV，身份由 CSV 决定 |
| Delay Thread creation until needed | 建议开启 | 避免一次性创建 5000 个线程造成 JMeter 自身卡顿 |
| Scheduler（持续时间） | 按场景定（见第 5 节） | 用"持续时间"控制比用"循环次数"更容易控制压测窗口，也便于对齐监控采样 |
| 出错后继续执行 | 必须开启 | 压测的目的之一就是看错误表现，中断执行会丢失失效模式的数据 |

### 3.3 CSV Data Set Config：准备 1000 个已登录用户 token

**目标：** 让每个虚拟用户以一个**真实存在、已登录、且各不相同**的用户身份发起请求。绝不能所有线程共用一个 token——那样测出来的不是并发下单，而是"同一用户的并发重复提交"，会全部命中去重逻辑（`40002`），完全测不到库存扣减路径。

**文件：** `data/seckill-tokens.csv`（放在 JMeter 脚本同级 `data/` 目录，随脚本一起版本管理——但 **token 是敏感信息，只提交脱敏样例文件 `seckill-tokens.sample.csv`，真实文件加入 `.gitignore`**）

**列设计：**

| 列名 | 示例值 | 用途 |
| --- | --- | --- |
| `userId` | （数字） | 结果校验、日志定位 |
| `username` | （字符串） | 可读性 |
| `token` | （JWT 字符串） | 放入 `Authorization: Bearer ${token}` |
| `requestIdPrefix` | （UUID 前缀） | 生成幂等键，保证每个请求的 `requestId` 唯一 |

**CSV Data Set Config 关键配置：**

| 配置项 | 取值 | 为什么 |
| --- | --- | --- |
| Filename | `data/seckill-tokens.csv` | 相对路径，随脚本迁移 |
| File encoding | `UTF-8` | Windows 下默认编码可能是 GBK，会导致中文列乱码 |
| Variable Names | `userId,username,token,requestIdPrefix` | 显式声明，不依赖首行 |
| Ignore first line | `true`（若文件含表头） | — |
| Delimiter | `,` | 若 token 中含逗号（JWT 不含，但 username 等可能含），改用 `\|` 或制表符更稳妥 |
| **Recycle on EOF** | **`True`** | 1000 个 token 要支撑 5000 并发，必须允许回绕复用。**注意：回绕意味着同一 token 会被多个线程同时使用**，这在 L4 档位会改变语义——同一用户重复下单会被去重拦截（`40002`）。**这是 L4 档位的一个必须记录的局限** |
| **Stop thread on EOF** | `False` | 与上一条配套 |
| **Sharing mode** | **`All threads`** | 所有线程共享一份文件游标，每个线程取到不同的行。若用 `Current thread`，每个线程各自从第 1 行开始读，会导致大量线程使用同一个 token |

**"Recycle on EOF + 5000 并发只有 1000 个 token"这个问题必须正视：**

- L1–L3（100 / 500 / 1000 并发）下，1000 个 token 足够，每个线程拿到独立身份，测的是真实并发下单。
- L4（5000 并发）下，必然出现 token 复用。此时**测出来的结果混合了两种行为**：新用户的下单路径 + 已下单用户的去重路径。由于去重路径更快（不触碰库存扣减），**L4 的 RT 会偏乐观**。
- 处理方式（二选一，必须在结果记录里注明用了哪种）：
  1. **扩充 token 池**：预先准备 5000+ 个用户与 token，消除复用。这是更正确的做法，只是准备成本高。
  2. **接受并标注**：记录"L4 档位存在 token 复用，结果混合了去重路径，RT 偏乐观"。

**token 从哪来？** 两条路：

| 方式 | 做法 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| 调登录接口批量获取 | 用脚本（JMeter setUp 线程组 / 独立的 Java 或 shell 脚本）循环调用 `POST /api/v1/auth/login`，把响应里的 token 写入 CSV | 真实、token 有效 | 登录接口有 BCrypt 计算，1000 次登录耗时较长；且会被登录限流拦截 | ✅ 采用，但**必须错峰执行**：单独跑一次生成 CSV，不要放在每次压测的 setUp 里（否则每次压测前都要等几分钟，且限流会失败） |
| 直接构造/从数据库取 | 绕过登录直接签 token，或从 DB 会话表导出 | 快 | 需要额外的签名密钥访问权限；若实现变更（如加白名单校验）会失效 | ⚠️ 仅作为生成缓慢时的备选 |

**推荐流程：** 压测**前**单独跑一次 `generate-tokens` 脚本生成 CSV → 人工抽查若干行确认 token 可用（用 curl 打一次 `/api/v1/users/me` 验证返回 200）→ 之后每次压测直接复用该 CSV。**"人工抽查"这一步不能省**：一个全部失效的 token 文件会让整场压测变成"5000 个 401"，而错误率指标会告诉你"系统错误率 100%"，误导方向。

### 3.4 参数随机化

**为什么必须随机化？** 如果所有请求打同一个 `activityId` + 同一个 `seatType`，测的是"单热点 key"的极限；如果都是不同活动，测的是"多 key 分散"的吞吐。两者结论完全不同。**必须明确每次压测测的是哪一种。**

| 参数 | 随机化方式 | 说明 |
| --- | --- | --- |
| `activityId` | 少量活动（如 1 个）用固定值；多活动场景用 `${__Random(a,b)}` 或 `__RandomFromMultipleVars` | **秒杀场景的真实形态是"少数热点活动"**，所以主场景应当故意集中打 1 个活动，这才是有意义的压测 |
| `seatType` | 从固定集合中随机（`__RandomFromMultipleVars` 或 CSV） | 不同座位类型的库存是独立 key，随机化可测多 key 的分散效果 |
| `passengerIds` | 固定或随机取一个存在的乘车人 ID | 需与 token 对应的用户匹配，否则会触发业务校验失败 |
| `requestId` | `${requestIdPrefix}-${__threadNum}-${__counter(FALSE,)}` | **必须保证全局唯一**。若 requestId 重复，幂等键会误判为重复请求，导致大量请求被"去重"返回，测不到真实路径 |
| 思考时间（Think Time） | 见 3.7 | — |

**关于 `requestId` 的一个陷阱：** 如果压测目的是测"防重能力"，那么**故意**让某些请求使用相同 requestId 才是正确的（构造重复提交场景）；而在测容量时，必须保证唯一。这两种脚本应当分开，不要混在一个线程组里。

### 3.5 断言设计

| 断言 | 配置 | 为什么 |
| --- | --- | --- |
| Response Assertion（HTTP 状态码） | 断言 `200` 或 `429` 为通过 | 429（限流）是**预期内的保护行为**，不应算作系统故障。若把 429 记为失败，错误率指标会误导优化方向——它会把"保护机制正常工作"报告成"系统有问题" |
| JSON Assertion | `$.code` 存在即可（或断言为预期集合 `[0, 30003, 40002, 30004, 30005]`） | 这些业务码都是**正常业务分支**，不是故障 |
| JSON Assertion（严格模式） | 单独一个事务/标签，只断言 `$.code == 0` | 用于单独统计"真实抢到票的比例"（业务成功率），与"系统健康度"分开看 |
| Duration Assertion | **不建议加** | 加了之后超时会被记为断言失败，与"请求本身失败"混在同一个错误率里。响应时间应当从聚合报告的 RT 分布去看，不要用断言来度量 |
| 响应体大小断言 | 可选，断言响应体 < 某阈值 | 防止异常情况下返回超大响应体（如错误页 HTML）拖垮压测机带宽 |

**核心原则：把"业务结果"和"系统健康度"分成两个指标来看。**

- `系统错误率` = (HTTP 非 200/429 + 超时 + 连接失败) / 总请求数 —— 衡量系统是否健康
- `业务成功率` = `code == 0` 的比例 —— 衡量有多少人真的抢到了
- `业务拒绝率` = `code ∈ {30003, 40002, ...}` 的比例 —— 衡量保护机制是否按预期工作

**只报一个"成功率"的压测报告是不可信的**，因为它无法回答问题："到底是系统崩了，还是票卖完了？"

### 3.6 监听器与报告配置

| 监听器 | 用途 | 注意事项 |
| --- | --- | --- |
| **Aggregate Report（聚合报告）** | 主报告：样本数、平均值、中位数、P90/P95/P99、最小/最大、错误率、吞吐量 | **压测时必须用"非 GUI 模式"运行，只在结束后用 GUI 打开 jtl 生成报告**。GUI 模式下监听器会把每个样本都渲染到界面，压测机自身的 CPU 会被监听器吃光，测出来的是 JMeter 的极限 |
| **Summary Report** | 快速概览 | 同上 |
| **Backend Listener（InfluxDB + Grafana）** | 实时曲线，便于观察趋势与拐点 | 需要额外部署 InfluxDB + Grafana。同机部署下它们也抢资源，**建议只在调试脚本时开启，正式压测关闭** |
| **Simple Data Writer** | 把原始样本写入 jtl（CSV） | 正式压测的唯一数据落地方式，后续用脚本做自定义分析 |
| **View Results Tree** | 调试单个请求用 | **正式压测必须关闭**，它会把全部响应体留在内存里，是压测机 OOM 的常见原因 |

**命令行运行（非 GUI）示例：**

```bash
jmeter -n \
  -t seckill.jmx \
  -l result/seckill-L3-<timestamp>.jtl \
  -e -o report/seckill-L3-<timestamp>/
```

| 参数 | 说明 |
| --- | --- |
| `-n` | 非 GUI 模式 |
| `-t` | 脚本路径 |
| `-l` | 原始结果文件（jtl）。**文件名必须带时间戳与档位**，这是第 7 节"结果可追溯"要求的一部分 |
| `-e -o` | 压测结束后自动生成 HTML 报告到指定目录 |
| 属性覆盖 | 可用 `-Jthreads=500` 之类的方式在命令行覆盖线程数，**避免每次都改 jmx 文件**（改文件容易忘记改回去，导致下次压测档位错误） |

**为什么强调命令行覆盖线程数？** 这是一个真实的踩坑点：在 GUI 里把线程数从 500 改成 1000 跑完，下次想跑 500 时忘了改回来，结果记录写的是"500 并发"、实际是 1000 并发。用 `-J` 参数覆盖，jmx 文件本身保持不变，档位由命令行显式决定，记录里也能原样记下命令行。

### 3.7 定时器：控制请求速率

| 定时器 | 用途 | 说明 |
| --- | --- | --- |
| **Constant Throughput Timer** | 把请求速率稳定在指定值（样本/分钟） | 用于"恒定压力"场景，观察系统在固定负载下的稳定性。**注意它的计算基于活跃线程数，线程数变化时实际速率会漂移** |
| **Precise Throughput Timer** | 更精确的速率控制 | 需要精确控制时优先选它；配置更复杂 |
| **Constant Timer（思考时间）** | 模拟用户操作间隔 | 若目标是"模拟真实用户"，需要加思考时间；若目标是"压出系统的容量上限"，**不应加**——加了思考时间测的是"用户行为模型的负载"，不是容量 |

**必须明确每次压测用的是哪种：**

| 模式 | 是否有思考时间 | 测什么 |
| --- | --- | --- |
| 容量模式 | 无（或极短） | 系统处理能力的上界 |
| 仿真模式 | 有（贴近真实用户） | 贴近生产的实际负载形态 |

秒杀场景的真实形态是"大量用户在极短时间内集中点击"，因此**尖峰场景（5.3）用容量模式、不加思考时间**才是贴近真实的；而稳态场景可以加思考时间。

### 3.8 JMeter 自身的瓶颈识别

**这是单机压测最容易被忽略的问题：你测出来的可能是 JMeter 的极限，不是被测系统的极限。**

识别信号：

| 信号 | 含义 |
| --- | --- |
| JMeter 进程 CPU 接近跑满（与应用争抢同一批核心） | 压测工具已成瓶颈 |
| JMeter 堆内存持续增长、频繁 Full GC | 压测工具已成瓶颈（可能是监听器没关、响应体被缓存） |
| 吞吐量随线程数增加不再上升，而应用侧 CPU 却不高 | 瓶颈在压测侧或网络侧 |
| 大量 `java.net.BindException` / 连接超时，且应用日志无对应记录 | 端口耗尽，请求根本没到应用 |

**应对：**

1. 先关掉所有非必需的监听器，用非 GUI 模式。
2. 用独立的 JMeter 实例（甚至独立机器）做对照。
3. 在结果记录中明确写下"本次压测 JMeter 自身资源占用情况"——若 JMeter CPU 已经很高，则本次的吞吐量数据只能作为**下界**，不能在优化对比中被当作有效基线。

## 4. 指标采集清单

**采集原则：** 每个指标都必须在压测**开始前**确认采集方式已就绪。压测中途才想起来"忘了看 Redis 命中率"，这一轮数据就废了（因为 Redis 的 `INFO stats` 是累计值，压测前后的差值才有意义）。

### 4.1 指标总表

| # | 指标 | 含义 / 为什么要看 | 采集工具 | 具体采集方式 | 采集频率 |
| --- | --- | --- | --- | --- | --- |
| 1 | **QPS** | 每秒请求数，衡量吞吐 | JMeter | Aggregate Report 的 Throughput 列；或对 jtl 按秒聚合 | 压测后统计；实时看用 Backend Listener |
| 2 | **TPS** | 每秒**成功完成的业务事务**数。与 QPS 的区别在于 TPS 只计成功且以"事务"为单位 | JMeter | 用 Transaction Controller 包裹业务动作，看其 Throughput；或对 `code == 0` 的样本单独聚合 | 同上 |
| 3 | **平均 RT** | 平均响应时间。**最容易被平均值骗**——它会被少量极快请求拉低 | JMeter | Aggregate Report 的 Average | 同上 |
| 4 | **P95 / P99 RT** | 95% / 99% 的请求在此时间之内完成。**比平均值更能反映用户体感** | JMeter | Aggregate Report 的 95% / 99% 行 | 同上 |
| 5 | **错误率** | 失败请求占比。**必须按 3.5 拆成系统错误率与业务拒绝率两个口径** | JMeter | Aggregate Report 的 Error %；拆口径需对 jtl 二次分析 | 同上 |
| 6 | **CPU 使用率** | 定位瓶颈是否在计算 | 任务管理器 / PerfMon / `typeperf` | Windows 下用 `typeperf "\Processor(_Total)\% Processor Time"` 采样；JMeter 的 PerfMon 插件可远程采 | 建议 5–10 秒一次 |
| 7 | **内存使用** | 应用堆、JMeter 堆、MySQL buffer pool、Redis 数据集 | JConsole / VisualVM（JVM）；任务管理器（进程级） | JVM 加 `-Dcom.sun.management.jmxremote` 后用 JConsole/VisualVM 连接 | 5–10 秒一次 |
| 8 | **GC 次数与耗时** | 频繁 Full GC 会造成 RT 抖动（Stop-The-World） | JConsole / VisualVM / GC 日志 | 建议开 GC 日志（`-Xlog:gc*`）与 JMX 同时采；GC 日志能给出精确的停顿时间分布 | 压测后分析；实时看 JMX |
| 9 | **DB 连接数** | 连接池是否打满。**打满后新请求会阻塞等待连接，RT 呈阶跃式上升** | 应用侧 HikariCP 指标 / MySQL `performance_schema` / `SHOW PROCESSLIST` | ① HikariCP 暴露 `hikaricp_connections_active`（需接 Micrometer，**待实现**）；② `SELECT COUNT(*) FROM performance_schema.threads WHERE PROCESSLIST_USER='app'`；③ `SHOW STATUS LIKE 'Threads_connected'` | 5–10 秒一次 |
| 10 | **慢 SQL** | 定位 DB 层瓶颈，尤其是缺索引的查询 | MySQL slow_query_log / `performance_schema` | ① 开 `slow_query_log`，设 `long_query_time`（**具体阈值待定**）；② `performance_schema.events_statements_summary_by_digest` 按总耗时排序，直接找出最耗时的 SQL 模板（**推荐**，不需要重跑压测） | 压测后分析 |
| 11 | **Redis 命中率** | 缓存是否有效。命中率低说明缓存策略有问题或 key 设计有问题 | Redis `INFO stats` | 压测前后各采一次 `keyspace_hits` / `keyspace_misses`，命中率 = hits / (hits + misses)。**注意是累计值，必须取差值** | 压测前后各一次（+ 中途可选） |
| 12 | **Redis QPS** | Redis 是否成为瓶颈。**Redis 是单线程的，一个慢命令会阻塞所有请求** | Redis `INFO commandstats` / `redis-cli --stat` | `INFO commandstats` 给出每种命令的调用次数与总耗时，可算出每种命令的平均耗时——**这比总 QPS 更有用**，能直接发现慢命令（如误用 `KEYS`、大 key 操作） | 压测前后各一次 |
| 13 | **MQ 堆积量** | 消费能力是否跟上生产速度。**堆积持续增长说明消费端是瓶颈** | RabbitMQ management HTTP API / `rabbitmqctl` | `curl -u user:pass http://localhost:15672/api/queues` 取 `messages` / `messages_ready` / `messages_unacknowledged`；或 `rabbitmqctl list_queues name messages consumers` | 10 秒一次（堆积是随时间变化的，必须连续采样） |
| 14 | **Tomcat 线程池** | `active` 线程数接近 `max` 说明请求在排队 | JMX（JConsole / VisualVM） | MBean `Catalina:type=ThreadPool,name=http-nio-*` 的 `currentThreadsBusy` / `maxThreads` | 5–10 秒一次 |
| 15 | **接口级 RT 分解** | 定位 RT 消耗在哪个环节（Redis / DB / MQ） | 应用内埋点（Micrometer + `@Timed`）/ 日志 | **待实现**。当前项目无任何埋点。没有这个，只能看到"接口慢"，无法回答"哪一步慢" | — |

### 4.2 采集方式的落地要点

**Redis（`INFO stats` 示例）：**

```bash
# 压测前
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses|total_commands_processed"
# 压测后（再采一次，用差值计算命中率与 QPS）
redis-cli INFO commandstats | sort -t= -k2 -rn | head -20
```

`commandstats` 的输出形如 `cmdstat_get:calls=N,usec=M,usec_per_call=X`，其中 `usec_per_call` 是每种命令的平均耗时。**这个字段是发现 Redis 层问题的关键**：如果某个命令的平均耗时异常（比如某个操作大 Set 的命令），它会在单线程模型下阻塞所有其他请求，而总 QPS 看起来可能还不高。

**MySQL（`performance_schema`）：**

```sql
-- 按总耗时排序的 SQL 模板（压测后执行）
SELECT DIGEST_TEXT,
       COUNT_STAR,
       ROUND(SUM_TIMER_WAIT/1000000000000, 3) AS total_sec,
       ROUND(AVG_TIMER_WAIT/1000000000, 3)     AS avg_ms,
       SUM_ROWS_EXAMINED,
       SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;
```

| 字段 | 怎么看 |
| --- | --- |
| `COUNT_STAR` | 执行次数。次数极高 + 单次很快，仍可能是总耗时大头 |
| `total_sec` | 该 SQL 模板的总耗时，**排序依据** |
| `avg_ms` | 平均耗时。高说明单次有问题（缺索引、锁等待） |
| `SUM_ROWS_EXAMINED` vs `SUM_ROWS_SENT` | **比值是关键**：扫描行数远大于返回行数，说明索引没走好或走了全表扫描。这是"慢 SQL 根因"最快的判断方式 |

**RabbitMQ：**

```bash
# 队列堆积与消费者数量
rabbitmqctl list_queues name messages messages_ready messages_unacknowledged consumers
# 或走 HTTP API（便于脚本连续采样）
curl -s -u guest:guest http://localhost:15672/api/queues | <解析 messages 字段>
```

`messages_unacknowledged` 高说明**消费端拿到了消息但处理不完或卡住了**，与 `messages_ready` 高（没人消费）是两种不同的故障，必须分开看。

**JVM（JConsole / VisualVM）：**

需要应用启动时开启 JMX：

```
-Dcom.sun.management.jmxremote
-Dcom.sun.management.jmxremote.port=<端口>
-Dcom.sun.management.jmxremote.authenticate=false   # 仅本机压测可用，切勿用于生产
```

**注意：JMX 连接与采样本身有开销**（尤其开着 VisualVM 的实时图表时）。在同机压测环境下，VisualVM 的采样开销也会与应用抢 CPU。**建议：正式压测时只开 GC 日志，用事后分析替代实时监控；实时监控只在调试脚本阶段使用。**

### 4.3 指标优先级（压测时先看什么）

压测过程中人力有限，不可能同时盯十几个指标。按以下顺序看：

| 顺序 | 指标 | 判断 |
| --- | --- | --- |
| 1 | 系统错误率（HTTP 层） | 先确认系统有没有崩，崩了后面都别看了 |
| 2 | P95 / P99 RT 曲线 | 看是否出现拐点 |
| 3 | 应用 CPU + Tomcat 活跃线程 | 判断是计算瓶颈还是排队 |
| 4 | DB 连接数 + 慢 SQL | 判断 DB 是否是瓶颈 |
| 5 | Redis 命令平均耗时 + MQ 堆积 | 判断中间件是否是瓶颈 |
| 6 | 业务成功率与拒绝码分布 | 判断保护机制是否按预期工作 |

## 5. 压测场景设计

### 5.1 S1 基准测试（Baseline）

| 项 | 内容 |
| --- | --- |
| **目的** | 建立可复现的基线。确认脚本正确、断言正确、指标可稳定复现 |
| **配置** | 并发 100，缓慢 Ramp-up，无思考时间（容量模式） |
| **被测接口** | 先单独测 `GET /api/v1/trains`（纯读、走缓存），再单独测 `POST /api/v1/seckill/orders`（写路径），**不要一上来就混合** |
| **步骤** | 1) 预热（见下）2) 跑 100 并发 3) 记录全部指标 4) **原地重跑一次** |
| **通过标准** | 两次重跑的指标接近（波动在可接受范围，具体阈值待首次实测后确定）；无系统错误；数据正确性校验通过 |
| **为什么必须重跑一次** | 首次运行包含 JIT 编译、连接池冷启动、缓存冷启动、OS 文件缓存未热等一次性开销。**只跑一次的基线是假的基线**，重跑才能暴露这些影响 |

**预热（Warm-up）是本场景的强制步骤：**

| 预热什么 | 怎么做 | 不预热会怎样 |
| --- | --- | --- |
| JVM | 低并发跑一段时间，触发 JIT 编译与类加载 | 前几秒的 RT 异常高，被平均值拉偏；若压测窗口短，整个结果都是"未预热"的数据 |
| 连接池 | 低并发跑，让 HikariCP 建立到 `minimumIdle` 的连接 | 首次高并发时集中创建连接，产生额外延迟尖刺 |
| 缓存 | 预热车次/库存缓存（`../api/api-spec.md` 4.6 提到的缓存预热） | 缓存未命中 → 全部打 DB → 测的是"缓存失效时"的容量，而非稳态容量 |
| OS 页缓存 | 读一次数据文件 | 磁盘 IO 尖刺 |

**预热数据不计入统计**：在 jtl 里通过时间戳切掉预热段，或用独立的预热线程组。

### 5.2 S2 递增并发（阶梯加压）

| 项 | 内容 |
| --- | --- |
| **目的** | 找到系统的行为拐点（性能开始非线性劣化的并发点） |
| **配置** | 阶梯：100 → 500 → 1000 → 5000，每一档持续一段时间（时长待定，需足够长以让指标稳定），档间有间隔（便于区分各档数据） |
| **实现方式对比** | ① 多个线程组串行（用 Scheduler 起止时间错开）；② 单个线程组 + `Ultimate Thread Group` 插件（阶梯配置直观）；③ 用 `-J` 参数分别跑四档，跑四次 |
| **推荐** | **③ 分别跑四次**。理由：同机环境下，阶梯测试的各档之间会相互影响（上一档的 GC、连接池状态、OS 缓存会带入下一档），而分次运行中间有冷却期，边界清晰；且分次运行天然符合第 7 节的"一次一记录"要求 |
| **观察重点** | RT 随并发的增长曲线：**线性增长是可扩展的信号，突然的阶跃上升说明撞到了某个硬限制**（连接池打满、线程池打满、锁竞争） |
| **通过标准** | 定量标准待首次实测后确定（先有基线，才能定阈值） |

**阶梯测试必看的三种曲线形态（面试常问）：**

| 形态 | 表现 | 含义 |
| --- | --- | --- |
| 线性 | RT 随并发近似线性上升，吞吐随并发线性上升 | 资源充足，系统还有余量 |
| 拐点 | 吞吐停止上升，RT 开始加速上升 | 撞到瓶颈。**这是最有价值的发现**——瓶颈在哪里，靠 4.3 的指标优先级去定位 |
| 崩溃 | 吞吐断崖式下降，RT 飙升，错误率飙升 | 过载保护失效，出现级联失败（如重试风暴、线程池耗尽） |

### 5.3 S3 尖峰测试（秒杀真实形态）

| 项 | 内容 |
| --- | --- |
| **目的** | 模拟秒杀开始瞬间的流量形态：**几乎无 Ramp-up，瞬间冲到目标并发** |
| **配置** | Ramp-up 极短（如 1 秒内起全部线程）；无思考时间；目标并发取 L3 / L4；持续时长以覆盖"库存被抢完"的完整过程为准 |
| **与 S2 的关键区别** | S2 测"稳态容量"，S3 测"抗瞬时冲击"。**同一套代码，两者结论可能完全不同**——因为连接池、线程池、缓存都来不及预热/扩容 |
| **重点观察** | ① 前 1–3 秒的 RT 尖刺有多高；② 是否触发限流（429 占比）；③ 库存扣减是否准确（见 5.4）；④ 系统能否从冲击中恢复（冲击结束后 RT 是否回到基线） |
| **典型失败模式** | 瞬间大量请求同时发现缓存未命中 → 全部去重建缓存（缓存击穿）→ DB 被瞬时打满 → 请求超时 → 客户端重试 → 雪崩。**这正是缓存预热与互斥重建要解决的问题**（`../api/api-spec.md` 4.6） |

### 5.4 S4 超卖校验（数据正确性，不是性能测试）

| 项 | 内容 |
| --- | --- |
| **目的** | 验证并发下数据一致性：**不超卖、不少卖、不重复下单** |
| **这一项优先级最高** | 性能差可以优化，超卖是**不可自动修复的数据事故**（见 `../api/api-spec.md` 5.7） |
| **配置** | 库存设为一个已知的小值 N（便于人工核对）；并发用户数远大于 N（如 N=100，并发 5000）；确保 token 不重复（此场景下 CSV 的 token 复用会污染结论） |
| **执行步骤** | 1) 记录压测前库存值 2) 跑压测 3) 压测后执行校验 SQL 4) 人工核对 |
| **校验 SQL** | 见下 |
| **通过标准** | 下面四条**必须同时成立**（无"部分通过"） |

```sql
-- ① 实际生成的订单数 == 初始库存 N（不多不少）
SELECT COUNT(*) FROM t_seckill_order WHERE activity_id = ? AND seat_type = ?;

-- ② 同一用户在同一场次同一座位类型下只有一张订单（唯一索引应保证，这里是验证它真的生效）
SELECT user_id, activity_id, seat_type, COUNT(*) AS c
FROM t_seckill_order
WHERE activity_id = ? AND seat_type = ?
GROUP BY user_id, activity_id, seat_type
HAVING c > 1;

-- ③ DB 剩余库存 == 初始库存 - 订单数，且不为负
SELECT available FROM t_stock WHERE activity_id = ? AND seat_type = ?;

-- ④ 对账：Redis 中标记为已抢到的用户数 == DB 中订单数（检查"Redis 扣了但 DB 没落"）
--    Redis: SCARD seckill:users:{activityId}
--    两者不一致时，差值就是需要补偿的订单数
```

| 校验项 | 期望 | 不满足说明什么 |
| --- | --- | --- |
| ① 订单数 = N | 相等 | 大于 N → **超卖**（Redis 原子性被破坏或 DB 兜底失效）；小于 N → **少卖**（Redis 扣了但落库失败，且无补偿） |
| ② 重复订单查询无结果 | 空集 | 唯一索引未生效或订单表结构不对 |
| ③ 剩余库存 ≥ 0 且 = 初始 - 订单数 | 成立 | 负库存 → 扣减 SQL 缺少 `AND available > 0` 条件 |
| ④ Redis 与 DB 一致 | 相等 | 存在未补偿的失败订单，需要定时对账任务兜底 |

**为什么 N 要取小值（如 100）而不是大值（如 100000）？** 一是便于人工核对（100 条订单可以直接看）；二是小库存能让"超卖"更快地暴露出来——如果库存 10 万而并发只有 5000，可能根本触碰不到边界，测试会假通过。**测边界要用边界条件，不是用大数字。**

### 7.2 元数据为什么是强制的

| 元数据 | 缺了会导致什么 |
| --- | --- |
| **机器配置** | 无法判断两次压测是否可比。8 核变 4 核，性能腰斩可能被误读为"代码改动导致性能下降" |
| **时间** | 无法排除环境干扰。如果上次压测时机器空闲、这次后台在跑 Windows 更新，数据差异来自环境而非代码 |
| **Git commit** | 无法复现。压测最有价值的部分是"发现问题后回到那次代码去复现"，没有 commit 就无法复现。**有未提交的本地改动时必须写明**，否则 commit hash 是假的 |
| **中间件版本与配置** | 中间件配置改动（如 buffer pool 从默认值调大）带来的提升，会被误归功于代码优化。版本不同（如 MySQL 5.7 vs 8.0）则架构与默认参数都不同，数据没有可比性 |
| **压测配置** | 见 3.2 与 3.7：Ramp-up 不同、有无思考时间，测的根本不是同一件事 |

### 7.3 明确"不可比"的判定情形

出现以下任一情形，两次压测的数据**不得放在同一张对比表里**：

1. 机器配置发生变化（CPU / 内存 / 磁盘）
2. 中间件版本或关键配置发生变化，但该变化不是本次要评估的优化项
3. Ramp-up、思考时间、token 数量、库存初始值等压测参数不一致
4. 存在未提交的本地代码改动，且无法说明改动内容
5. 压测期间机器上有明显的外部负载（浏览器、IDE、Windows 更新、杀毒扫描）
6. JMeter 自身成为瓶颈（3.8），此时吞吐量只能作为下界
7. 前后两次压测的档位不同（L2 与 L3 不能直接比）

## 8. 已知局限与本计划的边界

| # | 局限 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 1 | 全部组件同机部署 | 结论不能代表真实容量（见 2.2） | 结论限定为"行为与瓶颈位置"和"相对变化"；优先考虑把压测机独立出去 |
| 2 | Windows 环境 | 与生产 Linux 在网络栈、文件 IO、端口回收上行为不同 | 明确记录环境；不把绝对值外推 |
| 3 | 被测系统尚未实现 | 当前所有指标均为"待压测" | 先搭环境、先写脚本、先跑通链路，再谈数据 |
| 4 | 无应用内埋点 | 只能看到接口级 RT，无法分解到 Redis / DB / MQ | 待实现 Micrometer + `@Timed` 埋点（接口设计中已列为待办） |
| 5 | token 池可能不足 | L4 档位的 token 复用会污染结果（见 3.3） | 扩充 token 池，或在记录中明确标注该局限 |
| 6 | 单机 JMeter 可能成为瓶颈 | 高并发档位的吞吐量只是下界（见 3.8） | 每次记录 JMeter 自身资源占用；必要时改用独立压测机 |
| 7 | 无长时间稳定性测试 | 内存泄漏、连接泄漏、MQ 堆积缓慢增长这类问题测不出来 | 作为后续补充项（soak test） |
