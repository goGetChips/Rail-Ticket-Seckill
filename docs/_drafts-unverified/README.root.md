# Rail-Ticket-Seckill（铁路票务抢票系统）

> 一句话定位：一个把「余票查询 → 提交订单 → 扣减库存 → 支付 → 订单完结」这条主链路完整走通的铁路售票系统，重点不是功能有多全，而是把**高并发下如何不超卖、不重复下单、不把数据库打挂**这几件事的原理和取舍讲清楚。

## 二、为什么做这个项目

做这个项目有三个明确目的，按重要性排序：

**1. 教学：把中间件放回业务闭环里**

单独看「Redis 分布式锁」「MQ 削峰」「乐观锁」，概念都能背下来。但只有放进「一张票被 10 万人同时抢」这个具体场景，才会被迫回答一些真问题：锁加在哪一层？加锁失败是重试还是直接拒绝？MQ 消息丢了怎么办？这些问题的答案才是真正的知识。

**2. 面试：能讲清楚「难点是什么」**

面试里被问「你这个项目有什么难点」，含糊回答「用了 Redis 做缓存」是没有说服力的。这个项目的每个关键决策都会写进 ADR，格式固定为：做了什么 / 为什么这么做 / 不这么做会出什么问题 / 对比了哪些替代方案 / 为什么没选它们。目的是让开发者本人能对着文档复述出取舍，而不是背诵技术名词。

**3. 高并发实践：亲手制造并观察问题**

超卖、缓存击穿、消息重复消费、订单状态错乱——这些问题只有在并发下才暴露。项目会包含可复现的压测脚本和故障注入说明（**待编写，见开发路线图阶段 7**），目标是让每个结论都有真实日志或压测数据支撑，而不是「据说」。

### 4.2 三条主链路

**链路 A：查余票（读多写少，走缓存）**

```
Client → Gateway → train service → Redis(命中则返回)
                                 → 未命中 → MySQL → 回填 Redis → 返回
```

为什么这么走：查余票的请求量远大于下单量，如果每次都打到 MySQL，连接池会在秒杀开始瞬间被占满，导致下单请求也拿不到连接。缓存不是「为了快」，而是**为了保护数据库**。

**链路 B：下单（写链路，必须原子）**

```
Client → Gateway（限流/防重）→ ticket service
      → Redis + Lua：校验库存 + 扣减 + 记录购买者  （单次原子操作）
      → 扣减成功 → 发送 MQ 消息（订单创建）
      → 立即返回「排队中」给客户端
MQ 消费者 → order service → 写 MySQL 订单 → 更新库存流水
```

关键点：**Redis 里扣减的那一步必须是原子的**，这是「不超卖」的根基。具体做法与替代方案见下方「决策一」「决策二」。

**链路 C：支付与订单完结**

```
pay service（接收第三方回调）→ 校验签名 → 发送 MQ 支付成功消息
  → order service 消费 → 订单状态机流转：待支付 → 已支付 → 出票中 → 已出票
  → 失败分支：待支付 → 超时取消 → 回滚 Redis 库存 → 释放给其他用户
```

超时未支付的订单必须把库存还回去，否则库存会被「占着不付钱」的请求慢慢耗光（这是真实抢票系统里最常见的坑之一）。

### 4.3 服务边界

| 服务 | 职责 | 不该做的事 |
| --- | --- | --- |
| gateway | 路由、鉴权、限流、请求日志 | 不写业务逻辑，不直连数据库 |
| user service | 注册、登录、乘车人管理 | 不碰库存和订单 |
| train service | 车次、经停站、余票查询（读缓存） | 不做库存扣减（扣减只归 ticket service） |
| ticket service | 库存扣减、库存回滚、库存流水 | 不直接创建订单（通过 MQ 交给 order service） |
| order service | 订单创建、状态机流转、超时取消 | 不直接改 Redis 库存（通过 ticket service 接口或消息） |
| pay service | 支付单、第三方回调、对账 | 不直接改订单状态（发消息给 order service） |

边界原则：**库存只有一个归属方**。任何服务都可以查库存，但只有 ticket service 能改库存。这条规则看起来啰嗦，但它消灭了「两个服务并发改同一个库存字段」这一整类问题。

## 五、关键设计决策

以下每个决策都遵循同一个模板：做了什么 / 为什么 / 不这么做会怎样 / 替代方案对比 / 为什么没选。

### 决策一：库存扣减放在 Redis 用 Lua 脚本完成

**做了什么**：把每趟车次的余票数放在 Redis 里，用一段 Lua 脚本一次性完成「读库存 → 判断是否 >0 → 判断该用户是否已买过 → 扣减 → 记录购买者」。

**为什么**：Redis 单线程执行命令，一段 Lua 脚本在执行期间不会被其他命令打断，因此「读-判断-写」三步天然是原子的。同时它把并发压力挡在 Redis 层，MySQL 完全不用参与抢票瞬间的竞争。

**不这么做会怎样**：如果拆成 `GET` 再 `DECR` 两条命令，两个请求可能同时读到 1，各自判断「还有票」，最后卖出 2 张——这就是超卖。库存越少、并发越高，超卖越容易复现。

**替代方案对比**：

| 方案 | 原子性 | 性能 | 数据一致性风险 | 结论 |
| --- | --- | --- | --- | --- |
| Redis + Lua 脚本 | 单命令原子 | 高（内存操作） | 需处理与 MySQL 的最终一致 | **选用** |
| Redis 分布式锁 + 普通命令 | 靠锁保证 | 中（锁竞争、网络往返） | 需处理锁超时、误删 | 未选，见下 |
| MySQL 悲观锁 `SELECT ... FOR UPDATE` | 强 | 低（行锁排队，热点行串行） | 无 | 未选，见下 |
| MySQL 乐观锁 `UPDATE ... WHERE stock > 0` | 强 | 中（大量失败重试） | 无 | 作为兜底保留，见下 |
| MySQL 唯一索引兜底 | 强 | — | 无 | **保留，作为最后防线** |

**为什么没选分布式锁**：锁的粒度比 Lua 脚本粗，一次下单要多次网络往返（加锁、读、写、解锁），热点车次上锁竞争会把延迟推高；而且锁本身还有超时释放、误删他人锁等一串边界问题要处理。Lua 脚本把这些问题一次性消掉了。

**为什么没选 MySQL 悲观锁**：`FOR UPDATE` 会让同一车次的所有下单请求在数据库层面串行排队。热门车次上，这个排队会迅速吃满连接池，然后把整个系统拖垮——**抢票系统的瓶颈必须在 Redis 挡掉，不能下沉到 MySQL**。

**为什么保留 MySQL 乐观锁和唯一索引**：Redis 是内存存储，可能丢数据、可能被误操作清空。数据库层的 `UPDATE ... WHERE stock > 0` 和「一个用户对一个车次只能有一条有效订单」的唯一索引，是防止超卖和重复购票的最后一道防线。它们平时不承担并发压力，只在异常时兜底。

> 完整的 Lua 脚本、唯一索引 DDL 与边界说明见 `docs/architecture/` 与 `docs/database/`（待编写）。

### 决策二：下单异步化，用 MQ 削峰

**做了什么**：Redis 扣减成功后，不直接写 MySQL 订单，而是发一条 MQ 消息，立刻给客户端返回「排队中」，由消费者慢慢落库。

**为什么**：秒杀开始的那几秒，请求量是平时的几十上百倍。同步写库意味着每次下单都要占用一个数据库连接几百毫秒，连接池瞬间耗尽，结果是**所有人都失败**。异步化把「瞬时高并发」转换成「队列 + 匀速消费」，让数据库只承受它能承受的速率。

**不这么做会怎样**：数据库被打满 → 连接池等待超时 → 已扣减 Redis 库存但订单没落库 → 用户看到「扣了库存却没订单」，这是最难排查的一类线上问题。

**替代方案对比**：

| 方案 | 峰值承受能力 | 用户感知 | 复杂度 | 结论 |
| --- | --- | --- | --- | --- |
| 同步写库 | 取决于 MySQL 写入能力 | 立即知道结果 | 低 | 未选，峰值下会整体雪崩 |
| MQ 异步下单 | 取决于队列堆积能力 | 「排队中」，需轮询结果 | 中高 | **选用** |
| 内存队列（`BlockingQueue`） | 单机 | 同上 | 低 | 未选，重启丢数据、无法水平扩展 |
| 请求排队 + 定时任务 | 中 | 延迟大 | 中 | 未选，时效性差 |

**为什么没选内存队列**：进程重启即丢消息，而订单消息丢了就意味着「钱可能收了但票没出」。且内存队列无法跨实例，服务无法水平扩容。

**MQ 选型**：RocketMQ / RabbitMQ / Kafka 三者尚未最终确定，**待写入 ADR**。判断维度是：是否需要事务消息、是否需要延迟消息（订单超时取消会用到）、团队熟悉度、本地 Docker 启动成本。

**引入 MQ 带来的新问题（必须一并解决）**：

| 问题 | 应对思路 |
| --- | --- |
| 消息丢失 | 生产者确认 + 消费者手动 ACK + broker 持久化 |
| 消息重复 | 消费端幂等：以订单号做唯一键，重复消息直接忽略 |
| 消息顺序 | 同一订单的消息用同一个分片键（订单号）路由到同一队列 |
| 消息积压 | 监控堆积量，消费者水平扩容；设置告警阈值（**阈值待压测确定**） |

### 决策三：订单状态用状态机管，不用散落的 `if`

**做了什么**：把订单状态和允许的流转路径集中定义，所有状态变更必须走状态机校验。

**状态定义**（草案，**待评审**）：

```
待支付 ──支付成功──▶ 已支付 ──出票成功──▶ 已出票
   │                    │
   │超时/取消            │出票失败
   ▼                    ▼
已取消                出票失败（触发退款）
```

**为什么**：订单状态是典型的「状态少、路径多、出错代价高」。如果每个业务方法里都写 `if (order.getStatus() == 待支付)`，迟早会出现「已取消的订单被支付回调改成已支付」这种脏数据，而且这种 bug 只有在并发回调时才会暴露。

**不这么做会怎样**：状态流转散落在各处，没人能说清「哪些状态可以到哪些状态」。新增一个状态（比如「改签中」）时，需要通读全部代码才能确认影响面。

**替代方案对比**：

| 方案 | 约束强度 | 可读性 | 改动成本 | 结论 |
| --- | --- | --- | --- | --- |
| 枚举 + 状态机集中校验 | 强，非法流转直接抛异常 | 高，流转图即文档 | 低 | **选用** |
| 散落的 `if` 判断 | 弱，靠开发者自觉 | 低 | 高 | 未选 |
| 数据库触发器 | 强 | 低，逻辑藏在 DB 里 | 高，难测试 | 未选 |
| 工作流引擎（如 Flowable） | 强 | 中 | 高，杀鸡用牛刀 | 未选，状态数量不足以抵消引入成本 |

### 决策四：缓存与数据库的一致性策略

**做了什么**：缓存采用 Cache-Aside 模式，**更新数据库后删除缓存**（而不是更新缓存）。

**为什么**：删除缓存比更新缓存更安全。并发更新时，「先写库 A、再写库 B、再更新缓存」的顺序交错会让缓存长期停留在旧值；而删除缓存只是让下一次读回源，回源结果一定是最新的（在读写分离场景下还需注意主从延迟，**待验证**）。

**不这么做会怎样**：缓存里长期存在一个和数据库不一致的余票数，用户看到「有票」点进去却下不了单，或者反过来——显示无票但实际有票，直接影响转化。

**替代方案对比**：

| 方案 | 一致性 | 复杂度 | 结论 |
| --- | --- | --- | --- |
| 更新库 + 删除缓存（Cache-Aside） | 最终一致，窗口极短 | 低 | **选用** |
| 更新库 + 更新缓存 | 并发下易长期不一致 | 低 | 未选 |
| 延迟双删 | 更稳，仍有窗口 | 中 | 备选，真出问题时再上 |
| 订阅 binlog 异步刷新（Canal） | 较好 | 高 | 未选，本阶段不值得引入 |
| 强一致（分布式锁包住读写） | 强 | 很高 | 未选，性能代价不可接受 |

**缓存三大问题的应对**（结论待压测验证）：

| 问题 | 本项目应对 |
| --- | --- |
| 缓存穿透（查不存在的车次） | 空值缓存 + 参数校验；布隆过滤器**待评估** |
| 缓存击穿（热点 key 过期） | 热点车次缓存不设过期时间，由后台任务主动刷新 |
| 缓存雪崩（大量 key 同时过期） | 过期时间加随机抖动；Redis 部署形态待定 |

### 决策五：接口幂等

**做了什么**：下单接口要求客户端携带幂等键（或用「用户 ID + 车次 + 乘车人」组合），服务端在 Redis 里做去重。

**为什么**：用户手抖连点、网络超时后客户端重试、网关重发——这些都会产生重复请求。没有幂等保护，同一个用户可能买到两张票（如果库存充足），或在库存不足时产生一笔「扣了库存但没有对应订单」的悬挂数据。

**替代方案对比**：

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| 幂等键 + Redis `SET NX` | 快，有 TTL，适合抢票场景 | **选用** |
| 数据库唯一索引 | 强，但要等到写库那一刻才拦得住 | **同时保留**，作为兜底 |
| 分布式锁按用户维度 | 能防重，但锁粒度影响吞吐 | 未选，幂等键已足够 |
| 前端置灰按钮 | 只能防误触，防不住重试和恶意请求 | 仅作为体验优化，不作为方案 |

## 九、开发路线图

> 这是初步规划，**尚未经过评审**，会随 ADR 的产出调整顺序。每个阶段的「完成标准」都要求可验证，不接受「大概做完了」。

| 阶段 | 目标 | 主要产出 | 完成标准 |
| --- | --- | --- | --- |
| 阶段 0：环境与骨架 | 让项目能一条命令拉起 | Docker Compose（MySQL/Redis/MQ）、`docs/environment-setup.md`、多模块拆分决策 ADR | 新机器按文档可完成搭建，不依赖口头指导 |
| 阶段 1：领域建模与数据库 | 定下表结构与核心领域对象 | ER 图、建表 DDL、索引设计说明、`docs/database/` | DDL 可在空库直接执行；每个索引都写了它服务于哪条查询 |
| 阶段 2：查询链路与缓存 | 余票查询走通并落入缓存 | 车次查询接口、缓存读写、空值处理、`docs/api/` 起步 | 查余票接口功能正确；缓存命中与回源路径有日志可查 |
| 阶段 3：下单与库存扣减（核心） | 实现不超卖的下单 | Lua 脚本、唯一索引兜底、幂等键、并发测试 | 并发下单测试下库存不为负、同一用户不重复占票（**具体并发数待定**） |
| 阶段 4：异步落库与最终一致 | MQ 打通，订单异步创建 | 生产者/消费者、幂等消费、消息可靠性配置、堆积监控 | 杀进程重启后消息不丢；重复投递不产生重复订单 |
| 阶段 5：支付与订单状态机 | 订单全生命周期闭环 | 支付回调、状态机、超时取消与库存回滚 | 超时未支付订单能正确回滚库存；非法状态流转被拒绝 |
| 阶段 6：网关、限流与防刷 | 把恶意与异常流量挡在核心链路外 | 限流策略、鉴权、防刷规则 | 限流生效且不影响正常用户；规则有配置项可调 |
| 阶段 7：压测与可观测性 | 用数据说话 | 压测脚本、`docs/performance/` 压测报告、日志与指标 | 报告里每个数字都有压测环境说明；瓶颈定位有依据 |

**关于顺序**：阶段 3 是整个项目的核心难点，前面的阶段 0-2 都是为它铺路。如果时间有限，宁可把阶段 3、4 做扎实，也不要把功能铺开到阶段 6 却讲不清库存是怎么扣的。

## 十、AI-Assisted Development

这个项目在开发过程中使用了 AI 辅助。为了不产生「代码是 AI 写的、作者讲不清原理」的情况，这里明确界定 AI 参与的范围和**不参与**的部分。

### 10.1 AI 参与的工作

| 环节 | AI 的角色 | 具体的介入方式 |
| --- | --- | --- |
| 需求分析 | 提问者与查漏者 | 把「抢票」这个模糊需求拆成可验证的功能点；提示容易遗漏的边界（超时未支付、重复提交、退票回滚） |
| 架构方案讨论 | 备选方案提供者 | 给出多种技术路线的对比维度，帮助把「我习惯用 X」变成「X 在什么条件下优于 Y」 |
| 代码生成 | 草稿撰写者 | 生成样板代码、CRUD、配置模板、测试骨架；核心逻辑由开发者改写并逐行确认 |
| Debug | 假设提出者 | 根据异常栈提出可能原因，缩小排查范围；**验证由开发者执行** |
| 测试设计 | 用例枚举者 | 列出边界条件与并发场景清单，避免只测顺路径 |
| Code Review | 初审者 | 检查空指针、并发问题、资源未关闭、命名与分层问题；不替代人工评审 |
| 性能分析 | 线索整理者 | 帮助解读日志、梳理调用链、提出可能的瓶颈点 |
| 文档整理 | 结构化助手 | 把决策过程整理成 ADR 格式；统一术语与文档结构 |

### 10.2 关键原则

**关键技术决策、代码验证、性能测试和最终结果，全部由开发者本人确认。**

具体含义是：

- **技术决策由本人拍板**。AI 可以列出方案对比表，但「这个项目到底用哪个 MQ」「库存扣减放 Redis 还是 MySQL」，必须由开发者理解取舍后自己决定，并写进 ADR。采纳 AI 建议的唯一前提是——**能自己解释为什么选它，以及不选另一个会怎样**。
- **代码必须经过验证**。AI 生成的任何代码，未经过编译、运行、测试和逐行阅读，不进入主分支。AI 生成的代码出错时，定位和修复由开发者完成，不允许「让 AI 再改一版」当作修复手段。
- **性能数据必须实测**。本文档及 `docs/performance/` 中出现的任何数字，只能来自真实压测。AI 推测的数字一律标注「待压测」，不得当作结论引用。
- **最终结果由本人负责**。面试中被追问细节时，只有真正理解并能复现的人答得上来——这也是这个项目选择「宁可写详细，也不写含糊」的原因。

### 10.3 反面清单（明确不做的事）

- 不用 AI 生成性能数据、压测结论、用户量等无法验证的数字；
- 不用 AI 编造版本号和 API 细节，拿不准就标注「待验证」并去查官方文档；
- 不用 AI 生成没有真实日志支撑的「故障复盘」；
- 不把 AI 输出的方案对比表直接当结论，必须自己判断并补充本项目语境下的理由。
