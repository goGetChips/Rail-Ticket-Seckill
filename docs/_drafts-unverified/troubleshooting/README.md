# 踩坑记录本（Troubleshooting Log）

这个目录只有一个用途：**记录这个项目里真实踩过的坑，以及踩坑之后搞清楚的原因**。

它不是"知识点整理"，也不是"报错大全"。判断一条记录该不该留在这里的标准只有一条：

> 这个坑，我是先遇到了现象，然后花时间去查，最后改变了原有做法（或者想清楚了为什么现有做法没问题）。

没被真实触发过的问题，不写进"已确认记录"，只能进下面的"预判清单"。

## T-01 Redis 与 MySQL 库存不一致

- 状态：未复现
- 触发条件：待记录

### 1. 现象

（待填。预期形态：Redis 显示有票但下单失败并返回"库存不足"；或 Redis 显示无票但 MySQL 里还有余量；或对账时两侧差值不为 0。）

### 2. 相关日志

（待填。抓取时至少保留：traceId、车次+日期、预扣返回值、落库影响行数、回补动作。）

### 3. 初步判断

（待填）

### 4. 排查过程：可能方向

按"最可能先排除"的顺序：

1. **预扣成功但落库失败，没有回补。** Redis 扣减、MQ 投递、消费者写 MySQL 是三段，中间任何一段断了，Redis 就少了一份库存。
2. **回补路径只改了一侧。** 取消订单 / 超时关单时，只 `UPDATE` 了 MySQL 而没有 `INCR` 回 Redis（或者顺序反了、失败了没重试）。
3. **DB 扣减条件写漏。** `UPDATE stock SET remain = remain - #{n} WHERE train_no = ?` 少了 `AND remain >= #{n}`，在并发或异常路径下把库存扣成负数。
4. **缓存重建时用旧值覆盖新值。** 库存 key 过期或误删后，回源读 MySQL 时读到了未提交/主从延迟的旧值，写回 Redis 把已预扣的额度"变回来"。
5. **Redis 侧数据丢失。** 主从切换、未开持久化或重启导致预扣记录丢失，DB 仍认为已售出。

### 4.1 怎么验证

- 写一段对账 SQL，把两侧口径拉平：
  - MySQL 侧已售 = `初始库存 - remain`（按 车次 + 乘车日期 + 席别 聚合）
  - Redis 侧已售 = `初始库存 - GET 库存key`
  - 两侧差值 > 0 的记录就是不一致样本。
- 构造异常：在 MQ 消费者写库前人为抛异常 / 手动停消费者，观察 Redis 与 MySQL 的差值是否随时间扩大且无人收敛。
- 打开 `redis-cli monitor`（仅本地短时使用，压测时禁用），观察预扣与回补是否成对出现。
- 确认库存表是否有 `version` / `updated_at` 字段，便于回溯是哪一步改的。
- 确认对账任务是否存在。**当前设计中如果只有"预扣 + 落库"而没有定时对账，那这个坑的暴露只是时间问题。**

（待填）

### 6. 解决方案

（待填。候选方向：定时对账 + 差值修复、预扣时写预扣流水用于精确回补、回补操作幂等化、DB 侧加 `remain >= n` 兜底约束。）

方案对比（待实测后补充结论）：

| 方案 | 一致性强度 | 实现成本 | 主要风险 | 本项目是否选用 |
| --- | --- | --- | --- | --- |
| 只靠"预扣 + 落库"，不设对账 | 弱 | 最低 | 差异永远存在且无人发现 |  |
| 定时对账 + 差值修复 | 最终一致 | 中 | 修复动作本身要幂等 |  |
| 预扣流水 + 精确回补 | 最终一致（更准） | 中高 | 流水表膨胀，需要归档 |  |
| MQ 事务消息 + 消费确认闭环 | 较强 | 高 | 依赖 MQ 能力，学习成本高 |  |

### 7. 为什么这个方案有效

（待填。写清"堵住了哪条路径"以及"依赖什么前提"，例如：对账依赖 Redis 与 MySQL 都能被同一口径度量，一旦引入"预扣流水"作为唯一账本，Redis 就降级为加速层，不一致只影响性能不影响正确性。）

### 8. 优化前后对比

| --- | --- | --- | --- |

（待填。口述骨架：秒杀场景刻意让 Redis 承担预扣以扛住流量 → 代价是引入了两侧不一致 → 我们没有假装它不存在，而是承认"Redis 只是加速层，MySQL 才是账本" → 所以必须有对账把 Redis 拉回真相 → 定位手段是两侧同口径比对。）

## T-02 MQ 重复消费导致重复订单

- 状态：未复现
- 触发条件：待记录

### 1. 现象

（待填。预期形态：同一用户同一车次出现两条订单；或订单表出现相同 `order_no` 的多行；或库存被扣了两次。）

### 2. 相关日志

（待填。重点保留：消息 ID / 业务 key、消费位点、ack 时间、`insert` 影响行数。）

### 3. 初步判断

（待填）

### 4. 排查过程：可能方向

1. **MQ 的投递语义本身是"至少一次"。** 消费成功但 ack 丢失（消费者在 ack 前宕机 / 网络抖动 / 消费超时触发重投），消息会被再次投递。
2. **消费端没有业务幂等。** 直接 `insert` 订单，重投就多一条。
3. **重平衡（rebalance）导致重复。** 位点未提交时发生 rebalance，新消费者从上次提交位置重新拉取。
4. **业务重试与 MQ 重试叠加。** 消费失败后本地 catch 住自己重试一次，MQ 又重投一次，放大重复次数。

### 4.1 怎么验证

- 在消费者写库前 `sleep`（或本地断点）到超过可见性超时 / 心跳间隔，观察消息是否被重投，重投了几次。
- 查重 SQL：`SELECT order_no, COUNT(*) c FROM t_order GROUP BY order_no HAVING c > 1;`
- 查是否有唯一索引：
  ```sql
  SHOW INDEX FROM t_order;
  -- 期望看到 order_no 或 (user_id, train_no, travel_date, seat_type) 上的 UNIQUE
  ```
- 人为并发投递同一条消息（或同一用户两个请求），验证"先查再插"是否会双写成功。**这一步基本必然复现**——"先查后插"在并发下不构成幂等。
- 观察 MQ 控制台的消费重试次数与死信队列，确认重试策略。

### 5. 真正原因

（待填）

### 6. 解决方案

（待填）

幂等方案对比：

| 方案 | 原理 | 并发下是否可靠 | 成本 | 备注 |
| --- | --- | --- | --- | --- |
| 消费前先 `SELECT` 判存在 | 业务判断 | 不可靠 | 低 | 并发窗口内两次都查不到 |
| 唯一索引 + `INSERT IGNORE` / `ON DUPLICATE KEY UPDATE` | 数据库约束兜底 | 可靠 | 低 | 推荐作为最后一道防线 |
| Redis `SETNX` 消息 ID 去重 | 分布式标记 | 可靠但依赖 Redis | 中 | Redis 数据丢失会失效，且要考虑 key 过期 |
| 去重表（消息 ID 唯一索引） | 数据库 | 可靠 | 中 | 与订单表分属不同事务时需注意事务边界 |
| 订单状态机 CAS 更新 | 状态流转约束 | 可靠 | 中 | 适合"重复消息触发状态推进"的场景 |

参考 DDL（唯一索引这一层是底线，不能省）：

```sql
ALTER TABLE t_order
  ADD UNIQUE KEY uk_order_no (order_no),
  ADD UNIQUE KEY uk_user_train (user_id, train_no, travel_date, seat_type);
```

> 注：`uk_user_train` 属于业务规则约束（同一天同一车次同一席别只允许一单）。如果产品允许一人多单，就不能加，此时幂等只能靠 `uk_order_no`。**加不加这条，取决于业务语义，不要为了"防重"而强加。**

### 7. 为什么这个方案有效

（待填。要点：数据库唯一索引是并发安全的，它把"判断 + 写入"合并成一个原子操作，消除了应用层的检查-执行竞态；而 Redis 去重只是在更早的位置减少无效消费，不能替代约束。）

### 8. 优化前后对比

| 指标 | 优化前 | 优化后 | 观测方式 |
| --- | --- | --- | --- |
| 重投场景下的重复订单数 | 待压测 | 待压测 | 查重 SQL |
| 重复消息的消费耗时 | 待压测 | 待压测 | 消费者打点日志 |

### 9. 面试如何回答

（待填。骨架：MQ 是至少一次投递，重复是常态而不是异常 → 所以幂等是消费端的义务 → 应用层判断在并发下不成立 → 最终用唯一索引兜底 → 补充说明"哪一层负责减少重复、哪一层负责保证正确"。）

## T-03 Feign 首次调用超时或连接池耗尽

- 状态：未复现
- 触发条件：待记录

### 1. 现象

（待填。预期形态：服务刚启动后第一次调用下游超时，之后正常；或并发上来后大量 `Read timed out` / 线程长时间持有在 socket 读。）

### 2. 相关日志

（待填。抓取时保留：Feign 客户端名、目标实例地址、耗时、异常类名全文。）

### 3. 初步判断

（待填）

### 4. 排查过程：可能方向

1. **首次调用包含初始化成本。** 首次需要拉取/刷新服务实例列表、建立 TCP 连接、可能还有客户端类加载与 JIT，耗时明显高于稳态。
2. **底层 HTTP 客户端没有连接池或池太小。** 如果用默认实现，可能每次请求新建连接；如果换成连接池实现，池上限与下游承载能力不匹配时也会排队。
3. **超时配置缺失或过长。** 默认超时时间若不显式配置，会与业务预期不符；超时过长会导致线程被长时间占住，进而把上游线程池拖垮。
4. **重试与超时叠加放大。** Feign 重试 + LoadBalancer 重试 + 业务重试叠加，一次失败放大成多次调用。
5. **连接未复用。** 服务端或客户端有一侧关闭了 keep-alive，连接反复重建。

### 4.1 怎么验证

- 在调用处打点记录耗时（`System.nanoTime()` 前后差），冷启动后连续调用，观察第 1 次与第 N 次的差距。**具体数值以本机实测为准，不要引用外部结论。**
- 压测中执行 `jstack`，统计线程栈里有多少卡在 socket 读/写，以及卡住的 Feign 目标。
- 打开 Feign 完整日志（`Logger.Level.FULL`），确认请求/响应耗时与重试次数。
- `netstat -ano | findstr <端口>` 看 `TIME_WAIT` 数量是否异常增长。
- 检查配置里是否显式设置了 connectTimeout / readTimeout，以及底层客户端实现是什么。**当前配置是多少：待核对。**
- 确认下游 Tomcat 的线程数与最大连接数配置，避免"上游池很大、下游接不住"。

（待填）

（待填）

## T-05 Lua 脚本里用了非确定性命令导致主从或集群报错

- 状态：未复现
- 触发条件：待记录

### 1. 现象

（待填。预期形态：单机模式跑得好好的脚本，换到主从/集群环境报错；或脚本产生结果在主从之间不一致。）

### 2. 相关日志

（待填。保留 Redis 返回的完整错误串，例如包含 `Write commands not allowed after non deterministic commands` 或 `CROSSSLOT` 的原文。）

### 3. 初步判断

（待填）

### 4. 排查过程：可能方向

1. **脚本里混入了非确定性命令。** 例如读取时间、随机取元素、随机成员、遍历键空间这类命令。脚本在"逐命令复制"的复制模式下要求可重放且结果一致，非确定性命令会破坏这个前提。
2. **写命令出现在非确定性命令之后。** 这是上面那条的常见变体：先读了随机值，后面又写，引擎直接拒绝执行。
3. **集群模式下跨 slot。** 脚本里操作的多个 key 不在同一槽位，直接报错。库存 key 与流水 key 若不加 hash tag，就可能分属不同槽。
4. **Lua 与 Redis 的类型/数值边界。** 整数溢出、`NaN`、把 `nil` 参与运算等，会让脚本中断。
5. **脚本内异常未保护。** 用 `redis.call` 时脚本中途报错，**已执行的写操作不会自动回滚**，留下半成品状态；换成 `redis.pcall` 可以自己接住错误。

### 4.1 怎么验证

- 把脚本分别在单机、主从、集群三种拓扑下各跑一遍，对比行为差异。**本项目当前用的拓扑：待核对。**
- `INFO errorstats` 看是否有脚本相关的错误计数增长。
- `SLOWLOG GET` 确认慢脚本（大 key 上的脚本也会体现，见 T-08）。
- 手工用 `EVAL` 执行一份最小化脚本，逐步加回命令，定位是哪个命令触发的。
- 检查脚本里所有 key 是否用同一个 hash tag 固定到同一槽，例如 `{train:20260915:G1}:stock` 与 `{train:20260915:G1}:sold`。

一个需要避免的写法（示例，非项目代码）：

```lua
-- 反例：脚本内读取时间/随机值，且之后还有写命令
local now = redis.call('TIME')          -- 非确定性
local idx = redis.call('SRANDMEMBER', KEYS[2])  -- 非确定性
redis.call('DECRBY', KEYS[1], 1)       -- 非确定性命令之后的写命令
```

正确做法是把这些值由调用方计算好，通过 `ARGV` 传进脚本：

```lua
-- 正例：所有非确定性的东西都来自 ARGV，脚本本身纯粹且可重放
-- KEYS[1] 库存 key, ARGV[1] 扣减数量, ARGV[2] 请求唯一标识, ARGV[3] 过期秒数
local remain = tonumber(redis.call('GET', KEYS[1]))
if remain == nil then return -1 end        -- 未初始化
if remain < tonumber(ARGV[1]) then return 0 end  -- 库存不足
redis.call('DECRBY', KEYS[1], tonumber(ARGV[1]))
return 1
```

（待填）

### 6. 解决方案

（待填。方向：脚本内只用确定性命令、非确定性输入走 ARGV、多 key 用 hash tag 保证同槽、用 `redis.pcall` 处理可预期错误、脚本保持短小。）

### 7. 为什么这个方案有效

（待填。要点：脚本的可重放性是复制与集群转发的前提；把不确定性从脚本内部挪到调用方，等价于把"结果"提前算好，脚本只做判断和写入，任何副本重放都能得到同样的状态。）

## T-07 连接池（HikariCP）被打满

- 状态：未复现

### 3. 初步判断

### 4. 排查过程：可能方向

1. **连接泄漏。** 有代码路径没关连接（没用 try-with-resources / 手动 `getConnection` 后异常分支漏了 close）。
2. **连接被长时间持有。** 长事务、慢 SQL、缺索引导致全表扫描，连接一直不还。

- `SHOW PROCESSLIST;` 看是否有长时间 `Sleep`/`Query` 的连接。
- `SELECT * FROM information_schema.innodb_trx ORDER BY trx_started;` 找长事务。
- 通过 actuator 指标看活跃连接数与等待线程数随时间的变化，和接口 RT 曲线对齐。
- 全局搜索 `@Transactional` 方法体内是否出现 Feign 调用或耗时操作。
- 注意排查是否存在多处 `new` 出来的连接池（多数据源配错时常见）。

### 5. 真正原因

（待填）

### 6. 解决方案

（待填。方向：修泄漏点、拆分事务边界把远程调用挪出事务、把消费者与接口的连接池隔离、按数据库承载能力反推池上限而不是拍脑袋调大。）

### 7. 为什么这个方案有效

（待填。要点：连接池不是越大越快——数据库的连接数是全局稀缺资源，池上限应服从于数据库的并发处理能力与被压测验证过的拐点。因此先定位"为什么要占用这么久"，再谈调参。）

- `INFO commandstats` —— 看命令调用次数与平均耗时的分布，找出"调用量极高"的命令。

| --- | --- | --- | --- | --- |
| 只用 Redis | 受 TTL 控制 | 好 | 低 | 一般业务数据 |
| 本地缓存 + 短 TTL | 有窗口，多实例间不一致 | 最好 | 中 | 几乎不变的维度数据（车次、站点） |
| 本地缓存 + MQ/配置中心广播失效 | 窗口较小 | 最好 | 高 | 变更频率低但要求较快生效 |
| 本地缓存存库存 | **不安全** | 最好 | — | 不适用 |

关键结论：**库存、余票这类数据不进本地缓存。** 本地缓存只用于基础维度数据，并且必须带 TTL（加随机抖动避免同时失效）和容量上限。

### 7. 为什么这个方案有效

（待填。要点：本地缓存的失效通知永远无法做到"原子广播"，因此一致性只能靠"数据本身允许短暂不一致"来保证。把适用范围限制在低频变更的维度数据上，是用业务特性换取工程简化。）

### 4. 排查过程：可能方向

1. **注册 IP 是容器内网 IP。** 服务注册到 Nacos 时上报的是容器内地址，宿主机或其他容器根本连不上——这一条会伪装成 T-04（调用到不可用实例）。
2. **资源上限。** WSL2 与容器默认的内存/CPU 上限低于预期，压测时容器被杀或疯狂换页，数据完全不可用。
3. **网络访问差异。** 宿主机的 `localhost` 与 WSL 内的 `localhost` 不是同一个东西；端口映射缺失或方向搞反。
4. **时间不一致。** WSL/容器与宿主时间漂移，直接影响"超时未支付关单"这类基于时间的逻辑——订单可能被立刻关掉或永远不关。
5. **文件系统性能。** 跨系统访问挂载目录时 IO 性能下降，会影响依赖文件读写的组件。
6. **镜像/容器重启后数据丢失。** 没挂数据卷，MySQL / Redis 重启后数据回到初始状态，之前测出的"不一致"直接消失，导致问题无法复现。

### 4.1 怎么验证

- `docker stats` 看实时资源占用，确认是否触顶。
- `docker inspect <容器>` 看网络模式与 IP；对比 Nacos 控制台里注册的 IP 是否一致。
- 容器内 `/bin/date` 与宿主 `date` 对比（Windows 下用 `Get-Date`）。
- 从调用方容器内 `ping` / `curl` 目标实例，确认网络可达性。
- `wsl -l -v` 确认 WSL 版本与发行版；检查是否配置了资源上限。
- 确认 MySQL / Redis 是否挂了数据卷：`docker inspect -f '{{ .Mounts }}' <容器>`。
- 压测前先做一次基线：空压测（只测连通性）确认环境本身没问题。
