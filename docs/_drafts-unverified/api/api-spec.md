## 0. 本文档的定位与阅读前提

**规格来源说明。** 本仓库 `docs/architecture/design-spec.json` 当前内容为 `null`，即上游没有给出机器可读的接口清单（apiList）。因此本文档是**自拟的设计基线**，用于统一后续编码与压测的口径，而不是对既有代码的逆向描述。当前 `src/main/java` 下只有一个空的启动类，所有接口均**尚未实现**。

由此产生两条硬规则：

1. 本文档中的路径、字段、错误码在实现时**以本文档为准**；若实现过程中发现设计不合理，改本文档 + 在文末"变更记录"留痕，不要只改代码。

**目标读者。** 需要理解接口"为什么这么设计"的 Java 开发者，尤其是准备面试、需要能讲清秒杀链路取舍的人。

**本文档的组织方式。** 先讲全局约定（认证、响应体、错误码），再逐个接口展开，最后用一整节展开秒杀下单接口。每个接口都按同一模板写：

## 1. 全局约定

### 1.1 路径与版本

| 项 | 约定 | 理由 |
| --- | --- | --- |
| 基础路径 | `/api/v1` | 版本号进路径，未来不兼容变更走 `/api/v2`，避免用 Header 传版本（网关路由、日志排查、curl 调试都更麻烦） |
| 命名风格 | 资源用复数名词、小写中划线 | `GET /api/v1/orders`，不用 `getOrderList` 这类 RPC 风格 |
| 动词的使用 | 仅"非 CRUD 的动作"用子路径 | `POST /orders/{id}/cancel`。取消不是幂等的资源替换，硬套 PUT 反而难懂 |
| 运维端点 | `/actuator/**` 不走 `/api/v1` | 属于进程自身而非业务 API，方便网关按前缀屏蔽 |

**替代方案对比：**

| 方案 | 优点 | 缺点 | 是否采用 |
| --- | --- | --- | --- |
| 路径版本 `/api/v1` | 直观、易路由、易缓存区分 | URL 变长 | ✅ 采用 |
| Header 版本 `Accept: application/vnd.x.v1+json` | URL 干净、语义纯粹 | 调试与网关配置成本高，团队理解成本高 | ❌ |
| 不版本化 | 省事 | 一旦不兼容变更只能停机或强推 App 升级 | ❌ |

### 1.2 认证方式

**当前设计基线：** 登录后签发 JWT（无状态），客户端放 `Authorization: Bearer <token>`。

| 项 | 约定 |
| --- | --- |
| 传递方式 | 请求头 `Authorization: Bearer <token>` |
| 登出/失效 | 由于 JWT 无状态，服务端不能主动失效。设计上把 token 的 `jti` 写入 Redis 白名单（key 带 TTL＝token 剩余有效期），登出即删 key |
| 网关职责 | 校验签名与过期时间，解析出 `userId` 后以内部头（如 `X-User-Id`）透传给下游，并对**外部请求剥除**该内部头，防止伪造 |
| token 有效期 | 待定（实现时与产品确认后回填） |

**为什么不只用 JWT 的自包含校验、还查一次 Redis？**

- 只用 JWT：服务端无法"踢人"（改密码、风控封禁后旧 token 仍有效）。
- 加 Redis 白名单：多一次 Redis 查询（亚毫秒级），换来可主动失效。秒杀链路对这一次查询敏感，因此**秒杀下单接口允许只校验 JWT 签名不做白名单查询**（可接受的降级：极端情况下已登出用户在 token 过期前仍能下单，属于可接受风险，因为下单只是"占位"，最终支付仍需二次校验）。

**替代方案对比：**

| 方案 | 能否主动失效 | 每请求开销 | 水平扩展 | 结论 |
| --- | --- | --- | --- | --- |
| 纯 JWT（自包含） | 不能 | 仅验签，极低 | 好 | 部分采用（秒杀下单接口） |
| JWT + Redis 白名单 | 能 | +1 次 Redis GET | 好 | ✅ 默认采用 |
| 服务端 Session（内存） | 能 | 内存查表，但需粘性会话 | 差（多实例需广播或集中存储） | ❌ |
| Session 存 Redis（Spring Session） | 能 | +1 次 Redis GET | 好 | 与 JWT+白名单效果接近，但每次请求都要查；JWT 方案可只在需要时查，更灵活 |

### 1.3 统一响应体（概览，详细论证见第 3 节）

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "traceId": "b7f1c0f2a3d44e1e",
  "timestamp": 1730000000000
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | int | 业务码，`0` 表示成功，非 0 见第 3 节错误码规范 |
| `message` | string | 面向调用方的简短提示，**不包含堆栈、SQL、内部 IP** |
| `data` | object / array / null | 成功时的载荷；失败时为 `null` |
| `traceId` | string | 链路追踪 ID，与日志中的 `traceId` 一致，用于问题定位 |
| `timestamp` | long | 服务端毫秒时间戳 |

### 1.4 通用请求约定

| 项 | 约定 | 理由 |
| --- | --- | --- |
| Content-Type | `application/json;charset=UTF-8` | 单一格式，避免表单/JSON 双解析分支 |
| 时间格式 | 入参与出参统一用 `yyyy-MM-dd HH:mm:ss`（字符串）或毫秒时间戳（long，字段名带 `Millis` 后缀） | 不用 `Date` 默认序列化，避免时区歧义 |
| 金额 | 统一用 `long` 表示"分" | 绝不用 `double`，浮点误差在票务/支付场景不可接受 |
| 分页 | `pageNum` 从 1 开始，`pageSize` 默认 10、上限 100 | 上限防止 `pageSize=100000` 拖垮 DB |
| 幂等键 | 写接口可选带 `X-Request-Id`（客户端生成 UUID） | 用于服务端幂等去重，见秒杀下单接口 |
| 字符集 | 全链路 UTF-8 | Windows 环境下尤其要注意控制台与文件编码不一致导致的乱码 |

### 2.1 请求参数校验：统一走 Bean Validation

**做了什么。** 所有入参用 JSR-303 注解声明约束（`@NotNull`、`@NotBlank`、`@Min`、`@Max`、`@Pattern`、`@Size`），Controller 方法参数上加 `@Valid`，由 `@RestControllerAdvice` 统一把 `MethodArgumentNotValidException`、`ConstraintViolationException` 转成 `10001/10003`。

**为什么这么做。** 校验规则写在 DTO 字段旁边，是"声明式"的，规则和字段不会走散；手写 if 判断会散落在 Service 各处，且容易漏。

**不这么做会出什么问题。** 参数直接进 Service，`null` 会在深层代码里抛 NPE，被兜底异常处理器吞成 `500`，排查成本极高；或者非法参数直接打到 DB，造成无效慢查询——在秒杀场景里，无效流量和有效流量一样消耗资源。

**替代方案对比：**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Bean Validation 注解 | 声明式、生态成熟、错误信息可聚合 | 复杂跨字段规则表达弱 | ✅ 主方案 |
| Service 内手写 if | 灵活 | 散落、易漏、重复 | ❌ |
| 规则引擎（Drools 等） | 规则可动态配置 | 引入重量级依赖，秒杀接口追求链路短 | ❌ |

**高频疑问：参数校验失败该返回 400 还是 200？** 见第 3 节的错误码与状态码映射表。

## 3. 统一响应体与错误码设计（为什么不能所有失败都返回 500）

这一节单独展开，因为它是**最容易被写错、且最容易在面试里被追问**的设计点。

### 3.1 先明确要解决的三类失败

一个请求失败，原因可能来自完全不同的层次。把它们混在一起返回，是后面所有问题的根源：

| 层次 | 例子 | 谁的责任 | 调用方该做什么 |
| --- | --- | --- | --- |
| A. 协议/认证层 | 未登录、token 过期、无权限、请求体不是合法 JSON、请求过于频繁 | 调用方（或网关） | 重新登录、改请求、退避重试 |
| B. 业务层 | 库存不足、重复下单、秒杀未开始、订单状态不允许取消 | 业务规则 | **不要重试**，直接给用户提示 |
| C. 系统层 | DB 连接池耗尽、Redis 不可用、MQ 投递失败、未捕获异常 | 服务端 | 可以退避重试，且**必须告警** |

关键结论：**A、B、C 必须能被调用方、网关、监控系统区分开**。用一个 `500` 覆盖 A/B/C，等于把这三个维度的信息全部抹掉。

### 3.2 设计：HTTP 状态码 + 业务码，双层表达

**做了什么。** 状态码表达"这次 HTTP 交互在协议与基础设施层面是否正常"，业务码表达"业务规则是否通过"。两者组合成一张明确的映射表：

| 场景 | HTTP 状态码 | 业务码 | 说明 |
| --- | --- | --- | --- |
| 成功 | 200 | 0 | 正常返回 |
| 参数校验失败 | 400 | 10001 / 10003 | 请求本身不合法，重试无意义 |
| 请求体不可解析 | 400 | 10002 | JSON 语法错误 |
| 未登录 / token 无效 | 401 | 10004 | 触发客户端跳登录 |
| token 过期 | 401 | 10005 | 客户端可用 refresh 流程 |
| 无权限 | 403 | 10006 | 越权访问他人订单 |
| 资源不存在 | 404 | 10007 | 路径或 ID 不存在 |
| 方法不支持 | 405 | 10008 | 例如对下单接口发 GET |
| 被限流 | 429 | 10009 | **必须**是 429，客户端据此退避 |
| 依赖降级 / 系统繁忙 | 503 | 10010 / 5xxxx | 可重试，且应触发告警 |
| 业务规则不通过 | 200 | 3xxxx / 4xxxx | **注意：200**，见下方论证 |
| 未捕获异常 | 500 | 10999 | 兜底，必须脱敏 |

**为什么业务规则不通过要返回 200 而不是 4xx？** 这是本设计里最需要讲清的一点。

"库存不足"不是"请求错了"，而是"请求完全正常，只是这一时刻业务规则不允许"。用 4xx 表达它会有副作用：`422 Unprocessable Entity` 在语义上勉强成立，但大量客户端 SDK、网关重试策略、前端统一错误处理都把 4xx 当"调用方 bug"处理，会弹出"请求参数错误"这类误导提示。用 200 + 业务码，调用方拿到的是明确的"业务结果"，UI 可以直接展示"票已售罄"。

**权衡与代价。** 这样做牺牲了"仅看 HTTP 状态码就能判断成败"的纯粹性。缓解手段：所有响应都是统一响应体，调用方只需要判断 `code == 0`，不需要同时判断状态码和 code（唯一例外是 401，前端拦截器按 401 跳登录，因为此时响应体也可能被网关替换掉）。

### 3.3 错误码分段规范

| 段位 | 归属 | 示例 |
| --- | --- | --- |
| `0` | 成功 | — |
| `1xxxx` | 通用 / 协议 / 认证 / 限流 | 10001 参数校验失败、10004 未登录、10009 请求过于频繁、10010 系统繁忙 |
| `2xxxx` | 用户域 | 20001 用户名已存在、20002 用户名或密码错误、20003 账号被禁用 |
| `3xxxx` | 车次 / 库存域 | 30001 车次不存在、30003 库存不足、30004 秒杀未开始、30005 秒杀已结束 |
| `4xxxx` | 订单域 | 40001 订单不存在、40002 重复下单、40003 订单状态不允许该操作、40005 订单超时未支付 |
| `5xxxx` | 依赖 / 基础设施 | 50001 数据库繁忙、50002 缓存不可用、50003 消息投递失败、50004 第三方支付异常、50005 获取分布式锁失败 |

**分段的理由：** 线上排查时，光看错误码前两位就能把问题路由给对应模块（订单域报错激增 vs 基础设施报错激增，处置动作完全不同）。监控面板可以按段位做聚合告警。

**编码规则：** 5 位数字，前 1 位（或 2 位）为域，后几位为具体错误。段位一旦分配不再复用含义，废弃的错误码标记为"保留"而不是改含义（客户端可能仍在对旧码做分支）。

### 3.4 为什么"所有失败都返回 500"是错的：逐条论证

| # | 后果 | 具体机制 | 在秒杀场景下的放大效应 |
| --- | --- | --- | --- |
| 1 | 语义丢失 | 调用方只能看到"服务器错误"，无法区分"我传错了"和"票没了"和"服务崩了" | 用户看到的是"系统错误"，客服无法自助判断，全部转人工 |
| 2 | 触发无意义重试 | Nginx `proxy_next_upstream`、Spring Cloud LoadBalancer 重试、Feign `Retryer`、前端 axios 重试，默认都会对 5xx 重试 | 库存不足本是**预期内高频事件**，被当成故障重试，流量放大数倍，把一次正常的"售罄"放大成雪崩 |
| 3 | 熔断器误判 | Resilience4j / Sentinel 的熔断统计基于异常比例，5xx 计入失败率 | 秒杀开始瞬间大量"库存不足"5xx → 失败率瞬间超阈值 → **熔断器打开** → 把本来正常的服务熔断，真实用户全部失败。这是最严重的一条 |
| 4 | 告警淹没 | 5xx 是 SLO 黄金指标，监控告警通常直接绑 5xx 率 | "库存不足"导致错误率长期飘红 → 运维对告警脱敏 → 真实故障发生时没人看 |
| 5 | 日志级别失控 | 5xx 通常按 ERROR 记录，且常带完整堆栈 | 一次秒杀产出数百万行 ERROR 日志，磁盘 IO 与日志采集链路被打满 |
| 6 | 无法做精细化限流 | 限流组件按状态码判断是否需要退避 | 429 变成 500 后，客户端不会退避，持续冲击 |
| 7 | 排障成本 | 500 无法携带业务上下文，只能靠翻日志 | 缺少 `traceId` 与业务码，定位一次问题要跨多个系统捞日志 |

**一句话总结：** 500 的含义是"服务端出了它不该出的问题"。把业务规则失败塞进 500，等于把"可预期的业务分支"伪装成"不可预期的故障"，代价是整个可观测性体系与容错机制同时失效。

### 3.5 反面方案对比

| 方案 | 描述 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| 全 200 + 业务码 | HTTP 恒 200，一切靠 `code` | 客户端逻辑单一 | 丢失 HTTP 语义，网关/浏览器/缓存无法按状态码处理；401 无法被前端拦截器统一识别；监控拿不到天然的错误率 | ❌ 不采用 |
| 全语义化 HTTP 状态码 | 业务错误用 4xx/5xx 表达，无业务码 | 纯粹、RESTful | 状态码空间有限（几十个），无法表达"库存不足"与"重复下单"的区别；业务码段位化的可扩展性丧失 | ❌ 不采用 |
| **混合（本设计）** | 协议/认证/限流/系统故障用状态码；业务规则用 200 + 业务码 | 两者优势兼得：网关与监控看状态码，业务看 code | 需要团队统一认知，且必须在文档里写清映射表（即 3.2） | ✅ 采用 |
| GraphQL 风格（HTTP 恒 200 + errors 数组） | 单端点，错误在 body | 前端处理灵活 | 本项目是典型 REST 秒杀场景，引入 GraphQL 只增加复杂度 | ❌ |

### 3.6 实现要点（待实现，实现后回填类名）

- 全局异常处理：`@RestControllerAdvice` 捕获 `BizException`（业务异常，携带错误码）与 `Exception`（兜底 500）。
- **兜底 500 必须脱敏**：只返回 `10999 系统繁忙，请稍后重试` + `traceId`，绝不返回 `exception.getMessage()` 或堆栈（可能泄露表名、SQL、内网 IP）。
- 错误码用枚举定义（如 `ErrorCode`），禁止在业务代码里写裸数字。
- 每个错误码标注**日志级别**：业务码（3xxxx/4xxxx）记 WARN 且不打堆栈；5xxxx 记 ERROR 并打堆栈。这是控制秒杀场景日志量的关键。

## 4. 接口详细设计

### 4.1 POST /api/v1/auth/register — 用户注册

| 项 | 值 |
| --- | --- |
| 是否需要登录 | 否 |
| 幂等 | 由 `username` 唯一索引保证（不要靠"先查再插"，并发下会双写） |
| 高并发关注 | 低。注册不在秒杀链路，不需要特殊优化；但要防刷（同 IP 频率限制） |

**请求参数**

| 参数 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| `username` | string | 是 | `@NotBlank`，长度 4–32，`@Pattern("^[a-zA-Z0-9_]+$")` |
| `password` | string | 是 | `@NotBlank`，长度 8–64；服务端用 BCrypt 加盐哈希后存储 |
| `phone` | string | 否 | `@Pattern("^1[3-9]\\d{9}$")`，中国大陆手机号 |

**响应 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `userId` | long | 新用户 ID |
| `username` | string | 回显 |

**主要错误码：** `10001` 参数校验失败、`20001` 用户名已存在。

**为什么用 BCrypt 而不是 MD5/SHA-256 加盐？** MD5/SHA 是快速哈希，GPU 每秒可尝试数十亿次，加盐只防彩虹表、不防暴力破解。BCrypt 有可调 cost 因子，计算慢，专门用于口令。替代方案 Argon2 更强，但 Java 生态默认支持不如 BCrypt 普遍（`spring-security-crypto` 直接提供）。

**请求参数**

| 参数 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |

### 4.4 GET /api/v1/trains — 车次查询

| 项 | 值 |
| --- | --- |
| 是否需要登录 | 否 |
| 高并发关注 | **高**。秒杀开始前，用户会反复刷新车次列表，是全站 QPS 最高的读接口。主要手段是缓存 + 限流，不是加机器 |

**请求参数（Query）**

| 参数 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| `date` | string | 是 | `yyyy-MM-dd`；不得早于今天，跨度不超过 30 天 |
| `fromStation` | string | 是 | `@NotBlank`，长度 1–32，车站名或三字码 |
| `toStation` | string | 是 | 同上；且必须与 `fromStation` 不同 |
| `pageNum` | int | 否 | 默认 1，`@Min(1)` |
| `pageSize` | int | 否 | 默认 10，`@Min(1) @Max(100)` |

**响应 `data`：** 分页对象 `{ total, pageNum, pageSize, list: [ 车次摘要 ] }`，车次摘要含 `trainNo`、`fromStation`、`toStation`、`departTime`、`arriveTime`、`durationMinutes`、最低价、余票概览。

**高并发注意事项**

| 手段 | 做法 | 为什么 |
| --- | --- | --- |
| 缓存 | 以 `date + from + to + pageNum + pageSize` 为 key 缓存结果，TTL 待定（秒级）。车次时刻表是**准静态数据**，变化极低频 | 把 DB 查询挡在缓存外，这是本接口的主要收益来源 |
| 缓存穿透 | 查询无结果时也缓存空值（短 TTL），或对 key 做布隆过滤器 | 恶意构造大量不存在的站点组合，会全部打到 DB |
| 缓存击穿 | 热点 key（如"北京→上海 明天"）过期瞬间大量并发重建。用逻辑过期或互斥锁（Redis `SETNX` 重建） | 单个热点 key 失效可瞬间产生数千次相同 DB 查询 |
| 缓存雪崩 | 同一批 key 的 TTL 加随机抖动（如基础 TTL ± 随机百分比） | 全量 key 同时失效会把 DB 打挂 |
| 限流 | 网关层按 IP 限流 | 公开只读接口最容易被脚本抓取 |
| 分页 | 深分页（`pageNum` 很大）会变慢，用"上一页最大 ID"的游标分页替代 `LIMIT offset` | `LIMIT 100000, 10` 需要扫描并丢弃 10 万行，DB 开销与偏移量成正比 |

**替代方案对比（余票是否放缓存）：**

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| 余票查 DB，车次信息查缓存 | 余票实时性最好 | 秒杀时余票字段是被争抢的热点行，DB 压力大 |
| **余票也在缓存，DB 为准** | 余票是"近似值"，展示层允许秒级延迟 | ✅ 采用。但要明确：缓存余票只用于**展示**，真正的扣减判定必须走秒杀接口的 Redis 原子扣减 + DB 条件更新，不能信任展示值 |
| 余票完全不做缓存，全走 DB | 简单 | 秒杀场景 DB 撑不住，且没必要——用户看到的余票晚几秒并不可接受 |

### 4.6 GET /api/v1/seckill/activities/{activityId} — 秒杀场次详情

| 项 | 值 |
| --- | --- |
| 是否需要登录 | 否 |
| 高并发关注 | **极高**。这是全场最热的读接口，且必须读 Redis 而不是 DB |

**请求参数：** `activityId`（path，long，`@Min(1)`）。

**响应 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `activityId` | long | 场次 ID |
| `trainNo` | string | 车次 |
| `seatType` | string | 座位类型 |
| `price` | long | 秒杀价（分） |
| `startTime` / `endTime` | string | 场次起止时间 |
| `status` | string | `NOT_STARTED` / `ONGOING` / `ENDED`，由服务端时间判定，**不信任客户端时间** |
| `remaining` | int | 余票快照（来自 Redis），**标注为"仅供参考"** |

**为什么余票必须来自 Redis？** 如果每次刷新都 `SELECT remaining FROM t_stock WHERE activity_id = ?`，在秒杀开场瞬间，这一行会被数千个并发事务反复读取与加锁，直接成为瓶颈。Redis 单线程模型下，`GET` 是原子且无锁竞争的，量级完全不同。

**为什么 `status` 由服务端判定？** 客户端时间可被篡改。若前端用本地时间决定按钮是否可点，攻击者改系统时间即可提前发起请求；真正的拦截必须在服务端（秒杀下单接口里会再次校验时间窗口）。

**请求参数（Query）**

**高并发注意事项**

| 手段 | 做法 | 为什么 |
| --- | --- | --- |
| 缩短轮询链路 | 结果查询**只读 Redis**（下单成功后写入 `seckill:result:{userId}:{activityId}`），不查 DB | 轮询 QPS 通常是下单的 3–10 倍，查 DB 会把异步化的收益吃回去 |

| 轮询退避 | 返回体可带 `retryAfterMillis`（建议的下次轮询间隔），推荐客户端递增退避 | 把节流策略下发给客户端，比硬拒绝体验好 |
| 长轮询 / SSE 替代 | 见下方对比 | — |

**替代方案对比（如何拿到异步结果）：**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 客户端定时轮询 | 实现最简单，无状态，易水平扩展 | 有延迟与无效请求；间隔难调 | ✅ 采用（配服务端节流 + 退避提示） |
| 长轮询（hold 住请求） | 结果就绪即返回，延迟低 | 每个等待用户占一个连接/线程，5000 并发就是 5000 个挂起请求，Tomcat 线程池直接被占满 | ❌ 秒杀场景不可接受 |
| SSE / WebSocket 推送 | 实时性最好 | 需要维护长连接与推送通道，服务端要保存连接状态，复杂度与资源占用都高 | ❌ 本项目无必要 |
| 直接同步返回 | 无轮询 | 同步链路必须包含落库，RT 长、DB 压力大 | ❌ |

### 4.10 GET /api/v1/orders/{orderId} — 订单详情

| 项 | 值 |
| --- | --- |
| 是否需要登录 | 是 |
| 高并发关注 | 低—中。关键是**越权校验**，不是性能 |

**请求参数：** `orderId`（path，long，`@Min(1)`）。

**必须做的校验：** 查出订单后，比对 `order.userId == 当前登录 userId`，不一致返回 `10006`（无权限），而不是 `40001`（订单不存在）。

**为什么用 10006 而不是 40001？** 用"订单不存在"来掩盖越权是常见的做法（避免 ID 枚举）。但本设计中订单 ID 若为自增，攻击者本来就能枚举；因此更倾向于明确返回 403 语义，让日志能记录越权尝试。**这是一个需要在实现时确认的取舍：若订单号改为不可猜测的雪花 ID，则可以安全地返回 40001 来隐藏资源存在性。**

**注意：** 校验只能放在 SQL 条件里做（`WHERE id = ? AND user_id = ?`），不能"先查出来再在 Java 里 if 判断"——虽然结果一样，但前者少一次对象构造，且不会因为后续代码重构而漏掉判断。

### 4.11 POST /api/v1/orders/{orderId}/cancel — 取消订单

| 项 | 值 |
| --- | --- |
| 是否需要登录 | 是 |
| 幂等 | 必须幂等。重复取消返回成功或明确的状态错误码，但**绝不能重复回补库存** |
| 高并发关注 | 中。真正的风险是**库存回补的并发正确性**，不是吞吐 |

**请求参数：** `orderId`（path，long，`@Min(1)`）。

**响应 `data`：** `orderId`、`status`（`CANCELLED`）。

**主要错误码：** `40001` 订单不存在、`40003` 订单状态不允许该操作（如已支付、已出票）、`40004` 订单已取消。

**高并发注意事项**

| 手段 | 做法 | 为什么 |
| --- | --- | --- |
| 状态机约束 | 用"条件更新"实现状态流转：`UPDATE t_order SET status = 2 WHERE id = ? AND user_id = ? AND status IN (0)` | 判断与更新在同一条 SQL 里，天然原子。若先 `SELECT` 判断状态再 `UPDATE`，两个并发取消请求会**都**通过判断，导致库存被回补两次 |
| 校验受影响行数 | `affectedRows == 0` 即表示状态不满足或订单不属于该用户，直接返回失败，不做后续回补 | 这是把乐观锁用在状态机上的标准手法 |
| 回补库存 | 先改订单状态成功，再回补库存（Redis `INCR` + DB `available + 1`）。**顺序不能反** | 若先回补库存再改状态，一旦改状态失败，库存被凭空多补，直接导致超卖 |
| 回补的幂等 | 以订单 ID 为幂等键，回补操作本身也要幂等（例如 Redis 侧用一个 `seckill:restored:{orderId}` 标记） | MQ 消息可能重复投递（at-least-once），消费者必须能承受重复 |
| 消息重试 | 回补走 MQ 异步，失败重试；重试耗尽进死信队列人工介入 | 库存回补丢失会造成少卖（用户退票了但票没放出去），比起超卖是较轻的故障，但同样需要可见性 |

**取消订单的库存回补用同步还是异步？**

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| 同步回补 | 一个事务内改状态 + 改库存 | 简单，但把库存行重新拉回热点争抢区 |
| **异步回补（MQ）** | 改状态成功后发消息，消费者回补 | ✅ 采用。削峰，且回补与取消解耦；代价是回补有延迟（秒级），期间用户看到"票已放出但还买不到"是可接受的 |

### 4.12 POST /api/v1/pay/notify — 支付回调

| 项 | 值 |
| --- | --- |
| 是否需要登录 | 否（由第三方支付平台调用，靠签名验证身份） |
| 幂等 | **必须幂等**。支付平台会重复通知直到收到成功应答 |
| 高并发关注 | 中。回调通常是突发的，且必须快速返回 `success`，否则支付平台会持续重推 |

**请求参数：** 由支付平台定义的报文（含订单号、金额、交易状态、签名）。

**处理流程要点**

1. **验签**：用支付平台公钥验签。验签失败直接拒绝，不采信任何字段 —— 否则任何人都能伪造"支付成功"。
2. **幂等**：以支付平台的交易号 + 本地订单号为幂等键。若订单已是"已支付"，直接返回成功（不要报错，否则平台会无限重推）。
3. **金额校验**：回调金额必须与本订单金额一致，防止"1 分钱支付"篡改。
4. **快速返回**：回调处理只做"改订单状态 + 记录流水"，其余动作（发短信、写统计）走 MQ 异步。**不能**在回调里做重活。

**主要错误码：** 验签失败返回非成功应答（具体格式由支付平台协议决定）、`40005` 订单超时未支付、`50004` 第三方支付异常。

**为什么支付成功不能只依赖前端跳转？** 用户支付完成后跳回商户页面的动作不可靠（关页面、断网、伪造跳转都能触发）。**订单的支付状态只能由服务端收到的、验签通过的回调来变更**，前端跳转只用于触发一次"主动查询订单状态"来改善体验。

| 项 | 值 |
| --- | --- |

| 用途 | 负载均衡探活、压测时确认被测服务状态 |

## 5. 秒杀下单接口完整说明

### 5.1 基本信息

| 项 | 值 |
| --- | --- |
| 方法 | `POST` |
| 路径 | `/api/v1/seckill/orders` |
| 是否需要登录 | **是**（`Authorization: Bearer <token>`） |
| 语义 | 提交一次秒杀请求。成功仅代表"抢到了名额"，不代表已完成下单 |
| 返回时机 | **立即返回**（异步下单），结果通过 `GET /api/v1/seckill/result` 查询 |

### 5.2 请求参数

| 参数 | 类型 | 必填 | 校验规则 | 说明 |
| --- | --- | --- | --- | --- |
| `activityId` | long | 是 | `@NotNull @Min(1)` | 秒杀场次 ID |
| `seatType` | string | 是 | 枚举校验，非法值返回 `10001` | 座位类型 |
| `passengerIds` | array\<long\> | 是 | `@NotEmpty @Size(min=1, max=5)`，元素 `@Min(1)` | 乘车人 ID 列表，本项目简化为固定 1 人（限 1 张，防黄牛） |
| `requestId` | string | 否（建议必传） | 长度 ≤ 64，`@Pattern("^[A-Za-z0-9-]+$")` | 客户端生成的幂等键，用于下单结果未知时重试 |
| `X-Request-Id` | header | 否 | 同上 | 与 body 中 `requestId` 二选一，header 优先 |

**`userId` 不从请求体取。** 从 token 解析。任何"客户端传 userId"的设计都等于把越权漏洞直接开放。

**`requestId` 为什么建议必传？** 详见 5.7 的防重设计。

### 5.3 响应结构

成功受理（注意：这只是"已受理"，不是"下单成功"）：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "QUEUING",
    "requestId": "3f2a9c1e-...",
    "retryAfterMillis": 200
  },
  "traceId": "b7f1c0f2a3d44e1e",
  "timestamp": 1730000000000
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | string | `QUEUING`：已受理，排队中。若同步链路里已经能确定失败，则**不返回 200**，而是直接返回对应业务码 |
| `requestId` | string | 回显，客户端后续查询凭此 |
| `retryAfterMillis` | int | 建议的轮询间隔（毫秒） |

**重要：哪些失败在"同步返回时"就能确定，因而不进队列？**

| 情况 | 返回 | 是否进队列 |
| --- | --- | --- |
| 未登录 / token 无效 | HTTP 401，`10004` | 否 |
| 参数非法 | HTTP 400，`10001` | 否 |
| 被限流 | HTTP 429，`10009` | 否 |
| 秒杀未开始 / 已结束 | HTTP 200，`30004` / `30005` | 否（同步判定，无需占资源） |
| 重复下单（已抢过） | HTTP 200，`40002` | 否 |
| 库存不足 | HTTP 200，`30003` | 否 |
| Redis 中库存未预热 | HTTP 200，`10010`（系统繁忙） | 否 |

也就是说：**只有"预扣减成功"的请求才会进队列**。这一点是整个设计的关键——队列里只承载真正需要落库的请求，量级被 Redis 的原子扣减压到了"库存数量"这一量级，而不是"并发用户数"。

### 5.4 完整调用链路

| 步骤 | 动作 | 关键点 | 失败后果 |
| --- | --- | --- | --- |
| 1 | 网关校验 JWT，解析 `userId` | 网关侧完成，不占用应用线程 | 未登录直接 401 |
| 2 | 网关按 `userId` / IP 限流 | 秒杀开始瞬间的流量削峰第一道 | 超限 429 |
| 3 | 应用层校验场次时间窗口、活动状态 | **服务端时间判定**，不信任客户端 | 30004 / 30005 |
| 4 | 应用层幂等检查（`requestId`） | Redis `SETNX`，短 TTL | 重复请求直接返回上次结果 |
| 5 | **Redis Lua 原子预扣**（判库存 + 判重 + 扣减 + 记录用户） | 全链路最核心的一步，见 5.5 | 库存不足 30003 / 重复 40002 |
| 6 | 预扣成功 → 投递 MQ 消息 | 消息体只含 `userId`、`activityId`、`seatType`、`requestId` | 投递失败需回滚 Redis 预扣，见 5.8 |
| 7 | 立即返回 `QUEUING` | **不等 DB 落库** | — |
| 8 | 消费端异步落库 | 唯一索引兜底 + 条件更新扣 DB 库存 | 落库失败进重试/死信 |
| 9 | 写入结果缓存 + 更新订单状态 | 供 4.8 的结果查询接口读取 | — |
| 10 | 用户轮询结果 → 跳转支付 | 支付超时未付则取消并回补库存 | — |

### 5.5 核心：Redis Lua 脚本

**为什么必须是 Lua，不能分成多条 Redis 命令？**

如果用 `GET` 判断库存 → `DECR` 扣减 → `SADD` 记录用户 这三条命令分开执行，两个并发请求可能都读到 `stock = 1`，然后都执行 `DECR`，结果 `stock = -1`，**超卖**。这是经典的 check-then-act 竞态。

Lua 脚本在 Redis 中是**单线程原子执行**的：脚本执行期间不会有其他命令插入。所以"判断 + 扣减 + 记录"三步要么全做完，要么全不做。

```lua
-- KEYS[1] = seckill:stock:{activityId}:{seatType}   库存
-- KEYS[2] = seckill:users:{activityId}              已抢到的用户集合（去重）
-- ARGV[1] = userId
-- 返回: -1 未预热  0 售罄  1 预扣成功  2 重复下单
local stock = redis.call('GET', KEYS[1])
if stock == nil then return -1 end
if tonumber(stock) <= 0 then return 0 end
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return 2 end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

**逐段解释（面试常问）：**

| 细节 | 为什么 |
| --- | --- |
| `stock == nil` 返回 -1，而不是当成 0 售罄 | 区分"没预热"和"卖光了"。若混淆，缓存故障会伪装成"售罄"，静默地损失全部销量（少卖），且没有任何告警 |
| 用 `tonumber(stock) <= 0` 而不是 `== 0` | 若因历史 bug 出现负数，仍应判定为售罄，防止负数继续被扣 |
| 用 `SISMEMBER`/`SADD` 而不是给每个用户建一个 key | 一个 Set 承载一场活动的所有用户，key 数量可控；比 `SET user:xx:xx 1` 更省内存且天然幂等（`SADD` 重复元素不报错但返回 0，可据此判重） |
| 脚本里不做 `EXPIRE` | 库存 key 的 TTL 由预热的写入方统一设置，脚本里设置会与业务期望的过期策略冲突 |
| 返回值用数字而非字符串 | 减少网络传输与解析开销，调用方 `switch` 处理 |

**替代方案对比（防超卖）：**

| 方案 | 原子性 | 性能 | 问题 | 结论 |
| --- | --- | --- | --- | --- |
| `SELECT ... FOR UPDATE` 悲观锁 | 保证 | 差 | 同一行串行化，秒杀场景直接成为瓶颈；且长事务占连接 | ❌ |
| 乐观锁 `version` 字段 CAS | 保证 | 中 | 高冲突下大量失败重试，重试风暴反而放大 DB 压力 | 作为 DB 最后一道兜底（5.7） |
| `UPDATE ... SET available = available - 1 WHERE available > 0` 条件更新 | 保证 | 中 | 单条 SQL 原子，但仍在 DB 上，挨不住秒杀瞬时并发 | ✅ 作为 DB 层兜底 |
| `DECR` 单命令 | 保证单命令原子 | 好 | 只能扣减，**无法同时判重**，且扣到负数也照扣 | ❌ 不完整 |
| **Redis Lua 脚本** | 保证 | 好 | 脚本内逻辑复杂会阻塞 Redis 单线程（本脚本极短，可接受） | ✅ 主方案 |
| 分布式锁（Redisson） | 保证 | 差 | 加锁/解锁两次网络往返，且锁本身成为热点 | ❌ 用原子命令能解决的，不要用锁 |

### 5.6 为什么异步下单（同步 vs 异步对比）

| 维度 | 同步下单（在请求线程里落库） | 异步下单（Redis 预扣 + MQ + 消费落库） |
| --- | --- | --- |
| 接口 RT | 包含 DB 写入、事务提交，长且不稳定 | 只包含 Redis 操作与一次 MQ 投递，短且稳定 |
| 抗峰值 | 峰值直接打在 DB 上，DB 是最大瓶颈 | 峰值被 Redis 挡住，DB 只承受"库存数量"级的写入 |
| Tomcat 线程占用 | 长事务期间线程被占满，新请求排队 → 超时 → 重试 → 雪崩 | 线程快速释放 |
| 用户体验 | 立即知道结果 | 需要轮询，有短暂"排队中" |
| 一致性 | 强（同事务） | 最终一致，需要处理"Redis 扣了但 DB 没落"的补偿 |
| 复杂度 | 低 | 高（MQ 可靠投递、消费幂等、结果查询、补偿任务） |

**结论与取舍。** 秒杀场景选异步，因为**异步的复杂度是一次性的工程成本，而同步的容量瓶颈是每次大促都要面对的运维灾难**。但必须承认异步引入了两个必须处理的问题，见 5.8。

### 5.7 防重设计（三层，纵深防御）

单靠任何一层都不够，三层各自解决的问题不同：

| 层 | 手段 | 挡住什么 | 挡不住什么 |
| --- | --- | --- | --- |
| 前端 | 点击后置灰按钮、防抖 | 用户的**误操作**重复点击 | 脚本、多设备、抓包重放 |
| 应用 / Redis | `requestId` 幂等键 + Lua 脚本中的用户 Set 判重 | 同一请求的重放、同一用户的并发重复提交 | 缓存数据丢失后的重复（如 Redis 重启、key 被误删） |
| DB | **唯一索引** | 一切重复写入（最后的真相） | 不挡任何流量，只保证数据正确 |

**唯一索引 DDL（必须存在，否则并发下必然出现同一用户多张订单）：**

```sql
CREATE TABLE `t_seckill_order` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id`     BIGINT UNSIGNED NOT NULL,
  `activity_id` BIGINT UNSIGNED NOT NULL,
  `seat_type`   TINYINT UNSIGNED NOT NULL,
  `status`      TINYINT NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已取消 3已关闭',
  `create_time` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_activity_seat` (`user_id`,`activity_id`,`seat_type`),
  KEY `idx_status_create` (`status`,`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**为什么唯一索引是"最后防线"而不能省？** Redis 是有可能丢数据的（重启未持久化、主从切换、运维误删 key）。如果只靠 Redis 判重，一次 Redis 异常就足以让同一用户产生多张订单，而这类数据错误**事后无法自动修复**（你不知道该保留哪一张、该退哪一张）。数据库唯一索引是唯一能在存储层保证"同一用户同一场次只有一张票"的机制。

**`uk_user_activity_seat` 的字段顺序重要吗？** 重要。唯一索引的字段顺序决定了它能否被复用为查询索引。`(user_id, activity_id, seat_type)` 的前缀 `(user_id, ...)` 可以支撑"查某用户的订单"这类查询，这也是 4.9 订单列表能走索引的原因之一。若写成 `(activity_id, user_id, seat_type)`，则只能支撑按活动查询。

**`idx_status_create` 是给谁用的？** 给两个场景：① 定时任务扫描"超时未支付"的订单（`WHERE status = 0 AND create_time < ?`）；② 4.9 的订单列表在部分查询模式下按状态过滤 + 时间排序。

### 5.8 异步引入的两个问题与应对

| 问题 | 场景 | 应对 |
| --- | --- | --- |
| **Redis 扣了，DB 没落** | MQ 投递失败、消费者一直失败 | ① 投递失败立即回滚 Redis（`INCR` 库存 + `SREM` 用户），并返回 `10010`；② 消费侧重试 + 死信队列；③ 定时对账任务，比对 Redis 已扣用户集合与 DB 订单，修复不一致。**注意：对账任务只能修"少卖"，修不了"超卖"**，所以超卖必须靠 DB 条件更新 + 唯一索引在写入时就杜绝 |
| **MQ 消息重复投递** | at-least-once 语义下必然发生 | 消费端幂等：靠 `uk_user_activity_seat` 唯一索引（重复插入抛 `DuplicateKeyException`，捕获后视为已处理成功）+ DB 库存**条件更新**（`WHERE available > 0`，`affectedRows == 0` 即视为售罄并回滚 Redis 预扣） |

**DB 层扣减 SQL：**

```sql
UPDATE t_stock
   SET available = available - 1, version = version + 1
 WHERE activity_id = ? AND seat_type = ? AND available > 0;
```

判定依据是 `affectedRows`：`1` 表示扣减成功，`0` 表示 DB 侧已无库存，此时必须**回滚 Redis 的预扣**（否则 Redis 少卖了票，DB 却没有对应订单，用户排队后拿到失败结果）。

### 5.9 状态机

`t_seckill_order.status` 的允许流转（**所有流转必须用条件更新实现，不允许"先查后改"**）：

| 当前状态 | 允许流转到 | 触发动作 | 条件更新 SQL 的 WHERE 片段 |
| --- | --- | --- | --- |
| 0 待支付 | 1 已支付 | 支付回调（验签通过、金额一致） | `WHERE id = ? AND status = 0` |
| 0 待支付 | 2 已取消 | 用户主动取消 | `WHERE id = ? AND user_id = ? AND status = 0` |
| 0 待支付 | 3 已关闭 | 定时任务扫描超时未支付 | `WHERE id = ? AND status = 0 AND create_time < ?` |
| 1 已支付 | —（终态，退款走独立流程） | — | — |
| 2 已取消 | —（终态） | — | — |
| 3 已关闭 | —（终态） | — | — |

**为什么用状态机而不是几个布尔字段（`is_paid`、`is_cancelled`）？** 布尔字段可以组合出非法状态（`is_paid = true` 且 `is_cancelled = true`），且并发修改时无法用一条 SQL 约束。单一 `status` 字段 + 条件更新，把"状态校验"变成了原子操作，从根上消灭了非法状态。

### 5.10 秒杀下单接口的高并发注意事项汇总

| 维度 | 手段 | 为什么 / 不这么做会怎样 |
| --- | --- | --- |
| **限流** | 网关按 `userId` + IP 限流；应用层对同一 `userId` 的提交频率限流 | 秒杀接口是最容易被脚本刷的入口。没有限流，一个脚本就能占满全部库存名额（黄牛）与全部应用线程（DoS） |
| **缓存** | 库存全部走 Redis，DB 只做最终落库；结果查询也走 Redis | 见 4.6 / 4.8 |
| **防重** | 三层：前端置灰 / Redis 判重 + requestId / DB 唯一索引 | 见 5.7 |
| **削峰** | MQ 异步落库 | 见 5.6 |
| **快速失败** | 未开始/已结束/售罄/重复，都在**不触碰 DB** 的前提下直接返回 | 让无效请求的代价降到最低，把资源留给有效请求 |
| **超时控制** | Redis 操作、MQ 投递都设超时；不让任何下游拖住接口线程 | 一个慢依赖会通过线程池耗尽放大成全站不可用 |
| **降级** | Redis 不可用时**直接拒绝**该接口（返回 `10010`），而不是退化成查 DB | 退化成查 DB 会让瞬时的 Redis 故障升级为 DB 被打挂，故障面扩大。秒杀接口的正确降级是"少卖"而不是"拖垮全站" |
| **不返回敏感信息** | 响应里不含其他用户信息、不含内部库存总数 | 库存总数泄露会被黄牛用来判断"还剩多少可以抢" |
| **日志** | 售罄/重复这类高频业务失败记 WARN 且不打堆栈；只有真正的系统异常记 ERROR | 见 3.4 第 5 条 |
| **可观测** | 每个请求带 `traceId`，关键节点（限流、预扣、投递、消费）打点 | 异步链路的排障必须靠 traceId 串联，否则无法回答"用户到底卡在哪一步" |
