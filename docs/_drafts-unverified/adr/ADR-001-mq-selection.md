# ADR-001 消息中间件选型：RabbitMQ / RocketMQ / Kafka

## 状态

已接受

## 背景

### 项目与技术栈

本项目是铁路购票秒杀的教学项目，用于把"高并发扣库存"这件事从头讲清楚。当前工程事实（以仓库为准）：

- 构建：Maven，`spring-boot-starter-parent` 3.5.9，Java 17（见 `pom.xml`）。
- 当前 `pom.xml` 里只有 `spring-boot-starter` 和 `spring-boot-starter-test`，**尚未引入任何 MQ 依赖**，也就是说这份 ADR 是在"动手之前"做的选型决策。
- 开发环境：Windows 10 单机，无 Linux 服务器、无集群、无真实流量。

### 关于事实来源的说明

本 ADR 中"调研结果"的部分结论来自平台公开文档与社区共识。需要说明的是，仓库内 `docs/architecture/design-spec.json` 当前内容为 `null`（空），调研的原始文档并未随仓库提供。因此本 ADR 遵守一条硬规则：**凡是需要实测或需要核对具体版本文档才能确认的项，一律标注"待验证"或"待压测"，不写具体数字、不写版本号、不写未经核对的 API 细节。** 读者若要落地，请以所装版本的官方文档为准补齐这些标注项。

### 业务对 MQ 的三类硬需求

这个项目不是"为了用 MQ 而用 MQ"，需求是从秒杀链路里长出来的：

1. **削峰填谷（异步落库）**
   秒杀的本质是瞬时脉冲：开抢后几秒内的请求量可能是平时的成百上千倍。如果每个请求都同步写 MySQL，数据库会被打穿。做法是先用 Redis 原子扣减挡住绝大部分请求，扣减成功的请求以消息形式投递给 MQ，由消费者按数据库能承受的速率慢慢落库。这里 MQ 承担的是"缓冲队列"的角色。

2. **延时消息（订单超时未支付，自动取消并释放库存）**
   用户抢到票后需要在限定时间内完成支付，否则订单取消、库存归还。这是一个"到点触发"的需求。它有两种实现路径：MQ 原生延时能力，或者用定时任务扫表。这个需求的实现方式直接决定了我们需要 MQ 具备什么能力。

3. **可靠投递 + 消费幂等**
   消息丢失 = 少卖一张票（用户看到"抢到了"但库里没订单）；消息重复 = 可能超卖（同一张票被扣两次库存）。所以 MQ 必须能配合我们做到"至少投递一次 + 消费端幂等"，或者"恰好一次"。

### 可选需求（非必须）

- **事务消息**：解决"本地数据库事务"与"发送消息"的原子性问题。注意，即使 MQ 不提供这个能力，我们也可以用**本地消息表**自己实现，只是代码多写一点。
- **顺序消息**：同一车次的库存变更严格按顺序处理。当前业务模型（Redis 原子扣减 + 按订单维度落库）对全局顺序没有强依赖，属于"锦上添花"。

### 调研结论：三个关键维度上的事实差异

#### 延时消息

| 中间件 | 延时消息支持情况 |
| --- | --- |
| RocketMQ | 原生支持延时消息。默认提供一组**固定的延迟级别**（不是任意时刻，具体级别集合随版本不同，待以官方文档核对）；较新的版本支持自定义延时时间（具体上限待验证） |
| RabbitMQ | 本身**不支持**延时投递。两种做法：① TTL（消息过期时间）+ 死信队列（DLX）组合出延时效果，纯原生能力；② 安装 `rabbitmq_delayed_message_exchange` 插件，由插件提供延时 Exchange |
| Kafka | **无原生延时消息**。要自己实现时间轮、或者用外部调度表 + 定时扫描 |

这里有一个必须提前知道的坑：**TTL + DLX 的延时精度受队头阻塞影响**。RabbitMQ 的队列是先进先出的，队列级 TTL 只在消息到达队头时才会被判断过期。如果队头有一条 TTL 很长的消息，后面的短 TTL 消息即使已经过期，也要排队头那条消息处理完才能进入死信队列，延时因此变得不准。规避方式是为不同延时级别建不同的队列（每级一个队列，队列内 TTL 一致），代价是队列数量增加。具体误差量级待压测。

#### 事务消息

| 中间件 | 事务消息支持情况 |
| --- | --- |
| RocketMQ | 原生提供事务消息：先发"半消息"（对消费者不可见）→ 执行本地事务 → 根据结果 commit 或 rollback → 若 broker 长时间没收到确认，会**回查**生产者本地事务状态。这是"本地事务与发消息最终一致"的官方解法 |
| RabbitMQ | **没有**事务消息语义。`publisher confirm` 只能保证消息到达 broker（且是异步确认），无法与本地数据库事务原子绑定。要保证一致性必须自己写本地消息表 + 定时补偿 |
| Kafka | 有事务 API，但它面向的是**流处理的 Exactly-Once 语义**（消费-处理-生产 在一个事务里），不是"本地数据库事务 + 发消息"那套业务语义，直接拿来用解决不了本项目的问题 |

#### 部署复杂度与 Windows 可行性

这是**当前环境下权重最高的一维**，因为开发机是 Windows 10 单机。

| 中间件 | 运行依赖 | 组件数量 | Windows 可行性 |
| --- | --- | --- | --- |
| RabbitMQ | 需要 Erlang/OTP 运行时 | 单节点即一个 broker 进程 | 官方提供 Windows 安装包（会一并处理 Erlang 依赖）。装完即可用管理台查看队列。**待验证**：本机实际安装步骤与端口占用情况 |
| RocketMQ | JVM | NameServer + Broker（较新版本还有 Proxy 组件） | 启动脚本 `mqnamesrv` / `mqbroker` 是 shell 脚本，Windows 下需要手工改造或改用第三方脚本；官方部署文档以 Linux 为主，社区普遍推荐 Linux 部署。**待验证**：Windows 下是否能按预期跑起来 |
| Kafka | JVM | 较新版本用 KRaft 模式（Broker + Controller 角色），旧版本还需要 ZooKeeper | 发行包内提供 `.bat` 启动脚本，KRaft 单机可以跑起来。**待验证**：本机 JDK 版本与脚本兼容性 |

补充一个定性排序（本机**未压测**，仅作为量级参考，不要当结论用）：吞吐能力 Kafka > RocketMQ > RabbitMQ。本项目是教学项目，无真实流量，消息量级远低于任何一款 MQ 的瓶颈，所以这一维在当前阶段不构成选择依据。

### 消息模型差异（会影响代码写法）

- RabbitMQ：AMQP 协议，由 broker **推送（push）**给消费者，靠 Exchange + RoutingKey + Queue 做路由，路由能力灵活。
- RocketMQ / Kafka：**拉取（pull）**模型，Topic 下分多个队列/分区，消费者自己拉并维护位点（offset）。

推送模型对消费者有流控压力（需要 `prefetch` 限制未确认消息数），拉取模型天然由消费者控制节奏。这个差异在"消费者处理慢、需要精细控制速率"的落库场景下会体现出来，但对本项目的规模而言两者都能胜任。

## 决策

**选 RabbitMQ 作为当前阶段的默认消息中间件。**

配套的三个具体做法：

1. **延时需求**：优先用 TTL + 死信队列实现；为避免队头阻塞，按延时级别拆分队列。若精度仍不满足（例如要求精确到秒的任意时刻触发），再评估安装延迟插件。
2. **一致性需求**：**不依赖 MQ 的事务能力**。采用"本地消息表 + 定时补偿"自己实现最终一致：业务操作与"待发送消息"写进同一个本地事务，再由后台任务扫描并投递。
3. **可靠性需求**：生产者侧开启 `publisher confirm`，消费者侧改手动 ack，消费端用数据库唯一索引做幂等兜底。

**RocketMQ 列为条件反转的升级目标**，反转条件见下文"什么条件下这个决策会失效"。

## 备选方案对比表

| 维度 | RabbitMQ | RocketMQ | Kafka |
| --- | --- | --- | --- |
| 延时消息 | 不支持，需 TTL+DLX（精度受队头阻塞影响）或延迟插件 | 原生支持；默认固定延迟级别，新版本支持自定义延时 | 无原生支持，需自研时间轮或外部调度 |
| 事务消息 | 无，需自研本地消息表 + 定时补偿 | 原生支持（半消息 + 回查） | 有事务 API，但面向流处理 EOS，不匹配本地事务场景 |
| 顺序消息 | 单队列内天然有序，跨队列不保证 | 队列级顺序，支持得较成熟 | 分区内有序 |
| 消息模型 | broker 推送（push），Exchange 路由灵活 | 拉取（pull），Topic + 队列 | 拉取（pull），Topic + 分区，可回溯 |
| 消息回溯/重放 | 不支持（消费即删） | 支持（按位点回退，取决于存储策略） | 支持，能力最强 |
| Windows 本机部署 | 官方安装包，组件最少，最容易跑起来 | 部署文档以 Linux 为主，Windows 需额外改造（待验证） | 有 `.bat` 脚本，KRaft 单机可跑（待验证） |
| 运行依赖 | Erlang/OTP | JVM | JVM |
| 组件数量 | 1（broker） | 2~3（NameServer + Broker [+ Proxy]） | 1~2（KRaft 单机；旧模式需 ZooKeeper） |
| Spring Boot 集成 | `spring-boot-starter-amqp`，配置量小 | `rocketmq-spring-boot-starter` | `spring-kafka` |
| 吞吐量量级（定性，未压测） | 三者中最低 | 中 | 最高 |
| 可靠性机制 | publisher confirm + 手动 ack + 持久化队列 | 同步刷盘/异步刷盘、主从同步、事务消息 | 多副本 ISR、acks 配置 |
| 运维与排错成本 | 低（管理台直观，队列/连接/积压一眼可见） | 中高（组件多，脚本/配置多） | 中高（分区/副本/位点概念多） |
| 学习曲线 | 平缓，AMQP 概念少 | 中等 | 较陡 |
| 与本项目匹配度 | **高（当前环境下最优）** | 功能匹配度最高，但部署成本最重 | 功能过剩，延时需自研 |

## 决策理由

**1. 当前唯一确定的运行环境是 Windows 10 单机，部署成本直接决定项目能不能跑起来。**

这是最实际的理由。选型不是选"最强的"，是选"这个环境下能稳定跑起来、且我能把每一层讲清楚的"。RabbitMQ 官方提供 Windows 安装包，装完是一个 broker 进程，管理台能直接看到队列积压、消费者数、连接数——对教学项目来说，**可观测性本身就是教学价值**。RocketMQ 功能上最贴合，但把时间花在 Windows 上折腾启动脚本，收益是负的。

**2. 本项目的三个硬需求都不依赖 MQ 的高级特性，所以三款 MQ 在最终代码结构上几乎一样。**

- 延时 → TTL+DLX 可以做到；
- 可靠 → publisher confirm + 手动 ack 可以做到；
- 幂等 → **这个跟 MQ 无关**，是消费端用数据库唯一索引保证的。

换句话说，换 MQ 并不会让这三件事的代码结构发生本质变化，那么选择就应该由"部署成本"这一维来决定，而不是由功能列表决定。

**3. 事务消息不是刚需，而且自研的本地消息表面试价值更高。**

RocketMQ 的事务消息确实优雅，但它解决的是"本地事务 + 发消息"的原子性。本项目用**本地消息表**能达到同样的最终一致效果，且少了与特定 MQ API 的耦合（未来换 MQ 时这一层不用重写）。更重要的是：面试时，"你来说说怎么保证本地事务和消息的最终一致"，讲清楚本地消息表 + 定时补偿 + 幂等消费，比"我用了 RocketMQ 事务消息"更能体现理解深度——后者容易变成背 API。

**4. 不选 Kafka。**

Kafka 强在日志型、高吞吐、可回溯重放的流数据场景。本项目的消息是**低频业务指令**（下单、释放库存），量级小、不需要回溯、延时消息还要自研。这是典型的"用重型武器打小仗"。Kafka 的优势（分区并行、海量吞吐、消息重放）在这个项目里一个都用不上，而它的成本（概念多、延时缺失）却要实打实支付。

**5. 不选 RocketMQ 的核心原因只有一个词：部署。**

必须承认，**在功能维度上 RocketMQ 是三者中最贴合本项目的**：原生延时消息 + 原生事务消息，正好命中前两个硬需求。如果部署条件相同，这份 ADR 的结论可能会反过来。放弃它纯粹是环境权衡，不是技术判断——所以我在下一节把反转条件写得很明确。

## 代价与已知缺陷

1. **没有事务消息，必须自研本地消息表。**
   需要额外一张消息表、一个定时扫描补偿的任务、以及消费端幂等逻辑。这部分代码量不小，而且**本身就是 bug 高发区**（补偿任务重复投递、扫描漏记录、状态更新丢失）。这是选择 RabbitMQ 最主要的功能性代价。

2. **延时消息精度不可靠，且有队头阻塞这个经典坑。**
   TTL + DLX 的精度取决于队列结构和队头消息的过期时间。规避方式是"一级延时一个队列"，但这会让队列数量随延时级别线性增长。如果业务需要"任意时刻精确触发"，这套方案就不成立（见反转条件 1）。实际误差量级**待压测**。

3. **吞吐量三者中最低，压测时可能最先撞墙。**
   当前无真实流量，够用。但做压测实验时，RabbitMQ 很可能成为第一个瓶颈点。具体阈值**待压测**。

4. **消息积压时 RabbitMQ 的性能退化比较明显。**
   积压会加大内存/磁盘压力，极端情况下可能拖慢甚至拖垮 broker。必须设置队列长度上限 + 溢出到死信的兜底策略，否则"削峰"的缓冲层本身会变成故障点。

5. **消息默认消费即删，无法回溯重放。**
   如果将来需要"重放历史消息重新计算库存"（比如对账），RabbitMQ 做不到。这也是反转条件 4 的一部分。

6. **与 MQ API 的耦合点未来需要抽象。**
   如果后续切换到 RocketMQ，"延时消息""可靠投递"这两块代码要重写。降低代价的办法是在业务代码与 MQ 之间加一层薄封装（一个 `MessageProducer` 接口），把 MQ 特定的调用收敛到一处。

## 什么条件下这个决策会失效

以下任一条件成立，本文的推荐就会反转。写清楚是为了让未来的人知道"什么时候该推翻这份 ADR"，而不是把它当永久真理。

1. **需要精确到秒的任意延时触发。**
   例如"开抢前 3 秒给预约用户推送提醒"——TTL+DLX 的队列级延时和固定级别延时都给不了这个精度。此时应转向 RocketMQ 原生延时（若其自定义延时能力满足）或自研时间轮。

2. **有了 Linux 部署环境（服务器 / 云主机 / Docker Compose），且部署成本不再是主要矛盾。**
   这是最可能发生的反转。一旦部署不再是问题，RocketMQ 的功能优势（原生事务消息、原生延时、顺序消息、更高吞吐）开始全面占优，"用本地消息表补一致性"这套额外的复杂度就没有必要承担了。**判断信号：项目从"本机学习"进入"要部署给别人看/要上云"的阶段。**

3. **需要严格的顺序消息。**
   例如要求同一车次的库存变更严格按产生顺序处理。RocketMQ 在此场景的成熟度更高。

4. **消息量级增长到 RabbitMQ 单节点扛不住，或需要消息回溯重放。**
   具体阈值待压测，不预设数字。需要"重放历史消息重新对账"是一个明确信号——RabbitMQ 消费即删，做不到。

5. **团队/个人已有 Kafka 或 RocketMQ 的运维经验。**
   熟悉度会直接反转选择。运维一个自己不熟的中间件，出故障时的恢复时间是不可控的，这个成本往往超过功能差异。

6. **需要跨机房/多副本强可靠。**
   教学项目的 RabbitMQ 是单节点，没有镜像队列/仲裁队列配置，broker 挂了消息就没了。生产级可靠性要求出现时，选型需要整套重新评估。

## 面试追问与标准答法

**Q1：为什么不用 Kafka？**

答：Kafka 的定位是日志型、高吞吐、可回溯的流数据平台，它的优势是分区并行和海量吞吐。本项目的消息是低频业务指令（下单、释放库存），量级小、不需要回溯重放，而且**Kafka 没有原生延时消息**——订单超时取消这个需求要自研时间轮或外部调度表，等于把 MQ 该给我的能力自己再实现一遍。用它的成本（概念多、组件多、延时缺失）我一个都躲不掉，而它的优势我一个都用不上。这不是说 Kafka 不好，是场景不匹配。

**Q2：RabbitMQ 怎么实现延时消息？两种方式有什么区别？**

答：方式一是 TTL + 死信队列。消息设置过期时间，队列设置死信 Exchange，消息过期后自动被投递到死信队列，消费者监听死信队列就实现了"延时消费"。这里有个坑：**队列级 TTL 是队头判断**，队列是 FIFO 的，队头消息没过期，后面的消息即使过期了也要等，所以延时不准。规避办法是按延时级别拆队列，每个队列内 TTL 一致，这样队头就是最早的那条。方式二是装 `rabbitmq_delayed_message_exchange` 插件，由插件提供延时 Exchange，精度更高，但引入了第三方插件依赖。我选方式一，因为不引入额外组件，且"超时未支付"这种业务对误差不敏感。

**Q3：RocketMQ 的事务消息原理是什么？**

答：三步。第一步，生产者发一条"半消息"到 broker，这条消息对消费者不可见；第二步，broker 确认收到半消息后，生产者执行本地事务，然后根据结果向 broker 发送 commit 或 rollback；第三步，如果 broker 长时间没收到 commit/rollback（比如生产者挂了），broker 会**回查**生产者的本地事务状态，由生产者查询本地事务表返回结果。这样就保证了"本地事务成功"和"消息可被消费"最终一致。我没有选它，是因为用本地消息表能达到同样效果，而且不绑定具体 MQ 的 API。

**Q4：消息丢了怎么办？**

答：分三段防。生产端：开启 publisher confirm，确保消息真的到了 broker，没到就重发；同时用本地消息表把"要发的消息"和业务操作放在同一个本地事务里，即使发送失败，后台补偿任务也会重发。Broker 端：队列持久化 + 消息持久化。消费端：改手动 ack，处理成功才确认，失败就 nack 或让消息重新入队；但手动 ack 意味着重复投递的概率上升，所以消费端必须幂等。**注意"至少一次"是工程上更现实的选择，靠幂等把重复消化掉，而不是追求"恰好一次"。**

**Q5：怎么保证消息不重复消费？**

答：幂等做在消费端，不指望 MQ。本项目的做法是数据库唯一索引：订单表的 `(user_id, train_id, travel_date)` 建唯一索引，重复消费时插入直接撞唯一键，捕获异常后当作"已处理成功"直接 ack。更通用的做法是一张去重表（消息 ID 做唯一索引），或者用 Redis 的 `SETNX` 记录已处理的消息 ID。**关键认知是：幂等是消费端的责任，MQ 只能保证"至少一次"。**

**Q6：消息积压了怎么处理？**

答：先定位原因：是消费者挂了、消费逻辑变慢（比如慢 SQL）、还是生产速度突增。处理手段：增加消费者实例（RabbitMQ 同一队列多消费者可并行）、优化消费逻辑（批量处理、去掉不必要的远程调用）、临时扩容消费者并配合丢弃非核心消息。**治理层面**：设置队列最大长度 + 溢出到死信的策略，宁可丢非核心消息也不能让 broker 被拖死；同时做积压告警。"削峰"的缓冲层如果自己被压垮，整个链路就断了。

**Q7：`publisher confirm` 和消费者 ack 有什么区别？**

答：方向不同。`publisher confirm` 是**生产者到 broker** 的确认，broker 收到消息后异步告诉生产者"我收到了"，用来解决生产者发出的消息丢失。消费者 ack 是**broker 到消费者**的确认，消费者处理完后告诉 broker"我处理完了，可以删了"，用来解决消费者拿到消息后处理失败的问题。两者是两段独立的可靠性保障，缺一段就有丢消息的口子。

**Q8：为什么不直接用数据库表当队列（定时轮询）？**

答：小规模下可行，而且省一个组件。问题在于：轮询有延迟（取决于轮询间隔）、高频轮询给数据库增加无谓压力、并发消费要额外加锁防重复处理、清理历史数据也要额外做。MQ 把这些都做完了（推送/长轮询、并发消费、位点管理、死信处理）。**我的判断标准是：如果消息量小、实时性要求低，数据库表当队列是合理的极简方案；一旦有削峰和延时需求，就该上专业组件。**
