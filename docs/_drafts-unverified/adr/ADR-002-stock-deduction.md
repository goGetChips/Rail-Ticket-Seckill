# ADR-002 库存扣减方案：直接操作 MySQL / 乐观锁 / 悲观锁 / Redis + Lua 预扣 + MQ 异步落库

## 状态

待用户拍板

> 说明：这是全项目最重要的一个决策，它决定了系统的整体形态（引入几个组件、一致性等级、后续所有代码的写法）。因此本文不停留在"我推荐什么"，而是把四种方案的取舍完整摊开，由用户确认后再冻结。文中的推荐项可以作为讨论基线。

## 背景

### 要解决的问题

秒杀场景的核心矛盾只有一句话：**大量并发请求同时争抢同一行库存数据**。所有技术方案都是围绕这个矛盾在做取舍。

如果处理不当，会出现四种典型故障：

| 故障 | 表现 | 后果 |
| --- | --- | --- |
| 超卖 | 卖出的票数 > 库存数 | 最严重。用户付款后无票可出，属于资损事故 |
| 少卖 | 卖出的票数 < 库存数 | 库存浪费，商业损失 |
| 丢单 | 用户看到"抢到了"，但库里没有订单 | 用户投诉，且难以对账 |
| 打穿数据库 | 请求全部压到 MySQL，连接池耗尽 | 不只是秒杀接口挂，是整个应用挂（故障放大） |

### 库存模型

库存记录以 `(车次, 座位类型, 乘车日期)` 为维度，一条记录对应一个可售库存数。本方案**不涉及选座**（选座会把一条库存记录拆成座位级，模型完全不同，属于另一个量级的复杂度）。

### 目标与优先级

这四个目标在秒杀场景下**不可能同时最优**，必须排出优先级，否则方案选不出来：

1. **不超卖**——绝对优先级。这是资损红线，任何方案都不能在这条上妥协。
2. **不丢单、不少卖**——强优先级。用户看到"抢到了"，最终就必须真的有票；库存也不能因为故障被永久锁死。
3. **接口响应时间与吞吐**——秒杀的用户体验和系统承载能力。
4. **实现成本可控**——这是教学项目，每一行代码都要能讲清楚原理。

### 一致性等级：允许最终一致

这是本决策的前提，必须先说清楚，否则后面所有取舍都无法理解。

**本项目接受"最终一致"**：允许用户下单成功后，数据库落库存在数秒级的延迟。但有一条不可让步的约束：**用户看到的"成功"必须最终一定能兑现**——不能出现"提示抢到了，最后却没有订单"。也就是说，允许"中间态存在"，不允许"结果丢失"。

如果业务要求强一致（任何时刻 Redis 与 MySQL 的库存都必须一致、余票必须实时准确），那么本 ADR 的方案 D 直接不成立，必须回到同步落库并接受吞吐下降。这个边界写在"什么条件下这个决策会失效"里。

### 环境约束

- MySQL 单机，无集群、无分库分表。
- Redis 单机（具体部署形态待定）。
- 消息中间件待定，见 [ADR-001](./ADR-001-mq-selection.md)。
- Windows 开发机，无真实流量，所有吞吐结论**待压测**。

## 决策

**采用方案 D：Redis + Lua 预扣 + MQ 异步落库，并以 MySQL 的条件更新作为最后一道防线。**

核心设计原则三条：

1. **把流量挡在数据库之前。** Redis 承担"准入裁决"，绝大多数无效请求（库存不足、重复下单）在 Redis 层就被挡掉，根本走不到 MySQL。
2. **MySQL 是账本，Redis 是漏斗。** 权威数据以 MySQL 为准，Redis 是可重建的前置缓冲。
3. **幂等贯穿全链路。** 每个写操作都必须能重复执行而不产生副作用——这是所有重试和补偿机制的前提，也是本方案最容易出错的地方。

完整流程（七个环节）：

```
① 请求进入 → 限流 + 参数校验
② 幂等预检（可选，最终幂等靠第 ⑤ 步的唯一索引兜底）
③ Redis Lua 脚本原子执行：查库存 → 判断 → 扣减 → 记录用户占位
④ 脚本返回成功 → 发送 MQ 消息（下单事件，携带 requestId / 订单号）
   └─ 发送失败 → 同步返还 Redis 库存 → 返回用户失败
⑤ 消费端：创建订单（唯一索引幂等） + 扣减 MySQL 库存（同一个本地事务）
   └─ 失败 → 有限次重试 → 仍失败则进入失败表 → 返还 Redis 库存 + 告警
⑥ 超时未支付 → 延时消息触发 → 取消订单（状态机） → 返还 MySQL + Redis 库存
⑦ 定时对账 job：比对 Redis 与 MySQL 库存差异 → 以 MySQL 为准修复 + 告警
```

### Redis Lua 脚本（核心，必须原子）

为什么必须用 Lua：如果将"判断库存"和"扣减库存"拆成两条 Redis 命令，两条命令之间会有时间窗口，并发下会出现"都判断为有库存、然后都执行扣减"的情况，也就是超卖。Redis 执行 Lua 脚本期间不会插入其他命令，判断与扣减在同一个原子操作内完成。

```lua
-- KEYS[1] = 库存 key        KEYS[2] = 已购用户集合 key
-- ARGV[1] = userId          ARGV[2] = 扣减数量
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2                                  -- 重复下单
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
    return -3                                  -- 库存未预热
end
if stock < tonumber(ARGV[2]) then
    return -1                                  -- 库存不足
end
redis.call('DECRBY', KEYS[1], ARGV[2])
redis.call('SADD', KEYS[2], ARGV[1])           -- 占位，实现一人一单
return stock - tonumber(ARGV[2])
```

**返回码约定**（必须有明确定义，否则调用方无法区分失败原因）：

| 返回值 | 含义 | 上层处理 |
| --- | --- | --- |
| `>= 0` | 扣减成功，值为剩余库存 | 发送 MQ 消息 |
| `-1` | 库存不足 | 直接返回"已售罄"，不落库 |
| `-2` | 重复下单 | 返回"您已抢过该车次" |
| `-3` | 库存未预热 | 属于系统故障，告警 + 降级拒绝 |

注意：`SISMEMBER` 与 `SADD` 放在同一个脚本里，是为了让"判断是否重复"和"记录占位"也保持原子——否则同一个用户的两个并发请求可能都能通过重复检查。

### 数据库唯一索引（幂等的最后防线）

```sql
-- 一人一单：同一用户对同一车次同一乘车日期，只能存在一条订单
ALTER TABLE t_order
  ADD UNIQUE KEY uk_user_train_date (user_id, train_id, travel_date);
```

消费端插入订单时，如果撞上这个唯一索引，说明是重复消费（或用户重复提交），**捕获该异常后直接返回成功并 ack**，不做任何补偿——因为订单已经存在，业务语义上这次消费是"已完成"。

**重要口径说明**：本方案假设"一人一单一张"。如果业务允许一个用户买多张，唯一索引需要调整（例如加入座位序号，或改用"去重表 + 请求 ID"的方案），否则会把合法的第二张票误判为重复。这个口径必须先确认。

### 状态机

库存和订单都有状态流转，**所有状态变更都必须用条件更新**（`WHERE status = '旧状态'`）来保证只有合法流转能生效，这也是返还/取消操作幂等的实现方式。

**订单状态机：**

| 当前状态 | 可流转到 | 触发条件 |
| --- | --- | --- |
| 待支付 | 已支付 | 用户完成支付 |
| 待支付 | 已取消 | 超时未支付（延时消息）或用户主动取消 |
| 已支付 | ——（终态） | 不可逆，不可再取消 |
| 已取消 | ——（终态） | 不可逆，库存已返还 |

**库存扣减状态机：**

| 当前状态 | 可流转到 | 触发条件 |
| --- | --- | --- |
| Redis 预扣成功 | 落库确认 | 消费端在 MySQL 扣减成功 |
| Redis 预扣成功 | 已回滚 | 发消息失败 / 落库彻底失败 / 超时未支付 |
| 落库确认 | 已支付（终态） | 支付成功，库存不再返还 |

**取消订单的幂等写法**（关键）：

```sql
UPDATE t_order SET status = '已取消'
WHERE order_no = ? AND status = '待支付';
```

只有影响行数为 1 时才执行库存返还。这样即使延时消息重复投递（或用户取消与超时取消并发），库存也只会返还一次。**如果这里不做条件更新，重复返还就是超卖。**

## 备选方案对比表

| 维度 | A. 直接操作 MySQL | B. MySQL 乐观锁 | C. MySQL 悲观锁 FOR UPDATE | D. Redis + Lua + MQ（选定） |
| --- | --- | --- | --- | --- |
| 核心写法 | 先 SELECT 判断，再 UPDATE | `UPDATE ... WHERE version = ?` 或 `WHERE stock >= 1` | `SELECT ... FOR UPDATE` 包在事务里 | Redis Lua 原子预扣 + MQ 异步落库 |
| 超卖风险 | **有**（check-then-act 非原子，丢失更新） | 无（条件更新是原子的） | 无 | 无（Lua 原子 + DB 条件更新兜底） |
| 单机吞吐量级 | 低（且结果错误） | 低（重试放大后更低） | 低（单行锁串行化） | 高（大部分请求在 Redis 完成）——具体量级待压测 |
| 一致性强度 | 无保证 | 强一致 | 强一致 | 最终一致（秒级窗口，待压测） |
| 热点行争抢 | 无锁但结果错 | 有，且冲突时大量失败重试 | 有，行锁串行排队 | 转移到 Redis 单线程原子操作 |
| DB 连接占用 | 短 | 短 | **长**（整个事务期间持有） | 短（消费者按自己的速率落库） |
| 锁等待 / 超时 | 无 | 无（直接失败） | 有，`innodb_lock_wait_timeout` 超时报错 | 无 |
| 失败时的用户体验 | 超卖后才发现 | 高失败率，抢不到就是直接失败 | 排队，超时后报错 | Redis 层立即裁决，失败原因明确 |
| 实现成本 | 极低 | 低 | 低 | **高**（Redis 脚本 + MQ + 补偿 + 对账） |
| 依赖组件 | MySQL | MySQL | MySQL | MySQL + Redis + MQ |
| 宕机数据风险 | —— | —— | —— | Redis 宕机需降级；消息丢失需本地消息表兜底 |
| 多实例水平扩展 | 扩展无用（瓶颈在 DB） | 扩展无用 | **扩展反而更糟**（抢锁的实例更多） | 可扩展（消费者可加实例） |
| 面试价值 | 低（是反面教材） | 中（能讲清适用边界） | 中（能讲清为什么不选） | **高**（覆盖缓存、原子性、异步、幂等、最终一致） |
| 结论 | 排除 | 仅在低冲突场景可用 | 排除（场景错配） | **采用** |

## 决策理由

### 为什么不用 MySQL 悲观锁（SELECT ... FOR UPDATE）

这是被问得最多、也最容易答浅的一题。悲观锁**不是错的**，它是**用错了场景**。具体有六条理由：

1. **吞吐上限被单行锁锁死。**
   秒杀的全部请求竞争同一条库存记录。`FOR UPDATE` 把它们排成一个串行队列：第一个事务不提交，后面所有事务全部阻塞。整个系统的吞吐上限 = 单个事务的处理速率，加机器、加 CPU 都无济于事。**这就是瓶颈的物理位置：不在硬件，在那一把行锁。**

2. **锁的持有时间被严重放大。**
   锁在**事务提交时**才释放，而不是在 UPDATE 语句执行完就释放。所以持锁时长 = 整个事务的时长，包含网络往返、事务内的其他 SQL、甚至应用层的处理时间。也就是说，你锁住的是"整个事务"，不是"一条更新语句"。

3. **故障会放大到整个应用，而不只是秒杀接口。**
   每个等待锁的请求都占着一个数据库连接。连接池通常只有几十个连接，瞬时并发一冲，连接池立刻被等待锁的请求占满。**此时其他业务（登录、查询订单）拿不到连接，全站一起挂。**这是悲观锁最危险的后果——一个接口的慢，变成了整个应用的不可用。

4. **超时后可能形成第二波洪峰。**
   `innodb_lock_wait_timeout` 一到，大批请求同时抛错。如果客户端或网关有自动重试，这些重试会形成第二波并发冲击，而此时数据库本来就已经很吃力。

5. **无法通过加实例扩展。**
   增加应用实例只会增加抢同一把锁的并发数，瓶颈原地不动，甚至因为更多连接争抢而恶化。而秒杀的本质需求恰恰是"把流量挡在数据库之前"，悲观锁把这个方向做反了。

6. **它适用的场景与秒杀相反。**
   悲观锁适合**并发不高、但必须强一致**的场景，比如后台管理员调库存、财务扣款。这类场景请求量小，串行化的代价可以接受，换来的是实现简单和强一致。秒杀是"并发极高、允许最终一致"，两者前提正好相反。**选型错误往往不是因为方案本身差，而是因为没先问清楚场景前提。**

补充一句：有人会提出"库存分桶"来缓解——把一行库存拆成 N 行，请求分散到不同行上。这确实能降低冲突，但它本质上是一个自研的打散方案，工程复杂度不低于 Redis 预扣，而收益（仍然受限于 DB 总吞吐）更小。要做就打散到 Redis，没必要在 DB 里打散。

### 为什么不用 MySQL 乐观锁

四条理由：

1. **前提不成立。**
   乐观锁的适用前提是**冲突率低**（读多写少，或者不同请求操作不同的行）。秒杀是同一行、同一时刻、极高冲突——前提与场景完全相反。用一个假设"冲突很少"的机制去解决"冲突极多"的问题，方向就错了。

2. **重试风暴会把压力放大，而不是减小。**
   `version` 冲突后要重试。重试发生在数据库压力最大的时刻，所以数据库的实际负载 = 成功请求 + 所有失败请求的重试。也就是说，**乐观锁在冲突率高时会把失败率转换成额外的数据库负载**，与"减轻数据库压力"的初衷背道而驰。

3. **失败率高，用户体验差。**
   没有排队机制，抢不到就是失败或重试若干次后失败。用户看到的成功率低，且"先到先得"的公平性也没有保证。

4. **它只解决超卖，不解决吞吐。**
   这一点最容易被忽略：`UPDATE ... WHERE stock >= 1` 这条语句本身在 InnoDB 里**依然要加行锁**。所谓"乐观锁"在数据库层面仍然是加锁的，只不过持锁时间很短（一条语句的执行时间），而不是整个事务。所以它优化的是**持锁时长**，不是**消除争抢**。热点行上的请求依然要排队，只是队排得快一点。当并发量足够高时，短持锁依然会排成长队。

**但它有一个正确的用武之地**：当冲突率确实低的时候（比如库存分桶后每桶的冲突很低，或者后台改库存这种低频操作），条件更新是最省事且完全正确的方案。所以我把"库存分桶 + 条件更新"作为方案 D 的降级备选——**不是因为它更好，而是因为它更简单，在特定条件下足够。**

### Redis 扣减成功但订单失败怎么办

这是本方案最核心的工程问题，面试时能答清楚这一题，基本就说明真的做过。**关键是先区分失败发生在哪个环节**，不同环节的补偿方式完全不同。

#### 失败点 (a)：Redis 扣减成功，但发送 MQ 失败

处理：**同步返还 Redis 库存**（`INCRBY` 库存 + `SREM` 移除用户占位），然后向用户返回失败。

为什么可以在同步链路里返还：此时还没有任何持久化副作用，消息也没发出去，整个操作是"未发生"的，直接原地撤销即可。返还本身必须和扣减对称——扣了多少返多少，占位也要一起清掉，否则用户会被永久判定为"重复下单"，票再也抢不了。

如果**返还也失败**（Redis 抖动）：记录到本地失败表，由定时任务补偿返还，并告警。这是极小概率但必须处理的路径。

#### 失败点 (b)：消息发送成功，但消费端创建订单失败

这里必须先细分失败原因，**不能一刀切地当成"失败"处理**：

| 失败原因 | 处理方式 | 理由 |
| --- | --- | --- |
| 撞唯一索引（重复消费） | 直接 ack，视为成功 | 订单已存在，业务语义上本次消费已完成 |
| 数据库瞬时异常（连接超时、死锁） | 有限次重试（指数退避） | 大概率是瞬时故障，重试通常能成功 |
| 业务校验失败（用户不存在、车次已停售） | 不重试，直接进入失败处理 | 重试不会改变结果，只会浪费资源 |
| 重试次数耗尽 | 进入失败表 + 返还 Redis 库存 + 告警 | 必须回收库存，否则库存被永久锁死（少卖） |

#### 失败点 (c)：订单创建成功，但扣减 MySQL 库存失败

**把"创建订单"和"扣减 MySQL 库存"放进同一个本地事务**，失败则整体回滚，于是问题回到失败点 (b)。绝不能让这两个操作分开——否则会出现"有订单没扣库存"（超卖）或"扣了库存没订单"（少卖）。

#### 失败点 (d)：用户超时未支付

延时消息触发 → 取消订单（走前面的条件更新状态机，只有"待支付"才能取消）→ **同时返还 MySQL 库存和 Redis 库存**。

注意顺序和幂等：先条件更新订单状态，**只有影响行数为 1（确实抢到了这次取消）才执行返还**。这样即使延时消息重复投递，或者用户点"取消"和超时取消同时发生，库存也只会返还一次。

#### 兜底机制：定时对账

无论前面做得多细，只要有跨系统的写操作，就必须有对账。定时任务比对三个数：**Redis 剩余库存 + 已落库订单数 + MySQL 库存**，三者应当自洽。

发现差异时：**以 MySQL 为准修正 Redis**，输出告警和差异明细，而不是"当场双向修复"——当场修复会把压力带回数据库，且可能掩盖真正的 bug。对账的价值不只是修数据，更是**发现系统性缺陷的信号**。

#### 一句话总结补偿原则

**谁扣的谁返还，返还必须幂等，返还失败要兜底，最终差异靠对账。**四个环节缺一不可。

### Redis 与 MySQL 谁说了算

这是本方案最容易被面试官追问、也最能体现理解深度的一题。答案不是"谁替代谁"，而是**职责分离**：

**数据权威（source of truth）= MySQL。**

所有持久化的事实——订单、支付记录、真实的库存账目——以 MySQL 为准。Redis 里的库存是**可以重建的**：Redis 挂了或者数据丢了，从 MySQL 重新加载库存、重新预热即可恢复。这个性质非常重要，它意味着 Redis 的丢失是"可恢复的故障"而不是"数据灾难"。**如果反过来让 Redis 当权威，一旦 Redis 数据丢失（且没有持久化），库存就永久错乱了。**

**运行期裁决权（准入）= Redis。**

在秒杀窗口内，"谁有资格进入下单流程"由 Redis 的原子扣减决定。这是一个刻意的职责划分：Redis 决定**谁能进来**（把 99% 的无效请求挡在数据库之外），MySQL 决定**最终账目**（真正持久化了什么）。

**冲突时的处理原则：**

1. 以 MySQL 为准——这是权威定义。
2. 但**不要当场同步修复**——异步对账任务修复 + 告警。当场修复等于把已经挡住的流量又放回数据库。
3. 修复方向是"用 MySQL 修正 Redis"，而不是反过来。

**为什么必须分开而不是"只用 MySQL"：** 因为如果由 MySQL 做准入裁决，就回到了悲观锁方案——数据库成了瓶颈。让 Redis 做准入、MySQL 做账本，本质上是**用最终一致换取了吞吐**，这是一个明确的、经过权衡的交易，而不是疏忽。

## 代价与已知缺陷

1. **系统复杂度显著上升。**
   "一次下单"从一个数据库事务，变成"Redis 扣减 → 发消息 → 消费落库 → 对账"四个环节，每个环节都要有失败处理路径。引入 Redis 和 MQ 两个新组件，本地开发环境的搭建成本也随之上升（见 ADR-001 关于 Windows 部署的讨论）。

2. **存在最终一致窗口。**
   用户看到"抢到了"到数据库真正落库之间有延迟，具体量级**待压测**。在这个窗口内如果 MySQL 或 MQ 出问题，可能丢消息——需要本地消息表兜底，而本地消息表本身又是一套需要维护的机制。

3. **库存数据存在两份，天然有不一致的可能。**
   这是最终一致方案的固有代价，必须靠对账任务兜底。对账本身有开发成本和误报成本（比如对账时刚好有在途消息，会误判为不一致，需要设计好"在途窗口"的容忍度）。

4. **幂等是死穴，任何一处遗漏都会造成严重后果。**
   重试和补偿机制的存在，意味着**每个写操作都可能被执行多次**。所有写操作都要能重复执行：数据库靠唯一索引 + 条件更新，Redis 靠脚本内的 `SISMEMBER`，MQ 消费靠订单唯一键。任何一次重试不幂等，结果就是超卖或者库存泄漏。这是本方案最需要 review 的部分。

5. **测试难度高。**
   并发 bug 单测覆盖不到，必须做并发压测 + 结果断言（DB 库存、Redis 库存、订单数三者对账）。压测脚本本身也要写，属于额外工作量。方法见 Q11。

6. **Redis 单点问题未覆盖。**
   当前是单机 Redis，宕机则秒杀链路整体不可用。可以降级为"直接走数据库 + 严格限流"，但那意味着吞吐大幅退化。生产环境需要考虑主从/哨兵/集群，本方案没有覆盖这部分。

7. **一人一单的 Redis 占位集合会持续增长。**
   理论上需要给占位集合设置过期时间，但**过期时间必须与订单生命周期对齐**——如果占位过早过期，同一个用户就能再次下单，唯一索引虽然能兜住数据（不会真出两张票），但用户会看到"抢到了"然后失败，体验很差。这是一处需要仔细对齐的参数。

8. **Redis 只是第一道防线，数据库的条件更新不能省。**
   即使 Redis 判定成功，MySQL 侧仍然要用 `WHERE stock >= 1` 做条件更新并校验影响行数。原因有两个：一是防"Redis 与 MySQL 初始数据不一致"（预热错误），二是防"返还逻辑 bug 导致 Redis 库存虚高"。**Redis 是性能手段，MySQL 的条件更新才是数据正确性的最终保障。**把超卖防护完全寄托在 Redis 上是危险的。

9. **延时消息的精度问题（见 ADR-001）。**
   超时未支付的取消依赖延时消息，其精度受所选 MQ 的延时能力限制。误差量级**待压测**。

## 什么条件下这个决策会失效

以下任一条件成立，方案 D 就不再是正确选择，应当降级：

1. **库存本来就是分散的、冲突率低。**
   如果库存天然按车次/日期/席别分散，热点行根本不存在，那么直接用 MySQL 条件更新（乐观锁）更简单、更正确、更强一致。**引入 Redis + MQ 是为了解决热点争抢，没有热点就不该付这个复杂度。**

2. **业务要求强一致，不允许中间态。**
   如果余票必须实时准确（比如对外提供余票查询接口，要求与库存严格同步），那么"Redis 扣了但还没落库"的窗口不可接受，必须改为同步落库，并接受吞吐下降。**这是需求前提变了，不是方案变差了。**

3. **库存量远大于并发量。**
   库存充足、并发不高时（例如库存远多于同时抢购的人数），数据库完全扛得住，没有任何理由引入两个额外组件。**技术方案要和流量规模匹配。**

4. **没有可靠的消息基础设施或运维能力。**
   如果 MQ 在目标环境部署不起来，或者出问题没人能修，那么 MQ 带来的故障面大于它解决的问题。此时应退回"数据库限流 + 条件更新"的简化方案，牺牲吞吐换可用性。

5. **业务口径变为"一个用户可买多张"，或需要精确选座。**
   一人一单的幂等模型（唯一索引 + Redis 占位集合）和当前的库存模型都要重做。座位级库存是完全不同的模型，本方案不适用。

6. **Redis 不可用时的降级策略没有实现。**
   如果 Redis 挂了整个秒杀就完全不可用，且没有降级预案，那么这个单点就是系统的致命弱点。**必须有明确的降级决策**（例如：限流后直接拒绝、或临时切换到数据库条件更新模式），并在 Redis 故障时能自动或手动切换。

7. **压测后发现瓶颈并不在数据库。**
   如果压测显示数据库根本不是瓶颈（瓶颈在网关、在应用层、在带宽），那么引入 Redis + MQ 解决的是一个不存在的问题。**先压测定位瓶颈，再决定要不要上这套方案。**

## 面试追问与标准答法

**Q1：为什么不用 MySQL 悲观锁（SELECT FOR UPDATE）？**

答：不是悲观锁不对，是场景错配。三条硬伤：第一，秒杀所有请求抢同一行，`FOR UPDATE` 把它们变成串行队列，吞吐上限就是单个事务的速率，加机器也解决不了，瓶颈在锁不在硬件。第二，锁在事务提交时才释放，所以持锁时间是整个事务的时长，包含了网络往返和其他 SQL。第三，也是最危险的：每个等锁的请求都占着一个数据库连接，连接池被瞬间打满后，受影响的不是秒杀接口而是整个应用——其他业务拿不到连接就全站挂了。悲观锁适合的是"并发低但要求强一致"的场景，比如后台调库存、财务扣款，那里它是最优解。

**Q2：为什么不用乐观锁？**

答：乐观锁的前提是冲突率低，秒杀是同一行、高冲突，前提正好相反。冲突高的时候，`version` 不匹配导致大量重试，而重试发生在数据库压力最大的时刻，等于把失败率转换成了额外的数据库负载，和"减轻数据库压力"的初衷背道而驰。而且有个容易忽略的点：`UPDATE ... WHERE stock >= 1` 这条语句本身在 InnoDB 里依然要加行锁，所谓乐观锁在数据库层面仍然是加锁的，只是持锁时间短。它优化的是持锁时长，不是消除争抢。**但它有正确的用武之地**：冲突率低的时候——比如库存分桶之后，或者后台改价这类低频操作——条件更新是最省事且完全正确的方案。

**Q3：Redis 扣减成功但订单失败怎么办？**

答：先分清失败在哪个环节，补偿方式完全不同。① 发 MQ 就失败了：还没有任何持久化副作用，直接同步返还 Redis 库存并移除用户占位，返回用户失败即可。如果返还也失败，记录到本地失败表由定时任务补偿。② 消息发出去了但消费端建订单失败：要细分原因——撞唯一索引说明是重复消费，直接 ack 当成功；数据库瞬时异常就有限次重试；业务校验失败不重试，直接走失败处理。重试耗尽的，进失败表 + 返还 Redis 库存 + 告警，**必须回收库存，否则库存被永久锁死变成少卖**。③ 建订单成功但扣 MySQL 库存失败：把这两个操作放在同一个本地事务里，失败整体回滚，问题就回到第 ② 种。④ 超时未支付：延时消息触发取消订单，返还两边库存。还有一个贯穿全局的点：**所有返还操作必须幂等**，用条件更新（`WHERE status = '待支付'`）保证只有影响行数为 1 才返还，否则重试会导致多次返还，那就变成超卖了。最后靠定时对账兜底。

**Q4：Redis 与 MySQL 谁说了算？**

答：职责分离，不是谁替代谁。**数据权威是 MySQL**——订单、支付、真实库存账目都以 MySQL 为准，Redis 里的库存是可以从 MySQL 重建的，这个性质保证了 Redis 挂掉是"可恢复故障"而不是"数据灾难"。**运行期的准入裁决权是 Redis**——秒杀窗口内谁有资格进下单流程由 Redis 的原子扣减决定，目的是把绝大多数请求挡在数据库之前。冲突时以 MySQL 为准，但**不在线上当场同步修复**，而是异步对账修复 + 告警，因为当场修复等于把已经挡住的流量又放回数据库。一句话：Redis 决定谁能进来，MySQL 决定最终账目。

**Q5：为什么用 Lua 脚本？直接用 DECRBY 然后判断返回值不行吗？**

答：不行，这是两种不同的做法，风险不一样。如果先 `GET` 判断库存再 `DECRBY`，两条命令之间有时间窗口，并发下会"都判断有库存、都扣减"，直接超卖。有人会说那我直接 `DECRBY`，返回值小于 0 就说明扣失败，再 `INCRBY` 补回去——这个做法有两个问题：一是补偿之前的这段时间库存是错的（负数），期间其他请求会读到错误库存；二是如果进程在 `DECRBY` 之后、`INCRBY` 之前崩溃，这次多扣的库存就**永久泄漏**了，只能靠人工对账发现。Lua 脚本在 Redis 里是原子执行的，判断、扣减、占位在一个操作内完成，既不会出现负库存，也不存在补偿丢失的问题。另外我把"检查用户是否重复下单"也放进了同一个脚本，否则同一个用户的两个并发请求可能都通过重复检查。

**Q6：会不会超卖？最后一道防线在哪？**

答：分三层。第一层是 Redis 的 Lua 脚本，判断和扣减原子完成，挡掉绝大部分并发。第二层是数据库的条件更新 `UPDATE ... SET stock = stock - 1 WHERE stock >= 1`，校验影响行数，这一层是**数据正确性的最终保障**——它能兜住 Redis 与数据库初始不一致的情况（预热错误），也能兜住返还逻辑 bug 导致 Redis 库存虚高的情况。第三层是唯一索引，保证同一用户不会出两张票。**把超卖防护完全寄托在 Redis 上是危险的**，Redis 是性能手段，不是正确性保障。

**Q7：消息重复消费怎么办？**

答：幂等做在消费端，这是消费端的责任，MQ 只能保证"至少一次"。做法是订单表上建唯一索引 `(user_id, train_id, travel_date)`，重复消费时插入撞唯一键，捕获异常后直接 ack 当作成功——因为订单已经存在，业务上这次消费就是完成的。更通用的模式是一张去重表用消息 ID 做唯一索引，或者用 Redis 的 `SETNX` 记录已处理的消息 ID。

**Q8：用户超时未支付，库存怎么回去？**

答：延时消息在超时后触发取消订单。取消时先把订单状态从"待支付"条件更新为"已取消"，**只有影响行数为 1 才执行库存返还**（MySQL 和 Redis 都要返还）。这个条件更新就是幂等的关键：延时消息重复投递、或者用户手动取消和超时取消同时发生，库存都只会返还一次。如果不做条件更新，重复返还就是超卖。

**Q9：Redis 挂了怎么办？**

答：这个问题要先承认 Redis 在方案里是单点。当前教学环境是单机 Redis，挂了秒杀链路整体不可用。生产环境要做主从 + 哨兵/集群。更重要的是**必须有降级预案**：Redis 不可用时，要么限流后直接拒绝（保证不出错，牺牲可用性），要么临时切换到数据库条件更新模式（可用但吞吐退化，且要防止数据库被打穿）。**最坏的方案是没有预案，让 Redis 成为一个没有兜底的致命单点。**另外因为 MySQL 才是权威，Redis 恢复后可以从数据库重新预热库存，数据本身不会丢。

**Q10：库存怎么预热？预热时要注意什么？**

答：在秒杀开始前，把数据库里的库存数量加载到 Redis（例如活动开始前几分钟，由定时任务或管理端点触发）。要注意三点：一是**预热必须幂等**，重复执行不能把库存叠加（用 `SET` 而不是 `INCR`）；二是**预热期间要防止已经开抢**，否则会出现"用户已扣减的库存被预热覆盖回去"——通常做法是先预热再开放入口；三是**预热后要做一次校验**，比对 Redis 库存与数据库库存是否一致，不一致就告警。

**Q11：怎么验证没有超卖？怎么压测？**

答：分两步。第一步是并发压测：用压测工具（JMeter / wrk / 自己写并发脚本，具体工具待定）模拟远超库存量的并发请求打到下单接口，可以是本机的多线程压测。第二步是**结果断言**，这才是关键：压测结束后对三个数——数据库订单数、数据库库存扣减量、Redis 剩余库存——三者必须自洽，且订单数绝对不能超过初始库存。同时要观察失败请求的返回码分布，确认失败原因是"库存不足"而不是"系统异常"（后者说明有 bug 被掩盖了）。**光看接口 QPS 不叫压测，能对上账才叫压测。**具体并发量和 QPS 数据等实测后再补，本文不预设数字。

**Q12：为什么不直接在数据库前面加一层限流，而是引入 Redis？**

答：限流和 Redis 预扣解决的是不同问题，通常是组合使用。限流是"按速率丢弃请求"，它不知道库存还剩多少——假设限流放行了远多于库存数的请求，而库存只有少量几张，那么库存被抢完之后，剩下那些已经被放行的请求仍然会白跑一趟数据库。Redis 预扣是"按库存状态精确裁决"，库存为 0 之后所有请求都被挡在 Redis 层，一个都不落到数据库。**限流保护系统不被打垮，预扣保证流量被精确消化。**两者叠加使用效果最好：入口限流挡住明显过量的流量，Redis 预扣做精细裁决。

**Q13：这套方案和直接用数据库相比，复杂度值得吗？**

答：取决于流量规模，这是诚实的回答。如果并发量不大（比如同时几十个人抢），数据库完全扛得住，直接条件更新就是最优解，引入 Redis + MQ 纯属过度设计——这也是我把它写在"什么条件下这个决策会失效"里的原因。这套方案的价值在于它解决的是**高并发下数据库单点瓶颈**这个具体问题，并且它覆盖了缓存原子性、异步解耦、幂等、最终一致、对账补偿这一整套分布式系统的基本功。对本教学项目来说，即使流量用不上，这套链路本身是主要的学习目标——**但必须清楚地知道它是为多大的流量准备的，而不是无脑上。**
