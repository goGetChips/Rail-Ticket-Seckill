## 一、架构与拆分

### Q1.1 这个项目为什么要拆成多个服务？拆的依据是什么？

- **考点**：拆分的驱动力是不是真实存在的，还是"为了微服务而微服务"。
- **回答要点**：
  1. 拆分的依据是**变更频率与伸缩需求不同**，不是"模块多"。
  2. 秒杀链路（库存预扣 + 下单）的流量特征与查询链路（车次查询、订单查询）完全不同：前者瞬时高并发且要强一致，后者读多写少且能容忍短暂陈旧。
  3. 拆开之后，秒杀链路可以独立扩容和独立限流，查询链路挂了不影响抢票（反之亦然）。
  4. 拆分的代价要说清楚：跨服务调用带来网络不确定性、分布式事务问题、排障难度上升。
- **项目证据**：`docs/architecture/design-spec.json`（当前为空，拆分清单以最终架构文档为准）。
- **追问链**：
  - L1：**"那你怎么划边界？会不会拆得太细？"** → 答：按"是否会一起变化"划，不按技术分层划；如果两个服务每次需求都一起改，说明边界划错了，应该合并。判断标准是变更耦合度，而不是代码行数。
    - L2：**"拆完之后，原来一个本地事务能解决的事现在跨服务了，怎么办？"** → 答：先问能不能不跨——把强一致的写操作放到同一个服务同一个库（例如库存与订单落库都在订单域内，用本地事务）；真的跨了才谈最终一致 + 对账，见 Q4 组。
      - L3：**"那你现在跨服务的地方有哪些？"** → 答：必须能现场列举（例如下单服务 → 用户服务校验、→ 车次服务查票价）。**当前具体清单：待核对架构文档。**
- **常见错误回答**：说"微服务解耦、高内聚低耦合"但没有具体到本项目哪个模块为什么拆。

### Q1.2 为什么用 Redis + Lua 做预扣，而不是直接扣数据库？

- **考点**：是否理解"数据库连接数是稀缺资源"这一层。
- **回答要点**：
  1. 数据库能扛的并发写远低于 Redis（受连接数、行锁、redo 落盘限制），秒杀瞬时流量打过来会把连接池打满（见 T-07）。
  2. Redis 单线程执行 Lua，天然对"读-判断-写"提供原子性，不需要额外加锁。
  3. 代价：Redis 与 MySQL 变成两个数据源，引入不一致（见 Q2 组、Q4 组），必须配对账。
  4. 所以定位要讲清楚：**Redis 是挡流量的加速层和预筛层，MySQL 才是账本。**
- **项目证据**：库存预扣脚本（`docs/troubleshooting/README.md` T-05 中的正例写法与项目实现对照）。
- **追问链**：
  - L1：**"Redis 挂了怎么办？"** → 答：要分两种：Redis 完全不可用（此时应该快速失败/降级，而不是把流量打向数据库，否则数据库必挂）；Redis 数据丢失（靠 MySQL 为准 + 重建缓存，重建期间必须限流）。
    - L2：**"重建缓存的时候，库存怎么算？"** → 答：用 MySQL 的 `remain` 重建，但重建过程中如果有新的预扣在跑，会出现覆盖问题——所以重建要么在限流窗口内做，要么带版本号校验。**这一块当前设计是否覆盖：待核对。**
      - L3：**"Redis 主从切换时预扣记录丢了，会超卖吗？"** → 答：会存在窗口，取决于持久化策略与切换时机。诚实回答：这是当前设计的薄弱点之一，见 Q9.2。
- **常见错误回答**："Redis 快"——这只回答了性能，没回答原子性和一致性代价。

### Q1.3 这个项目里哪些数据允许最终一致，哪些必须强一致？你怎么分的？

- **考点**：一致性分级能力，这是架构题的核心。
- **回答要点**：
  1. 分类维度是**出错代价**，不是技术难度。
  2. 必须强一致（用本地事务保证）：订单与库存的落库扣减、支付结果。
  3. 允许最终一致：Redis 与 MySQL 的库存镜像、缓存数据、统计类数据。
  4. 判断方法：问"如果两个数据在 1 秒内不一致，会造成资损吗？"会，就不能最终一致。
- **项目证据**：库存表扣减语句必须带 `remain >= n` 条件（见 Q3.1），这就是"强一致"落在地面的样子。
- **追问链**：
  - L1：**"最终一致的窗口有多长？你量化过吗？"** → 答：这是当前回答最容易翻车的地方。正确姿势是承认："当前没有量化，只有对账任务的执行周期作为上限，具体周期是<待核对>，我打算用对账差值条数随时间的曲线来度量。"
    - L2：**"如果对账发现不一致，修哪边？"** → 答：以 MySQL 为准修 Redis，因为 MySQL 有本地事务与约束，Redis 只是镜像；这条规则必须先定下来，否则对账会来回震荡。
- **常见错误回答**：所有数据都说"最终一致"，包括库存。

### Q1.4 秒杀链路的完整流程是什么？每一步的失败会怎样？

- **考点**：能否把主链路讲成一条闭环，尤其是**失败路径**。
- **回答要点**（骨架，具体接口名以代码为准）：
  1. 前置：活动/车次校验、用户资格校验（是否重复下单）、限流。
  2. 预扣：Redis Lua 原子判断 + 扣减，返回三种结果（未初始化 / 库存不足 / 成功）。
  3. 投递：预扣成功后发 MQ 消息（消息体带业务唯一键）。
  4. 消费：幂等落库（唯一索引 + 状态机），写订单、扣 MySQL 库存。
  5. 回执：前端轮询/推送查询下单结果（异步下单必须给用户一个"排队中"的中间态）。
  6. 失败路径必须逐条说：预扣失败直接返回；预扣成功但投递失败 → 需要回补；投递成功但消费失败 → MQ 重试 + 死信；消费成功但回执丢失 → 用户重查即可，幂等保证不重复下单。
- **项目证据**：`docs/troubleshooting/README.md` T-01 / T-02 的排查方向就是按这条链路的分段来定位的。
- **追问链**：
  - L1：**"预扣成功但 MQ 投递失败怎么办？"** → 答：这是最典型的坑。要么在预扣成功后用一个可靠投递机制（本地消息表 / 事务消息），要么接受窗口并靠对账回补。**当前用的是哪种：待核对。**
    - L2：**"对账回补的粒度是什么？怎么保证只回补一次？"** → 答：回补必须以"业务唯一键 + 幂等标记"为单位，不能靠"发现差值就 INCR"，否则重复对账会重复加库存。
      - L3：**"那你怎么知道这次差值是真不一致，而不是有一笔订单正在路上？"** → 答：必须给在途操作留出宽限期（等待超过 MQ 最大重试耗时的数据才判定为不一致）。**宽限期取值：待压测。**
- **常见错误回答**：只讲成功路径。

### Q1.5 为什么下单要做成异步？异步带来的复杂度你接受吗？

- **考点**：是否算过异步的收益与成本。
- **回答要点**：
  1. 收益：把"用户请求线程"从"写库 + 事务 + 可能的锁等待"里解放出来，接口 RT 只取决于 Redis + 一次消息投递，前端能快速得到"排队中"。
  2. 收益的代价：用户看不到即时结果，必须做结果查询接口；链路变长，排障要从"看一次调用栈"变成"串 traceId"。
  3. 不这么做的替代方案：同步下单（简单、结果实时，但数据库压力上限低，峰值必崩）、Redis 直接写订单（数据可靠性不足）。
  4. **结论要落在"这是取舍而非优越"**：项目定位是抢票，抢的体验是"秒回 + 稍后确认"，异步匹配业务形态。
- **项目证据**：结果查询接口与订单状态机（状态字段取值以代码为准）。
- **追问链**：
  - L1：**"用户一直查到'排队中'怎么办？"** → 答：必须有超时兜底：MQ 侧有最大重试与死信，业务侧有超时未支付关单（见 Q3.4），前端轮询要有次数上限与失败提示。
    - L2：**"关单和支付同时发生怎么办？"** → 答：靠状态机 CAS 更新，谁先改成功谁生效；支付回调与关单任务是两个并发写，必须用 `WHERE status = ?` 做条件更新。
- **常见错误回答**：只说异步"性能好"，说不出用户侧体验怎么补。

### Q1.6 如果只能保留一个优化，你留哪个？为什么？

- **考点**：有没有真正的优先级判断，而不是"全都重要"。
- **回答要点**：
  1. 先定义"优化"的目标：是提升吞吐、降低 RT，还是保证正确性？
  2. **正确性优先于性能**：任何绕过一致性约束换来的吞吐都是负债。
  3. 如果目标是最小改动换来最大收益，候选通常是"把同步写库从请求链路里拿掉"（即异步下单）或"在入口加限流"。
  4. 要能说出"不选其他项"的理由。
- **项目证据**：需要有实测数据支撑（**待压测**），没有数据就明确说这是待验证的判断。
- **追问链**：
  - L1：**"你怎么知道它是最大收益？你测过吗？"** → 答：不测不能下结论。这里必须承认"这是基于原理的预期，压测计划是……"。
    - L2：**"那你的压测计划是什么？"** → 答：要能说出对照分组（有/无限流、同步/异步）、观测指标（RT 分布、错误率、连接池水位、CPU）、以及每轮只改一个变量。
- **常见错误回答**：报一堆优化点，说不出排序依据。

## 二、Redis 与缓存

### Q2.1 Lua 脚本为什么能保证原子性？它和加锁有什么区别？

- **考点**：是否理解 Redis 单线程模型与 Lua 执行的关系。
- **回答要点**：
  1. Redis 处理命令是单线程的（指命令执行阶段），脚本作为一个整体被调度，执行期间不会插入其他客户端的命令。
  2. 所以"读-判断-写"在脚本内是原子的，不需要额外的分布式锁。
  3. 与锁的区别：锁是"先抢资源再操作"，会有抢不到、锁超时、锁失效、死锁等问题；脚本把互斥做进了服务端，客户端不需要持有状态。
  4. **代价**：脚本是阻塞的，长脚本会卡住整个实例，所以脚本必须短小（见 Q2.2）。
- **项目证据**：库存预扣脚本（T-05 中的正例）。
- **追问链**：
  - L1：**"脚本执行期间，其他请求在干什么？"** → 答：在排队等待。这就是为什么脚本不能做重活——一次慢脚本会拖慢整个实例的所有请求。
    - L2：**"那你怎么保证脚本不慢？"** → 答：脚本里只做 O(1) 级别的操作（GET/DECRBY/EXISTS），不遍历、不取大集合；监控 SLOWLOG 与 `INFO commandstats`。
      - L3：**"如果确实需要在预扣时做较重的逻辑呢？"** → 答：把重逻辑移出脚本——脚本只做判断和扣减，其余在应用层或异步做。要举例说明哪些逻辑被这样挪走了。
- **常见错误回答**："Lua 是原子操作"却解释不出为什么。

### Q2.2 库存 key 会不会成为热 key？怎么处理？

- **考点**：能不能识别出"这是设计上的必然代价"。
- **回答要点**：
  1. 会，而且是必然的：同一车次的库存必须放在同一个 key 上才能保证原子扣减，所以无法通过分片分散。
  2. 能做的缓解：控制 value 体积（只存数字，不存列表）、短脚本、连接池复用、必要时本地缓存挡读（但库存不缓存，只缓存车次维度数据）。
  3. 不能做的：把一个逻辑库存拆成 N 个 key 分桶——它会破坏"总量原子性"，除非业务上允许按座位段拆分并且能接受跨桶的总量误差。
- **项目证据**：`docs/troubleshooting/README.md` T-08。
- **追问链**：
  - L1：**"那读请求（查余票）会不会把 Redis 打死？"** → 答：查余票是高频读，通常是真正的读热点。可选：读走本地缓存（允许短暂陈旧）、接口限流、结果缓存极短 TTL。
    - L2：**"本地缓存余票不就查到旧数据了吗？"** → 答：要区分"展示用余票"和"下单用库存"——展示可以陈旧（用户看到有票但下单失败是可接受的），下单必须走 Redis + Lua 的实时判断。**这个区分当前设计是否明确：待核对。**
- **常见错误回答**：说"用 Redis 集群就能解决热 key"——集群对同一个 key 没有帮助。

### Q2.3 缓存穿透、击穿、雪崩，这个项目各是怎么防的？

- **考点**：能不能落到本项目具体场景，而不是背概念。
- **回答要点**：
  1. **穿透**（查不存在的数据）：车次/订单查询如果查一个不存在的 ID，每次都会打到数据库。防护：缓存空值（带短 TTL）或布隆过滤器。要不要用布隆过滤器取决于参数空间大小，本项目 ID 是有限集合还是无限增长要先确认（**待核对**）。
  2. **击穿**（热点 key 过期瞬间）：余票热点 key 过期会造成瞬时全量打库。防护：热点数据逻辑过期/永不过期 + 异步刷新，或加互斥重建。
  3. **雪崩**（大量 key 同时过期）：TTL 加随机抖动。
  4. **共性前提**：所有防护都要能说出"不加会怎样"，否则就是背概念。
- **项目证据**：缓存写入处的 TTL 设置（**当前取值待核对**）。
- **追问链**：
  - L1：**"库存 key 会不会过期？"** → 答：这是关键问题。库存 key 如果带过期，过期瞬间会被当成"未初始化"（脚本返回 -1），流量会去打库或者误判无票。所以库存 key 的生命周期必须和活动周期绑定，并有明确的重建路径。
    - L2：**"那你怎么保证它不过期？"** → 答：活动开始前预热写入并设定覆盖整个活动周期的 TTL；同时在脚本里把"key 不存在"和"库存为 0"区分开（返回不同值），避免把异常当业务结果。
- **常见错误回答**：三个概念各背一段定义，一个都不落地。

### Q2.4 缓存和数据库怎么保持一致？你选的是哪种方案？

- **考点**：是否知道各种缓存一致性方案的取舍和适用边界。
- **回答要点**：

| 方案 | 一致性 | 主要风险 | 适用性 |
| --- | --- | --- | --- |
| 先更新 DB 再删缓存 | 较好 | 删除失败会长期脏数据 | 通用首选 |
| 先删缓存再更新 DB | 差 | 并发下旧值被回填 | 不推荐单独用 |
| 延迟双删 | 较好 | 延迟时间靠猜 | 兜底手段 |
| 订阅 binlog 异步失效 | 最终一致 | 引入额外组件 | 数据量大时值得 |
| 缓存永不过期 + 版本号 | 可控 | 逻辑复杂 | 特定场景 |

  1. 本项目的库存不走"缓存-数据库"这套读写模型，而是**写两侧 + 对账**（Redis 预扣、MySQL 落库），性质与普通业务缓存不同，要主动区分开。
  2. 普通业务数据（车次、站点）用"先更新 DB 再删缓存"。
  3. 关键：**删除失败要有补偿**（重试 + 兜底 TTL），否则脏数据会一直留着。
- **项目证据**：缓存更新的代码位置（**待核对**）。
- **追问链**：
  - L1：**"为什么是先更新 DB 再删缓存，不是反过来？"** → 答：反过来时，删完缓存到 DB 更新完成之间，有读请求把旧值读回来写进缓存，脏数据会长期存在（读多写少时概率不低）。
    - L2：**"那先更新 DB 再删缓存就绝对安全吗？"** → 答：不安全。典型反例是读请求在"缓存未命中 → 读 DB（旧值）→ 写缓存"的间隙里，删缓存已经执行完了，旧值仍然被写回。所以要么用延迟双删，要么接受窗口 + TTL 兜底。
      - L3：**"你怎么判断这个窗口能不能接受？"** → 答：看数据的错误代价：展示类数据可以接受，余额/库存这类不能接受——所以库存根本不走这套模型。
- **常见错误回答**：说"延迟双删就完美解决了"。

### Q2.5 Redis 的持久化怎么配？丢了数据怎么办？

- **考点**：是否想过"缓存层挂了会怎样"。
- **回答要点**：
  1. RDB 与 AOF 的取舍：RDB 恢复快但有数据丢失窗口；AOF 丢失窗口小但文件大、恢复慢。**本项目实际配置：待核对。**
  2. 对库存来说，丢失预扣记录意味着 Redis 认为库存比实际多，**这是会导致超卖的方向**，所以不能只依赖 Redis 的可靠性。
  3. 兜底逻辑：Redis 数据丢失后，以 MySQL 为准重建库存 key，重建期间限流或直接拒绝新预扣，避免用错误库存继续放量。
- **项目证据**：Redis 容器/配置中的持久化参数（**待核对**，见 T-10 关于数据卷的检查项）。
- **追问链**：
  - L1：**"重建期间用户请求怎么办？"** → 答：限流 + 快速失败（返回"系统繁忙"），这比放量造成超卖好。
    - L2：**"你怎么知道 Redis 数据丢了？"** → 答：靠监控与对账——对账跑出的差值会异常放大；也可以用启动探针检查库存 key 是否存在。
- **常见错误回答**："Redis 不会丢数据"。

### Q2.6 为什么 Lua 脚本里要把"key 不存在"和"库存为 0"分开返回？

- **考点**：细节意识——是不是把异常当成了业务结果。
- **回答要点**：
  1. 两者语义完全不同：key 不存在 = 缓存未初始化/被清空（系统问题）；库存为 0 = 正常售罄（业务问题）。
  2. 混在一起会导致：缓存被清空时，用户看到的是"已售罄"这种错误提示；或者系统问题被当成业务结果，掩盖了故障。
  3. 因此脚本返回码要分档，例如：未初始化 = -1，库存不足 = 0，成功 = 1（**具体取值以项目代码为准**）。
  4. 应用层对 -1 要有明确处理：触发重建或快速失败，而不是直接告诉用户没票。
- **项目证据**：T-05 中的脚本示例展示了 `return -1` / `return 0` / `return 1` 的分档方式。
- **追问链**：
  - L1：**"那如果 key 不存在时你直接让它返回 0，会有什么后果？"** → 答：活动期间 Redis 抖动/重启后，所有用户都被告知售罄，等于业务中断且无人报警。
    - L2：**"你怎么监控这种情况？"** → 答：对返回码 -1 的次数单独打点并告警，因为它代表的是系统异常而非业务结果。
- **常见错误回答**：从来没想过这个区分。

## 三、库存与超卖

### Q3.1 你怎么保证不超卖？说清楚每一层防线。

- **考点**：这是最核心的问题，能不能分层回答。
- **回答要点**：
  1. **第一层 Redis Lua**：原子判断 + 扣减，挡住绝大部分并发，避免流量落到数据库。
  2. **第二层 MySQL 条件更新**：`UPDATE stock SET remain = remain - #{n} WHERE id = #{id} AND remain >= #{n}`，靠影响行数判断是否扣减成功。**这一层是最终的正确性保障**，即使 Redis 出错也不会把库存扣成负数。
  3. **第三层唯一索引**：防止重复订单占用同一份库存。
  4. 三层的关系：第一层是性能，第二、三层是正确性。**不能只讲 Redis。**
- **项目证据**：库存表 DDL 与扣减 SQL（**位置待核对**）。
- **追问链**：
  - L1：**"有了 Redis 为什么还要数据库再判一次？"** → 答：因为 Redis 不可靠（主从切换、丢失、脚本 bug、回补遗漏），数据库的条件更新是最后一道防线，成本极低（多一个 WHERE 条件）。
    - L2：**"那如果数据库扣减失败（影响行数 0），Redis 已经扣了怎么办？"** → 答：要触发回补（`INCR`），并且回补必须幂等，否则修复动作本身会制造新的不一致。
      - L3：**"回补失败呢？"** → 答：落到对账任务兜底。这里要承认：**回补链路当前是否闭环：待核对**，如果没有闭环就是设计缺口。
- **常见错误回答**：只说 Redis Lua，不说数据库兜底。

### Q3.2 为什么用 `remain >= n` 条件更新而不是 `SELECT ... FOR UPDATE`？

- **考点**：是否理解悲观锁与乐观/条件更新的差异。

| 方案 | 加锁 | 并发表现 | 死锁风险 | 备注 |
| --- | --- | --- | --- | --- |
| `SELECT ... FOR UPDATE` | 行锁，锁到事务结束 | 串行化该行，持锁时间长 | 有 | 事务里做别的事时风险大 |
| 条件更新 `WHERE remain >= n` | 由存储引擎行锁短暂保护 | 好 | 低 | 推荐 |
| 版本号乐观锁 | 无锁 | 冲突时重试 | 无 | 冲突率高时重试放大 |

  1. 条件更新只需一条语句，原子性由数据库保证，持锁时间极短。
  2. `FOR UPDATE` 会把锁持有到事务提交，如果事务里还有远程调用或耗时操作，锁等待会迅速蔓延。
  3. 本项目库存扣减放在消费端的事务里，事务边界必须短——所以条件更新更契合。
- **项目证据**：扣减 SQL 的实际写法（**待核对**）。
- **追问链**：
  - L1：**"条件更新在什么情况下会失败？"** → 答：库存不足（正常）、记录不存在（数据问题）、并发下被其他事务抢先（正常）。要区分"业务失败"和"异常"。
    - L2：**"高并发下条件更新会不会大量失败？"** → 答：会，但这正是"不超卖"的体现——失败的是超出库存的请求，本来就该失败。要注意的是失败后的行为（返回售罄而不是异常）。
- **常见错误回答**：把 `FOR UPDATE` 当成标准答案。

### Q3.3 一个人抢多张票、或者重复提交，怎么处理？

- **考点**：业务幂等与库存原子性的关系。
- **回答要点**：
  1. 库存扣减要支持数量参数（`DECRBY n`），并且判断 `remain >= n`，不能拆成循环扣 1（循环会破坏原子性，出现扣到一半的情况）。
  2. 重复提交的防护分两层：前置（同一用户短时间内的重复请求，用幂等 token 或限流挡掉）+ 后置（唯一索引兜底）。
  3. 唯一索引的字段选择取决于业务规则：一人一单是 `(user_id, train_no, travel_date, seat_type)`；如果允许一人多单，则只能靠 `order_no` 保证不重复下单，而不能阻止"多买"。
  4. **要主动说出：加不加这条唯一索引是业务决策，不是技术决策。**
- **项目证据**：`docs/troubleshooting/README.md` T-02 中的 DDL 与说明。
- **追问链**：
  - L1：**"幂等 token 放在 Redis 里，Redis 挂了怎么办？"** → 答：token 只是减少无效请求，不是正确性保障；挂了就退化成只有唯一索引兜底，正确性不受影响。
    - L2：**"那 token 和唯一索引是不是重复了？"** → 答：不是，层级不同：token 在入口挡掉重复流量（省资源），唯一索引在落库保证正确（保底线）。
- **常见错误回答**：只讲技术手段，不谈业务规则对索引设计的影响。

### Q3.4 超时未支付怎么回补库存？回补和支付同时发生怎么办？

- **考点**：并发写同一份数据的经典竞态。
- **回答要点**：
  1. 回补触发方式：定时任务扫超时未支付订单（或 MQ 延迟消息/定时消息，取决于 MQ 能力，**选型待定**）。
  2. 竞态：关单任务与支付回调可能同时到达。
  3. 解决：**状态机 CAS 更新**，例如：
     ```sql
     UPDATE t_order SET status = 'CANCELLED'
      WHERE id = ? AND status = 'UNPAID';   -- 影响行数 0 表示状态已变，放弃回补
     ```
     只有把订单从"未支付"改成"已取消"成功的那个执行者才有权回补库存，另一个直接放弃。
  4. 回补同样要双写：MySQL `remain + n` 与 Redis `INCRBY n`，且两者都要幂等。
- **项目证据**：订单状态取值与流转（**以代码为准**）。
- **追问链**：
  - L1：**"如果支付回调先到，关单任务查到的还是未支付怎么办？"** → 答：以 CAS 的结果为准——关单更新影响行数为 0 就不回补，不会出现"付了钱还被取消"。
    - L2：**"那用户支付成功了但订单已经被取消（极端时序）怎么办？"** → 答：必须有退款/人工处理路径，这类问题不可能靠代码完全消除，要承认并给出兜底方案。
      - L3：**"你怎么知道发生了这种情况？"** → 答：靠对账——支付流水与订单状态比对，差异单报警。
- **常见错误回答**：不考虑竞态，认为"定时任务扫一遍就行了"。

### Q3.5 库存预热怎么做？预热错了怎么办？

- **考点**：是否想过"活动开始前"这一段。
- **回答要点**：
  1. 预热时机：活动开始前，把 MySQL 的 `remain` 写入 Redis（key 带车次 + 日期 + 席别维度）。
  2. 预热必须幂等：重复执行不能把已经扣过的库存重置回去。做法：只在 key 不存在时写入（`SETNX`），或者带版本号。
  3. 预热失败的处理：宁可让活动延迟开始，也不能在没有库存数据的情况下开放流量（否则脚本返回 -1，全部快速失败）。
  4. 必须有一个"预热完成"的校验步骤：抽查若干 key 的值是否与 MySQL 一致。
- **项目证据**：**预热代码当前是否实现：待核对。**
- **追问链**：
  - L1：**"预热用 SETNX 的话，活动进行中 Redis 重启后 key 没了，会重新预热成旧值吗？"** → 答：会——这是一个真实风险。所以重启后的重建必须以 MySQL 的实时 `remain` 为准，而不是用活动开始时快照的初始值；这两个值在活动开始后就不一样了。
    - L2：**"那你怎么区分'需要重建'和'已经卖完了'？"** → 答：key 不存在（-1）与值为 0 是两回事，见 Q2.6。
- **常见错误回答**：把预热写成"启动时把初始库存写进去"，忽略活动进行中重启的场景。

### Q3.6 如果让你重新设计库存模型，你会改什么？

- **考点**：反思能力，这题答好非常加分。
- **回答要点**（以下为思考方向，不是已落地的改动，回答时必须说明"这是设想"）：
  1. 引入**预扣流水表**作为唯一账本：每次预扣/回补写一条流水，Redis 变成纯粹的加速层。这样 Redis 丢了也能精确重建，不必依赖对账猜差值。
  2. 把"库存"与"座位"解耦：现在的模型若按席别扣减，会出现"有票但分不到具体座位"的问题，需要额外的座位分配步骤与失败回滚。
  3. 明确区分"展示余票"与"可售库存"两个口径，避免用户看到有票却下不了单。
  4. 所有回补走同一套幂等接口，禁止散落的 `INCR`。
- **项目证据**：`docs/troubleshooting/README.md` T-01 的方案对比表。
- **追问链**：
  - L1：**"加了流水表，写放大怎么办？"** → 答：流水表是追加写，可以按时间分区/归档，且它是与订单在同一个事务里的，不额外增加一次网络往返。
    - L2：**"那 Redis 还需要吗？"** → 答：需要——它挡的是"根本不该到数据库"的流量。流水表解决的是可恢复性，不是吞吐。
- **常见错误回答**：把改动说成"已经做了"。

## 四、MQ 与一致性

### Q4.1 MQ 在这里解决什么问题？不用行不行？

- **考点**：是否清楚引入 MQ 的真实动机。
- **回答要点**：
  1. 三个作用：**削峰**（把瞬时并发转成平稳消费）、**解耦**（下单链路不依赖落库服务的实时可用性）、**异步**（请求快速返回）。
  2. 不用 MQ 的替代：同步落库（简单但峰值必崩）、线程池异步（进程内，重启丢任务）、定时批处理（延迟不可接受）。
  3. 代价：消息可能重复、可能丢失、可能积压、可能乱序，每一条都要有对策。
- **项目证据**：**MQ 具体选型未定**，面试时按最终选型回答，并说明选型理由（如：是否需要事务消息、是否需要延迟消息、是否需要严格顺序）。
- **追问链**：
  - L1：**"消息会丢吗？"** → 答：会，分三段——生产端发送失败、broker 未持久化、消费端处理失败未 ack。每段的对策不同：生产端要有发送结果确认与重试；broker 侧按可靠性要求配置刷盘/副本；消费端失败要重试 + 死信 + 告警。
    - L2：**"消费端重试一直失败呢？"** → 答：进死信队列 + 告警 + 人工介入。**当前死信处理流程是否落地：待核对。**
- **常见错误回答**："MQ 保证不丢消息"。

### Q4.2 消息重复消费怎么防？（必问）

- **考点**：幂等的落地方式。
- **回答要点**：
  1. 前提认知：**至少一次投递**是常态，重复不可避免，所以幂等是消费端的义务。
  2. 幂等键选择：优先用业务唯一键（订单号 / 用户+车次+日期+席别），而不是消息 ID——消息 ID 在生产者重发时会变。
  3. 落地手段：
     - 唯一索引 + `INSERT IGNORE` / `ON DUPLICATE KEY UPDATE`（正确性底线）。
     - 状态机 CAS（重复消息不会推进已完成的状态）。
     - Redis 去重（减少无效处理，不作为正确性保障）。
  4. **明确说出"先查后插"在并发下不成立**，这是加分点。
- **项目证据**：`docs/troubleshooting/README.md` T-02 的对比表与 DDL。
- **追问链**：
  - L1：**"用消息 ID 去重有什么问题？"** → 答：生产者重发时消息 ID 可能变（取决于实现），去重失效；另外消息 ID 与业务无关，无法阻止"同一用户两次点击"产生两条不同 ID 的消息。
    - L2：**"那业务唯一键就一定可靠吗？"** → 答：取决于业务规则是否真的唯一。若业务允许多单，就不能用它做约束，只能退回到订单号维度。
- **常见错误回答**："用 Redis 存消息 ID 去重"，然后说这是保证不重复下单的手段。

### Q4.3 消息乱序要不要处理？

- **考点**：是否想过顺序问题在库存场景意味着什么。
- **回答要点**：
  1. 先问：乱序会造成什么后果？对本项目而言，若同一订单的"下单"和"取消"两条消息乱序，最终状态就可能错。
  2. 如果需要有序：同一业务键的消息路由到同一个队列/分区（按 key 分区），消费端单线程处理该分区。
  3. 如果不需要严格有序：用**状态机 + 版本号/时间戳**让乱序消息自然失效（旧状态不允许覆盖新状态）。
  4. 取舍：全局有序代价很大，通常只需"同一业务键局部有序"。
- **项目证据**：**当前是否按业务键分区：待核对。**
- **追问链**：
  - L1：**"按 key 分区会不会导致某个分区倾斜成热点？"** → 答：会，热点车次会集中到一个分区，这与 T-08 的热 key 是同一类问题；缓解靠业务上拆分子键或接受单分区串行（因为库存操作本来就需要串行）。
    - L2：**"单分区串行，吞吐上不去怎么办？"** → 答：把"串行范围"缩小——按车次+日期而不是全局串行；吞吐上限由单分区能力决定，需压测确认是否满足需求（**待压测**）。
- **常见错误回答**：没想过乱序，或者回答"MQ 保证顺序"。

### Q4.4 怎么保证"扣了 Redis 库存"和"发了消息"这两件事不脱节？

- **考点**：这是本项目最薄弱的一环，能不能诚实且有方案地讲。
- **回答要点**：
  1. 问题本质：Redis 和 MQ 是两个系统，没有跨系统事务，中间必然有窗口。
  2. 候选方案：

| 方案 | 思路 | 可靠性 | 成本 |
| --- | --- | --- | --- |
| 先预扣再发消息，失败不管 | 简单 | 低，会漏单/少卖 | 最低 |
| 预扣 + 发送失败即回补 | 补偿式 | 中，回补本身可能失败 | 低 |
| 本地消息表（同库事务写消息，异步投递） | 可靠投递 | 高 | 中 |
| MQ 事务消息（若选型支持） | 半消息 + 回查 | 高 | 中高，需实现回查 |
| 预扣流水 + 定时对账补偿 | 最终一致 | 中高 | 中 |

  3. **诚实结论**：如果当前实现是前两种，要主动说明"当前依赖对账兜底，这是已知缺口"，而不是硬说没问题。
- **项目证据**：**当前实现属于哪一种：待核对代码。**
- **追问链**：
  - L1：**"对账兜底的窗口有多长？这段时间用户看到什么？"** → 答：窗口 = 对账周期 + 补偿执行时间（**待压测/待定**）；用户侧应当是在"排队中"直到超时提示，不能显示成功。
    - L2：**"如果对账任务自己挂了？"** → 答：对账任务必须可监控、可重跑、幂等，且要有"对账任务未执行"的告警——监控缺失是对账方案最大的失败模式。
- **常见错误回答**：声称"Redis 和 MQ 之间没有问题"。

### Q4.5 消息积压了怎么办？

- **考点**：应急处理能力。
- **回答要点**：
  1. 先定位原因：消费端变慢（慢 SQL、连接池打满见 T-07）还是生产端突增（活动开始/被刷）。
  2. 应急手段：提高消费并发（受分区数限制）、临时扩容消费者实例、跳过非关键消息、降级非核心逻辑、必要时限流入口。
  3. 处理积压时的顺序陷阱：加并发会破坏原有的顺序保证（见 Q4.3），要确认业务能否接受。
  4. 长期：监控消费延迟（lag）而不是只看队列长度。
- **项目证据**：**当前是否有 lag 监控：待核对。**
- **追问链**：
  - L1：**"你怎么知道是消费慢而不是生产快？"** → 答：看两个曲线：生产速率与消费速率，以及消费端单条耗时分布；如果单条耗时上升，是消费端问题。
    - L2：**"消费端单条耗时为多少算慢？"** → 答：要对照压测基线与业务 SLA，**没有实测就没有发言权**。
- **常见错误回答**："加机器"。

### Q4.6 如果 MQ 整个不可用了，系统怎么表现？

- **考点**：依赖失效时的降级设计。
- **回答要点**：
  1. 表现：预扣成功但无法投递 → 用户永远停在"排队中"；或者预扣直接失败。
  2. 正确做法：入口快速失败（限流/熔断），不要继续放量预扣——否则 Redis 库存被扣光，却没有订单落库，形成大面积不一致。
  3. 恢复后：靠对账把预扣而没落库的部分回补。
  4. 关键原则：**下游不可用时，上游要"少做"而不是"先做了再说"。**
- **项目证据**：**当前是否有针对 MQ 不可用的熔断：待核对。**
- **追问链**：
  - L1：**"你怎么判断 MQ 不可用而不是慢？"** → 答：用发送超时 + 连续失败计数；短时抖动靠重试，持续失败才熔断。
    - L2：**"熔断后怎么恢复？"** → 答：半开状态试探，恢复后要能处理积压，且对账任务要能覆盖故障期间的数据。
- **常见错误回答**："MQ 是高可用的，不会挂"。

## 五、Spring Cloud

### Q5.1 OpenFeign 的调用流程是什么？第一次调用为什么慢？

- **考点**：是否知道 Feign 背后的组件链。
- **回答要点**：
  1. 流程：接口代理 → 编码请求 → 负载均衡选取实例（从注册中心拿到的列表 + 本地缓存）→ HTTP 客户端发起调用 → 解码响应。
  2. 第一次慢的原因：需要初始化负载均衡器、拉取/刷新实例列表、建立连接、类加载与 JIT。
  3. 因此需要显式配置超时，并在启动后预热（主动调用一次）。
  4. 连接池很关键：默认实现可能不复用连接，换成带连接池的客户端后表现不同（见 T-03 对比表）。
- **项目证据**：`docs/troubleshooting/README.md` T-03；**当前客户端实现与超时配置：待核对**。
- **追问链**：
  - L1：**"Feign 的超时和负载均衡的重试叠加会怎样？"** → 答：会放大请求量。要明确哪些接口允许重试——**下单接口默认不能重试**，除非有幂等保证。
    - L2：**"那读取类接口重试呢？"** → 答：可以，但要限次数，并且服务端要有保护（限流），否则重试风暴会把故障放大。
- **常见错误回答**：只说"Feign 是声明式调用"。

### Q5.2 Nacos 的注册与发现原理？服务下线后调用方多久感知不到？

- **考点**：是否理解注册中心的最终一致性窗口。
- **回答要点**：
  1. 临时实例靠心跳维持，超时后被摘除；持久化实例不靠心跳。
  2. 调用方本地缓存实例列表，靠推送 + 定时拉取更新，所以必然存在窗口。
  3. 因此不能依赖"下线即刻生效"，要靠**优雅下线**（先反注册、等在途请求结束再停进程）。
  4. 心跳与刷新间隔的具体默认值以所用版本为准（**待核对，不要凭印象报数字**）。
- **项目证据**：`docs/troubleshooting/README.md` T-04 的对照实验设计。
- **追问链**：
  - L1：**"`kill -9` 和优雅下线差多少？"** → 答：差异就是"心跳超时 + 摘除 + 客户端刷新"这三段之和，具体数值必须实测（T-04 的 A/B 实验），不能猜。
    - L2：**"窗口期的失败请求怎么减少？"** → 答：有限重试（仅幂等接口）+ 熔断 + 调用方对连接失败快速失败。
- **常见错误回答**：报一个凭印象的秒数。

### Q5.3 多个实例部署时，有哪些"单机时正常、多机才暴露"的问题？

- **考点**：分布式意识，这题非常能区分人。
- **回答要点**：
  1. 本地缓存各自持有 → 不一致（T-09）。
  2. 定时任务重复执行 → 同一批数据被多个实例处理（需要分布式调度或数据库抢占式加锁）。
  3. 内存态限流/计数失真 → 单机限流变成 N 倍限流。
  4. 会话/幂等 token 存在本地 → 用户请求打到另一台就失效。
  5. 实例注册 IP 不可达（容器环境，T-10）。
- **项目证据**：需逐个确认当前实现（**待核对**）。其中"定时任务在多个实例上是否会重复执行"是最容易被忽略的。
- **追问链**：
  - L1：**"定时任务重复执行会有什么后果？"** → 答：以关单任务为例，重复执行本身若用 CAS 是无害的；但如果是"回补库存"这种没有幂等的动作，就会把库存加多——所以关键看动作是否幂等。
    - L2：**"怎么保证只执行一次？"** → 答：几种方案：数据库抢占（`UPDATE task SET owner = ? WHERE owner IS NULL`）、分布式调度组件、Redis 锁（要考虑锁失效）。**当前用哪种：待核对。**
- **常见错误回答**：没意识到多实例的影响。

### Q5.4 熔断、限流、降级在这个项目里分别用在哪？

- **考点**：是否理解三者的区别与落点。
- **回答要点**：
  1. 限流：入口（按用户/接口维度），目的是保护自己不被压垮；秒杀场景优先按用户维度限，防止单人刷。
  2. 熔断：调用下游连续失败时快速失败，目的是防止线程被拖死（Feign 调用尤其需要）。
  3. 降级：牺牲非核心功能保核心链路（例如查询余票走缓存旧值、关闭推荐）。
  4. **关键**：降级策略必须逐接口定义"降级后返回什么"——返回错误、返回缓存值还是返回空，业务含义完全不同。
- **项目证据**：**当前接入的组件（是否引入熔断组件）：待核对。**
- **追问链**：
  - L1：**"限流阈值怎么定？"** → 答：靠压测找拐点（见 Q7 组），不能拍脑袋；先定容量上限，再定限流值。
    - L2：**"被限流的用户看到什么？"** → 答：要给出明确提示与重试引导，不能是超时或空白。
- **常见错误回答**：把三者混为一谈。

### Q5.5 分布式事务你打算怎么处理？（诚实版）

- **考点**：会不会不懂装懂。
- **回答要点**：
  1. **第一步是缩小问题**：优先通过服务边界设计把跨服务写操作变成同一个本地事务（库存与订单落库在同一个库）。
  2. 真的跨服务时，按一致性要求选：强一致（代价高，本项目未采用）/ TCC（补偿逻辑复杂，需大量业务改造）/ 事务消息 / 本地消息表 + 对账（本项目实际采用的层级，**待核对**）。
  3. 明确表态：**本项目不追求分布式强一致，走的是"本地事务 + 最终一致 + 对账兜底"**，并且说清楚这个选择的风险（窗口期数据可见但不正确）。
  4. 反问自己：所有最终一致的地方，对账在哪里？没有对账的最终一致就是"不一致"。
- **项目证据**：需要能列出每一处跨服务写操作及其补偿方式（**待核对**）。
- **追问链**：
  - L1：**"为什么不直接用 Seata？"** → 答：要能说出理由，而不是"没学过"。可从三方面答：引入中间件带来的运维与理解成本、AT 模式对 SQL 的隐式改写增加了排障难度、本项目的跨服务写场景其实很少（先缩小问题优先于上框架）。**如果项目规模确实需要，这个判断可以改。**
    - L2：**"那你现在有哪些地方其实是最终一致但对外表现为'立即成功'？"** → 答：这是最锋利的一问。必须能指出具体接口，或者承认"没有逐一对过，这是我的待办"。
- **常见错误回答**：背 Seata 的四种模式，却说不清本项目用了什么。

### Q5.6 服务间接口的幂等与重试，你们是怎么约定的？

- **考点**：工程规范层面的思考。
- **回答要点**：
  1. 写接口必须支持幂等键（客户端生成的请求 ID / 业务唯一键）。
  2. 读接口可以重试，写接口默认不重试，除非明确声明幂等。
  3. 重试要有次数上限、退避策略，并且只对可重试的异常重试（连接失败可重试，业务失败不重试）。
- **项目证据**：**当前接口是否统一带幂等键：待核对。**
- **追问链**：
  - L1：**"超时算成功还是失败？"** → 答：不知道，这正是分布式调用的经典困境——超时不代表失败。因此写接口必须可查（提供幂等查询接口），调用方超时后应查询而不是盲目重试。
- **常见错误回答**：默认超时就重试写接口。

## 六、数据库与索引

### Q6.1 订单表怎么设计的？关键索引有哪些？

- **考点**：是否从查询模式反推索引。
- **回答要点**：
  1. 先列查询模式：按用户查订单列表、按订单号查详情、按车次+日期统计、对账扫描。
  2. 对应索引：`uk_order_no`（唯一 + 查询）、`idx_user_time (user_id, create_time)`（列表页按时间倒序）、`idx_status_time (status, create_time)`（扫描超时未支付）。
  3. 唯一索引除了查询还有幂等作用（见 Q3.3）。
  4. 反例：不要给每个字段都加索引，写入放大且优化器可能选错。
- **项目证据**：**实际 DDL 位置待核对。**
- **追问链**：
  - L1：**"`idx_user_time` 为什么是 (user_id, create_time) 而不是反过来？"** → 答：最左前缀原则——查询条件里 `user_id` 是等值，`create_time` 是范围/排序，把等值放前、范围放后才能用上索引排序。
    - L2：**"如果查询是 `WHERE user_id = ? ORDER BY create_time DESC`，还能用上吗？"** → 答：可以用到索引的有序性，避免额外排序（前提是排序方向与索引一致，或版本支持降序索引）。
- **常见错误回答**：只报索引名，说不出为什么。

### Q6.2 怎么发现并优化慢 SQL？

- **考点**：排查手段是否可复现。
- **回答要点**：
  1. 先开启慢查询日志（阈值按业务定，具体值**待核对**），拿到真实慢 SQL，不要靠猜。
  2. 用 `EXPLAIN` 看：访问类型、命中索引、扫描行数、是否临时表/文件排序。
  3. 常见根因：缺索引、索引失效（函数/隐式转换/前导通配符）、返回数据量过大、深度分页。
  4. 优化顺序：先改 SQL（减少返回列、用游标分页）→ 再改索引 → 最后才考虑改结构。
- **项目证据**：慢查询配置（**待核对**）。
- **追问链**：
  - L1：**"深度分页怎么优化？"** → 答：用"上一页最大 ID"做游标（`WHERE id > ? LIMIT n`）替代 `LIMIT offset, n`，避免扫描并丢弃前 offset 行。
    - L2：**"`EXPLAIN` 里你最先看哪一列？"** → 答：先看 `type`（访问类型）和 `rows`（预估扫描行数），再看 `Extra` 是否出现排序/临时表。
- **常见错误回答**：说"加索引就好了"，不看执行计划。

### Q6.3 事务隔离级别是什么？这个项目需要调整吗？

- **考点**：是否知道默认级别及其影响。
- **回答要点**：
  1. 默认通常是"可重复读"（具体以所用数据库版本为准，**待核对**）。
  2. 本项目库存扣减用条件更新，是"当前读"，天然会读最新已提交数据并加锁，不依赖隔离级别提供的一致性。
  3. 需要注意的不是隔离级别，而是**事务边界**：事务里不要有远程调用、不要做耗时操作（T-07 的根因之一）。
  4. 如果确实存在"先查后判断再更新"的业务写法，在并发下要警惕——这属于典型的检查-执行竞态，应该改成条件更新。
- **项目证据**：**事务注解的位置与事务内是否有 Feign 调用：待核对**（排查方法见 T-07）。
- **追问链**：
  - L1：**"为什么事务里不能有远程调用？"** → 答：会长时间持有数据库连接与行锁，远程调用的 RT 抖动会直接传导成锁等待，进而把连接池打满。
    - L2：**"那业务上就是需要'查到结果再决定'怎么办？"** → 答：把远程调用挪到事务外，先查后开事务；或者把远程结果作为参数传入事务方法。
- **常见错误回答**：大谈四种隔离级别与幻读定义，不落到事务边界。

### Q6.4 为什么库存扣减要用 `remark` 之外的字段？库存表应该怎么设计？

- **考点**：数据建模的严谨性。
- **回答要点**：
  1. 关键字段：`id`、`train_no`、`travel_date`、`seat_type`、`total`、`remain`、`version`（可选）、`updated_at`。
  2. `remain` 与 `total` 分开存，便于对账时算"已售出"（`total - remain`）而不依赖订单表统计。
  3. 唯一索引 `(train_no, travel_date, seat_type)` 防止重复建库存行。
  4. 不要用"已售数量"这种需要累加的字段做判断依据——累加字段在异常时无法自证正确，而 `remain` 可以直接与初始值比对。
- **项目证据**：**实际 DDL 待核对。**
- **追问链**：
  - L1：**"用 `total - remain` 算已售，和直接 `COUNT` 订单，哪个更可信？"** → 答：两者都要看，且不一致本身就是重要信号——一个反映"库存账"，一个反映"订单账"，对账的价值就在于比对两个独立口径。
- **常见错误回答**：只说"加个库存字段"。

### Q6.5 为什么订单表要有状态机？用布尔字段不行吗？

- **考点**：状态建模能力。
- **回答要点**：
  1. 订单生命周期有多个状态（待支付、已支付、已取消、已完成等，**取值以代码为准**），布尔字段无法表达多态。
  2. 状态机让并发写有明确语义：`WHERE status = 'UNPAID'` 的条件更新天然实现了 CAS，解决关单与支付的竞态（Q3.4）。
  3. 状态流转要有明确规则，禁止跳变（例如未支付不能直接到已完成）。
  4. 排查时的价值：状态字段可以回答"这笔订单卡在哪一步"，布尔字段回答不了。
- **项目证据**：**状态定义与流转位置待核对。**
- **追问链**：
  - L1：**"状态流转怎么防止被绕过？"** → 答：所有更新都走同一套带条件的 SQL，不提供无条件的 `UPDATE status`；必要时用状态变更流水表记录每次流转。
- **常见错误回答**："加个 status 字段就行"。

## 七、压测与优化

### Q7.1 你的压测方案是什么？怎么保证结论可信？

- **考点**：方法论，比数字重要得多。
- **回答要点**：
  1. 先定义目标：验证容量上限、验证限流阈值、验证一致性问题（不是只测 TPS）。
  2. 变量控制：每轮只改一个变量；记录环境参数（机器规格、容器资源、是否同机压测、JVM 参数）。
  3. 区分压测机瓶颈与服务瓶颈（**这是 T-06 的核心**）：用命令行模式、监控压测机 CPU 与端口状态。
  4. 数据准备要有区分度：不能所有请求打同一个用户/同一车次（那测的是单点极限），也要有贴近真实的参数分布。
  5. 结论要标注边界：本地单机 Docker/WSL 环境的数据**不能外推到生产**。
- **项目证据**：JMeter 脚本与结果文件（**待补充**）。
- **追问链**：
  - L1：**"你的压测机和服务在同一台机器上吗？"** → 答：必须在回答里明确说明。同机会互相抢 CPU，数字只能做相对比较，不能当容量结论。
    - L2：**"那你为什么还用这种环境测？"** → 答：教学/开发阶段资源有限，此环境用于**验证正确性与找瓶颈拐点**，不用于定容量；要能说出两者区别。
- **常见错误回答**：报一个大 TPS 数字，但说不清环境与方法。

### Q7.2 压测中出现错误，你怎么区分是压测工具的问题还是服务的问题？

- **考点**：排查思路（对应 T-06）。
- **回答要点**：
  1. 同时采集两侧指标：客户端（错误类型分布、连接状态、机器负载）与服务端（RT、连接池水位、容器线程数、GC）。
  2. 判据：服务端指标未饱和而客户端已大量报错 → 大概率是客户端/网络侧问题。
  3. 对照实验：命令行模式重跑、降低线程数重跑、换 keep-alive 配置重跑，看错误是否消失。
  4. 具体到 Windows：检查 TIME_WAIT 数量与动态端口范围。
- **项目证据**：`docs/troubleshooting/README.md` T-06 的验证步骤。
- **追问链**：
  - L1：**"错误率是在某个线程数突然跳变的吗？"** → 答：如果是在某个点陡增，说明触到了某个资源的硬上限（端口、连接数、线程数）；如果是线性增长，更可能是配置或逻辑问题。**拐点数值待压测。**
- **常见错误回答**：把所有压测错误都归给"服务性能不行"。

### Q7.3 你是怎么发现系统瓶颈的？用了哪些工具？

- **考点**：是否有成体系的排查工具链。
- **回答要点**：
  1. 自顶向下：接口 RT 与错误率 → 应用层指标（连接池、线程池、缓存命中率）→ JVM（GC、线程栈）→ 系统层（CPU、内存、IO、网络）→ 存储层（慢 SQL、Redis 慢命令）。
  2. 工具：`jstack`（线程卡在哪）、`jstat`/GC 日志（是否 GC 停顿）、连接池与缓存指标、数据库慢查询、Redis SLOWLOG。
  3. 原则：**先看指标再看代码**，不要一上来就翻代码。
- **项目证据**：**当前是否接入了指标采集（actuator / 监控组件）：待核对**。
- **追问链**：
  - L1：**"如果 RT 高但 CPU 不高，你会往哪查？"** → 答：往"等"的方向查——等锁、等连接、等下游、等 IO。对应到本项目：连接池等待、Redis 慢命令、Feign 调用的下游 RT。
    - L2：**"怎么区分是在等数据库还是在等下游？"** → 答：看线程栈里阻塞在哪个方法上，配合连接池指标与下游调用耗时打点。
- **常见错误回答**："用 VisualVM 看了一下"。

### Q7.4 缓存类优化和数据库类优化，你会先做哪个？

- **考点**：优化顺序的判断。
- **回答要点**：
  1. 原则：**先保证正确性，再消除明显浪费，最后才加缓存。**
  2. 加缓存是最后一步，因为它是"用一致性换性能"，代价最高、最难回退。
  3. 先做的事：消除 N+1 查询、加必要索引、减少不必要的数据传输、缩短事务与持锁时间。
  4. 本项目里缓存已经用在关键路径（库存预扣），所以讨论重点应是"缓存写坏了怎么恢复"，而不是"要不要加缓存"。
- **项目证据**：待压测前不做结论。
- **追问链**：
  - L1：**"为什么说缓存的代价最高？"** → 答：因为它把一份数据变成两份，之后所有的 bug 都可能出在"哪份是对的"上，且故障模式是静默的数据错误，比报错更难发现。
- **常见错误回答**：无脑说"加缓存"。

### Q7.5 压测数据怎么呈现才算专业？

- **考点**：会不会汇报。
- **回答要点**：
  1. 不报单一均值，报分布：P50 / P95 / P99 / 最大值，以及错误率。
  2. 必须带上下文：并发数、数据规模、机器规格、单机还是分布式压测、是否同机。
  3. 对比要成对出现：优化前 vs 优化后的同一指标、同一环境。
  4. 明确说明**哪些是实测、哪些是预期**。
- **项目证据**：**本文档不预设任何数字，全部待压测填入。**
- **追问链**：
  - L1：**"为什么 P99 比平均值重要？"** → 答：用户感知的是尾部延迟，平均值会被大量快请求稀释；对秒杀这类场景，尾部延迟直接决定多少人抢不到。
- **常见错误回答**：只报 TPS 峰值。

## 八、项目踩坑

> 这一节的问题答案都来自真实踩坑经历。**目前项目处于架构阶段，尚未积累真实案例**，因此下列问题先给出"该准备哪个故事"的指引，等你踩到后回填到 `docs/troubleshooting/README.md`，再把这里补成完整叙述。

### Q8.1 讲一个你排查时间最长的问题。

- **考点**：排查方法论与诚实度。
- **准备指引**：优先从 T-01（库存不一致）、T-04（Nacos 延迟）、T-06（压测 socket 异常）里挑，因为它们的排查过程有"分层排除"的清晰结构。
- **回答结构**：现象 → 我的第一判断（可以是错的） → 我做了哪些验证 → 真正的根因 → 改动 → 结果。
- **追问链**：
  - L1：**"你中间走过什么弯路？"** → 答：**必须有弯路。**说"一路顺利"的人不可信，也浪费了这题的价值。
    - L2：**"如果再遇到同类问题，你会怎么更快定位？"** → 答：落到"我增加了什么可观测性"上（日志、指标、对账），这比"我会更仔细"强一百倍。

### Q8.2 你遇到过的最隐蔽的 bug 是什么？

- **考点**：是否踩过"逻辑看起来对但就是不对"的坑。
- **准备指引**：候选来自 T-05（Lua 非确定性命令，单机正常集群报错）、T-09（本地缓存多实例不一致）、T-02（并发下"先查后插"失效）。
- **回答要点**：隐蔽性来自"环境差异"或"并发时序"，这两类问题的共性是**单机/低并发复现不出来**。
- **追问链**：
  - L1：**"你是怎么让它稳定复现的？"** → 答：这是关键——把不可复现变成可复现（加并发、改拓扑、注入延迟），有这一步才叫定位了问题。

### Q8.3 有没有哪个设计是你后来推翻重做的？为什么？

- **考点**：反思与取舍能力。
- **准备指引**：`docs/troubleshooting/README.md` 里每一条的"方案对比表"就是素材库；另外"本地缓存缓存了不该缓存的数据""回补逻辑散落在多处"都是典型的推翻点。
- **回答要点**：重点讲清"推翻的依据是什么"——是数据（对账差值）、还是故障（线上问题）、还是压测结论。
- **追问链**：
  - L1：**"重做花了多少成本？值得吗？"** → 答：要能算账，包括返工成本与不做会造成的损失。

### Q8.4 系统出过一次数据不一致，你是怎么处理的？

- **考点**：面对已污染数据的态度。
- **回答要点**：三段式——止血（先停止放大，例如限流/暂停回补）、修复（按什么口径修、修哪些数据、修复动作如何幂等）、预防（增加对账/约束/监控）。
- **诚实提醒**：修复动作本身如果幂等没做好，会造成二次污染，这一点面试官很爱追问。
- **追问链**：
  - L1：**"修数据的时候怎么保证不误伤正常数据？"** → 答：先只读导出待修清单 + 人工抽样核对 + 小批量灰度修复 + 修复前后对账比对。
    - L2：**"怎么保证修复脚本重跑不重复生效？"** → 答：修复以"目标状态"为准而不是"增量动作"，例如把 `remain` 设为计算值而不是 `remain + n`；或记录修复批次标记。

### Q8.5 你线上（或本地）遇到过连接池打满吗？怎么定位的？

- **考点**：对应 T-07，这是有经验的人一定踩过的坑。
- **回答要点**：开泄漏检测拿到占用栈 → 区分"泄漏"还是"慢" → 常见根因是事务里做远程调用或慢 SQL。
- **追问链**：
  - L1：**"抓到栈之后你怎么判断是泄漏还是单纯慢？"** → 答：看同一段栈是否反复出现、连接持有时间是否远超业务 RT、以及流量下降后连接数是否回落。**不回落 = 泄漏。**

### Q8.6 你觉得这个项目现在最大的技术风险是什么？

- **考点**：清醒程度。这题答得好，前面的小失误都会被原谅。
- **回答要点**（建议按此顺序）：
  1. **预扣与落库之间缺少可靠的投递保障**（Q4.4）——这是正确性风险，优先级最高。
  2. **对账机制若未落地，所有"最终一致"都只是说法**（Q5.5）。
  3. **压测结论尚未产出**，容量与限流阈值都是未知数（Q7.5）。
  4. **本地单机环境的结论不可外推**，缺少接近生产的验证环境。
- **追问链**：
  - L1：**"你打算怎么解决第一个？"** → 答：给出优先级排序与验证方式（本地消息表 / 事务消息 / 对账补偿三选一 + 对应验证手段）。
- **常见错误回答**："没什么大风险"。

## 九、这个项目最可能被问倒的 5 个问题

> 这一节是**自我体检清单**，不是问题库。列在这里的都是当前设计**确实不够严密**的地方。面试时被问到，正确策略是"承认 + 说清边界 + 给出改进方向"，不要硬答。

### D1. "Redis 预扣成功之后，任何一步失败，库存怎么回到正确状态？"

**为什么不严密**：预扣 → 投递 → 消费 → 落库 是四段，中间没有跨系统的原子性。当前如果依赖"发送失败即回补 + 定时对账"，那么回补本身失败、对账周期过长、对账任务挂掉这三种情况都会让不一致持续存在。

**当前的诚实回答**：说清"Redis 是加速层、MySQL 是账本"的定位；承认回补链路是否为闭环**尚未验证**（待核对代码）；说明下一步会引入预扣流水或本地消息表把可恢复性补上。

**被追问时不要做的事**：不要把"最终一致"当成万能挡箭牌——面试官会立刻追问"窗口多长、谁负责收敛、怎么证明收敛了"。

### D2. "Redis 主从切换 / 实例重启时的那一瞬间，会超卖吗？"

**为什么不严密**：如果库存 key 依赖异步复制且持久化策略偏性能，故障切换时确实存在预扣记录丢失、库存被"变多"的窗口。分布式锁在这类场景（主从切换导致锁失效）也有同样的经典问题。

**当前的诚实回答**：承认窗口存在；说明缓解手段（持久化策略、故障后以 MySQL 重建 + 限流、脚本把 key 不存在与库存为 0 区分开）；说明这些手段**尚未做故障演练验证**（待验证）。

### D3. "并发下你怎么保证同一个用户不会下两单？"

**为什么不严密**：说"先查后插"或"用 Redis 去重"都是错的；唯一索引也要先确认业务规则是否真的"一人一单"，而这个规则**当前是否已确认：待核对**。如果产品允许一个用户买多张，唯一索引的字段就得换。

**当前的诚实回答**：讲清"入口幂等 token 减少无效流量 + 数据库唯一索引保证正确"的分层；明确说出唯一索引字段取决于业务规则；承认"先查后插"在并发下不可靠。

### D4. "你的对账任务扫什么、多久跑一次、怎么保证它不重复修复？"

**为什么不严密**：这是"最终一致"方案能不能成立的关键，但目前很可能只有方向没有细节。三个必答项：扫描口径（如何界定"在途"与"异常"）、执行频率与数据量（扫全表会越来越慢）、修复动作的幂等性。

**当前的诚实回答**：承认这三项还没有定论（**待压测/待定**）；给出思路：以业务唯一键为粒度、给在途操作设宽限期、修复写成"目标状态"而非"增量动作"、对账任务自身要有执行监控与告警。

### D5. "你压出来的 TPS 是多少？这个数字能代表生产吗？"

**为什么不严密**：压测结果尚未产出，而且即使产出，本地 Windows + Docker/WSL 单机环境的数据**不能外推**（压测机与被测服务常在同一台机器，容器资源有上限，网络拓扑与生产不同）。

**当前的诚实回答**：不要报数字。说明"压测用于验证正确性与找瓶颈拐点，不用于定容量"；如果被追问容量，回答"需要独立的压测环境与分级加压方案，这是待补的验证环节"。
